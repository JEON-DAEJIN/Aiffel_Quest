# Cloud Run에 AI 서비스를 배포하고 운영하는 법 — N046·N047 방법론을 실제로 적용하기

> 이 문서는 N046(AI 서비스 인 프로덕션)·N047(Cloud Run에서 AI 서비스 운영하기) 강의가 가르친 순서를, 실습용 서비스 `friend-agent`에 처음부터 끝까지 적용해본 기록이다. N045 방법론 문서와 같은 형식으로, "이 단계에서 무엇을 왜 하는지"는 일반 원리로, "실제로 어떻게 됐는지"는 friend-agent 예시로 함께 보여준다. N046과 N047을 나누지 않고 한 편으로 묶은 이유는, 같은 서비스를 이어서 다루고 키·로그·리비전이 겹쳐서 둘로 나누면 중복되기 때문이다. 마지막 부록에는 **아직 코드가 없는** ASP·MSM·GoodNews 세 프로젝트에 나중에 적용할 계획을 "계획"이라고 분명히 밝히고 따로 적었다.

## 1. 한 장 요약 {#ch0}

### 전체 흐름

```
처음 배포하기 → 키 분리(Secret Manager) → 운영 손잡이 네 가지(타임아웃·인스턴스·동시성·비용) → 로그 3종으로 원인 찾기 → 실사용·부하로 한계 확인
```

### 단계별 요약표

| 단계 | 원문 챕터 | 이 단계에서 할 일(일반 원리) | friend-agent에서 실제로 한 일 | 산출물 |
|---|---|---|---|---|
| 1 | N046 2~4장(Cloud Run 개념·소스 배포) | 소스를 Cloud Run에 올리고 공개 여부·환경변수를 정한다. 시작 명령은 `PORT` 환경변수를 리슨해야 함 | `hello/` 템플릿으로 배포 연습 → `friend-agent` 소스 배포. 빌드 계정 403을 오류 메시지에 나온 계정에 역할 하나만 부여해 해결 | 배포된 서비스, 403 해결 기록 |
| 2 | N046 5장(Secret Manager) | API 키를 환경변수에 평문으로 넣지 않고 시크릿으로 분리한다 | `llm-api-key` 시크릿 생성 → `LLM_API_KEY`에 `latest` 버전 연결. 키 값은 이번 실습 내내 한 번도 대화에 받지 않음 | 시크릿 연결 완료 |
| 3 | N047 2~4장(타임아웃·인스턴스·비용) | 운영 손잡이 네 가지(타임아웃·동시성·최대/최소 인스턴스·비용 한도)를 하나씩 바꿔 효과와 한계를 실측한다 | 타임아웃 3초→잘림(상태 코드는 200), 10분 콜드 스타트 실측(1.0초→4.8초), 최대 인스턴스×동시성으로 처리량 계산 | 수치 기록 |
| 4 | N047 5장(로그 3종) | 요청·컨테이너·시스템 로그를 구분해 원인을 재구성한다 | `LLM_PROVIDER=unknown`으로 일부러 배포 실패 → 로그 5줄에서 진짜 원인(컨테이너 ERROR) 특정 → 원래 값으로 복구 | 로그 타임라인 |
| 5 | N047 6~7장(실사용·부하·회고) | 다른 기기로 실사용 + 부하 테스트로 설정의 실제 한계를 체감한다 | 휴대폰(모바일 데이터)으로 실사용 → remote IP로 구분. 별도 `load-test` 서비스로 설정 3종 비교 → **최대 인스턴스보다 스케일업 속도가 먼저 한계**에 부딪힘을 발견 | 부하 테스트 표, 회고표 |

> 💡 **팁**: N046(배포)과 N047(운영)은 사실 하나의 흐름이다. 배포에서 정한 것(공개 여부, 환경변수, 시크릿)이 운영 단계의 모든 설정(타임아웃·인스턴스·로그)의 전제가 된다. 두 강의를 나눠 듣더라도, 실습은 한 서비스로 이어서 하는 쪽이 더 맞는다는 것을 이번에 확인했다.

## 2. 1단계 — 처음 배포하기 {#ch1}

### 일반 원리

Cloud Run은 컨테이너 단위로 배포한다. `--source`로 소스 배포를 하면 Buildpacks가 Dockerfile 없이 알아서 이미지를 빌드해준다. 단, 시작 명령은 반드시 `PORT` 환경변수가 가리키는 포트를 리슨해야 하고, 공개(`--allow-unauthenticated`) 여부는 "지금 당장 결정"이 아니라 "누가 어떻게 쓸지"까지 생각해서 정해야 한다. 소스 배포 중 빌드를 수행하는 서비스 계정에 적절한 역할이 없으면 403이 난다 — 이때 포괄적인 역할(Editor 등)을 주는 대신, 오류 메시지가 가리키는 **그 계정에 그 역할 하나만** 주는 게 안전하다.

### friend-agent에서 실제로

🧪 **예제 — 배포 연습부터**: `hello/` FastAPI 템플릿으로 먼저 배포 연습을 했다(이번 세션에서도 부하 테스트용 `load-test` 서비스로 같은 패턴을 한 번 더 썼다 — 템플릿 하나가 여러 번 재사용됐다).

🧪 **예제 — 403과 복구**: 실제 서비스 `friend-agent`를 배포할 때 403이 났다. 원인은 Cloud Build 기본 서비스 계정(`<프로젝트 번호>-compute@developer.gserviceaccount.com`)에 `roles/cloudbuild.builds.builder` 권한이 없었던 것. 오류 메시지에 나온 그 계정에 그 역할 하나만 부여해서 풀었다(Editor처럼 넓은 역할은 주지 않음).

> 📌 **요약**: 첫 배포에서 나는 오류 대부분은 "권한이 없다"거나 "포트를 못 열었다" 둘 중 하나다. 전자는 오류 메시지가 가리키는 계정에 역할 하나만, 후자는 코드가 `PORT` 환경변수를 쓰는지 먼저 본다.

### 체크리스트

- [ ] 시작 명령이 `PORT` 환경변수의 포트를 리슨하는가
- [ ] 공개 여부(`--allow-unauthenticated`)를 "누가 쓸지"까지 생각해서 정했는가
- [ ] 403이 나면 오류 메시지에 나온 "그 계정"에 "그 역할 하나"만 부여했는가(Editor 금지)
- [ ] 리전·프로젝트가 의도한 곳인지 `gcloud config list`로 확인했는가

## 3. 2단계 — 키를 코드에서 분리하기 {#ch2}

### 일반 원리

API 키를 환경변수에 평문으로 넣으면 `gcloud run services describe`나 콘솔 화면에 값이 그대로 노출된다. Secret Manager에 키를 저장하고, 서비스에는 "시크릿 이름 + 버전(`latest`)"만 연결하면 서비스 설정 어디에도 키 값이 남지 않는다. 접근 권한(`secretAccessor`)은 프로젝트 전체가 아니라 그 시크릿 하나에만 좁게 준다.

### friend-agent에서 실제로

🧪 **예제 — 시크릿 연결**: `llm-api-key` 시크릿을 만들고, `friend-agent`의 `LLM_API_KEY` 환경변수를 그 시크릿의 `latest` 버전에 연결했다. 이번 실습 전체(지난 세션 N046부터 오늘 N047 마무리까지)에서 **키 값은 한 번도 대화에 입력받지 않았다.** 확인은 항상 "시크릿 이름이 있는지"(`gcloud secrets list`), "생성 시각이 같은지"로만 했다.

> ⚠️ **주의**: 시크릿이 "있다"는 확인과 "값이 맞다"는 확인은 다르다. 전자는 이름·버전으로, 후자는 서비스가 실제로 정상 응답하는지(3단계·4단계)로 간접 확인한다. 키 값 자체를 출력해서 맞춰보지 않는다.

### 체크리스트

- [ ] 키는 `.env`/시크릿에만 있고 커밋된 코드·대화 기록에는 없는가
- [ ] 서비스 설정을 describe해도 키 값이 아니라 이름·버전만 보이는가
- [ ] `secretAccessor` 권한을 그 시크릿 하나에만 좁게 부여했는가(프로젝트 전체 아님)

## 4. 3단계 — 운영 손잡이 네 가지 {#ch3}

### 일반 원리

타임아웃·동시성·최대/최소 인스턴스·비용 상한은 서로 다른 것을 조절하는 **별개의 손잡이**다. 하나를 바꾸면 다른 것에 부작용이 생길 수 있어, 바꾸기 전에 반드시 "평소 값"부터 재고, 하나씩만 바꿔 실측해야 한다.

### friend-agent에서 실제로

🧪 **예제 — 타임아웃**: 평소 요청 전체(답을 보낸 뒤 기억 정리까지 포함) 시간이 4.1초임을 먼저 쟀다. 타임아웃을 3초로 줄이자 답이 문장 중간에서 끊겼는데, **상태 코드는 여전히 200**이었다(스트리밍이 첫 글자를 보내는 순간 이미 200을 보내기 때문). 서버 로그의 `Truncated response body` 경고 3개가 화면에 뜬 경고 3번과 정확히 1:1로 대응했다. 확인 뒤 300초로 복원했다.

🧪 **예제 — 인스턴스·콜드 스타트**: 10분 이상 쉬었다가 다시 요청하니 평소 1.0~1.4초이던 첫 처리가 4.8초로 늘었다(없는 주소를 열어 404를 만든 테스트에서는 7.8초 vs 2ms로 더 극명했다). 같은 순간 서버 메모리에 저장했던 대화·약속이 **사라지고** AI가 지어낸 가짜 약속 1개만 남아 있었다 — 인스턴스가 0개로 줄면 메모리도 함께 사라진다는 걸 직접 확인했다.

🧪 **예제 — 비용 계산**: 최대 인스턴스 2 × 동시성 80 = 동시 160건까지 처리 가능. 하지만 이 숫자는 **"한 번에 처리하는 규모"**일 뿐, 시간이 지나며 쌓이는 **총 호출 횟수(=LLM 비용 총액)**는 전혀 막아주지 않는다. 총액은 LLM 제공사의 월 사용 한도로 따로 막아야 한다.

> 📌 **요약**: 네 가지 손잡이 중 어느 것도 "비용 폭증을 막는 안전장치"는 아니었다. 전부 "규모와 속도를 조절하는 다이얼"일 뿐이다.

### 체크리스트

- [ ] 바꾸기 전 "평소 값"을 먼저 쟀는가(타임아웃은 요청 전체 기준, 첫 글자만이 아님)
- [ ] 타임아웃을 줄였을 때 "상태 코드만 보는 모니터링"으로는 못 잡는 잘림이 있는지 확인했는가
- [ ] 콜드 스타트 지연과 서버 메모리 소멸을 서로 다른 문제로 구분해서 실측했는가
- [ ] 최대 인스턴스 숫자를 "비용 상한"으로 착각하지 않았는가

## 5. 4단계 — 로그 3종으로 원인 찾기 {#ch4}

### 일반 원리

로그에는 세 종류가 섞여 있다: **요청 로그**(접수 기록, 몇 시에 어떤 주소로 몇 초 걸려 응답했는지), **컨테이너 로그**(앱 내부가 찍은 진짜 원인), **시스템 로그**(인스턴스 시작·종료 같은 인프라 사건). 터미널에 뜨는 짧은 오류 메시지는 "결과"일 뿐이고, 진짜 원인은 보통 컨테이너 로그 한 줄에 있다.

### friend-agent에서 실제로

🧪 **예제 — 일부러 고장 내고 로그로 원인 찾기**: 이미 정상 동작 중인 서비스의 `LLM_PROVIDER`를 존재하지 않는 값(`unknown`)으로 바꿔 일부러 배포를 실패시켰다. 터미널에는 "PORT 포트를 못 열었다"는 메시지만 떴는데, 이건 **N046에서 키 자체가 없었을 때와 똑같은 메시지**였다. 로그 탐색기에서 실패한 리비전의 로그 5줄을 시간순으로 읽자, 컨테이너 로그의 ERROR 한 줄(`LLM_PROVIDER 값 'unknown'을 알 수 없어…`)이 진짜 원인임이 드러났다. **실패하는 동안에도 서비스는 멈추지 않았다** — 실패한 리비전은 트래픽을 받지 않고, 이전 정상 리비전이 계속 응답했다(확인: HTTP 200, 0.35초). 복구는 환경변수를 제거하는 게 아니라 **원래 값(`openai`)으로 다시 명시**했다(처음부터 명시적으로 넣어둔 값이었기 때문).

> 📌 **요약**: 같은 터미널 메시지("포트를 못 열었다")가 전혀 다른 두 원인(키 누락 / 잘못된 설정값)에서 똑같이 나왔다. **메시지만으로는 원인을 구분할 수 없고, 반드시 컨테이너 로그까지 내려가야 한다.**

### 체크리스트

- [ ] 터미널 메시지만 보고 원인을 단정하지 않았는가
- [ ] 요청/컨테이너/시스템 로그 중 어디서 원인을 찾았는지 구분해서 적었는가
- [ ] 실패 중에도 서비스가 이전 리비전으로 계속 응답했는지 확인했는가
- [ ] 복구 방법(제거 vs 원래 값으로 재설정)이 처음 설정한 방식과 맞는지 확인했는가

## 6. 5단계 — 실제로 부딪힌 운영 한계 {#ch5}

### 일반 원리

설정은 "규모와 속도를 조절하는 손잡이"이지 "문제를 완전히 막는 안전장치"가 아니다. 이 사실은 숫자를 계산해서는 잘 안 보이고, **다른 기기로 실제 사용해보고 실제로 부하를 줘봐야** 비로소 드러난다.

### friend-agent에서 실제로

🧪 **예제 — 다른 기기로 실사용**: 휴대폰을 와이파이가 아닌 모바일 데이터로 바꿔 접속시켰다. 로그를 조회하니 최근 30건 중 28건이 같은 IPv6 주소(휴대폰)에서, 1건만 다른 IPv4 주소(PC·집 와이파이)에서 온 것으로 **remote IP로 정확히 구분**됐다. 다만 이 방법은 같은 와이파이를 쓰는 사용자끼리는 통하지 않는다는 한계도 동시에 확인했다.

🧪 **예제 — 부하 테스트로 발견한, 강의 자료에 없던 사실**: LLM을 부르지 않는 별도 서비스 `load-test`를 만들어(`/slow`가 2초 대기 후 응답) 동시 요청 50개를 세 가지 설정으로 보냈다.

| 설정 | 200 개수 | 200이 아닌 응답 | p50 | 최대 |
|---|---|---|---|---|
| A. 동시성 80, 최대 인스턴스 3 | 50 | 0 | 4.6초 | 6.0초 |
| B. 동시성 1, 최대 인스턴스 20 | 15 | 35(500) | 10.4초 | 12.3초 |
| C. 동시성 1, 최대 인스턴스 3 | 15 | 35(500) | 10.6초 | 12.3초 |

B와 C가 **거의 같은 결과**였다. 실패 로그를 보니 `The request was aborted because there was no available instance`(지연 0초, 즉 기다리지도 않고 즉시 거절)였다. 즉 **최대 인스턴스 숫자(3이든 20이든)보다, 순간적으로 몰리는 요청에 새 인스턴스를 띄우는 "속도" 자체가 먼저 한계에 부딪힌다.** 설정 A가 전부 성공한 건 인스턴스를 더 적게 쓰는 대신, 동시성 80으로 기존 인스턴스가 요청을 쌓아 처리했기 때문이다.

> 📌 **요약**: "최대 인스턴스를 늘리면 더 잘 버틴다"는 직관은 순간적인 트래픽 폭주 앞에서는 틀릴 수 있다. 부하 테스트 없이는 이 한계가 숫자 계산만으로 보이지 않는다.

### 체크리스트

- [ ] "최대 인스턴스를 늘리면 무조건 더 잘 처리된다"고 가정하지 않고 실측했는가
- [ ] 거절된 요청의 로그를 보고 "느려서 실패"와 "즉시 거절"을 구분했는가
- [ ] 사용자 구분·데이터 보존을 설정이 아니라 설계(로그인, 외부 DB)로 풀어야 한다는 걸 인지했는가
- [ ] 테스트용으로 띄운 서비스(`load-test` 등)를 끝나고 삭제했는가

## 7. 부록 A — 실제 명령 런북 {#app-a}

실제로 겪은 순서 그대로다. 본인 프로젝트·서비스에서만 쓰고, 키 값은 어디에도 붙여 넣지 않는다.

```
# 1. 시작 상태 확인(읽기 전용)
gcloud config list
gcloud run services describe <서비스> --region <리전> --format="value(status.url, status.latestReadyRevisionName)"
gcloud run services get-iam-policy <서비스> --region <리전>
gcloud secrets list

# 2. 처음 배포(소스 배포, Buildpacks)
gcloud run deploy <서비스> --source <폴더> --region <리전> --allow-unauthenticated --max-instances <N>
# 403이 나면: 오류에 나온 계정에 오류에 나온 역할 하나만 부여 후 재시도

# 3. 시크릿 연결(키는 여기서도 값으로 안 보임)
gcloud secrets create <시크릿이름> --data-file=<로컬 임시 파일, 직접 콘솔/.env에 입력 권장>
gcloud run services update <서비스> --region <리전> --update-secrets=<ENV이름>=<시크릿이름>:latest

# 4. 운영 손잡이 실험(하나씩)
gcloud run services update <서비스> --region <리전> --timeout <초>
gcloud run services update <서비스> --region <리전> --concurrency <N> --max-instances <N>

# 5. 로그 3종 조회(PowerShell은 작은따옴표로 필터 감싸기)
gcloud logging read 'resource.type=cloud_run_revision AND resource.labels.service_name=<서비스> AND severity>=WARNING' --freshness=30m --limit=20
gcloud logging read 'resource.type=cloud_run_revision AND resource.labels.service_name=<서비스> AND httpRequest.status>=500' --freshness=30m --limit=20 --format='table(timestamp, severity, httpRequest.status, httpRequest.latency, textPayload)'

# 6. 일부러 고장 내고 복구
gcloud run services update <서비스> --region <리전> --update-env-vars <KEY>=<잘못된 값>   # 실패 확인용
gcloud run services update <서비스> --region <리전> --update-env-vars <KEY>=<원래 값>     # 복구(remove 아님)

# 7. 정리
gcloud run services delete <테스트용 서비스> --region <리전> --quiet
gcloud run services remove-iam-policy-binding <서비스> --region <리전> --member=allUsers --role=roles/run.invoker  # 공개만 닫기
```

> ⚠️ **PowerShell 주의**: `gcloud logging read` 필터처럼 큰따옴표가 들어간 문자열은 PowerShell에서 `\"`로 escape하면 안 된다(PowerShell은 그 지점에서 문자열이 끝난 걸로 처리해 오류가 난다). **전체를 작은따옴표로 감싸서** 큰따옴표가 그대로 전달되게 한다. 빈 문자열 비교(`!=""`)도 Cloud Logging 필터 문법에서 막히니, "값이 존재하는지"를 뜻하는 `:*`를 쓴다.

## 8. 부록 B — ASP·MSM·GoodNews에 적용하면(계획) {#app-b}

**이 절은 전부 계획이다.** 세 프로젝트 모두 Cloud Run에 배포한 적이 없고, 지금 코드가 있는 건 friend-agent뿐이다. N045 방법론 문서와 같은 원칙으로, "실제로 한 일"과 "계획"을 섞어 쓰지 않는다.

### ASP (AI Story Partner)

지금은 기성 AI 도구(Claude 프로젝트)로 운영 중이고(N045 문서의 2단계에서 전환 조건 네 가지가 전부 미충족으로 확정됨), PRD의 아키텍처 문서에 "원고 입력은 기본 미저장"이 이미 정해져 있다. 나중에 전환 조건이 충족돼 웹앱으로 옮기게 되면:

- PRD의 "기본 미저장" 결정을 Cloud Run의 서버 메모리/DB 선택에 그대로 반영한다 — 오늘 friend-agent에서 서버 메모리가 인스턴스 교체로 사라지는 걸 직접 봤으니, "저장해야 하는 것"과 "저장 안 해도 되는 것"을 배포 전에 먼저 표로 정리한다.
- PD 1인 PoC 단계에서는 `--allow-unauthenticated`로 바로 공개하지 말고, 특정 계정만 호출하게 인증을 건다.
- 비용 통제가 필요한 시점(전환 조건 ②)이 오면, 최대 인스턴스가 아니라 LLM 제공사의 사용자별·일별 호출 한도부터 설계한다.

### MSM (My-Story-Maker)

지금은 로컬 파이프라인(원고→웹소설 각색→웹툰 스토리보드→컷 이미지, episode 040·041로 실제 API 검증 완료)이고, 클라우드 배포는 아직 없다. 배포하게 되면:

- 이미지 생성 API 키를 지금의 로컬 `.env` 구조에서 Secret Manager로 그대로 옮긴다(friend-agent의 `llm-api-key` 패턴 재사용).
- 파이프라인 한 편 처리에 시간이 걸릴 수 있으므로, 타임아웃은 "가장 느린 에피소드 처리 시간"을 먼저 실측한 뒤 그걸 기준으로 정한다(오늘 "평소 값을 먼저 잰다"는 원칙 그대로).
- 중간 산출물(`outputs/` 폴더에 해당하는 것)을 서버 메모리에 두지 않는다 — 콜드 스타트나 재배포로 인스턴스가 바뀌면 사라진다는 걸 오늘 실측했으니, 외부 스토리지(Cloud Storage 등) 연결을 배포 전에 먼저 설계한다.

### GoodNews (뉴스로 축하해)

지금은 기획 단계(사업제안서·총괄계획서만 존재)이고 코드는 없다. 나중에 서비스가 구현되면:

- 사용자 요청(축하 메시지·콘텐츠 생성)마다 LLM을 부르는 구조이므로, 오늘 4단계에서 확인한 대로 **최대 인스턴스가 아니라 사용자별·일별 호출 한도**를 비용 통제의 1순위로 설계한다.
- 공개 테스트를 할 경우, 오늘 friend-agent를 "실습이 끝날 때까지만 공개하고 그 뒤 닫는다"고 미리 정한 방식을 그대로 가져와, 공개 기간과 종료 조건(언제, 무엇을 보고 닫을지)을 배포 전에 문서로 먼저 정한다.

## 9. 부록 C — 용어 사전 {#app-c}

- **Cloud Run**: 컨테이너 단위로 요청이 있을 때만 켜지는 서버리스 실행 환경.
- **소스 배포**: Dockerfile 없이 소스 코드를 올리면 Buildpacks가 알아서 이미지를 빌드하는 방식.
- **Secret Manager**: API 키 같은 민감한 값을 환경변수와 분리해 저장하고, 서비스에는 이름·버전만 연결하는 서비스.
- **콜드 스타트**: 인스턴스가 0개로 줄었다가 요청이 와서 새로 켜질 때 생기는 지연.
- **동시성(concurrency)**: 인스턴스 하나가 동시에 처리하는 요청 수.
- **최대/최소 인스턴스**: 자동으로 늘어나는 인스턴스 수의 위아래 한계.
- **리비전**: 설정이나 코드를 바꿀 때마다 새로 생기는 배포 단위. 트래픽은 리비전 단위로 분배한다.
- **요청/컨테이너/시스템 로그**: 접수 기록(요청)·앱 내부 기록(컨테이너)·인프라 사건 기록(시스템). 진짜 원인은 보통 컨테이너 로그에 있다.
- **no available instance**: 순간적인 트래픽 폭주로 새 인스턴스를 제때 띄우지 못해, 기다리지도 않고 요청을 즉시 거절하는 Cloud Run의 동작.
