3. Ch03 — Google Cloud 준비

학습서가 요구한 것

프로젝트 이름을 friend-agent-course 로 만들었는데, 프로젝트 ID는 friend-agent-course-471203 으로 정해졌습니다. gcloud 명령의 --project 나 gcloud config set project 에 넣어야 하는 값은 무엇인가요?

(학습서 요구 절차: 무료 체험 가입 → 새 프로젝트 → gcloud 설치와 gcloud init → 기본 리전 설정 → API 4개 사용 설정)

제가 수행한 결과

  1. 프로젝트 생성: 이미 무료 체험 계정(남은 크레딧 ₩435,523, 평가판 15일 남음)이 있어서 다른 용도의 기존 프로젝트와 섞이지 않도록 새 프로젝트를 만들었습니다. 이름 friend-agent-course, 프로젝트 ID <프로젝트 ID>, 프로젝트 번호 <프로젝트 번호>입니다. 퀴즈의 답처럼 명령에는 이름이 아니라 ID를 썼습니다.
  2. gcloud 설치·로그인: Windows에서 Google Cloud SDK 589.0.0을 "나만 사용(Single user)"으로 설치했습니다. 설치 직전에 열어 둔 PowerShell에서는 gcloud를 찾지 못했는데(PATH 미반영), 창을 새로 열자 해결됐습니다.
  3. 프로젝트·리전 설정: gcloud config list에서 project와 region이 비어 있어 gcloud config set project와 gcloud config set run/region으로 직접 정했습니다.
  4. API 4개 활성화: gcloud services enable run cloudbuild artifactregistry secretmanager가 finished successfully로 끝났고, gcloud services list --enabled에서 4개를 모두 확인했습니다.
gcloud config set project <프로젝트 ID>
gcloud config set run/region us-central1
gcloud services enable run.googleapis.com cloudbuild.googleapis.com artifactregistry.googleapis.com secretmanager.googleapis.com

4. Ch04 — 배포 명령 하나가 하는 일

학습서가 요구한 것

hello 앱을 배포했는데 서비스 URL을 열어도 화면이 나오지 않는다고 가정해 보세요. 콘솔의 어느 화면을 어떤 순서로 열어 원인을 찾을지 이 섹션의 확인 순서를 근거로 적어 보세요.

(학습서 요구 절차: my-hello/ 폴더에 파일 4개를 만들고 gcloud run deploy hello --source . --region us-central1 --allow-unauthenticated 실행, 이후 콘솔에서 5단계 확인)

제가 수행한 결과

my-hello/에 main.py, requirements.txt, Procfile, .python-version 네 파일을 만들고 배포했습니다. 첫 시도는 실패했습니다.

⚠️ 첫 배포 실패와 해결

소스 업로드까지는 ✓였는데 Deployment failed가 났고, 메시지는 <프로젝트 번호>-compute@developer.gserviceaccount.com does not have storage.objects.get access였습니다. 코드나 명령의 문제가 아니라 새 프로젝트에서 빌드를 맡는 서비스 계정에 권한이 없던 것입니다. Editor 같은 넓은 권한은 주지 않고, 빌드에 필요한 역할 하나(roles/cloudbuild.builds.builder)만 그 계정에 부여했습니다. 같은 배포 명령을 다시 실행하자 성공했습니다. 빌드 기록에 실패 시도가 남지 않은 것도 "빌드가 시작되기 전 권한 단계에서 막혔다"는 증거였습니다.

gcloud projects add-iam-policy-binding <프로젝트 ID> \
  --member="serviceAccount:<프로젝트 번호>-compute@developer.gserviceaccount.com" \
  --role="roles/cloudbuild.builds.builder"

배포 후 서비스 주소를 열어 /에서 "안녕하세요, 첫 배포입니다"와 /health에서 {"status":"ok"}를 확인했고, 2장 표의 ①~④를 콘솔에서 찾았습니다. 리비전 상세에서 설정이 함께 기록돼 있음도 확인했습니다.

hello-00001-7c5에 기록된 설정값

동시 실행(동시성)80
CPU 한도 / 메모리 한도1 / 512MiB

환경 변수0개 (뒤 7장에서 키가 서버에 없는 이유와 연결됨)

이해 점검에 대한 답

서비스 URL을 열어도 화면이 안 나오면 ① Cloud Build 기록에서 빌드가 성공했는지, ② Artifact Registry에서 이미지가 생겼는지, ③ Cloud Run의 리비전 탭에서 배포 버전과 트래픽을, ④ 측정항목에서 인스턴스가 떴는지, ⑤ 로그에서 요청·오류를 차례로 봅니다. 이번 403 사례처럼 빌드 단계 앞에서 막히면 빌드 기록 자체가 비어 있으므로, 터미널의 오류 메시지가 첫 단서가 됩니다.

5. Ch05 — 같은 일을 혼자: 리비전, 롤백, 트래픽 분할

학습서가 요구한 것

1. my-hello/main.py 의 화면 문구를 "두 번째 배포입니다"로 바꿉니다. 2. 같은 배포 명령으로 다시 배포하고, 브라우저에서 문구가 바뀌었는지 봅니다. 3. 리비전 목록을 보고 리비전이 몇 개인지, 지금 트래픽을 받는 리비전이 어느 것인지 적습니다. 4. 트래픽 100%를 첫 리비전으로 전환해 화면이 처음 문구로 돌아가는지 봅니다. 5. 다시 최신 리비전이 트래픽을 받게 돌려놓습니다.

제가 수행한 결과

단계수행확인한 결과
1·2화면 문구를 "두 번째 배포입니다"로 바꾸되 글자를 크게(화면 폭의 7%) 하고 위아래로 움직이며 색이 바뀌게 만들어 재배포리비전 hello-00002-f9k 생성, 서비스 주소에서 새 화면 확인
3gcloud run revisions list리비전 2개. hello-00002-f9k가 ACTIVE(yes), hello-00001-7c5는 트래픽 없음
4update-traffic --to-revisions hello-00001-7c5=100출력 100% hello-00001-7c5, 서비스 주소가 첫 화면으로 돌아옴. 새 리비전은 삭제되지 않고 남음
추가트래픽 50:50 분할처음에는 PowerShell이 쉼표를 목록 구분자로 해석해 not an integer 오류. 값을 큰따옴표로 감싸 해결하고 분할 설정 성공
5update-traffic --to-lateststatus.traffic가 latestRevision: True, percent: 100, revisionName: hello-00002-f9k
gcloud run revisions list --service hello --region us-central1
gcloud run services update-traffic hello --region us-central1 --to-revisions hello-00001-7c5=100
gcloud run services update-traffic hello --region us-central1 --to-revisions "hello-00001-7c5=50,hello-00002-f9k=50"
gcloud run services update-traffic hello --region us-central1 --to-latest
📌 확인한 원리

롤백은 코드를 삭제하거나 리비전을 지우는 것이 아니라 사용자 요청이 가는 대상을 바꾸는 것입니다. 특정 리비전에 트래픽을 고정해 두면 이후 새 배포가 트래픽을 받지 못하므로 확인이 끝나면 --to-latest로 반드시 돌려놓아야 합니다.

6. Ch06 — 배포 전 로컬 실행

학습서가 요구한 것

.env 에서 LLM_PROVIDER=fake 를 openai 로 바꾸고(받은 키가 Gemini 키라면 gemini), LLM_API_KEY= 뒤에 키를 붙여 넣고 저장합니다. 키는 편집기로 직접 넣습니다. 에이전트 대화창에 붙여 넣으면 키가 대화 기록에 남습니다.

제가 수행한 결과

  1. 내 GitHub 계정에 템플릿으로 비공개 저장소 friend-agent를 만들어 내려받았습니다(gh repo create ... --template 88chacha/friend-agent-template --private --clone).
  2. 가상환경 .venv를 만들고 requirements.txt를 설치했습니다(fastapi 0.150.0, uvicorn 0.54.0, openai 3.35.1 등). 컴퓨터의 Python은 3.14이고 저장소는 3.13을 지정하지만 설치와 실행에 문제가 없었습니다.
  3. .env.example을 .env로 복사한 뒤 먼저 fake 모드로 uvicorn app.main:app --port 8080을 실행했습니다. 시작 로그가 JSON 한 줄(severity, provider: fake, storage: memory, auth: none)로 찍히고 Application startup complete.가 나오는 것을 확인했습니다.
  4. .env를 직접 열어 LLM_PROVIDER=openai로 바꾸고 키를 직접 붙여 넣었습니다. 키 값은 AI 어시스턴트와의 대화에 입력하지 않았고, 설정이 들어갔는지는 제공사 이름과 키 글자 수만 확인하는 방식으로 점검했습니다. 서버를 다시 띄워 진짜 OpenAI 답변이 오는 것을 확인했습니다.
💡 확인한 것

.gcloudignore에 .env가 들어 있어서 소스 배포 때 이 파일은 서버로 올라가지 않습니다. 로컬에서 되는 것과 서버에서 되는 것이 다를 수 있다는 점이 7장의 실패로 이어집니다.

학습서가 요구한 것

③ Secret Manager 연결은 다음 순서로 했습니다.

  1. 콘솔에서 시크릿 이름을 입력하다가 llm-api-key를 lim-api-key로 잘못 친 것을 만들기 전에 화면에서 발견해 고쳤고, 키 값은 콘솔 값 칸에 직접 붙여 넣었습니다. (이름이 다르면 이후 명령이 모두 실패하므로 만들기 전에 잡은 것이 핵심입니다.)
  2. gcloud secrets describe llm-api-key --format="value(name)"로 이름을 확인했습니다(값은 출력되지 않음).
  3. 서비스가 쓰는 계정에 이 시크릿 하나에 대해서만 읽기 역할(roles/secretmanager.secretAccessor)을 부여했습니다.
  4. --update-secrets LLM_API_KEY=llm-api-key:latest, --update-env-vars LLM_PROVIDER=openai, --max-instances 2를 붙여 다시 배포했습니다. 첫 배포가 실패한 상태여서 update가 아니라 deploy를 썼습니다.
gcloud secrets add-iam-policy-binding llm-api-key \
  --member="serviceAccount:<프로젝트 번호>-compute@developer.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"

gcloud run deploy friend-agent --source . --region us-central1 --allow-unauthenticated \
  --update-secrets LLM_API_KEY=llm-api-key:latest --update-env-vars LLM_PROVIDER=openai --max-instances 2

이해 점검에 대한 답

터미널 메시지만 보고 포트 설정이 문제라고 판단했다면 포트나 시작 명령을 고치는 불필요한 변경만 생기고 문제는 풀리지 않았을 것입니다. 같은 앱이 로컬 8080에서는 잘 떴으므로 포트 설정은 원인일 수 없었고, 실제 원인은 앱이 시작하다 키가 없어 스스로 종료한 것이었습니다. 직접 고칠 때는 실패한 리비전의 로그를 먼저 읽고 로그에 적힌 오류를 근거로 원인을 정합니다. 코딩 에이전트에 맡길 때는 "로그를 근거로 원인을 설명해 줘, 아직 아무것도 고치지 마"를 함께 요청하고, 변경 명령과 대상(서비스 이름·시크릿 이름·역할)을 확인한 뒤 승인합니다.

8. Ch08 — 회고

학습서가 요구한 것

섹션 1에서 Vercel 배포 버튼을 누른 뒤 일어나는 일을 짐작해 적었습니다. 그 답을 다시 읽고, 오늘 콘솔에서 직접 찾은 단계와 비교했을 때 짐작이 맞았던 부분과 새로 알게 된 부분을 적어 보세요.

제가 수행한 결과

실습에서 직접 확인한 것을 중심으로 정리합니다.

  • 배포는 버튼 하나가 아니라 여러 단계였고, 단계마다 확인할 화면이 따로 있었습니다(빌드 기록, 이미지 저장소, 리비전, 인스턴스, 로그). 빌드 단계 앞의 권한 오류(403)처럼 어떤 실패는 빌드 기록에도 남지 않는다는 점도 알게 됐습니다.
  • 롤백은 되돌리는 것이 아니라 가리키는 곳을 바꾸는 것입니다. 새 리비전은 남아 있어서 언제든 다시 최신으로 돌릴 수 있었습니다.
  • 터미널 메시지는 결과이고 원인은 로그에 있습니다. 포트 오류처럼 보였지만 진짜 원인은 키 누락이었습니다.
  • 로컬에서 되는 것이 서버에서도 되는 것은 아닙니다. .env는 .gcloudignore로 서버에 올라가지 않으므로 키는 Secret Manager로 따로 연결해야 했습니다.
  • 배포 성공 메시지와 서비스가 실제로 일하는 것은 별개입니다. 주소 응답(200), 실제 LLM 답변, 콘솔의 키 연결 표시를 각각 확인했습니다.
⚠️ 남은 위험과 후속 과제

friend-agent는 --allow-unauthenticated로 공개돼 있고 요청마다 제 LLM 키로 비용이 나갑니다. --max-instances 2는 동시 처리 규모만 제한할 뿐 호출 총량을 막지 못하며, 비용 총액은 LLM 제공사의 월 사용 한도가 막아야 합니다. 이 서비스는 다음 실습(N047: 요청 타임아웃, 인스턴스 수, 비용 한도, 로그 읽기)에서 그대로 이어 쓰며, 그 전까지 서비스 주소를 공유하지 않습니다. 또 서비스가 대화를 서버 메모리에 저장하므로 새 리비전 배포 때 캐릭터와 대화가 사라질 수 있다는 점도 N047에서 확인할 대상입니다.
