## 6. 가끔 느린 답과 늘어난 요금 (학습서 6장)

**방법**: 사용자가 도구를 쓰는 메시지와 잡담을 더 보낸 뒤 Langfuse에서 Is Root Observation=True·Latency 정렬로 확인했다(화면 캡처). 숫자는 같은 트레이스를 API로 읽어 단계별 시작·끝 시각, 토큰, 비용까지 표로 냈다(원문은 읽지 않음). 표본은 진짜 LLM을 쓴 `chat-turn` 14개 — 사용자 12개(저장소 = Supabase) + 내가 일회용 스크립트로 돌린 2개(저장소 = 내 컴퓨터 메모리).

**총 시간(Latency)**: 가장 느린 것 10.28초(`내일 부산 미세먼지 어때?`, 도구 두 개: 대기질+날씨), 가장 빠른 것 3.77초(내 스크립트 실행). 사용자 12개만 보면 4.75~10.28초, 평균 약 7.5초.

**느린 단계 비교(사용자 12개 평균)**

|---|---|---|

**사용자가 기다린 시간(요청 시작 → `reply` 첫 글자)**: 사용자 12개 평균 약 5.1초(3.0~7.6초). 이 중 이름 없는 앞 구간이 평균 2.5초로 **약 절반**이다. 전체 Latency(평균 7.5초)와 체감 대기(평균 5.1초)의 차이는 `memory-update`·저장 구간 등 첫 글자 뒤에 도는 일이다.

**해석**: 동료가 말한 "가끔 한참 있다가 와요"는 (a) 도구를 두 개 쓰는 메시지(10.28초), (b) 앞 구간이 3.8초까지 늘 때(9.70초) 같은 경우였다. 앞 구간은 한 번만 느린 것이 아니라 12개 전부에 1.3~3.8초가 깔려 있는 **상시 비용**이다. 한두 트레이스로 단정하지 않았지만, 12개가 같은 방향이어서 저장소 접근이라고 본다(메모리 저장소로 돌렸을 때 0.01초라는 대조가 근거). 어느 호출(설정·캐릭터·기억·요약·최근 대화·메시지 저장)이 얼마씩인지는 아직 못 나눴다.

- 한계: 표본이 14개뿐이고 내 스크립트 2개는 기억·대화가 비어 있어 가장 싼 값(443 토큰, $0.000336)이 그쪽이다. 메시지당 평균 비용은 실제 사용자 트레이스가 쌓인 뒤 다시 계산해야 의미가 있다. 가격은 Langfuse가 gpt-4o-mini 가격표로 계산한 값이다.

**고친 것(이 관찰의 결과)**: 계측 구조표에 없던 저장소 접근 구간을 `load-context`(설정·캐릭터·기억·요약·최근 대화를 읽고 내 메시지를 저장), `save-turn`(답 저장), `summary-check`(요약할 때인지 확인)라는 span 세 개로 `app/agent.py`에 더했다. 서버가 `--reload`로 떠 있어 저절로 다시 시작됐다(사용자에게 알림). 테스트 26개 통과(순서 기대값 갱신). 이 변경이 구간을 실제로 채우는지는 새 메시지를 보내 다시 확인한다.

**새 단계 확인(사용자 화면, 10:04 `추운데 오늘 낮에는 어떻게 입고갈까?`)**: 총 7.58초 아래에 `load-context` 1.64초·`safety`·`choose-tools` 1.70초·`tool:get_weather` 1.20초·`reply` 1.16초·`save-turn` 0.57초·`memory-update` 0.68초·`summary-check` 0.41초가 나란히 보인다. 단계들의 합이 약 7.36초로 총 7.58초에 거의 맞아 **이름 없던 구간이 채워졌다**(남은 0.2초 정도는 단계 사이의 짧은 틈). `load-context`는 이번에 1.64초로 앞서 12개의 범위(1.3~3.8초) 안이다.

## 6-2. 실습 중 우연히 재현된 "엉뚱한 답" — 공휴일 (6장 중, 사용자 발견)

사용자가 `다음 공휴일이 언제고 어떤 날인지 알려줘`에 "다음 공휴일은 11월 9일(월)이고, 한글날이야!"라는 답을 받고 "10월 9일이 한글날인데"라고 지적했다. 오늘은 2026-11-02이고 11월에는 공휴일이 없다(다음은 12월 25일). 학습서 5장 순서대로 거슬러 읽었다(트레이스 읽기 전용 조회, 같은 질문 `다음 공휴일이 언제야?`도 같은 모양).

| 단계 | 값 |
|---|---|
| `reply` 출력 | "다음 공휴일은 11월 9일(월)이고, 한글날이야!" — **지어낸 답**(한글날은 10월 9일, 11월 9일은 달력상 월요일일 뿐) |
| `reply` 입력의 `[도구 결과]` | "2026-11-02부터 2026-11-30까지 공휴일이 없습니다." + "2026-11-01부터 2026-11-30까지 공휴일이 없습니다." — **도구는 '없다'고 정확히 전달**했는데 모델이 무시함 |
| `tool:get_holidays` ×2 | 둘 다 11월 말까지만 조회(`to: 2026-11-30`) → 결과 "없음"(그 범위 안에서는 사실) |
| `choose-tools` 출력 | `get_holidays` 두 번, **범위를 11월 30일까지만** 잡음(`reason`: 다음 공휴일 정보를 얻기 위해…) — '다음' 공휴일은 12월 25일이라 한 달 범위로는 못 찾음 |

**처음 어긋난 단계와 고칠 곳**: 두 곳이다. ① `choose-tools`가 "다음 공휴일"에 한 달짜리 범위를 골라 답을 못 찾는 결과를 만들었다(도구 `get_holidays`는 '기간 안의 공휴일'만 알려 주고 '다음 공휴일'을 찾는 기능이 없다 → 선택 프롬프트·규칙에 범위를 넉넉히(예: 1년) 잡으라는 지침, 또는 도구에 '다음 공휴일' 기능). ② 그 "없음"을 받고도 `reply`가 날씨 때와 달리 **실제 있는 것처럼 지어냈다**(답 만들기 프롬프트에 '도구가 없다고 하거나 못 찾았다면 추측하지 말고 그 범위에서 못 찾았다고 알린다' 규칙). 도쿄 날씨에서는 재현되지 않았던 "도구 결과를 받고도 지어내는" 유형이 여기서 재현됐다 — 같은 모델이라도 질문에 따라 다르다.

**아직 하지 않은 것**: 위 두 곳의 수정과 수정 뒤 같은 질문으로 재확인. (고치면 같은 트레이스 읽기로 수정 전후를 비교할 수 있다.) 학습서 5장의 "이해 점검" 답안은 이 공휴일 트레이스로 쓸 수 있다.

## 6-3. 공휴일 오답 수정과 수정 전후 비교 (같은 브랜치 `langfuse-tracing`, 계측과 별도 변경)

**바꾼 곳**(서비스 동작이라 계측 변경과 섞이지 않게 파일을 나눴다): `app/router.py`(도구 선택 지침), `app/tools.py`(공휴일 도구 설명·"없음" 결과 문구), `app/persona.py`(답 만들기 규칙), `tests/test_holiday.py`(새 파일 5개).

**① 도구 선택** — "다음 공휴일" 같은 질문은 `get_holidays`를 반드시 고르고 `args`를 `{}`로 두게 했다(도구는 `from`·`to`가 없으면 이미 오늘부터 1년을 찾는다). 도구 설명에도 "비우면 오늘부터 1년"을 적었다.
- **첫 시도가 새 문제를 만들었다**: 지침에 "args 를 빈 객체로 둔다"라고만 썼더니 모델이 이것을 `tools: []`(도구를 안 고름)로 읽었다. 같은 질문 4번 중 3번 도구 없이 답했고(`이유`에 "빈 객체를 선택했습니다"), 그 3번 모두 `[도구 결과]` 없이 날짜를 지어냈다("11월 15일 개천절/한글날/…"). 규칙 문장이 기존의 "tools 를 빈 배열로 둔다"와 같은 말로 읽힌 것이 원인이다.
- **고친 문장**: "반드시 get_holidays 를 고르고 args 는 {} 로 둔다. 예: {"name": "get_holidays", "args": {}} … 도구를 고르지 않고 tools 를 빈 배열로 두면 안 된다." — 예시를 JSON으로 보여 줬다.
- **수정 뒤 결과(실제 LLM, 같은 입력)**: `다음 공휴일이 언제고 어떤 날인지 알려줘` 4/4, `다음 공휴일이 언제야?` 4/4 모두 `get_holidays {}` → 12월 25일 크리스마스(1월 1일 새해까지) 정답. 수정 전에는 같은 질문 두 번 모두 한 달 범위로 "공휴일 없음" → 지어낸 답이었다. `11월에 공휴일 있어?` 3/3도 "11월에는 없고 다음은 12월 25일"로 정확. 회귀 확인으로 `도쿄 날씨 어때?` 3/3은 "확인할 수 없어"로 정직하게 답했다.

**② 답 만들기** — `FIXED_RULES`에 "[도구 결과]가 '없습니다', '지원하지 않습니다', '찾지 못했다'는 뜻이면 있는 것처럼 꾸며 말하지 않는다. 조회한 범위에서는 없었다고 그대로 알리고, 더 넓게 찾아볼지 묻는다. 달력의 날짜나 아는 공휴일 이름을 도구 결과인 것처럼 섞어 말하지 않는다."를 더했다. 공휴일 도구의 "없음" 결과 문구에도 "(이 기간 밖은 조회하지 않았습니다)"를 붙였다.
- **이 규칙의 효과는 불분명하다**: 도구가 "11월에는 공휴일이 없습니다"라고 준 같은 입력으로 수정 전·후 규칙을 5번씩 비교했더니(도구 선택은 건너뜀) 사람이 읽고 판정해서 **수정 전 3/5, 수정 뒤 2/5가 지어냈다.** 표본이 5개뿐이라 차이가 있다고 말할 수 없다. 처음에 만든 자동 판정(키워드 검사)은 "세종대왕 탄신일"·"구정 연휴" 같은 지어낸 말을 못 잡아 수정 전 0/5로 잘못 나왔고, 사람이 다시 읽어 고쳤다 — 자동 채점의 한계를 직접 본 것이다.
- **남은 약점**: 이 서비스의 모델(gpt-4o-mini)은 규칙에 "지어내지 않는다"가 이미 있었는데도(수정 전 `FIXED_RULES`에 같은 취지의 줄이 있었다) 지어냈다. 규칙 한 줄을 더하는 것으로는 막을 수 없고, 막으려면 도구 선택을 바로잡아 정확한 결과를 주는 것(①)이 더 믿을 만했다. 도구를 아예 안 고른 채 날짜를 묻는 질문에 지어내는 경우는 코드 규칙(예: 공휴일 키워드가 있는데 도구가 없으면 키워드 규칙으로 보충)이 필요할 수 있으나 이번에는 하지 않았다.

**테스트**: `pytest -q` → **31 passed**(계측 26 + 공휴일 5). 실제 답은 매번 달라 테스트로 판정할 수 없어서, 테스트는 고친 지시문·도구 동작이 그대로 있는지만 지킨다.

**아직 하지 않은 것**: 커밋·PR(두 변경을 별도 커밋으로 나눌 예정), 도구 없이 지어내는 경우의 코드 안전장치, 수정 뒤 사용자가 화면에서 직접 한 번 더 확인.

## 6-4. 고쳤는데 화면에서는 여전히 틀렸다 — 틀린 답이 대화 기록에 쌓여 다음 답을 오염시켰다

**사용자 확인(화면)**: 6-3 수정 뒤 `다음 공휴일은 언제야?`를 세 번 보냈더니 세 번 모두 "11월 9일(월) 한글날"이었다("아직 안 바뀌었나봐").

**트레이스를 거슬러 읽은 결과(01:26~01:27, 3개)**: 도구 선택·도구 결과는 **이미 고쳐져 있었다.** `choose-tools`가 `get_holidays {}`를 골랐고 `tool:get_holidays`가 "12월 25일 크리스마스, 1월 1일 새해, …"를 정확히 돌려줬으며 그 문장이 `reply` 입력의 `[도구 결과]`에 들어 있었다. 그런데 `reply` 입력에는 앞선 대화 20개가 함께 들어 있었고, 그 안에 **내가(어시스턴트가) 앞서 한 틀린 답("다음 공휴일은 11월 9일(월)이야!…") 2~4개**가 있었다. 모델은 정확한 도구 결과보다 자기 앞선 말을 따라 했다(세 번째 시도에서는 틀린 답이 4개로 늘어 더 굳어짐). 이 실습의 6장 "도구 결과는 맞는데 답이 틀렸다 → reply" 유형이며, 오류가 대화 기록에 남아 다음 답의 재료가 되는 **되먹임**이다.

**왜 내 시험에서는 안 보였나**: 6-3의 확인은 매번 빈 대화(`MemoryStore`)로 보냈다. 앞선 틀린 답이 없는 대화에서는 도구 선택이 고쳐지는 것만으로 정답이 나왔다. 대화 기록이 있는 실제 조건을 재현해야 했다.

**실제 입력 그대로 재생(같은 입력 12번씩, 판정은 답에 '12월 25일'이 있는가)**
| 변형 | 정답 |
|---|---|
| A. 기록된 그대로(지금까지의 규칙) | **0/12** — 화면의 오답이 그대로 재현됨 |
| B. 규칙 한 줄 추가("앞선 말과 달라도 도구 결과를 따른다") | 1/12 — 규칙 문장으로는 못 막음 |
| C. **도구 결과를 질문 바로 앞에 system 메시지로 한 번 더** | **11/12** |
| D. 도구 결과를 마지막 user 메시지 뒤에 붙임 | 1/12 — 사용자 말로 읽혀 효과 없음 |
작은 시뮬레이션(틀린 답 3쌍만 넣은 빈 저장소)에서는 A도 6/6이었다 — 오염은 대화가 길고 틀린 답이 여럿 쌓였을 때 생긴다.

**고친 것**: `app/agent.py`에 `tool_note()`를 만들어, 도구를 쓴 턴에서는 "[방금 조회한 도구 결과 — 앞선 대화에서 내가 한 말과 달라도 이 결과를 따른다] - …"를 **대화 마지막, 사용자 질문 바로 앞**에 system 메시지로 넣었다(시스템 지시문의 `[도구 결과]`는 그대로). 도구를 안 쓴 턴에는 넣지 않는다. 기존 규칙 줄(B)은 효과가 없었지만 해로울 것이 없어 남겼다.

**수정 뒤 확인**: 화면에서 틀렸던 실제 대화 20개를 저장소에 넣고 `run_turn`을 그대로(도구 선택부터) 8번 돌렸더니 **8/8 정답**("12월 25일(금) 크리스마스", 한 번은 "미안해, …"로 바로잡음). 테스트 `pytest -q` → **33 passed**(계측 26 + 공휴일 7).

**한계**: ① Claude 클래스는 system 메시지를 한곳(맨 앞)으로 모아 보내므로(`llm.py to_claude`) 이 위치 효과가 없다 — OpenAI 호환 모델(현재 쓰는 `gpt-4o-mini`)에서만 확인했고 Claude에서는 확인하지 못했다. ② 틀린 답이 이미 쌓인 사용자 대화는 지우지 않았다(사용자 데이터). ③ 이 수정은 도구를 쓴 턴에만 있다. 도구를 안 고른 채 지어내는 경우(6-3 첫 시도에서 본 것)는 여전히 규칙으로는 못 막는다.

**6-4 수정 뒤 사용자 확인(화면)**: 틀린 답이 6개쯤 남아 있는 같은 대화에서 `다음 공휴일은 언제야?` → "12월 25일(금) 크리스마스야!", 이어 `다음 공휴일이 언제인지 말해줄래? 어떤 날인지 의미도 알려주고` → "12월 25일(금) 크리스마스야! 크리스마스는 예수님의 탄생을 기념하는 날로, …" 두 번 모두 정답. (두 번째 질문의 문장은 새로 바꿔 보낸 것이라 앞선 질문과 겹치지 않는다.)

## 7. 속성 붙이기 — 사용자·세션·환경·버전 (학습서 7장, 요청 틀 2)

**요청 틀의 빈칸**: `user_id` = 서버가 로그인으로 확인한 사용자 ID(이메일은 넣지 않음), `session_id` = 사용자 ID + 한국 날짜, `environment` = 환경변수 `ENV`, `version` = Cloud Run 리비전(`K_REVISION`, 없으면 `local`), `metadata` = 커밋(`COMMIT_SHA`), `tags` = 고른 도구 이름·안전 응답. `chat-turn`과 `greeting` 모두에 붙인다.

**일회용 시험으로 먼저 알아낸 것**: `propagate_attributes`는 그 `with` 안에서 **만든** 관찰 단위에만 속성을 붙인다. 루트만 안에서 만들고 자식을 밖에서 만들면 자식에는 `environment`만 있고 user·session·version이 비었다(`spikeA-child-outside`). 그런데 `run_turn`은 멈췄다 이어지는 제너레이터라 `with`를 길게 열어 둘 수 없다.

**설계**: `app/observe.py`에 `Handle`(관찰 단위 + 같은 트레이스가 공유하는 속성 사전)을 만들어, 관찰 단위를 **만드는 순간에만** `propagate_attributes`를 열어 붙이게 했다. 태그는 알게 된 뒤(안전 응답 여부, 고른 도구)부터 만드는 관찰 단위에 붙는다(`root.tag(...)`). `app/agent.py`는 `start_trace(..., user_id=uid)`와 `root.tag(...)` 세 줄만 바뀌었다. 키가 없어 계측이 꺼졌을 때는 `NOOP`가 `tag`도 받아 아무 일도 안 한다.

**테스트**: 속성 값(사용자 ID·한국 날짜 세션·`ENV`·`K_REVISION`·커밋·이메일 없음)과, 루트와 자식 모두에 속성이 전달되며 나중에 더한 태그는 그 뒤 자식부터 붙는 것을 확인하는 3개를 더했다. `pytest -q` → **36 passed**.

**실제 Langfuse 확인(일회용 스크립트, 사용자 `attrs-check-user`, 도구를 쓰는 질문)**: 한 트레이스의 **9개 관찰 단위 모두**(`chat-turn`, `load-context`, `safety`, `choose-tools`, `tool:get_holidays`, `reply`, `save-turn`, `memory-update`, `summary-check`)에 user=`attrs-check-user`, session=`attrs-check-user:2026-11-02`, environment=`local`, version=`local`이 붙었고 루트 메타데이터에 `commit: local`이 있다. 이전 트레이스(속성 붙이기 전)는 같은 필드가 모두 비어 있었다.
- 확인하지 못한 것: **태그**. 조회 API의 `tags` 필드는 속성을 붙인 일회용 시험에서도 비어 있었다(필드 이름·조회 방식 문제인지, 태그가 안 붙은 것인지 구분 못 함). Langfuse 화면의 Trace Tags 필터로 사용자가 확인한다.
- 알아 둘 것: 루트 메타데이터에 SDK가 자동으로 `scope.attributes.public_key`(공개키 앞부분이 아니라 전체 공개키)를 넣는다. 공개키는 혼자서는 쓸 수 없는 식별자라 문제는 없으나, 이 필드가 보이는 화면을 공유할 때는 알아 둔다.

**아직 하지 않은 것**: 사용자의 이사 이야기 시나리오(화면), Users·Sessions 화면 확인, staging 연결, 리비전 비교, 커밋·PR.

## 7-2. 이사 이야기 시나리오 — 속성은 붙었고, 기억이 "틀린 값"으로 저장됐다 (학습서 7장 실습, 사용자 화면 + 트레이스)

**화면(사용자)**: `나 다음 주 토요일에 이사 가` → 말풍선 아래에 "⏰ 약속을 저장했습니다: 11월 7일(토) 09:00에 '이사 가기'"와 "🧠 기억함: 11월 12일(토) 이사"가 함께 떴다. 잡담 3개 뒤 `내가 다음 주에 뭐 한다고 했지?` → "다음 주 토요일, 11월 7일에 이사 간다고 했어!".

**속성 확인(성공)**: 다섯 `chat-turn` 모두 user=`02604922-…`(사용자 UUID), session=`<사용자 ID>:2026-11-02`, environment=`local`, version=`local`이 붙었다(조회 API로 확인, 6장 구현 결과).

**거슬러 읽은 결과** — 오늘은 2026-11-02(월)이고 [달력]에 "다음 주: …11/14(토)…"가 적혀 있어 **정답은 11월 14일(토)**. 그런데 값이 세 개로 갈렸다.
| 곳 | 값 | 판정 |
|---|---|---|
| `choose-tools` → `tool:create_reminder` | `due_at 2026-11-07 09:00`, "이사 가기" 약속 저장 | **두 가지가 틀림**: ① 사용자는 알려 달라고 부탁한 적이 없다(라우터 지시문에 "분명히 부탁할 때만"이 있는데도 모델이 어김, 이유란에 "알림을 생성"). ② 날짜가 '이번 주 토요일'(11/7)이다 |
| `memory-update` 출력 | `added: ["11월 12일(토) 이사"]` | **지어낸 날짜**: 11/12는 목요일이다(요일과 날짜가 안 맞음). 날짜 근거가 어디에도 없다 |
| 마지막 `choose-tools` → `list_reminders` | "저장된 약속: 11월 7일(토) 09:00 '이사 가기'" | 틀린 약속이 다음 답의 재료가 됨 |
| 마지막 `reply` 출력 | "다음 주 토요일, 11월 7일에 이사 간다고 했어!" | 입력에 11/7(약속)과 11/12(기억)이 같이 있었고 모델은 약속을 따름 |

**기억이 끊긴 세 곳(저장·전달·활용)으로 보면**: 저장은 됐고 `reply` 입력의 `[기억 메모]`에도 전달됐지만 **저장된 값이 틀렸다** — 학습서가 말한 세 곳 말고 네 번째 자리(저장된 내용이 틀림)다. 그리고 틀린 값이 하나가 아니라 둘이어서 활용 단계에서는 둘 중 하나를 고르게 됐다.

**원치 않은 부작용(사용자 데이터)**: 틀린 약속 "11월 7일 09:00 이사 가기"가 사용자의 Supabase에 **저장돼 있다**(11/7 이후 앱을 열면 "약속 알림"으로 먼저 말을 건다). 틀린 기억 "11월 12일(토) 이사"도 저장돼 있다. 사용자 데이터라 지우지 않았고 사용자가 화면에서 지우도록 안내한다.

**왜 기존 테스트가 못 잡았나**: `tests/test_no_reminder_without_request.py`는 "일정이 있다는 말만으로는 약속을 저장하지 않는다"를 확인하지만 **가짜 LLM(키워드 규칙)** 경로만 지난다. 진짜 모델이 지시문을 어기는 경로는 테스트에 없다.

**아직 하지 않은 것**: 위 오류 수정(① 모델이 고른 `create_reminder`에 코드 안전장치, ② 날짜와 요일이 안 맞는 기억 저장 막기), 사용자의 Users·Sessions 화면 확인.

## 7-3. 이사 이야기 오류 수정과 수정 뒤 확인 (같은 브랜치, 서비스 동작 변경)

**바꾼 곳**: `app/router.py`(안전장치 둘), `app/memory.py`(안전장치 하나), `tests/test_moving_story.py`(새 파일 6개). 지시문이 아니라 **코드 규칙**으로 막았다 — 지시문은 이미 있었는데(`create_reminder`는 "분명히 부탁할 때만") 모델이 어겼기 때문이다.
1. **원치 않은 약속 저장 막기**: 모델이 `create_reminder`를 골랐는데 메시지에 부탁하는 말(`알려`·`알림`·`리마인드`·`깨워`·`잊지`·`말해 줘`)이 없으면 그 도구를 빼고 `guards`에 "알려 달라는 부탁이 없는데 모델이 약속 저장을 골라서 뺐습니다."를 남긴다.
2. **약속 날짜 바로잡기**: 부탁은 했는데 모델이 정한 날짜가 메시지의 날짜 표현(`다음 주 토요일` 등)을 규칙으로 계산한 날짜와 다르면 날짜만 규칙의 날짜로 고친다(시각은 모델 것). 수정 전 같은 부탁("다음 주 토요일 아침에 이사 준비하라고 알려 줘") 6번 중 2번이 날짜가 틀렸다(11/12·11/7, 정답 11/14).
3. **날짜와 요일이 안 맞는 기억 저장 막기**: `11월 12일(토)`처럼 날짜와 요일이 함께 있는데 올해·내년 어디서도 안 맞으면(2026-11-12는 목요일) 저장하지 않고 경고 로그만 남긴다(내용은 로그에 안 남김). 맞는 날짜를 만들어 주지는 않는다.

**수정 뒤 실제 LLM 확인(트레이스는 끄고, 같은 입력)**
- `나 다음 주 토요일에 이사 가`(부탁 없음) 6번: **약속 저장 0/6**, 요일이 안 맞는 기억 0/6(기억이 남은 4번은 모두 "11월 14일(토) 이사"로 정확). 두 번은 모델이 약속 저장을 골랐다가 안전장치가 뺐다(`guards`에 기록).
- 부탁 표현 5가지 × 4번 = 20번 중 **20/20 날짜 정확**(기대값은 오늘 2026-11-02 월요일 달력으로 사람이 계산): `다음 주 토요일 아침`→11/14 09:00, `내일 아침 8시`→11/3 08:00, `모레 저녁`→11/4 19:00, `이번 주 금요일 오후 3시`→11/6 15:00, `다음 주 수요일`→11/11 09:00.
- 테스트 `pytest -q` → **42 passed**(계측 29 + 공휴일 7 + 이사 6). 새 테스트는 "모델이 어긴 것처럼 답하는 가짜 모델"을 써서 진짜 모델 경로를 흉내 낸다(기존 테스트가 가짜 LLM 경로만 지나 못 잡았던 빈틈).

**한계**
- 요일이 안 맞는 날짜만 막는다. 요일이 맞는 엉뚱한 날짜(예: 11월 19일(목))나 요일 없이 지어낸 날짜는 못 막는다.
- 약속 날짜 보정은 규칙 파서가 읽는 표현에서만 작동한다. 파서가 못 읽는 표현은 모델 날짜를 그대로 둔다.
- 이미 저장된 틀린 약속("11월 7일 09:00 이사 가기")과 틀린 기억("11월 12일(토) 이사")은 사용자 데이터라 지우지 않았다.

## 7-4. "기억을 지웠는데도 똑같다" — 틀린 약속이 남아 있었고 그것이 다시 기억으로 들어갔다

**사용자 확인(화면)**: 7-3 수정 뒤 사용자가 틀린 **기억**만 지우고 `나 다음주 토요일에 이사 가`를 보냈더니 "응, 맞아! 다음 주 토요일인 11월 7일에 이사 간다고 했지!"와 "🧠 기억함: 11월 7일(토) 이사"가 다시 떴다("기억을 지웠는데도 똑같아"). 틀린 **약속**("11월 7일 09:00 이사 가기")은 지우지 않은 상태였다.

**거슬러 읽은 결과(트레이스, 01:53)**
| 단계 | 값 |
|---|---|
| `choose-tools` | `list_reminders`를 골랐다(이유란에 "이사 가는 날을 알려 달라고 요구했기 때문"). 사용자는 **물은 것이 아니라 평서문**이었다 |
| `tool:list_reminders` | "저장된 약속: 11월 7일(토) 09:00 '이사 가기'" — 이전에 잘못 저장된 약속 |
| `reply` 입력 | `[도구 결과]`에 위 약속, 앞선 대화 20개 중에 내 틀린 답("11월 7일에 이사 간다고 했어!")이 하나 있음 |
| `reply` 출력 | "응, 맞아! 다음 주 토요일인 11월 7일에 이사 간다고 했지!" |
| `memory-update` 출력 | `added: ["11월 7일(토) 이사"]` — **요일은 맞는 날짜**라 7-3의 요일 검사를 통과했다 |
틀린 값이 **되먹임 고리**를 만들었다: 틀린 약속 → 조회 결과가 답에 섞임 → 답에서 다시 기억으로 저장. 지운 것은 기억뿐이라 약속이 다시 기억을 만들어 냈다.

**고친 것(코드 안전장치 둘)**
1. `router.py`: 질문이 아닌 말(물음표·`뭐/언제/있어/알려/확인/기억…` 같은 묻는 말이 없음)에 모델이 `list_reminders`를 골랐으면 뺀다. 묻는 말(`내가 다음 주에 뭐 한다고 했지?`)에서는 그대로 둔다.
2. `memory.py`: 사용자가 `내일`·`다음 주 토요일` 같은 상대 날짜로 말했는데 기억 문장의 `M월 D일`이 그것과 다르면 고친다 — 날짜가 하나면 맞는 날짜와 요일로 바꾸고(`11월 7일(토) 이사` → `11월 14일(토) 이사`), 둘 이상이면 어느 쪽이 틀렸는지 몰라 저장하지 않는다. 사용자가 상대 표현을 안 썼거나 기억에 날짜 숫자가 없으면 건드리지 않는다.
테스트 `pytest -q` → **46 passed**(이사 이야기 테스트 10개).

**수정 뒤 같은 조건 재현(실제 LLM, 틀린 약속 + 앞선 틀린 답이 있는 대화, 6번)**: 기억은 **6번 모두 "11월 14일(토) 이사"**(저장 단계 틀림 0/6), `list_reminders`는 **0/6** 사용. 그러나 **답에 "11월 7일"이 나온 것이 2/6** — 앞선 대화에 남은 내 틀린 답을 모델이 되풀이한 것이다(공휴일 6-4와 같은 되먹임).

**한계(사실대로)**
- 도구 없이 나오는 답에서의 되풀이는 못 막았다. 공휴일에서는 정확한 도구 결과를 질문 바로 앞에 넣어 막았지만, 여기서는 정확한 근거 자체가 없다(기억도 막 14일로 고쳐 저장됨). 앞선 대화의 틀린 답이 사라지지 않는 한 남는다.
- 이미 저장된 틀린 **약속**은 그대로 있다. 사용자 데이터라 지우지 않았고, 사용자가 취소해야 한다. 약속을 취소하지 않으면 `내 약속 뭐 있어?` 등 약속 조회에서 계속 11/7이 나온다.
- 상대 날짜 표현 보정은 규칙(`when.day_offset`)이 읽는 표현에서만 작동한다.

**배운 것**: 틀린 값은 한 곳에서 안 끝난다. 저장소·약속·기억·대화 기록이 서로를 재료로 삼아 퍼진다. 한 군데를 지우면 다른 곳이 되살린다.

**7-4 수정 뒤 사용자 확인(화면)**: 사용자가 틀린 약속을 취소하고(약속 칸에 "취소됨") 기억 목록에서 틀린 기억 한 줄만 지운 뒤, 같은 대화에서 `나 다음주 토요일에 이사 가`를 보냈다. 답은 "알겠어! 다음 주 토요일에 이사 간다니 기대된다!"(날짜를 말하지 않음)이고 "🧠 기억함: **11월 14일(토)** 이사"로 정확히 저장됐다. 약속 저장은 뜨지 않았다. 답이 날짜를 되풀이하지 않은 것은 이번 한 번뿐이라 효과가 있다고 말하기 이르다(재현 조건 6번 중 2번은 되풀이했다).
`내 데이터 모두 삭제`는 캐릭터 설정까지 지워서 쓰지 않았다(사용자와 판단: 필요한 것은 약속 취소와 기억 한 줄이었다).

## 8-4. flush를 넣었는데도 빠졌다 — 마지막 이벤트 **뒤**의 코드는 CPU 없이 돈다

**PR #39 배포 뒤 확인(리비전 `friend-agent-staging-00044-fav`, 커밋 `0801522`)**: 사용자가 메시지를 정확히 5개 보냈다. 요청 로그 `POST /api/chat` **5건**(02:44:34·44·54, 02:45:01·13, 모두 200, 한 인스턴스가 모두 처리), Langfuse `chat-turn` **3개**(02:44:36·02:44:44·02:45:13). 02:44:54와 02:45:01 요청의 트레이스가 없다. 관찰 단위 수는 37 → 64(+27 = 3개 × 9)로 부분 도착도 아니다. 다른 환경으로 갔는지도 전체 환경으로 조회해 확인했다(없음). 2분 뒤 다시 세어도 같았다(SDK 설명은 전달된 데이터가 화면에서 읽히기까지 15~30초라고 하나 이 격차는 그보다 크고, 앞선 00041의 누락은 20분이 지나도 안 돌아왔다). Cloud Run 로그에 내보내기 실패 메시지(`export`·`opentelemetry`)는 없고 경고는 날짜·요일 안전장치 한 줄뿐이었다.
**도착 비율**: #39 이전 4/10(40%) → #39 이후 3/5(60%). 표본이 작아 개선이라고 말하기 어렵다. flush가 효과가 없었다.

**원인 재추정**: `flush`를 제너레이터의 `finally`(마지막 이벤트 `done`을 **보낸 뒤**)에 뒀다. `done`을 받은 브라우저가 연결을 닫으면 Cloud Run은 요청이 끝났다고 보고 CPU를 거의 주지 않는다. 그 뒤에 도는 `finally` 안의 flush가 멈출 수 있다. 이 서비스가 `memory-update`를 `done`을 보내기 **전에** 처리하는 것과 같은 이유(`agent.py` 머리말: "응답을 닫기 전에 처리한다")인데 같은 원리를 내가 새 코드에 적용하지 않았다. 직접 확인한 것은 아니다 — 확인하려면 배포 뒤 다시 5건을 세야 한다.

**고친 것(PR [#40](https://github.com/JEON-DAEJIN/friend-agent/pull/40))**: `observe.close_trace()`가 트레이스를 닫고 flush를 한 번만 하며 **`done`을 보내기 전에** 부른다(위기 응답 경로도). `finally`는 이미 닫지 않았을 때(예외)만 닫는다. `Handle.end`는 두 번 불려도 한 번만 닫는다. 테스트 `pytest -q` → **50 passed**(새 테스트: `done`이 나오는 시점에 flush가 이미 한 번 불렸고 끝난 뒤 다시 안 불린다, 위기 응답도 같다).

**배운 것**: 같은 저장소 안에 이미 "응답을 닫기 전에 처리한다"는 규칙이 있었다(`memory-update`). 새 기능(관측)을 붙일 때 그 규칙의 이유(Cloud Run의 응답 뒤 CPU 제한)를 읽고도 `finally`에 flush를 두었다. 같은 환경의 기존 설계 결정은 이유까지 읽고 새 코드에 옮겨야 한다.

**PR #40 머지**: CI 두 개 통과·머지 가능(CLEAN) 확인 뒤 `staging`에 머지했고 `deploy`가 시작됐다. 배포 뒤 5건을 보내 요청 로그 건수와 트레이스 개수를 다시 센다.

## 8-5. flush를 done 앞으로 옮겼는데도 빠졌다 — 원인을 두 번 추정했고 둘 다 맞지 않았다

**알려진 사실**: 모든 리비전에서 **첫 번째 요청의 트레이스는 항상 도착**했다(00041·00030·00044·00046 모두 #1). 요청은 모두 한 인스턴스가 처리했고(`maxScale=1`, 동시성 80), 서버는 uvicorn 한 프로세스(워커 여러 개 아님)이고 SDK 클라이언트는 프로세스당 한 번 만들어졌다("Langfuse 관측을 켰습니다." 리비전마다 1줄). 로컬에서는 사용자가 보낸 12개가 12개 모두 도착했다. Cloud Run 로그에는 내보내기 실패 메시지가 없다(`export`·`opentelemetry`·`Langfuse` 검색). 도착한 트레이스는 단계 9개가 모두 있고 빠진 것은 통째로 없다. 다른 환경으로 간 것도 아니다(전체 환경 조회). 옛 `/api/public/traces`는 HTTP 410(제거됨)이라 다른 경로로 교차 확인하지 못했다.

**아직 모르는 것**: 빠지는 요청이 무엇이 다른지(앞 요청과의 간격, 도구 사용 여부 등은 규칙이 없었다), SDK가 실제로 보내는지, 서버가 받고도 버리는지. 추정을 더 쌓기보다 증거가 필요하다.

**다음 진단(사용자 승인 필요)**: staging에 `LANGFUSE_DEBUG=True`를 잠깐 켜서 SDK가 내보내기마다 남기는 로그(트레이스 ID, 응답 코드)를 Cloud Run 로그에서 본다. 주의: 디버그 로그에는 기록 내용(대화 원문)이 섞일 수 있어 이 프로젝트의 Cloud Logging에 남는다 — 확인이 끝나면 곧바로 끄고, 필요하면 해당 로그를 지운다.

**결정(사용자)**: 이 문제는 여기서 정리하고 넘어간다 — 원인을 확인하지 못한 채 **한계로 남긴다.** 사실대로 적으면: Cloud Run(staging)에서 대화 트레이스는 40~60%만 Langfuse에 도착했다(10/4, 5/3, 5/2). flush를 넣고 위치를 옮겨도 달라지지 않았다. 로컬에서는 12/12 도착했다. 원인으로 CPU 제한·flush 위치를 추정했으나 둘 다 증거로 지지되지 않았다. 디버그 로그(`LANGFUSE_DEBUG`)로 요청별 내보내기를 추적하는 진단은 하지 않았다. **production에서 이 서비스를 운영하려면 그 전에 원인을 찾아야 한다**(비용·지연·점수 분석이 틀어진다). PR #39·#40의 flush는 효과가 확인되지 않았지만 해롭지도 않아(응답 시간 변화 미미) 그대로 두었다.
**정리**: 비교용으로 더했던 `BANNER` 환경변수를 `--remove-env-vars BANNER`로 되돌렸다(새 리비전 생성, `/version`의 banner가 비었는지 확인).

## 9. 점수 수집 — 좋아요·별로예요·신고 (학습서 8장, 요청 틀 3)

**요청 틀의 빈칸(학습서의 선택지 가운데)**: 반응을 받는 API는 **좋아요·별로예요는 새로 만들고**(`POST /api/feedback`), 신고는 기존 `POST /api/report`를 넓혔다. 메시지와 트레이스 잇기는 **메시지 `meta`에 트레이스 ID 저장**(화면을 다시 열어도 이어지는 쪽, `done` 이벤트에 싣는 쪽은 택하지 않음). 점수 이름·값: `user-feedback` 좋아요 1·별로예요 0(BOOLEAN), `report` 신고 1(BOOLEAN), 신고 사유는 `comment`. 서버가 로그인한 사용자의 답인지 확인. 키가 없으면 점수 전송만 건너뛰고 오류 없이 응답.
