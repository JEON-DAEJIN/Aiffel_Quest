# N054 오늘 학습 정리 — 에이전트가 왜 틀렸는지 기록으로 거슬러 읽기

> 버전 v1.0 · 2026-11-02 · 강의 N054 「Langfuse로 에이전트 문제 찾기」와 오늘 실습(3~9장)을 내 방식으로 한 장에 정리했다. 28년 기획·경영 경험에 빗대 쓰고, 숫자는 오늘 실습 진행기록에서 가져왔다. 확인하지 못한 것은 "추정" 또는 "확인 못 함"이라고 적었다.

## 오늘의 한 문장

> 📌 **요약** — 에이전트가 틀렸을 때는 감으로 고치지 않고, 요청 한 건의 **처리 이력(트레이스)을 처음 어긋난 단계까지 거슬러 읽은 뒤** 그 단계만 고친다. 기록을 남기는 일과 그 결과가 좋은지 판단하는 일은 별개다.

## 1. 경영 경험으로 풀면

| 오늘 배운 것 | 경영에 빗대면 |
|---|---|
| **서버 로그 vs 트레이스** — 로그는 "요청이 들어와 끝났다"만 남기고, 트레이스는 단계마다 입력·출력까지 남긴다 | 로그는 **결재 완료 대장**, 트레이스는 **결재선 전체 이력**이다. 결과가 이상하면 이력을 거슬러 올라가 처음 어긋난 결재 단계를 찾는다 |
| **관측 ≠ 평가** — 기록을 남기는 것과 답이 좋았는지 점수를 매기는 것은 다른 일이다 | **회의록과 성과 평가**의 차이. 회의록이 있다고 성과가 좋아지지는 않는다. 좋아요·별로예요·신고가 평가표 역할을 한다 |
| **속성(사용자·세션·환경·버전)** — 트레이스에 붙이는 꼬리표 | 택배 상자의 **받는 사람·주소·날짜 이름표**. 이름표가 없으면 동료 다섯 명의 대화와 내 시험이 한 목록에 섞인다 |
| **틀린 값은 한 군데서 안 끝난다** — 약속·기억·대화 기록이 서로를 재료로 삼아 퍼진다 | **잘못 전결된 규정이 여러 문서에 복사된 것**. 원본 한 장만 고쳐도 사본이 규정을 되살린다 |

> 💡 **팁** — 비유의 한계: 결재선은 한 줄이지만 트레이스는 나무 모양(단계 안에 단계가 들어간다)이고, 결재 이력과 달리 입력·출력 원문까지 담겨서 개인정보를 가리는 설정이 따라붙는다.

## 2. 오늘 직접 해서 알게 된 것

1. **한 메시지에 모델을 세 번 부른다.** `choose-tools`·`reply`·`memory-update`로, 잡담에도 도구를 고르는 호출이 매번 돈다. 평균 비용은 메시지당 약 $0.0004(약 0.6원)였다. 다만 표본이 14개이고 그중 2개는 기억·대화가 빈 내 스크립트라 평균 비용은 실제 사용 기록이 쌓인 뒤 다시 계산해야 한다.
2. **느린 구간의 절반이 계측되지 않은 저장소 접근이었다.** 처음에는 요청 시작 후 첫 단계까지 이름 없는 빈 구간이 평균 약 2.5초였다(사용자가 기다린 5.1초의 약 절반). 같은 코드를 내 컴퓨터 메모리 저장소로 돌리면 0.01초였다. 구간에 `load-context` 같은 이름을 붙이자 단계 합이 총 시간에 거의 맞았다. 어느 호출이 얼마씩인지는 아직 못 나눴다.
3. **틀린 답이 대화 기록에 쌓여 다음 답을 오염시켰다.** 공휴일 질문에서 도구 선택과 도구 결과는 이미 고쳐졌는데 화면 답은 계속 틀렸다. 앞선 대화에 내가 한 틀린 답이 여럿 있었고 모델은 정확한 도구 결과보다 자기 앞선 말을 따랐다. 같은 입력을 12번씩 재생하자 기록 그대로는 0/12, 도구 결과를 질문 바로 앞에 한 번 더 넣으면 11/12가 맞았다.
4. **지시문보다 코드 안전장치가 믿을 만했다.** 라우터 지시문에 "분명히 부탁할 때만 약속을 저장한다"가 이미 있었는데 모델이 어겼다. 규칙 한 줄을 더해 본 비교는 수정 전 3/5, 수정 뒤 2/5로 차이를 말할 수 없었다. 반면 부탁 표현이 없으면 도구를 빼는 코드 규칙은 6번 중 0번 저장으로 막았다.
5. **Cloud Run(staging)에서 트레이스가 40~60%만 도착했고 원인은 확인하지 못했다.** 요청 로그 건수와 Langfuse를 세 번 맞춰 보니 4/10, 3/5, 2/5였다. 로컬은 12/12 도착했다. 도착한 트레이스는 단계가 모두 있고 빠진 것은 통째로 없었다. production 연결 전에 원인을 찾아야 한다.

## 3. 오늘 틀린 것·고친 것

| 틀린 것 | 어떻게 알았나 | 고친 것·배운 것 |
|---|---|---|
| **"staging은 별도 사용자라 대화가 비어 있을 것"이라고 한 말** | 앱을 열자 10월 29일부터의 대화가 남아 있었다. staging도 같은 저장소를 쓰고 게스트 로그인이 이어졌다 | 확인하지 않고 말한 것. 환경이 다르다는 말은 **저장된 값을 보고** 한다 |
| **트레이스 누락 원인을 두 번 추정했는데 둘 다 틀렸다** — 처음에는 응답 뒤 CPU 제한 때문이라 보고 flush를 넣었고, 다음에는 flush 위치(마지막 이벤트 뒤)가 문제라 보고 앞으로 옮겼다 | 도착 비율이 40~60% 안에서 오르내릴 뿐 달라지지 않았다 | 증거 없이 추정을 쌓지 않는다. 원인은 모르는 채로 한계로 남기고, 이어서 쓰는 이 서비스의 기존 설계 이유(응답을 닫기 전에 처리한다)도 새 코드에 옮겼어야 했다 |
| **첫 수정이 새 문제(회귀)를 만들었다** — 공휴일 도구 지침에 "args를 빈 객체로 둔다"라고만 썼다 | 모델이 이 문장을 "도구를 안 고른다"로 읽어, 같은 질문 4번 중 3번 도구 없이 날짜를 지어냈다 | 예시를 JSON 형태로 보여 주고 "도구를 안 고르면 안 된다"를 덧붙였다. 고친 뒤 4/4 정답. 수정 뒤에는 **고친 곳이 아닌 곳**도 다시 돌려 본다 |

## 4. 내일 이어서 할 것

1. production에 연결하기 전에 트레이스가 빠지는 원인을 찾는다. 후보는 staging에 디버그 로그를 잠깐 켜서 요청별로 내보내기를 추적하는 것이다. 대화 원문이 로그에 섞일 수 있어 켠 뒤 곧바로 끄고 필요하면 로그를 지워야 한다.
2. 점수(별로예요·신고)로 거른 트레이스를 사람이 직접 읽는 연습을 한다. API 조회로는 걸러내기를 확인했지만 Langfuse 화면의 Scores 탭과 검색창 동작은 확인하지 못했다. 점수를 자동으로 매기는 평가는 그다음 단계로 둔다.
3. 도구를 안 고른 채 날짜를 지어내는 경우를 코드 규칙으로 막을 수 있는지 살펴본다. 오늘은 규칙으로 못 막았고 앞선 대화의 틀린 답을 되풀이한 경우가 6번 중 2번 남았다.

## 5. 아직 모르는 것

- 트레이스가 빠지는 이유와 빠지는 요청의 공통점
- 도쿄 날씨 질문에서 동료가 겪은 엉뚱한 답이 이번에 재현되지 않은 이유(모델·지시문이 그때와 달라졌는지, 동료의 문장이 달랐는지)
- 도구 결과를 질문 바로 앞에 넣는 방식이 Claude 모델에서도 통하는지(gpt-4o-mini에서만 확인)
- 트레이스에 붙인 태그가 제대로 붙었는지(조회 방식으로는 비어 있었고 화면에서 확인하지 못함)
