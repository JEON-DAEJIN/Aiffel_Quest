핵심 한 문장 요약

📌 요약 — Expo Go로 보던 앱은 노트북의 개발 서버가 켜져 있을 때만 내 폰에서 돈다. 다른 사람 폰에서 혼자 돌게 하려면 코드·이미지·설정을 앱 파일 하나로 묶고 서명하는 빌드가 필요하고, Expo는 이 일을 EAS Build가 클라우드에서 대신해 주므로 Windows 노트북에는 Node.js만 있으면 된다. ① 같은 코드가 폰에 들어가는 길은 세 가지다 — 개발 실행(Expo Go), 빌드해서 설치(preview, APK, 설치 링크), 스토어 배포(production, AAB·iOS, 개발자 계정). ② 빌드한 앱에는 코드가 고정되므로 화면을 고치면 다시 빌드해야 하고(해설서는 조건이 맞으면 EAS Update로도 된다고 덧붙인다), 서버의 프롬프트·백엔드·DB는 고쳐도 다시 빌드할 필요가 없다. ③ 빌드에 들어갈 값은 커밋하지 않는 .env가 아니라 eas.json 프로필의 env에 적고, 그 값은 앱 안에 그대로 들어가므로 비밀값은 넣지 않는다. ④ 패키지 이름과 서명 키는 스토어가 앱을 알아보는 기준이라 한 번 정하면 바꾸기 어렵다. ⑤ 스토어는 앱이 돌아가는지만 보지 않고 개인정보·데이터 삭제·AI 답 신고·AI 표시·앱 안 판매·연령 등급을 심사하며, 테스트 단계의 앱은 사람이 버튼을 눌러 넘기기 전에는 공개되지 않는다.

🧪 예제 — 한 줄 예: 스토어에 올린 AI 친구 앱에서 (가) 서버의 프롬프트를 바꿔 말투를 부드럽게 하고 (나) 전송 버튼 문구를 바꾸려 한다. (가)는 서버만 다시 배포하면 모든 사용자에게 바로 적용되고 앱은 그대로 둔다. (나)는 문구가 앱 파일 안의 번들에 들어 있으므로 새로 빌드해 업데이트를 내야 한다(학습서 p3 퀴즈, 정답 (나)만). 핵심은 고치려는 것이 앱 파일 안에 있는지, 서버에 있는지를 먼저 가르는 것이다.

🧪 예제 — 실습 결과(2026-11-06, v1.1에서 더함): 내 앱(N057에서 만든 하루친구)을 preview 프로필로 빌드해 Android 폰에 설치했고, 설치한 앱에서 메시지를 보내 답이 왔으며 카메라 권한·글자 인식도 됐다. 교안에 없던 일은 세 가지였다. ① 시작 전에 staging 백엔드가 결제 꺼짐으로 죽어 있어 새 결제 계정을 연결하고 서비스를 새 리비전으로 깨웠다(4-2절). ② build:configure가 app.json에 마이크 권한(RECORD_AUDIO)까지 넣었다(4-4절). ③ 설치 앱의 권한 목록에 마이크가 선언돼 있었는데, 원인은 expo-image-picker 플러그인의 기본값이었다(4-6절). 사실은 실습/N058_실습_진행기록.md에 있고, 노트북 개발 서버를 끈 상태에서 한 시험이라는 확인과 새 게스트로 시작했다는 확인은 받지 못했다.

한눈에

  • 무엇을 하나 — N057에서 Expo Go로 내 폰에 띄운 AI 친구 앱(friend-agent-mobile)을 EAS Build로 앱 파일(APK)로 만들어 폰에 설치하고, 노트북을 꺼도 앱이 도는지 확인한다. 이어서 스토어에 올리기 전에 무엇이 필요한지 점검표를 만들고, 후반부에는 내가 만들고 싶던 작은 앱을 새로 만들어 빌드·설치까지 간다.
  • 어떻게 배우나 — 앱 파일과 빌드가 무엇인지 → 폰에 들어가는 세 경로 → app.json·eas.json을 고쳐 preview 빌드 → 설치해 노트북 없이 확인 → 스토어 배포 단계와 AI 앱 출시 점검표 → 내 앱으로 스테이지 0~4.
  • 순서 — 빌드의 뜻 → 세 경로와 빌드 프로필 → 실습(설정·빌드·설치) → 스토어 배포와 출시 점검 → 내 앱 만들기 → 정리.
  • 오늘의 교훈 — Expo Go에서 화면이 보이는 것과 실제 설치 파일이 사용자 폰에서 제대로 도는 것은 다른 단계다. 그리고 앱 파일이 만들어졌다고 출시가 끝나는 것이 아니라, 테스트·보안·개인정보·결제 정책까지 준비해야 사용자에게 갈 수 있다.

⚠️ 주의 — 오늘의 범위: 실습의 기본 경로는 ① 개발 실행과 ② 빌드해서 설치(Android APK)까지다. ③ 스토어 배포는 유료 개발자 계정이 있는 사람의 선택 과제이고(학습서 p4 그림), iPhone 수강생은 Expo Go로 확인하고 설치는 짝의 Android 폰으로 한다(학습서 p4·p7).

1. Expo Go로 잘 도는 앱을 왜 다시 '빌드'해야 하나? (원문 Ch01)

1-1. 오늘의 상황

N057에서 만든 AI 친구 앱은 Expo Go 안에서 돈다. 그런데 학습서는 이렇게 묻는다 — 이 앱은 노트북이 켜져 있고 개발 서버가 돌 때만 내 폰에서 움직인다. 친구에게 보내려면 어떻게 해야 할까? 앱 파일은 누가 어디서 만들고, 폰에는 어떻게 들어가며, 스토어에 올리려면 무엇이 필요한가?

오늘은 이 질문에 답하는 순서로 간다. EAS Build로 앱 파일을 만들어 내 폰에 설치하고, 스토어에 올리기 전에 무엇을 점검해야 하는지 보고, 후반부에는 내 앱을 직접 만들어 빌드까지 간다(학습서 p1).

해설서는 이 강의의 목적을 네 가지로 정리한다: 노트북이 꺼져도 실행되는 앱, 친구에게 설치 파일로 전달, 수정하면 새 버전 배포, 최종적으로 Google Play·App Store 출시. 핵심 기술은 클라우드에서 앱을 빌드하는 Expo EAS Build다(EAS = Expo Application Services).

1-2. Expo Go와 실제 빌드 앱은 무엇이 다른가?

해설서의 비유: "Expo Go는 앱을 시험 운전하는 것이고, 실제 빌드 앱은 자동차를 완성해서 출고하는 것입니다."

1-3. EAS Build는 어떤 흐름으로 일하나?

해설서가 그린 흐름은 이렇다: 내 컴퓨터에서 개발 → 코드를 Expo 클라우드에 전달 → 클라우드가 빌드 → 앱 파일 다운로드 → 폰에 설치하거나 스토어에 제출. "마치 내가 설계도를 보내면 전문 공장에서 완제품을 만들어 주는 것과 같습니다."

해설서는 여기에 빌드와 업데이트를 구분해 덧붙인다.

  • 네이티브 기능이나 앱 자체의 구성 변경 → 새로운 빌드가 필요할 수 있다.
  • JavaScript 코드나 화면 구성 변경 → EAS Update를 쓰면 조건에 따라 앱 전체를 다시 설치하지 않고 업데이트할 수 있다.
  • "즉, EAS Build는 앱을 만드는 공장이고 EAS Update는 이미 설치된 앱에 변경사항을 전달하는 방법이라고 이해하시면 됩니다."

⚠️ 주의 — EAS Update는 학습서에는 나오지 않는다. 오늘 실습에서 "문구를 고쳤는데 설치한 앱이 그대로다"를 보면, 학습서의 답은 "다시 빌드"다. EAS Update를 쓰려면 따로 설정해야 하고, 업데이트 대상 앱의 네이티브 부분과 호환되어야 한다(해설서 p11).

2. 앱 파일은 무엇이고, 빌드는 무엇을 하나? (원문 Ch02)

2-1. 웹은 매번 받아 오고, 앱은 파일을 설치해 둔다

웹은 주소를 열 때마다 서버에서 화면 코드를 받아 온다. 앱은 화면 코드·이미지·앱 이름·권한 설정을 앱 파일 하나에 담아 설치해 두고 실행한다. 소스 코드를 이 앱 파일로 바꾸는 과정을 빌드(build)라고 하고, 빌드를 하지 않으면 폰에 설치할 수 없다(학습서 p1).

해설서의 비유: "빌드는 쉽게 말해 사람이 작성한 설계도를 컴퓨터가 실행할 수 있는 완제품으로 만드는 과정입니다. 예를 들어 건축가가 작성한 설계도만으로 사람이 건물에 들어가 살 수는 없습니다. 실제 건물을 지어야 합니다."

2-2. 빌드가 꼭 필요한 이유 세 가지

학습서가 드는 이유는 세 가지다. ① 폰의 CPU는 사람이 쓴 코드를 바로 돌리지 못한다 — 컴파일이 필요하다. ② 운영체제는 정해진 형식의 앱 파일만 설치한다 — 패키징이 필요하다. ③ 개발자 키로 만든 서명(signing)이 없으면 설치를 거부한다. 폰과 스토어는 서명으로 "누가 만든 앱인지, 같은 개발자의 새 버전인지"를 확인한다.

과정의미쉬운 비유
컴파일(Compile)사람이 작성한 코드를 기계가 실행할 수 있는 형태로 변환외국어를 한국어로 번역
패키징(Packaging)코드, 이미지, 설정 등을 하나의 앱 파일로 묶음제품을 상자에 포장
서명(Signing)개발자가 만든 앱임을 인증제품에 제조사 인증 도장 찍기

📌 요약 — "스마트폰은 개발자가 작성한 소스 코드를 그대로 받아 실행하는 것이 아니라, 운영체제가 요구하는 형식과 인증 조건을 충족한 앱 파일을 설치합니다."(해설서)

2-3. 네이티브 앱은 어떻게 빌드하나? — iOS와 Android

네이티브로 만들면 Android는 Gradle과 Android SDK가 Kotlin 코드를 컴파일해 APK나 AAB로 묶고 내가 만든 서명 키로 서명한다. Windows·Mac·Linux 어디서나 된다. iOS는 Xcode가 Swift 코드를 컴파일해 IPA로 묶고 Apple이 발급한 인증서로 서명하는데, Xcode는 Mac에서만 돈다. 그래서 네이티브로는 같은 앱을 두 번 만들고 두 번 빌드한다(학습서 p2).

2-4. Expo는 빌드를 어떻게 대신하나?

Expo 앱은 두 부분으로 되어 있다 — 내 코드(TypeScript)와 네이티브 부분(화면 그리기, 카메라·알림 같은 기기 기능). 내 코드는 JavaScript로 실행되므로 컴파일하지 않고 Metro가 번들(bundle) 하나로 묶는다. Expo Go는 Expo 팀이 자주 쓰는 네이티브 기능을 미리 빌드해 스토어에 올려 둔 앱이라, 노트북은 번들만 보내면 된다(학습서 p2).

남에게 줄 앱 파일은 EAS Build가 만든다. app.json을 보고 android/·ios/ 폴더를 새로 만든 뒤, Linux 서버와 Mac 서버에서 컴파일하고 Expo 계정에 보관한 키로 서명한다. 그래서 노트북에는 Node.js만 있으면 되고, Windows 노트북으로도 iOS 앱 파일을 만들 수 있다.

⚠️ 주의 — "다만 Apple 개발자 계정과 인증서 등 iOS 배포에 필요한 준비까지 없어지는 것은 아닙니다."(해설서 p10) Mac 없이 iOS 파일은 만들 수 있지만, iPhone에 설치하거나 App Store에 올리려면 유료 Apple 개발자 계정이 필요하다(3-2절).

2-5. 클라우드 빌드에 .env가 안 들어가는 이유, 그리고 실패했을 때

EAS 클라우드 서버는 저장소에 있는 파일만 받는다. 커밋하지 않은 .env의 값은 빌드에 들어가지 않는다(자세한 것은 3-4절). 빌드가 실패하면 빌드 로그에서 멈춘 단계부터 본다 — 패키지 설치 단계에서 멈췄으면 package.json의 버전 충돌을, 네이티브 컴파일 단계에서 멈췄으면 네이티브 라이브러리나 app.json 설정을 의심한다(학습서 p2).

2-7. 웹과 앱은 업데이트가 어떻게 다른가?

3. 같은 코드가 폰에 들어가는 길은 몇 가지인가? (원문 Ch03)

3-1. 세 경로 — 개발 실행, 빌드해서 설치, 스토어 배포

학습서 p4 그림은 같은 코드가 폰에 들어가는 길을 셋으로 나눈다. "같은 코드라도 어디서 어떻게 실행하느냐에 따라 누가 받을 수 있는지와 코드를 고쳤을 때 반영되는 방식이 다릅니다."

읽는 법: 왼쪽에서 오른쪽으로 갈수록 받을 수 있는 사람이 넓어지고, 그 대신 코드를 고쳤을 때 반영이 느려진다. 위 두 칸(①②)이 오늘 실습, 맨 오른쪽(③)은 선택 과제다.

그림 2. 같은 코드가 폰에 들어가는 세 경로(학습서 p4 그림을 다시 그림). 오른쪽으로 갈수록 받는 사람은 넓어지고, 코드를 고쳤을 때 반영은 느려진다.
  • ① 개발 실행 — Expo Go는 네이티브 부분을 미리 컴파일해 스토어에 올린 앱이라, 개발 서버가 번들만 보내면 실행되고 저장하는 즉시 바뀐다. 대신 개발 서버가 꺼지면 앱도 멈추고, 같은 와이파이나 tunnel로 연결된 내 폰에서만 열린다.
  • ② 빌드해서 설치 — 남이 받으려면 빌드가 필요하다. EAS Build가 클라우드에서 APK를 만들고 설치 링크를 준다. 스토어를 거치지 않으므로 개발자 계정이 필요 없고, 링크를 받은 Android 폰이면 누구나 설치할 수 있다.
  • ③ 스토어 배포 — 스토어용 파일(AAB, iOS 파일)을 만들어 올리는 일을 제출(submit)이라고 한다. EAS Submit이나 스토어 웹 화면으로 올린다. 해설서: "Build는 앱 파일을 만드는 것이고, Submit은 만들어진 앱 파일을 스토어에 제출하는 것입니다."
구분자동차 비유실제 의미
Expo Go운전 연습용 시뮬레이터개발 중인 앱을 즉시 확인
Preview Build시험 운행용 완성 자동차실제 설치 가능한 앱 파일
Production Build정식 판매용 자동차앱스토어에 출시할 앱

3-2. iPhone은 왜 경로 ②가 어렵나?

iPhone은 스토어 밖 설치가 막혀 있어, 경로 ②로 설치하려면 유료 Apple 개발자 계정에 그 iPhone을 미리 등록해야 한다. 그래서 실습에서 iPhone 수강생은 ① Expo Go로 확인하고, ②는 Android 폰을 가진 사람과 짝을 지어 하며, ③은 개발자 계정이 있는 사람의 선택 과제로 한다(학습서 p4). Mac과 Xcode가 있으면 케이블로 연결해 설치하는 방법도 있다(4-7절).

3-3. 빌드 프로필 — eas.json의 preview와 production

빌드 방식은 eas.json의 프로필로 정한다. 모바일 템플릿에는 프로필이 두 개 있다(학습서 p5).

프로필만드는 파일쓰는 곳
previewAndroid APK, 내부 배포(internal distribution)설치 링크로 내 폰이나 팀원 폰에 바로 설치
productionAndroid AAB, iOS 스토어용 파일. 빌드할 때마다 버전 번호를 자동으로 올림스토어에 제출

해설서의 예: "Preview: 친구 5명에게 앱을 보내서 테스트합니다. / Production: 테스트 결과를 반영한 앱을 앱스토어에 출시합니다. 즉, Preview는 제품 검증 단계이고 Production은 정식 출시 단계입니다."

💡 팁 — [보충 비유] 경영 언어로 바꾸면 preview는 파일럿(시범 운영), production은 정식 런칭이다. 파일럿 결과를 보고 런칭을 결정하듯, preview로 소수에게 먼저 써 보게 한 뒤 production을 만든다.

3-4. 서명 키 — 왜 시크릿처럼 지키나?

스토어는 처음 올린 파일의 서명 키를 기억하고, 같은 키로 서명한 파일만 그 앱의 새 버전으로 받는다. 키를 잃어버리면 업데이트를 낼 수 없고, 키가 남에게 넘어가면 남이 내 앱인 척할 수 있다. 그래서 서명 키는 시크릿처럼 다룬다(학습서 p5).

EAS는 첫 빌드 때 키를 만들어 Expo 계정에 보관하고, 빌드할 때마다 꺼내 쓴다. 그래서 키 파일이 노트북이나 저장소에 생기지 않는다. 학습서 원문: "저장소의 .gitignore에도 키 파일 형식(*.jks, *.p12, *.p8)을 막아 두었습니다."

해설서는 이것을 "중요한 문서에 찍는 공식 도장", "디지털 신분증", "앱의 신분증"에 비유하고 지킬 것을 정리한다.

  • 서명 키는 비밀번호처럼 보호해야 합니다.
  • GitHub 저장소에 올리면 안 됩니다.
  • .gitignore에 키 파일을 제외하도록 설정합니다.
  • 키를 분실하거나 유출하지 않도록 관리해야 합니다.

💡 팁 — [보충 비유] 서명 키는 회사의 법인 인감과 같다. 인감을 잃으면 계약서(업데이트)를 낼 수 없고, 남의 손에 넘어가면 회사 이름으로 엉뚱한 계약이 나간다. 그래서 인감은 금고(Expo 계정)에 두고, 직원(노트북·저장소)이 사본을 들고 다니지 않게 한다.

3-5. 빌드에 들어갈 값 — .env가 아니라 eas.json에

개발할 때는 .env의 EXPO_PUBLIC_API_URL(백엔드 주소)을 개발 서버가 앱에 넣어 준다. 그런데 .env는 커밋하지 않는 파일이라 빌드할 때 Expo 클라우드로 올라가지 않는다. 그래서 빌드에 쓸 값은 eas.json의 프로필마다 env에 따로 적는다. 학습서 원문: "이 값을 빠뜨리면 빌드는 성공하지만, 설치한 앱을 열었을 때 "백엔드 주소가 비어 있습니다"가 뜹니다."

해설서가 개념적으로 보여 준 두 곳은 이렇다(전체 eas.json이 아니라 해당 부분만).

# .env (개발 서버용, 커밋하지 않음)
EXPO_PUBLIC_API_URL=https://my-api.example.com
{
  "build": {
    "preview": {
      "env": {
        "EXPO_PUBLIC_API_URL": "https://my-api.example.com"
      }
    }
  }
}

해설서: "개발 서버에서는 정상 실행됩니다. EAS Build도 성공할 수 있습니다. 하지만 설치한 앱에서는 백엔드 주소를 찾지 못해 오류가 발생합니다. 즉, 빌드 성공과 앱의 정상 작동은 서로 다른 문제입니다."

EXPO_PUBLIC_으로 시작하는 값은 앱 파일 안에 그대로 들어가 누구나 꺼내 볼 수 있다. 그래서 공개돼도 되는 값만 넣고, LLM API 키나 Supabase secret key 같은 시크릿은 넣지 않는다. 학습서 원문: "앱이 쓰는 Supabase 주소와 publishable key는 백엔드 /api/config에서 받아 오도록 템플릿을 만들어 두었습니다."

정보앱에 포함해도 되는가?
백엔드 API 주소가능
Supabase 프로젝트 URL가능
Supabase publishable key공개 사용을 전제로 보안 규칙을 적용하면 가능
LLM API Secret Key절대 넣으면 안 됨
Supabase Secret Key절대 넣으면 안 됨
서버 비밀번호절대 넣으면 안 됨

(해설서 p18) 해설서의 예: "OpenAI API 키를 모바일 앱에 직접 넣으면 앱을 분석하는 사람이 키를 추출해 사용할 수 있습니다." 안전한 구조는 ① 모바일 앱이 백엔드 서버에 요청하고 ② 백엔드 서버가 AI API를 호출하고 ③ AI가 응답을 생성하면 ④ 백엔드 서버가 결과를 앱에 전달하는 것이다. "API 키는 백엔드 서버에서만 관리하는 것이 원칙입니다."

⚠️ 주의 — 표의 "Supabase publishable key 가능"은 해설서의 일반론이다. 이 실습의 템플릿은 publishable key도 앱에 넣지 않고 백엔드 /api/config에서 받아 온다(학습서). 템플릿을 따를 때는 eas.json의 env에 백엔드 주소 하나만 있으면 된다.

3-6. 앱 이름과 패키지 이름

app.json의 name은 홈 화면에 보이는 앱 이름이다. android.package와 ios.bundleIdentifier는 스토어와 폰이 앱을 구분하는 이름으로, 보통 kr.회사이름.앱이름처럼 도메인을 뒤집어 짓는다. 같은 패키지 이름의 앱은 한 폰에 하나만 설치되므로, 템플릿의 com.example.harufriend를 그대로 두면 남의 앱과 부딪힌다. 학습서 원문: "스토어에 한 번 올린 패키지 이름은 바꿀 수 없고, 바꾸면 완전히 다른 앱이 됩니다."

3-7. Expo Go로 안 되는 것 — 개발용 빌드

Expo Go에는 자주 쓰는 네이티브 기능만 들어 있다. Expo Go에 없는 네이티브 라이브러리(앱 안 결제, 일부 로그인 SDK 등)를 쓰거나 Android에서 서버 푸시 알림을 받으려면 개발용 빌드(development build)가 필요하다. 개발용 빌드는 내 앱 전용으로 네이티브 부분까지 다시 컴파일한 실행 앱이다. 한 번 설치하면 Expo Go처럼 개발 서버에서 코드를 받아 바로 바뀌지만, 네이티브 라이브러리를 더하거나 app.json의 권한을 바꿀 때마다 다시 빌드해야 한다(학습서 p5~6).

화면, 문구, 동작(JavaScript)저장하면 반영저장하면 반영다시 빌드

(학습서 p6) 해설서는 같은 표에서 preview의 화면 변경을 "새 빌드 또는 호환되는 업데이트 필요", 개발용 빌드의 노트북 없이 실행을 "기본 개발 서버 연결은 필요"로 적었다. 뜻은 같다.

💡 팁 — [보충 비유] 개발용 빌드는 우리 회사 전용으로 맞춘 시험 차량이다. 공용 시뮬레이터(Expo Go)에는 없는 장비(결제·특수 로그인)를 달아 볼 수 있지만, 장비를 바꿀 때마다 차를 다시 조립해야 한다.

3-8. SDK 버전이 안 맞으면

오늘은 Expo Go와 preview 빌드만 쓴다. Expo Go는 보통 최신 Expo SDK 하나만 지원하므로, 프로젝트의 SDK(package.json의 expo)가 폰의 Expo Go와 맞지 않으면 앱이 열리지 않는다. 그때는 SDK를 올리거나 강사에게 버전을 확인한다(학습서 p6).

npx expo install expo@latest --fix

해설서가 정리한 실습 순서: Expo Go 실행 → app.json 이름·패키지 확인 → eas.json 프로필 확인 → preview에 백엔드 주소 → EAS Build → APK 링크 → 설치·실행 확인. 핵심은 "앱 파일이 만들어졌다는 사실보다 설치한 앱이 실제 백엔드와 정상적으로 통신하는지"다.

▶ 한 줄 요약: 같은 코드라도 Expo Go(내 폰) → preview APK(링크 받은 사람) → production(스토어)으로 갈수록 받는 사람이 넓어지고, 빌드용 값은 eas.json의 env에, 서명 키는 Expo 계정에, 패키지 이름은 처음부터 내 것으로 정한다.

Cloud Run 로그에 billing is disabled for this project가 있었고, 결제 계정이 닫혀 있었다(무료 체험 종료로 보임). 사용자가 콘솔에서 새 결제 계정을 만들고(카드 정보는 직접 입력), 프로젝트를 새 계정에 연결하자 billingEnabled가 true가 됐다. 그런데도 약 15분 동안 /health가 503·429였고(로그: "사용 가능한 인스턴스를 기다리다 중단됨"), 서비스에 라벨 하나만 더해 새 리비전을 배포하자 바로 200이 됐다. 결제를 켜고도 서비스가 안 깨어나면 새 리비전 배포를 해 본다. 같은 옛 결제 계정을 쓰던 다른 두 프로젝트는 새 계정으로 옮기지 않고 그대로 남겼다.

4-3. 앱 이름·패키지 이름·빌드 설정값 정하기

앱 이름은 폰에서 알아볼 수 있게(예: 하루친구 지수), 패키지 이름은 다른 수강생과 겹치지 않게 별칭을 넣는다(예: kr.study.harufriend.jisu — 영문 소문자·숫자·점만). 빌드용 백엔드 주소는 .env와 같은 주소다(학습서 p8).

학습서가 편집기에서 직접 고치는 순서:

  1. app.json의 name을 내 앱 이름으로 바꿉니다.
  2. app.json의 android.package와 ios.bundleIdentifier를 내 패키지 이름으로 바꿉니다. 두 값은 같게 둡니다.
  3. eas.json의 preview와 production 프로필 env에 있는 EXPO_PUBLIC_API_URL을 내 백엔드 주소로 바꿉니다. 끝에 /를 붙이지 않습니다.
  4. npx expo start로 Expo Go에서 다시 열어 앱이 그대로 도는지 확인합니다. app.json을 바꾼 뒤에는 개발 서버를 껐다 켭니다.
{
  "expo": {
    "name": "하루친구 지수",
    "android": {
      "package": "kr.study.harufriend.jisu"
    },
    "ios": {
      "bundleIdentifier": "kr.study.harufriend.jisu"
    }
  }
}

(해설서 p24~25) 에이전트에게 맡길 수도 있다(부록 C-1의 요청 2). 학습서 원문: "실행 전에 바뀌는 줄이 이 다섯 값뿐인지 봅니다. 패키지 이름은 스토어에 올리면 바꿀 수 없으므로, 에이전트가 임의로 짓지 않고 내가 정한 값이 들어갔는지 확인합니다."

💡 팁 — "다섯 값"은 name, android.package, ios.bundleIdentifier, preview의 EXPO_PUBLIC_API_URL, production의 EXPO_PUBLIC_API_URL이다. 해설서는 preview에는 테스트용(staging) 백엔드, production에는 운영 백엔드 주소가 들어가야 한다고 덧붙인다(4-8절).

🧪 예제 — 실습 결과: 앱 이름은 사용자가 "대진이의 하루친구"로, 패키지 이름은 Claude가 kr.study.harufriend.djeon(GitHub 아이디에서 딴 별칭)으로 추천했다. git diff --stat로 바뀐 줄이 다섯 값뿐(app.json 6줄·eas.json 4줄)임을 확인했고, 빌드 전에 npx tsc --noEmit(오류 없음)과 npx expo-doctor(20/20)를 돌렸다. preview에는 staging 주소, production에는 운영 주소를 넣었다. 운영 주소가 실제로 응답하는지는 호출하지 않았다.

4-4. Expo 계정에 연결하고 빌드하기

eas는 설치하지 않고 npx eas-cli@latest로 그때그때 최신판을 쓴다. login으로 로그인하고, build:configure로 저장소를 내 Expo 계정의 프로젝트에 연결한다 — 이때 app.json에 프로젝트 ID가 들어가고, 이미 있는 eas.json을 그대로 쓴다. 플랫폼을 물으면 Android 또는 모두를 고른다(학습서 p8).

npx eas-cli@latest login
npx eas-cli@latest build:configure
# 클라우드에서 Android APK를 만든다. 처음이면 서명 키를 만들지 묻는다 → Yes
npx eas-cli@latest build --profile preview --platform android

(학습서 p9) 지킬 것 세 가지:

  • 로그인은 내가 직접 — 브라우저나 터미널에서 직접 하고, 비밀번호를 에이전트 대화에 붙여 넣지 않는다.
  • 빌드 승인 전에 확인 — 프로필이 preview, 플랫폼이 android인지 본다.
  • 검사를 먼저 — 학습서 원문: "무료 플랜은 월 빌드 횟수가 정해져 있어서(2026년 10월 기준 월 30회, 낮은 우선순위 대기열), 타입 검사나 설정 검사에서 걸러질 실수로 빌드 한 번을 쓰지 않게 검사를 먼저 돌립니다." npx tsc --noEmit은 타입 오류를, npx expo-doctor는 설정·의존성을 검사한다(해설서 p28, "실제 한도와 대기열은 변경될 수 있습니다").

💡 팁 — [보충 비유] 월 30회는 월 인쇄 예산과 같다. 교정(타입·설정 검사)을 안 보고 인쇄소에 넘기면 오탈자 하나 때문에 인쇄 한 번을 날린다. 그래서 인쇄 전에 교정부터 본다.

🧪 예제 — 실습 결과: ① 가입 화면에서 사용자 이름(영문·숫자·하이픈, 앞뒤 하이픈 불가)을 정했고 "조직 만들기" 화면은 건너뛰어 개인 계정으로 썼다(DJ-Jeon). ② login은 이메일·비밀번호를 터미널에 묻지 않고 브라우저 로그인이었다. 대기 중에는 터미널이 입력을 받지 않아 "입력할 수가 없다"는 말이 나왔는데, 터미널이 아니라 브라우저에서 허용 화면(Redirects to localhost)을 승인해야 했다. ③ build:configure는 프로젝트를 만들어 연결했고(@dj-jeon/friend-agent-mobile, 플랫폼 Android), 노트가 말한 프로젝트 ID 말고도 android.permissions에 CAMERA와 RECORD_AUDIO를 넣었다. 이 앱은 마이크를 일부러 막아 두었기 때문에 그 배열을 지웠다. 설정을 만드는 명령도 끝난 뒤 git diff로 무엇이 바뀌었는지 본다.

4-5. 빌드는 어떻게 진행되고, 끝나면 무엇이 보이나?

명령은 프로젝트를 Expo 서버로 올리고, 대기열에 넣고, 빌드 페이지 주소를 보여 준다. 학습서 원문: "무료 플랜은 대기열이 길어서 시작하기까지 몇 분에서 수십 분이 걸릴 수 있고, 시작한 뒤에도 10분 안팎이 걸립니다." 터미널을 닫아도 서버에서 계속된다. 끝나면 터미널과 빌드 페이지에 설치 링크와 QR 코드가 나온다. 서명 키를 만들었다면 빌드 페이지의 Credentials에 Android 서명 키가 Expo 계정 보관으로 나온다 — 이때 노트북에 키 파일이 생기지 않았는지도 확인한다(학습서 p9).

4-6. 폰에 설치하고 노트북 없이 확인하기

학습서가 정한 순서(p10):

  1. 폰으로 설치 링크를 열거나 QR 코드를 찍어 APK를 내려받습니다.
  2. "출처를 알 수 없는 앱" 설치를 허용할지 물으면 이번만 허용합니다. Play 프로텍트가 "인식하지 못하는 앱"이라고 경고하면 내용을 읽고 그래도 설치를 고릅니다. 스토어를 거치지 않은 앱이라 나오는 경고입니다.
  3. 홈 화면에 내가 정한 앱 이름으로 앱이 생겼는지 보고, 노트북의 개발 서버를 끈 상태에서 앱을 엽니다.
  4. 캐릭터를 만들고 메시지를 보내 답이 오는지 봅니다.

결과 해석 — 노트북 없이 도는 앱. 개발 서버를 꺼도 앱이 열리고 대화가 된다. 코드가 앱 파일에 번들로 들어 있고, 앱이 직접 백엔드로 요청하기 때문이다. 해설서: "노트북을 꺼도 앱이 작동하는 이유는 화면 코드가 휴대폰에 들어갔기 때문이지, AI 백엔드까지 휴대폰에 들어갔기 때문은 아닙니다."

처음 열면 캐릭터 화면부터 나온다. Expo Go에서 만든 캐릭터와 대화가 보이지 않는다. 설치한 앱은 Expo Go와 저장 공간이 따로라서 새 게스트 사용자로 로그인했기 때문이다. 학습서 원문: "데이터가 사라진 것이 아니라 다른 사용자가 된 것입니다." 해설서의 비유: "같은 휴대폰에 카카오톡과 다른 메신저 앱이 있다고 생각해 보시면 됩니다. 서로 다른 앱의 내부 저장 공간은 자동으로 공유되지 않습니다."

문구를 고치면? Expo Go는 즉시 바뀌지만 설치한 앱은 그대로다. 다시 빌드해야 하고, 그때마다 빌드 횟수를 1회 쓴다.

🧪 예제 — 실습 결과: 폰 카메라로 QR을 찍어 설치했다. 빌드가 끝나자 터미널이 Install and run the Android build on an emulator? (Y/n)에서 멈췄는데, 실제 폰에 설치했으므로 n(또는 Ctrl+C)으로 끝내면 되고 빌드에는 영향이 없다. 설치 앱에서 "안녕 폰에 앱을 설치하고 처음으로 써봐"를 보내자 "안녕! 앱 처음 써보는 거구나. 어떤 기능이 궁금해?"가 왔고(사용자 보고), 카메라 찍기는 권한을 요구한 뒤 사진 속 글씨를 인식했다. 권한 목록은 허용됨: 카메라 / 앱이 계속 작동하도록 허용됨: 근처 기기 / 허용되지 않음: 마이크였다. 마이크가 선언된 원인은 expo-image-picker 플러그인이 microphonePermission을 false로 두지 않으면 RECORD_AUDIO를 기본으로 넣기 때문이었다(플러그인 코드로 확인). 고치려면 설정 한 줄과 재빌드가 필요해 이번에는 기록만 했다. 확인하지 못한 것: 개발 서버를 끈 상태였는지, 처음 열 때 새 게스트(캐릭터 화면부터)였는지, 홈 화면 앱 이름.

4-7. iPhone에서 빌드한 앱 실행하기 (선택, Mac과 Xcode가 있을 때)

iPhone은 스토어 밖 앱 파일 설치가 안 되므로, Mac에 Xcode를 설치하고 iPhone을 케이블로 연결해 내 Mac에서 빌드해 설치한다. npx expo run:ios --device가 Xcode 빌드와 설치를 함께 한다. 학습서 원문: "무료 Apple 계정으로도 설치할 수 있지만 그렇게 설치한 앱은 7일 뒤에 열리지 않아 다시 설치해야 하고, iPhone 설정에서 개발자 모드를 켜야 합니다."

# iPhone을 케이블로 연결하고, 처음이면 iPhone에서 '이 컴퓨터를 신뢰' 를 누른다
npx expo run:ios --device
# 개발 서버 없이도 열리는 앱으로 설치할 때 (번들을 앱 안에 넣는다)
npx expo run:ios --device --configuration Release

(학습서 p11) run:ios의 기본은 개발용 구성(Debug)이라 설치한 앱이 노트북의 개발 서버에서 코드를 받는다. 노트북 없이 확인하려면 --configuration Release로 번들을 앱 안에 넣는다. 이 명령이 만드는 ios/ 폴더는 app.json으로 언제든 다시 만들 수 있으므로 커밋하지도 직접 고치지도 않는다.

4-8. 스토어에 올리는 빌드 (개발자 계정이 있을 때)

Google Play는 새 앱을 APK가 아니라 AAB(Android App Bundle)로만 받는다. AAB는 스토어가 기기별 APK로 나눠 내려보내는 형식이라 폰에 바로 설치할 수 없다. 그래서 스토어용은 production 프로필로 만든다 — Android AAB, iOS App Store 제출 파일, 빌드마다 빌드 번호 자동 증가(학습서 p11~12).

# Google Play에 올릴 AAB
npx eas-cli@latest build --profile production --platform android
# App Store에 올릴 iOS 빌드 (유료 Apple 개발자 계정 필요)
npx eas-cli@latest build --profile production --platform ios

⚠️ 주의 — production 빌드에는 eas.json production 프로필 env의 백엔드 주소가 들어간다. 스토어용이면 staging이 아니라 운영(production) 백엔드 주소여야 한다. 실행 전에 프로필 이름과 주소를 함께 확인한다(학습서 p12).

4-9. 코딩 에이전트로 빌드 상태 보기

4-10. 이 장의 세 원칙 (해설서)

해설서 p30은 실습에서 얻을 원칙 세 가지를 정리한다. ① 개발 환경과 실제 서비스 환경은 다르다 — 실기기에서 테스트한다. ② 앱과 백엔드를 나눈다 — AI 모델 호출과 비밀 API 키는 백엔드에 둔다. ③ 테스트용(staging)과 운영용(production) 서버를 구분한다.

▶ 한 줄 요약: 검사(tsc·expo-doctor) → app.json·eas.json의 다섯 값 → login·build:configure·build --profile preview → 설치 → 개발 서버를 끄고 대화까지가 오늘의 클리어이며, 처음 열면 새 게스트로 시작하는 것은 고장이 아니다.

5-3. Apple은 어떤 단계를 거치나?

TestFlight에서 팀원은 내부 테스터로 바로 받고(최대 100명, 학습서 p13 그림), 외부 테스터는 베타 심사를 거쳐 초대 링크로 받는다. 유료 Apple 개발자 계정이 있어야 시작할 수 있다. 해설서의 예: 가족·지인에게 TestFlight로 배포해 대화가 자연스러운지, 오류가 없는지 확인한다.

⚠️ 주의 — 두 스토어 공통: 패키지 이름과 번들 ID는 한 번 올리면 바꿀 수 없고, 빌드를 올린 앱은 콘솔에서 지워지지 않고 남는 경우가 많다. 그래서 연습이라도 이름을 제대로 정해 올리고, 끝나면 테스트 트랙을 일시중지하고 테스터를 지워 정리한다(학습서 p14).

스토어는 앱이 돌아가는지만 보지 않는다. 사용자 데이터를 어떻게 다루는지와 앱 안에서 무엇을 파는지를 심사하고, AI 앱은 AI가 만든 콘텐츠를 어떻게 다루는지가 더해진다(학습서 p14).

▶ 한 줄 요약: 스토어 출시는 계정 → production 빌드 → 테스트 트랙(사람이 넘김) → 심사 → 공개이고, AI 앱은 개인정보·데이터 안전·삭제·AI 신고·AI 표시·앱 안 판매·연령 등급 7항목을 docs/store-readiness.md에 "있음/없음"으로 채워 빈칸부터 메운다.

스테이지 2의 핵심은 권한을 거부해도 앱이 멈추지 않는 것이다. 해설서의 흐름: 새 산책 기록 화면 → 사진 촬영 또는 선택 버튼 → 카메라 권한 요청 → 허용하면 사진 촬영 진행 / 거부하면 사진 없이 기록 진행. "사용자가 권한을 거부해도 앱 전체가 멈추면 안 됩니다. … 이것을 예외 상황을 고려한 앱 설계라고 합니다."

6-5. 스테이지 3 — 빌드와 설치

npx eas-cli@latest build --profile preview --platform android

해설서가 꼽은 성공 조건: Expo Go 화면이 설치한 앱에도 보이고, 고른 기기 기능이 동작하고, 개발 서버를 끈 뒤에도 실행되고, 데이터를 저장하고 다시 볼 수 있다. "가장 중요한 성공 기준: 노트북을 닫고 개발 서버를 꺼도 휴대폰에 설치한 앱이 독립적으로 실행되어야 합니다."

학습서의 힌트(빌드, 원문): "새 프로젝트에는 eas.json이 없으므로 npx eas-cli@latest build:configure가 만들어 줍니다. 만들어진 preview 프로필이 Android를 APK로 만드는지("android": { "buildType": "apk" })와, 앱이 쓰는 EXPO_PUBLIC_ 값이 프로필의 env에 있는지 확인합니다. 빌드가 실패하면 빌드 로그에서 처음 실패한 단계를 보고, 코딩 에이전트에게 "npx eas-cli@latest 로 가장 최근 빌드가 왜 실패했는지 로그로 설명해 줘"라고 물어볼 수도 있습니다. 같은 오류로 두 번 빌드하지 않게, 고친 뒤 npx expo-doctor를 먼저 돌립니다."

⚠️ 주의 — 템플릿과 달리 새 프로젝트에는 eas.json이 없다. build:configure가 만든 preview 프로필에 "buildType": "apk"가 없으면 AAB가 나와 폰에 바로 설치할 수 없다(4-8절). 빌드 전에 이 한 줄부터 본다.

6-6. 스테이지 4 — 점검표와 권한 문구

5장의 점검표 7항목을 내 앱으로 다시 채운다. 해설서: "각 항목에 반드시 있음 또는 없음을 적습니다. 그리고 비어 있는 항목 중 하나를 실제로 개발하거나 보완합니다."

여기서 학습서의 이해 점검 질문이 나온다 — Expo Go에서 본 카메라 권한 창과 빌드한 앱의 권한 창은 앱 이름과 설명 문구가 다르다. 왜일까? 해설서의 답: "Expo Go는 Expo Go라는 개발용 앱의 설정을 사용하지만, 독립 설치 앱은 내가 만든 앱의 설정을 사용하기 때문입니다. 카메라나 위치 등의 권한 설명 문구는 앱의 설정 파일인 app.json 또는 app.config.js에서 설정합니다."

{
  "expo": {
    "plugins": [
      [
        "expo-image-picker",
        {
          "cameraPermission": "산책 기록에 사용할 사진을 촬영하기 위해 카메라 접근 권한이 필요합니다.",
          "photosPermission": "산책 기록에 사진을 첨부하기 위해 사진 접근 권한이 필요합니다."
        }
      ]
    ]
  }
}

(해설서 p48~49 예시) 지킬 것: 권한을 왜 허용해야 하는지 구체적으로 설명하고, 실제 기능과 관련된 권한만 요청하며, 권한 설명을 바꾸면 네이티브 설정이 바뀌므로 새 빌드가 필요하다.

💡 팁 — [보충] 권한 문구는 스토어 심사에서도 본다. "앱 기능 향상을 위해" 같은 막연한 문구보다 "산책 기록에 사진을 첨부하기 위해"처럼 어떤 화면의 어떤 기능인지 적는 편이 사용자에게도 심사에도 낫다.

6-7. 서로 보여 주기

학습서 원문: "옆 사람과 짝을 지어 5분씩 내 앱을 보여 줍니다. 노트북을 닫은 상태에서 설치한 앱을 열고(iPhone이라면 Expo Go나 짝의 Android 폰으로), 화면을 하나씩 넘기며 앱 계획 표와 맞는지 봅니다. 듣는 사람은 "이 화면의 데이터는 어디서 오는가"와 "코드를 고치면 설치한 앱에 반영하려면 무엇을 해야 하는가"를 물어봅니다. 보여 주기 전에 앱 코드와 eas.json에 시크릿이 없는지, .env와 서명 키 파일이 저장소에 없는지 한 번 더 봅니다."

회고 질문은 "오늘 가장 오래 막힌 곳을 하나 골라, 무엇을 보고 막힌 줄 알았는지, 원인을 어디서 찾았는지, 어떻게 풀었는지"다(부록 G 문제 9). 해설서: "이 문제는 정답을 맞히는 퀴즈가 아니라 문제 해결 과정을 돌아보는 질문입니다."

해설서의 교훈: "AI가 코드를 대신 작성해 줄 수는 있지만, 무엇을 만들고 어떻게 작동해야 하는지를 결정하는 것은 나의 역할입니다."

▶ 한 줄 요약: 내 앱은 계획 표(화면·데이터 위치·기기 기능) → Expo Go로 화면과 기능 → 빌드는 한 번 → 점검표로 가고, 권한을 거부해도 멈추지 않게, 권한 문구는 app.json에 내 앱 기준으로 적는다.

7. 오늘 배운 것을 한 장으로 정리하면? (원문 Ch07)

7-1. 학습서의 네 묶음

  • 개발 실행, 빌드, 제출 — Expo Go는 개발 서버에서 코드를 받아 바로 바뀌지만 내 폰에서만 열린다. EAS Build는 클라우드에서 앱 파일을 만들어 링크로 나눠 주고, 스토어는 개발자 계정으로 올려 테스트와 심사를 거친다. 학습서 원문: "빌드한 앱에는 코드가 고정되므로 고치면 다시 빌드해야 하고, 빌드에 들어갈 값은 .env가 아니라 eas.json에 적습니다."
  • 한 번 정하면 바꾸기 어려운 것 — 패키지 이름과 서명 키. 스토어가 앱을 알아보는 기준이다. 서명 키는 EAS가 보관해 내 컴퓨터와 저장소에 남기지 않는다.
  • 출시 준비 — 스토어는 개인정보처리방침, 데이터 안전 항목, 계정과 데이터 삭제, AI 생성 콘텐츠 신고, 앱 안 판매를 심사한다. 테스트 단계의 앱은 사람이 넘기고 심사를 통과하기 전에는 공개되지 않는다.
  • 내 앱 만들기 — 화면 목록과 데이터가 오는 곳을 먼저 정하고 구현은 에이전트에게 맡기며, 기기 기능 하나를 붙여 빌드·설치까지 간다.

  • 나누는 기준 — 화면은 앱에, AI 로직·프롬프트·비밀 키는 백엔드에.
  • 프로젝트 매핑 — AI 친구(대화 화면 ↔ AI 응답·기억), MSM(일기·사진·음성 입력 ↔ 글 분석·말투 보존·자서전/웹소설 생성), ASP 컨설팅(고객·프로젝트 관리 ↔ 분석·보고서), Travel Creator(일정·사진 기록 ↔ 일정 추천).

F-1. 이 강의로 할 수 있게 된 것

  • Expo Go로 보던 앱을 EAS Build로 APK를 만들어 내 폰과 다른 사람 폰에 설치한다.
  • 빌드가 컴파일·패키징·서명이라는 것과, 무엇을 고치면 다시 빌드해야 하는지 가른다.

  • 스토어 배포 단계(트랙·TestFlight·심사)와 AI 앱 출시 점검표 7항목을 내 앱에 맞춰 채운다.
  • 내가 만들고 싶던 작은 앱을 계획 표 → 화면 → 기기 기능 → 빌드 → 점검표 순서로 끝까지 만든다.

문제 1. [시작 질문] (주관식) 지금 Expo Go로 실행하는 앱과 스토어에서 받은 앱은 무엇이 다를까요? 노트북을 껐을 때, 코드를 고쳤을 때, 친구에게 보내고 싶을 때로 나눠 적어 보세요.

모범 답안(해설서 p6): ① 노트북을 껐을 때 — Expo Go는 개발 서버가 종료되면 개발 중인 앱을 실행할 수 없지만, 빌드된 앱은 독립적으로 실행할 수 있다. ② 코드를 고쳤을 때 — Expo Go는 개발 서버를 통해 변경사항을 바로 확인할 수 있지만, 설치된 앱은 새로운 빌드나 EAS Update 등 적절한 배포 절차가 필요하다. ③ 친구에게 보내고 싶을 때 — Expo Go는 개발 환경 연결이 필요하지만, 빌드된 앱은 APK 등의 설치 파일이나 앱스토어를 통해 전달할 수 있다. 한 문장으로: "Expo Go는 개발자가 앱을 시험해 보는 도구이고, EAS Build로 만든 앱은 노트북과 독립적으로 작동하며 실제 사용자에게 배포할 수 있는 제품입니다."

문제 2. (객관식) 스토어에 올린 AI 친구 앱에서 (가) 서버에 있는 에이전트의 프롬프트를 바꿔 말투를 부드럽게 하고, (나) 앱 화면의 전송 버튼 문구를 바꾸려 합니다. 앱을 다시 빌드해야 하는 것은?

① (가)와 (나) 모두 ② (가)만 ③ (나)만 ④ 둘 다 다시 빌드하지 않아도 된다

정답: ③ (가) 서버의 프롬프트는 백엔드에서 관리하므로 서버에 반영하면 되고 앱을 다시 빌드할 필요가 없다. (나) 앱 화면 문구는 앱의 JavaScript 코드에 포함되어 있으므로 새로운 앱 빌드 또는 호환되는 EAS Update가 필요하다. 해설서는 "엄밀하게 말하면 (나)는 반드시 재빌드해야 하는 것은 아니지만, 업데이트 배포는 필요합니다"라고 덧붙인다(학습서 p3, 해설서 p13~14).

문제 3. (객관식) preview 빌드로 APK를 만들어 폰에 설치했는데, 앱을 열자 "백엔드 주소가 비어 있습니다"가 떴습니다. Expo Go로 실행할 때는 잘 됐습니다. 가장 먼저 확인할 곳은?

① 폰의 와이파이 설정 ② eas.json의 preview 프로필 env에 EXPO_PUBLIC_API_URL이 내 백엔드 주소로 들어 있는지 ③ .gitignore에서 .env를 지웠는지 ④ Expo Go의 SDK 버전

정답: ② Expo Go는 로컬의 .env 값을 읽지만 EAS 클라우드 빌드는 로컬 .env를 가져가지 않는다. ①은 주소 자체가 전달되지 않은 상황이라 와이파이 문제가 아니고, ③ .env를 커밋에서 빼는 것은 정상적인 보안 관리이며, ④ SDK 문제라면 실행·호환성 오류가 난다(학습서 p6, 해설서 p22).

문제 4. (객관식) 버튼 문구 하나를 고친 뒤 Expo Go에서는 바로 바뀌었는데, 폰에 설치한 앱은 그대로입니다. 가장 알맞은 설명은?

① 설치한 앱이 백엔드에서 화면을 받아 오는데 백엔드를 다시 배포하지 않았다 ② 설치한 앱에는 빌드할 때의 코드가 번들로 들어 있어서, 바꾼 코드를 반영하려면 다시 빌드해야 한다 ③ Expo Go의 캐시가 설치한 앱에 남아 있다 ④ 앱 이름이 Expo Go와 달라서 개발 서버에 연결되지 않았다

정답: ② "설치된 앱은 기존 코드가 들어 있는 별도의 실행 파일입니다. 따라서 변경된 화면 코드를 반영하려면 새로 빌드하거나, 네이티브 호환 범위 내에서 EAS Update를 사용해야 합니다."(해설서 p31~32) 앱은 화면 코드를 백엔드에서 받지 않고(①), Expo Go 캐시가 설치 앱에 남지 않으며(③), 앱 이름과 개발 서버 연결은 무관하다(④).

문제 5. (객관식) 에이전트 서비스 앱에서 AI 크레딧을 팔고 싶습니다. 스토어 결제 정책을 지키는 구조로 가장 알맞은 것은?

① 앱 안에 웹 결제 페이지를 띄워 크레딧을 판다 ② 크레딧 구매는 웹 서비스에서 하고, 앱에서는 같은 계정의 크레딧을 사용만 하게 한다 ③ 앱 안에서 팔되 스토어 심사 때만 결제 버튼을 숨긴다 ④ 크레딧이라고 부르지 않고 후원이라고 부른다

정답: ② ①은 외부 결제 유도 정책에 저촉될 수 있고, ③ 심사 때만 숨기는 것은 정책 준수가 아니며, ④ 이름을 바꾼다고 결제 정책이 달라지지 않는다. "단, 2번도 플랫폼별 외부 결제 관련 정책을 확인한 뒤 구체적인 구현 방식을 결정해야 합니다."(학습서 p15~16, 해설서 p41)

문제 6. [추가] (객관식) 연습 삼아 패키지 이름을 com.example.harufriend 그대로 두고 Google Play 내부 테스트에 올렸습니다. 나중에 정식 이름으로 바꾸려면?

① app.json의 android.package만 바꿔 다시 올리면 같은 앱의 새 버전이 된다 ② 스토어에 한 번 올린 패키지 이름은 바꿀 수 없으므로, 새 이름으로 올리면 완전히 다른 앱이 된다 ③ 서명 키를 바꾸면 패키지 이름도 바꿀 수 있다 ④ 빌드 번호를 올리면 된다

정답: ② "스토어에 한 번 올린 패키지 이름은 바꿀 수 없고, 바꾸면 완전히 다른 앱이 됩니다."(학습서 p5) 그리고 빌드를 올린 앱은 콘솔에서 지워지지 않고 남는 경우가 많다(학습서 p14). 그래서 연습이라도 이름을 제대로 정해 올린다.

문제 7. [추가] (객관식) production 프로필로 만든 Android 파일을 친구 폰에 보내 설치하려 했더니 설치가 되지 않습니다. 이유는?

① production 빌드는 서명이 없어서 ② production 프로필은 AAB를 만드는데, AAB는 스토어가 기기별 APK로 나누는 형식이라 폰에 바로 설치할 수 없어서 ③ 친구 폰의 Expo Go SDK가 달라서 ④ 빌드 번호가 자동으로 올라가서

정답: ② 직접 설치는 preview(APK), 스토어 제출은 production(AAB)이다(학습서 p5·p11). production도 서명은 되어 있고(①), 설치 앱은 Expo Go와 무관하며(③), 빌드 번호는 스토어용 구분 번호다(④).

문제 8. [이해 점검] (주관식) Expo Go에서 카메라 권한 창을 확인했는데, 빌드해서 설치한 내 앱에서는 권한 창의 앱 이름과 설명 문구가 다르게 떴습니다. 왜 다르게 보이는지, 출시 전에 이 문구를 어디서 정하고 무엇을 적어야 하는지 설명해 보세요.

모범 답안(해설서 p48~49, 300자 예시): "Expo Go는 Expo Go 자체의 권한 설정을 사용하지만, 독립 설치 앱은 내가 만든 앱의 설정을 사용하기 때문에 문구가 다릅니다. 권한 설명은 app.json의 플러그인 설정에서 정합니다. 카메라나 사진 접근이 왜 필요한지 실제 기능과 연결해 구체적으로 설명하고, 문구를 변경하면 새 빌드로 반영해야 합니다." 설정 모양은 부록 A-12.

문제 9. [직접 해 보기 회고] (주관식) 오늘 가장 오래 막힌 곳을 하나 골라, 무엇을 보고 막힌 줄 알았는지, 원인을 어디서 찾았는지, 어떻게 풀었는지 순서대로 적어 보세요.

가이드(해설서 p49~50): 정답을 맞히는 문제가 아니라 문제 해결 과정을 돌아보는 질문이다. 순서는 ① 무엇에서 막혔는가 ② 처음에는 왜 문제가 생겼다고 생각했는가 ③ 어떤 로그나 문서를 확인했는가 ④ 실제 원인은 무엇이었는가 ⑤ 어떻게 해결했는가. 작성 예시: "Expo Go에서는 정상 작동했지만 설치 앱에서 카메라 권한 문구가 다르게 표시되었습니다. 처음에는 앱 코드의 문제라고 생각했지만 Expo 설정 문서를 확인해 권한 설명이 앱별 네이티브 설정에서 관리된다는 사실을 알았습니다. app.json의 권한 문구를 수정하고 새로 빌드해 해결했습니다." 실제 실습에서 겪은 문제로 쓴다.

문제 10. [회고] (주관식) 1장에서 적은 시작 질문의 답을 다시 읽고, 오늘 직접 본 것(노트북 없이 열린 앱, 고친 코드가 반영되지 않은 설치 앱, 새 게스트로 시작한 앱, 스토어 배포 단계)과 비교해 맞았던 것과 새로 알게 된 것을 적어 보세요.

모범 답안(해설서 p56, 300자 예시): "처음에는 Expo Go와 설치 앱의 차이가 개발 서버 연결 여부와 코드 반영 속도라고 이해했습니다. 직접 실습해 보니 설치한 앱은 노트북의 개발 서버를 꺼도 실행되고, 코드를 수정해도 기존 앱에는 반영되지 않는다는 것을 확인했습니다. 또한 Expo Go와 설치 앱은 저장 공간이 달라 새 게스트로 시작했습니다. 스토어 배포도 파일 업로드로 끝나는 것이 아니라 테스트와 심사를 거쳐야 한다는 점을 새롭게 배웠습니다." 비교표는 7-3절.

문제 11. [추가] (객관식) 서명 키를 노트북에 내려받아 두었다가 노트북을 잃어버렸고, Expo 계정에도 키가 없습니다. 이미 스토어에 올린 앱에 무슨 일이 생기나?

① 아무 일도 없다 — 새 키로 서명하면 된다 ② 스토어는 처음 올린 파일의 서명 키를 기억하므로, 같은 키로 서명한 업데이트를 낼 수 없게 된다 ③ 패키지 이름만 바꾸면 된다 ④ 빌드 번호를 크게 올리면 된다

정답: ② 스토어는 같은 키로 서명한 파일만 새 버전으로 받는다. 키를 잃으면 업데이트를 낼 수 없고, 남에게 넘어가면 남이 내 앱인 척할 수 있다(학습서 p5). 그래서 EAS가 키를 Expo 계정에 보관하고 노트북·저장소에 남기지 않게 한다. ③ 패키지 이름을 바꾸면 다른 앱이 된다.

문제 12. [추가] (객관식) 설치한 앱을 처음 열었더니 Expo Go에서 만든 캐릭터와 대화가 없고 캐릭터 만들기 화면부터 나왔습니다. 가장 알맞은 설명은?

① 빌드할 때 데이터베이스가 지워졌다 ② eas.json에 백엔드 주소가 잘못 들어갔다 ③ 설치한 앱은 Expo Go와 저장 공간이 달라 새 게스트 사용자로 로그인했다 ④ 서명 키가 달라서 데이터를 못 읽는다

정답: ③ "데이터가 사라진 것이 아니라 다른 사용자가 된 것입니다."(학습서 p10) 서로 다른 앱의 내부 저장 공간은 자동으로 공유되지 않는다(해설서). 같은 데이터를 보려면 공통 로그인이 필요하다(부록 F-2). 주소가 잘못됐다면 대화 자체가 안 된다(②).

문제 13. [추가] (주관식) 2023년 11월 이후 만든 개인 Google Play 개발자 계정으로 이번 주 안에 정식 출시하겠다는 계획이 왜 어려운가? 출시 일정을 잡을 때 무엇부터 정해야 하나?

모범 답안: 2023년 11월 이후 만든 개인 개발자 계정은 테스터 12명 이상이 14일 동안 비공개 테스트를 해야 프로덕션 출시를 신청할 수 있다(학습서 p14, 해설서는 "14일 연속"). 그 뒤에도 심사를 통과해야 하고, 테스트 단계에서 다음 단계로는 사람이 직접 넘긴다. 그래서 일정은 ① 테스터 12명을 누구로 할지 ② 14일 테스트를 언제 시작할지 ③ 출시 점검표(개인정보처리방침·데이터 안전·삭제·신고 등)를 그 전에 채울 수 있는지부터 정한다.
