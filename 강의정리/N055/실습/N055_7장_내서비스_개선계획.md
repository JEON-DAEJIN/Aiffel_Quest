# N055 7장 — 내 서비스 개선 계획 (MSM 본안 + ASP 보조안)

> 작성 2026-11-03. 교안 7-3의 계획 틀을 **내 프로젝트 폴더의 실제 코드와 문서를 읽고** 채웠다(부록 A-11의 "계획이 실제 코드와 맞는지 확인"). 코드는 고치지 않았다.
> 표기: **[확인]** 파일을 읽어서 안 것 · **[추론]** 내 판단 · **[미확인]** 아직 확인하지 못한 것.

## 0. 먼저 — 교안의 예를 그대로 베끼면 안 되는 곳

교안 7-5는 MSM의 실패 유형을 "원문에 없는 인물이나 사건 생성"으로 적는다. **내 MSM은 그것을 실패로 보지 않는다.** 2026-09-10 실전 피드백으로 "사실+연출(사건 불변)"을 버리고 "문학적 재구성(창작 허용)"으로 바꿨다. `unconfirmed_claims`를 0으로 강제하는 안전장치가 오히려 창작을 억눌러 밋밋한 결과를 냈기 때문이다 [확인: `docs/DECISIONS.md`]. 교안의 기준 문장을 가져오면 **MSM이 이미 겪은 실패를 되풀이하는 평가**가 된다(N035 제안 문서가 "이미 한 번 겪은 실패의 반대편"이라고 쓴 바로 그 위험). 그래서 금지선을 내 PRD의 좁은 원칙으로 다시 썼다: "원문에 없는 사건·발언을 지어내 **실존 인물에게 붙여 정체성을 왜곡하지 않는다**"(실명 여부와 무관하게 항상) [확인: `docs/N035_평가자최적화자_게이트_제안.md`가 인용한 PRD].

## 1. MSM(My-Story-Maker) 개선 계획 — 채운 틀

```text
서비스: My-Story-Maker (원고 → 웹소설 각색 N → 웹툰 스토리보드 → 컷 이미지)
고칠 실패 유형: 실존 인물에게 원문에 없는 발언·행동을 붙여 그 사람의 정체성을 왜곡함
               (아직 실제로 일어났는지 모름 — 가설. 아래 "먼저 할 일")
처음 어긋날 단계: N 변환(웹소설 각색, engine.py run_adapt_stage / run_revision_stage)
판정 기준 문장: "웹소설에서 실명으로 등장하는 인물의 발언·행동 가운데 원문에 없는 것은,
                그 인물이 원문에서 보인 성격·입장·관계를 뒤집거나 훼손하지 않는다.
                (창작 자체는 허용. 원문 핵심 사건의 결과를 바꾸는 것은 실패)"
데이터셋 이름: msm-identity-preservation   항목 수: 실패 6 / 정상 6 (합성 포함, 아래)
고정해 넣을 앞 단계 결과: 있음 — R 단계 결과(r_text). 이미 DB에 저장돼 있다.
평가자: 코드 + LLM 심사   판정할 것: 코드=실명이 그대로 있는가 / LLM=발언·행동이 정체성을 뒤집는가
고칠 곳: 우선 프롬프트 버전(문학적 해석의 문제) — 같은 항목이 두 번 실험에서 계속 틀리면 코드(실명·결과 대조)
회귀 확인 데이터셋: msm-creativity-regression (창작 보존: added_details 개수 등)
내보낼 기준: 실패 6개 중 5개 이상을 실패로 가려내고(재현율), 정상 6개는 모두 정상으로(거짓 경보 0),
            창작 보존 지표는 기준선(041편 added_details 6건)의 70% 아래로 내려가지 않음
평가를 걸 지점: 프롬프트 production 라벨 변경 전(데이터셋 실험). 머지 전 게이트는 코드 검사만 비용 없이
```

### 1-1. 왜 이 실패 유형을 골랐나
- 교안 기준: "일어나면 피해가 큰 유형은 개수가 적어도 올린다" [교안 7-2]. 실존 인물(회사 사람들)에게 하지 않은 말을 붙이는 것은 한 번이어도 사람을 해친다. PRD가 "협상 불가 원칙"으로 올려 둔 이유다 [확인].
- **그러나 이 실패가 실제로 있었다는 증거는 아직 없다.** 검증된 2편(040·041)은 사람이 전문을 읽고 "정체성을 왜곡하지 않았다"고 확인했고 `unconfirmed_claims` 0건이었다(040) [확인: DECISIONS.md]. 그래서 이 계획은 가설에서 시작한다. 교안의 순서(실패를 읽고 → 유형 → 데이터셋)를 지키려면 **먼저 실패를 모아야 한다.**

### 1-2. 먼저 할 일 (계측과 실패 모으기) — 교안 7-4의 ⚠
1. **계측 먼저**: MSM에는 Langfuse가 없다(코드에서 `langfuse` 검색 0건). 대신 단계마다 `event_log_json`(3~4KB)과 세션 ID가 DB에 남는다. LLM 호출은 `sdk_client.py`의 **`run_structured_query` 한 곳**으로 모여 있어(호출 4곳: R·N·수정·스토리보드) 계측 지점은 하나다 [확인]. friend-agent의 `TracedLLM`처럼 이 함수를 감싸 입력·출력·토큰을 남기면 된다. [미확인] Claude Agent SDK 호출을 Langfuse가 자동으로 기록하는지는 확인하지 않았다. 안 되면 수동으로 generation을 만든다.
2. **실패 모으기**: `README`의 next_action이 이미 "나머지 11편 반복 실행"이다(원문 13편 중 2편만 완주) [확인]. 그 11편의 N 결과를 읽고, 실명 인물에게 붙은 창작 발언을 하나씩 표로 적는다(처음 어긋난 단계 = N인지 R인지 확인).
3. **트레이스·원문 개인정보**: 원문에는 실명과 실제 직장 이야기가 들어 있다. 트레이스에 그대로 가면 Langfuse에 30일 남는다(6장). 마스킹으로는 인명을 못 가린다 — 이 서비스는 "비공개 + 본인 소재"이므로 **보관을 받아들일지 운영자(나)가 정해야 한다** [추론].

### 1-3. 코드와 맞춰 본 결과 (부록 A-11 네 질문)
| 질문 | 확인한 것 |
|---|---|
| ① 처음 어긋난 단계가 코드의 어느 함수이고 입출력이 남는가 | `engine.py` `run_adapt_stage`(첫 각색)·`run_revision_stage`(수정 요청). 입력은 `r_text`, 출력은 `n_json`(`novel_text`·`based_on`·`added_details`)이 **DB에 남는다** [확인]. Langfuse 트레이스는 없다 |
| ② 고정해 넣을 앞 단계 결과를 데이터셋 input으로 만들 수 있나 | 된다. `runs.r_text`가 N의 입력이다. 단 **지금 DB에는 2건(040·041)뿐**이고 원문은 13편(`app/episodes/data/*.md`)이다. 나머지 11편은 R·N을 돌려야 한다 [확인] |
| ③ 프롬프트가 어디에 있고 변수로 둘 부분은 | `engine.py` `_adapt_prompt(r_text, notes)`와 `REAL_NAME_NOTE`(코드 안 문자열). 변수는 `{{r_text}}`와 수정 요청 `{{notes}}`(없으면 빈 문자열). `REAL_NAME_NOTE`는 안전 문구라 코드에 남기고 나머지 문단만 프롬프트 관리로 옮기는 쪽이 6장·5장의 분리와 같다 [추론] |
| ④ SDK 문서 근거 | 이 프로젝트는 `claude-agent-sdk`를 쓰고 `langfuse`는 의존성에 없다. **Langfuse 설치·연결 방법은 이 계획에서 확인하지 않았다** [미확인] |
- **주의할 차이**: `run_adapt_stage`는 `resume=refine_session_id`로 R 단계의 **대화 세션을 이어서** 호출한다. 실험에서 `r_text`만 넣어 새 세션으로 부르면 프로덕션과 입력이 다르다(원문 O를 R 단계에서 이미 본 상태가 아님). 데이터셋 실험은 두 방식 중 하나로 통일하고 그 차이를 기록해야 한다 [추론].

### 1-4. 데이터셋 설계
- **정상 6**: 완주한 실제 N 결과 중 정체성을 훼손하지 않은 것 — 040·041과, 먼저 모을 11편에서 사람이 승인한 것.
- **실패 6**: **실제 실패를 모아야 한다.** 모으기 전에는 정상 N 결과에 **합성 실패**를 넣어 시험 문제를 만든다(예: 원문에서 신중한 본부장이 사람들 앞에서 팀장을 모욕하는 대사로 바꿈). 합성은 `source: synthetic`으로 표시하고, **실제 실패가 모이면 바꾼다.** 합성만으로 평가자를 믿으면 안 된다(friend-agent에서 심사가 내가 만든 경계 사례 6개에서만 갈린 것과 같은 함정, 13절).
- LLM 심사 지시문은 3장의 holiday-reply 심사를 출발점으로 **기준·판정하지 않을 것·예시**를 바꿔 쓴다. 판정하지 않을 것에 "문체, 재미, 창작 자체"를 넣어 창작을 억누르지 않게 한다.
- **심사 검증**: 사람(나)이 12~22개를 먼저 판정하고 심사와 맞춰 일치율과 놓친 실패를 본다(3장 방식). 이걸 하기 전에는 심사 점수를 게이트에 쓰지 않는다.

### 1-5. 내보낼 기준 — 실험 전에 정한 숫자
| 기준 | 값 | 이유 |
|---|---|---|
| 실패 항목을 실패로 가려냄 | 6개 중 5개 이상 | 교안 예(5개 증가)를 12개 규모로 줄임 |
| 정상 항목을 정상으로 | 6개 모두(거짓 경보 0) | 거짓 경보는 창작을 억누르는 쪽으로 가는 길 [확인: 이미 겪은 실패] |
| 창작 보존 | `added_details` 개수가 기준선 6건(041편)의 70%(4.2건→4건) 아래로 안 내려감 | **9월 10일의 "밋밋함" 실패의 반대편을 숫자로 막는 회귀 확인** |
| 항목별 흔들림 | 같은 항목을 2번 이상 돌림(5장 결과: 실행마다 3~4개가 흔들림) | 한 번의 결과로 결정하지 않음 |
- 이 값들은 **심사가 사람과 90% 이상 맞는다고 확인된 뒤에** 쓴다. 맞지 않으면 숫자가 아니라 심사 지시문을 먼저 고친다.

### 1-6. 평가를 걸 지점 (6장 표에 맞춰)
- **프롬프트 변경 전**: 위 데이터셋 실험 + 창작 보존 회귀 → 기준을 넘어야 production 라벨. (13편 규모라 A/B는 쓰지 않는다. 5장 결론과 같다.)
- **코드 변경 전(CI)**: 비용 없는 검사만 — 예: "원문에 있는 실명이 웹소설에 그대로 있다"(이름 목록을 에피소드 설정에 적어 두는 경우). 실제 LLM이 드는 평가는 라벨이나 버튼으로(6장 `eval.yml` 방식).
- **가드레일**: 시스템 지시문 공개 요청 차단은 MSM이 **사용자 입력으로 지시를 받지 않는 구조**(원문만 입력, 수정 요청 `notes`만 자유 입력)라 우선순위가 낮다 [추론]. `notes`에 개인정보나 지시문 탈취가 들어올 수는 있어 6장의 마스킹과 같은 점검을 `notes`에 한다.

## 2. ASP(AI Story Partner) 보조 계획 — 가볍게

> ASP는 코드가 아니라 **시스템 프롬프트 + 템플릿(챗봇)**이고 PRD v1.0 확정·파일럿 직전이다 [확인: README]. 계측·데이터셋 이전 단계라 계획을 짧게 둔다.

```text
서비스: ASP (원고를 7개 기준으로 분석하는 챗봇 — 훅·갈등축·결핍제시시점·캐릭터분석·장르관습·유사사례 포지셔닝·페이싱)
고칠 실패 유형: 6번 "유사사례 포지셔닝"의 근거 약함 — 비교 작품을 출처 없이 단정함(가설)
처음 어긋날 단계: 분석 답 만들기(근거가 되는 데이터를 못 찾아 모델의 기억에 의존)
판정 기준 문장: "답에 나온 비교 작품·수치는 제공된 그라운딩 자료에 있어야 한다. 없으면 '근거 없음'으로 표시한다."
데이터셋: asp-similar-cases, 실패 5 / 정상 5 이상 (입력 다양성: 시놉시스·1화·10화)
고정해 넣을 앞 단계 결과: 있음 — 검색·제공한 유사사례 자료
평가자: 코드(작품명이 자료에 있는지) + LLM 심사(근거 표현이 단정인지 유보인지)
고칠 곳: 근거 자료 보강은 데이터(그라운딩), 단정/유보 표현은 프롬프트, 자료 대조는 코드
내보낼 기준: 실험 전에 정함 (실패 5개 중 4개 이상 통과, 정상 5개 모두 통과 — 초안)
평가를 걸 지점: 프롬프트 변경 전
```
- **근거**: 제출보고서에서 6번 기준의 "근거 약함"을 "추가 개발이 필요한 문제"로 분류해 파일럿 과제로 넘겼고, README의 next_action이 "6번 기준 그라운딩 데이터 보강"이다 [확인]. "비교 작품을 지어낸다"는 증상은 **관찰된 것이 아니라 내 가설**이다 [미확인] — 파일럿에서 실제 답을 읽어 확인한다.
- **교안 7-5의 ASP와 다르다**: 교안은 ASP를 "컨설팅 보고서 생성"으로 적는다. 내 ASP는 웹소설·웹툰 원고 구조 분석이다. 계획 틀은 같지만 내용은 다르게 채웠다.
- 먼저 할 일: 파일럿 대화를 저장해 읽을 수 있게 한다(계측). 챗봇 형태라 트레이스가 없으면 대화 기록 파일이라도 모은다.

## 3. 내가 이번 실습에서 직접 한 것과의 대응 — 이 계획이 그대로 따르는 흐름

| 단계 | friend-agent에서 한 것 | MSM에서 할 것 |
|---|---|---|
| 실패 읽기 | 트레이스 네 건 → 실패 유형표 | 11편 N 결과 읽기 → 유형표 |
| 기준 문장 | 유형마다 통과 조건 | 위 "정체성 왜곡" 문장 |
| 데이터셋 | holiday-reply 11개(실패 6·정상 5), 앞 단계 결과 고정 | msm-identity-preservation 12개, `r_text` 고정 |
| 평가자 | LLM 심사 + 사람 판정 22개와 일치율 | 같은 방식(12~22개) |
| 고칠 곳 | 프롬프트 1·코드 3 (계산·규칙은 코드) | 해석은 프롬프트 우선, 반복되면 코드 |
| 숫자 | 33/41, T34 필수 | 5/6·0·70% (실험 전에 고정) |
| 지점 | 프롬프트 라벨 전 + CI 라벨 실행 | 프롬프트 라벨 전 + 코드 검사만 CI |

## 4. 이 계획이 말해 주지 않는 것
