0. 한눈에

그림: 오늘의 흐름. 이미지는 staging 브랜치 실행에서 한 번만 만들고, main 실행은 그 이미지를 읽어 그대로 production에 보낸다.

배포한 것과 확인한 것이 같다고 말하려면 이미지를 한 번만 만들어야 한다. 그래서 이미지를 Actions 러너에서 커밋 SHA 태그로 만들어 올리고, production은 staging 리비전의 다이제스트를 읽어 그대로 받게 바꿨다.

5. 로컬에서 만든 이미지 시험 (교안 4장 "직접 해 보고 싶다면")

시험용 저장소 local-test와 시험용 서비스 local-test를 따로 만들어 로컬 이미지를 올려 보고 지웠다.

  • 이 PC는 Intel/AMD(x86_64)라 docker image inspect의 아키텍처가 amd64/linux로 나왔고 배포는 성공했다. 교안이 말한 Apple Silicon의 linux/amd64 오류는 재현하지 못했다.
  • 그래도 /version이 "commit":"local", "env":"local"로 커밋 SHA가 없었다(기록·무결성 문제는 그대로). 로그인 없이 호출하면 403이었다(공개되지 않음).
  • 확인 후 서비스·저장소를 이름 local-test를 다시 확인하고 삭제했고, 로컬 이미지도 지웠다.
  • 이어서 AGENTS.md의 "배포와 권한"에 "배포용 이미지는 GitHub Actions에서만 만든다. 로컬 환경에서 만든 이미지를 Artifact Registry에 올리거나 배포하지 않는다." 한 줄을 PR #28로 올려 머지했다. 이 시험은 규칙을 넣기 전에 했다.
  • 교재와 다르게 한 것: Docker Desktop이 꺼져 있어 직접 켰다. 이 시험 중 docker push 결과 마지막 줄 크기가 856으로 나왔는데(이미지 본체가 아니라 매니페스트 목록으로 보임), 원인까지는 확인하지 않았다.

6. 정리 정책 (교안 5장)

docs/cleanup-policy.json(삭제: 7일 초과, 유지: 최근 10개)을 만들어 friend-agent와 cloud-run-source-deploy 두 저장소에 --dry-run으로 걸었다. 조회로 두 저장소 모두 cleanupPolicyDryRun: true를 확인했다.

  • 이미지 40개로 시뮬레이션한 삭제 대상: 지금 0개 → 내일(10-28) 6개 → 3일 뒤(10-30) 저장소 전체 기준 20개, 이미지 이름별 기준 16개.
  • 오늘은 가장 오래된 이미지(10월 20일 06시 UTC)가 아직 7일이 안 돼 지울 것이 없다. 감사 로그를 조회했으나 아직 기록이 없었다.
  • 롤백 기준 점검: production 8243335·staging 1010a7d·직전 3201e13·def3165가 모두 friend-agent 저장소의 최근 10개 안이다.
  • 불확실한 것: "최근 10개"를 저장소 전체로 세는지 이미지 이름(패키지)별로 세는지는 확인하지 못했다. 드라이런 결과(감사 로그)로 확인할 일이다.
  • 풀지 못한 것: 실제 삭제(--no-dry-run) 전환과 드라이런 결과 확인은 하루 뒤로 남겼다. 정책 파일은 작업 폴더의 docs/cleanup-policy.json에 git 미추적 파일로만 있고 PR로 올리지 않았다.

7. 고장 난 Dockerfile 4종 (교안 6장)

문제증상(관찰)원인(원본과 비교)복구 후
A. OCR만 실패컨테이너는 정상 시작, 사진을 보내면 500 사진에서 글자를 읽는 프로그램이 서버에 없습니다RUN apt-get install … tesseract-ocr tesseract-ocr-kor 줄 없음HTTP 200, 일정표 글자 반환
B. 이미지 안의 파일ls -a /app에 .env 보임(서비스는 정상).dockerignore에서 .env 줄 없음(**/ 패턴도 빠짐).env 사라지고 .env.example만
C. 실행 사용자서비스·/health 정상, whoami가 rootRUN useradd … appuser·USER appuser 줄 없음whoami = appuser
D. 접속 안 됨컨테이너 Up, localhost:8080 응답 없음(HTTP 000), 로그가 0.0.0.0:8000을 리슨CMD가 ${PORT:-8080} 대신 --port 8000 고정8080과 PORT=9000에서 모두 200
  • 문제 A는 내가 먼저 "운영체제 시스템 패키지이고 Dockerfile의 설치 명령에 있을 것 같다"고 짐작했고 맞았다. B~D는 짐작 없이 바로 원본과 비교했다(내 선택).
  • 교재와 다르게 한 것: 교안은 cp starter/Dockerfile Dockerfile로 되돌리라고 하는데, 이 저장소의 Dockerfile은 N050에서 PDF용 poppler-utils를 더한 버전이라 starter/로 되돌리면 그 기능이 사라진다. 그래서 git checkout -- Dockerfile·.dockerignore로 되돌렸다.
  • Actions 이미지였다면 드러나지 않았을 문제는 B(로컬 폴더의 .env는 GitHub에 없음), 서비스가 정상으로 보여 지나쳤을 문제는 C이다.
  • 문제 A를 처음 시도했을 때 Docker Desktop이 꺼져 빌드가 실패했다. 그 사이 루트 Dockerfile이 고장 난 상태로 남았으나 데몬을 다시 켠 뒤 진행하고 git checkout으로 되돌렸다(git status 깨끗).

11. 정리

  • 이미지 이름은 저장 위치·프로젝트·저장소·이미지 이름·태그이고, 태그는 옮겨 붙을 수 있고 다이제스트는 내용으로 정해진다. 찾아갈 때는 커밋 SHA 태그, 실제로 무엇이 도는지는 다이제스트로 본다.
  • 연결표 다섯 칸(커밋 → 태그 → 다이제스트 → 리비전 → /version)이 채워지면 "지금 도는 코드는 어느 커밋인가"에 화면 몇 개로 답한다.
  • 이미지 승격: main 머지에서 이미지를 다시 만들지 않고 staging 리비전의 다이제스트와 COMMIT_SHA를 읽어 그대로 보낸다. 승인의 뜻이 "새로 만들어 내보낸다"에서 "확인한 그 이미지를 내보낸다"로 바뀐다.
  • 로컬에서 만든 이미지는 올리지 않는다: CPU 아키텍처 문제와 함께, 이 PC에서도 확인한 기록·무결성(/version에 커밋 없음) 문제가 있다.
  • 정리 정책은 삭제+유지를 함께, 드라이런 먼저. 롤백에 필요한 이미지를 남긴다.
  • 고장 난 Dockerfile: 빌드 성공과 서비스 정상은 다르다. 증상 → 가설 → 확인 → 복구 → 재검증.

12. 궁금했던 것

아래 질문은 이번 실습의 사고 표에서 뽑은 것이다.

Q. 태그가 있으면 이미지를 정확히 가리키는 것 아닌가? 왜 다이제스트가 따로 필요한가?

  • 태그는 같은 이름을 다른 이미지에 다시 붙일 수 있다. 다이제스트는 내용으로 정해져 옮겨 붙지 않는다. Cloud Run도 태그로 배포해도 배포 순간의 다이제스트로 바꿔 기록한다. 오늘 연결표에서 리비전의 이미지 주소가 …@sha256:…로만 보인 것이 그 예다.

Q. main에 머지하는 커밋이 새로 생기는데 /version의 commit이 4ab996a가 아니라 8243335로 나오는 이유는?

  • 승격 워크플로는 main에서 이미지를 만들지 않고 staging 리비전의 COMMIT_SHA를 읽어 그대로 넣는다. /version은 이미지를 만든 staging 쪽 커밋을 보여 주므로 커밋에서 이미지까지의 연결이 끊기지 않는다.

Q. Intel PC에서 로컬 이미지 배포가 성공했는데 왜 규칙이 필요한가?

  • 아키텍처 때문에 실패하지 않아도 로컬 이미지는 내 폴더의 파일로 만들어져 커밋과 연결되지 않는다. /version의 commit이 local이었고 PR 검토·CI·승인도 건너뛴다.

Q. 정리 정책을 걸었는데 왜 오늘은 지워진 것이 없나?

  • 가장 오래된 이미지가 아직 7일이 안 됐고, 정책 반영과 감사 로그 확인에도 하루쯤 걸린다. 그래서 오늘은 드라이런으로 걸고 목록으로 계산한 뒤, 하루 뒤에 결과를 확인하는 것이 순서다.
