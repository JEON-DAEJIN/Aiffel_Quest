3-4. staging 만들기 — 키 문제와 공개 전환

staging 전용 키를 만들지 못했습니다. 교재는 LLM 제공사에서 staging용 키와 낮은 한도를 따로 만들라고 하지만, 제가 쓰는 키는 수업에서 받은 키였습니다. OpenAI 대시보드를 확인하니 제 조직(Personal)은 무료 체험에 크레딧 $0.00이었고 두 프로젝트의 월 사용액이 모두 $0이라, 그 키는 제 계정 것이 아님을 확인했습니다. 그래서 기존 시크릿 llm-api-key 값을 값을 출력하지 않고 별도 시크릿 llm-api-key-staging으로 복사했습니다(해시 비교로 값 동일 확인). 이름과 권한은 환경별로 분리했지만 키와 사용 한도는 production과 공유합니다. 첫 시도는 Windows에서 프로세스 치환이 지원되지 않아 시크릿이 만들어지지 않았고, 표준 입력 파이프로 다시 했습니다.

런타임 서비스 계정 friend-agent-runtime에는 llm-api-key-staging 하나에 대해서만 secretmanager.secretAccessor를 주고, 정책을 다시 읽어 그 계정 하나만 등록돼 있음을 확인했습니다.

friend-agent-staging 서비스를 --allow-unauthenticated, ENV=staging, 최소 0·최대 인스턴스 1로 만들었습니다(리비전 00001-tn9). staging 화면에는 "테스트 환경" 배너가 보이고 production에는 없습니다.

GitHub 환경은 staging(변수 SERVICE=friend-agent-staging, ENV=staging)과 production(SERVICE=friend-agent, ENV=production)을 만들었습니다. production에 승인자를 거는 단계에서 이렇게 거절됐습니다.

Failed to create the environment protection rule. Please ensure the billing plan
supports the required reviewers protection rule. (HTTP 422)

저장소가 비공개라서 승인자와 브랜치 보호(유료 플랜 기능)가 막힌 것이었습니다. 저장소 전체와 커밋 기록 25개를 검사해(OpenAI·Google·Supabase·Anthropic 키 패턴, 개인키, JWT, GitHub 토큰) 노출된 키가 0건이고 .env가 한 번도 커밋되지 않았음을 확인한 뒤, 제가 직접 공개로 전환했습니다. 전환이 GitHub 쪽에 반영되기까지 한 번은 PRIVATE으로 보였고, 다시 확인하자 PUBLIC이었습니다. 그 뒤 승인자 JEON-DAEJIN(prevent_self_review=false)이 걸렸습니다.

3-6. 브랜치 보호

gh api로 main과 staging에 같은 규칙을 걸었습니다. PR 필수(승인 수 0), 필수 상태 체크 test, enforce_admins: true입니다. 두 브랜치만 protected=true이고 다른 브랜치는 보호되지 않습니다.

main에 빈 커밋을 만들어 직접 push해 보니 이렇게 거절됐습니다.

remote: error: GH006: Protected branch update failed for refs/heads/main.
- Changes must be made through a pull request.
- Required status check "test" is expected.

거절된 빈 커밋을 로컬 main에서 지우려는 git reset --hard origin/main은 AI 도우미 환경의 안전 검사가 "되돌릴 수 없는 로컬 삭제"로 막아서, 이 커밋(1f7dfd4)은 로컬 main에 아직 남아 있습니다(원격에는 올라가지 않음).

문제실패한 테스트와 로그원인 한 문장

3-8. 문제 D — CI를 통과해 staging에서 발견한 변경 (#17·#18)

static/index.html 95번째 줄 .send{...}에 display:none;을 넣은 PR #17을 staging으로 올렸습니다. CI는 통과했고(test·hello 통과, CLEAN) 보호 규칙이 걸려 있어도 머지됐습니다. 테스트가 화면 모양을 확인하지 않기 때문입니다.

머지 후 staging(e264971, 리비전 새 배포)에서 .send 버튼의 CSS display가 none이고 화면에 보이지 않음을 브라우저로 확인했습니다. production은 fae6cc9 그대로였고, 이 변경은 main으로 보내지 않았습니다.

되돌릴 때는 머지 커밋이라 부모가 둘이어서 git revert -m 1이 필요했습니다. Revert PR #18을 staging으로 올려 체크 통과 후 머지하자 staging이 3b5d42a로 바뀌고 .send의 display가 none에서 block으로 돌아왔습니다(production은 계속 fae6cc9).

4. 이 실습에서 얻은 핵심 다섯 가지

  1. 로컬에서 통과한 것이 서버에서 통과한다는 보장은 없다. 시간대 변경은 한국 시간 로컬에서 11 passed였고 UTC 러너에서만 08:00이 17:00이 됐다. 테스트는 서버와 같은 환경에서도 돌려야 한다.
  2. CI는 "알려 주는 것"이고 "막는 것"은 브랜치 보호다. 같은 실패 PR이 보호 전에는 UNSTABLE(머지 가능), 보호 후에는 BLOCKED였다. PR 필수와 필수 체크는 둘 다 걸어야 빈틈이 없다.
  3. CI를 통과해도 사람이 써 봐야 보이는 문제가 있다. 버튼이 사라진 변경은 모든 체크를 통과했고 staging에서 열어 본 사람만 발견할 수 있었다. 그래서 gate가 세 겹(테스트·staging·승인)이다.
  4. 교안의 명령은 교안 그대로 재현해야 한다. 제가 python -m pytest로 돌려서 pytest만 칠 때의 app 모듈 문제가 CI에서야 드러났다.
  5. 유료·계정 의존 기능은 시작 전에 확인해야 한다. 비공개 저장소는 환경 승인자와 브랜치 보호를 쓸 수 없었고, 수업에서 받은 키로는 staging 전용 키와 한도를 분리할 수 없었다.

5. 발견한 한계와 풀지 못한 것

  • staging 전용 키와 낮은 사용 한도를 만들지 못했습니다. 수업 키를 별도 시크릿으로 복사해 이름·권한만 환경별로 분리했고, 비용·한도는 production과 공유합니다. 제 OpenAI 계정(Personal)은 무료 체험에 크레딧 $0.00이었고, 그곳의 friend-agent-staging 프로젝트는 쓰이지 않는 빈 프로젝트로 남아 있습니다.
  • 저장소를 비공개에서 공개로 바꿨습니다. 승인자와 브랜치 보호를 쓰려면 필요했고, 전환 전에 키 패턴 검사로 노출 위험이 없음을 확인했습니다. 다만 공개 저장소의 Actions 로그에는 프로젝트 ID 같은 식별자가 보일 수 있습니다.
  • 중간 과제(배포 결과 메신저 알림)와 도전 과제(내 앱에 CI 붙이기)는 하지 않았습니다. 기본 과제만 수행했습니다.
  • 배포 후 모니터링·알림은 만들지 않았습니다. 시작 질문에서 막을 수 있는 지점으로 떠올렸지만 이 실습에서 만든 게이트는 아닙니다. 다양한 시간대·날짜 경계 테스트와 화면(브라우저) 자동 테스트도 만들지 않았습니다. 문제 D를 CI에서 막으려면 이런 테스트가 더 필요합니다.
  • UTC 재현을 로컬에서 직접 하지 못했습니다. Windows PowerShell에서 TZ=UTC가 되지 않아 UTC 쪽 확인은 CI 결과로 대신했습니다.
  • 문제 A·B의 실제 실패 로그는 교재·해설서에 제시되지 않았습니다. 해설서도 "직접 실행한 결과를 근거로 확인해야 한다"고 적었고, 이 보고서의 3-7이 제가 실행해서 얻은 결과입니다.
  • 처음 누른 production 승인이 반영되지 않았습니다. 원인은 확인하지 못했고(확정 버튼까지 누르지 않았을 가능성), 다시 눌러 해결했습니다.
  • 로컬 main에 거절된 빈 커밋 1f7dfd4가 남아 있습니다. 안전 검사가 git reset --hard를 막았고, 원격에는 올라가지 않았습니다.
  • BUILD_SA는 교재가 말한 변수 5개에 있지만 이 템플릿에는 없고 어디서도 쓰지 않았습니다. 교재와 템플릿 버전 차이로 보이나 확정하지는 못했습니다.
