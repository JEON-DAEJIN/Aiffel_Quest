0. 한눈에

자동 배포는 머지된 코드를 그대로 내보낼 뿐 맞는지는 확인하지 않는다.

그래서 기계가 보는 CI → 사람이 먼저 써 보는 staging → 직접 누르는 승인을 겹겹이 세우고, 브랜치 보호로 그 검사를 우회하지 못하게 막았다.

  • 저장소: friend-agent (공개로 전환함 — 4번 참고)
  • 오늘 연 PR 11개 (머지 7 · 닫음 4)
  • staging 자동 배포 4번 · production 자동 배포 1번(내가 직접 승인) · 손으로 친 배포 명령 1번(staging 서비스를 처음 만들 때)
  • 일부러 망가뜨린 변경 4개: CI가 잡은 것 3개 · CI를 통과해 staging에서 사람이 발견한 것 1개

1. 시작 상태 (2장)

  • N048에서 만든 deploy.yml(main 머지 시 배포)과 저장소 변수 4개, 최근 deploy 실행 completed success를 확인했다

2. 테스트를 만들고 일부러 깨뜨려 보기 (3~4장)

  • 로컬 pytest로 템플릿 테스트 10 passed → "내일 아침 8시" 테스트(E07)를 더해 11 passed
  • 시간대 정보를 빼는 한 줄 패치를 넣어도 한국 시간 로컬에서는 여전히 11 passed — 버그가 숨는다
  • 기존 테스트 test_reminder_is_saved_with_timezone은 시간대 정보 유무(형식)만 봐서 통과, 새 테스트는 사용자가 보는 08:00을 확인해 같은 버그를 잡는다
  • Windows PowerShell에는 TZ=UTC가 안 먹어서 UTC 쪽 확인은 CI로 넘겼다

3. CI 붙이기 (5장)

  • ci.yml을 넣은 첫 실행이 실패했다: ModuleNotFoundError: No module named 'app'
  • 원인: CI 러너에서 pytest만 치면 저장소 루트가 import 경로에 들어가지 않는다. 내가 로컬에서 python -m pytest로 돌려서 가려져 있었다(로컬에서도 pytest만 치면 재현됨)
  • 교재와 다르게 한 것: ci.yml은 그대로 두고 루트에 pytest.ini(pythonpath = ., testpaths = tests) 추가
  • 그다음 시간대 변경을 PR로 올리자 CI가 08:00 기대·17:00 저장으로 실패 — 로컬에서는 통과했던 변경이다
  • 이때 Merge 버튼은 눌렸다(UNSTABLE). CI는 알려 줄 뿐 막지는 않는다

6. 우회를 막기 — 브랜치 보호 (7장)

  • main·staging에 PR 필수(승인 수 0) · 필수 체크 test · 관리자에게도 적용
  • main에 직접 push 시도 → 거절
remote: error: GH006: Protected branch update failed for refs/heads/main.
- Changes must be made through a pull request.
- Required status check "test" is expected.
  • "PR 필수"와 "필수 체크"는 서로 다른 규칙이라 둘 다 걸어야 빈틈이 없다
  • 거절된 빈 커밋은 로컬 main에 남았고, git reset --hard가 AI 도우미 환경의 안전 검사에 막혀 내가 허락한 뒤 main 브랜치·앞선 커밋 1개를 확인하고 정리했다

9. 풀지 못한 것 · 교재와 달라진 것

  • staging 전용 키와 낮은 사용 한도를 만들지 못했다(수업 키 공유)
  • 저장소를 비공개에서 공개로 바꿨다 — 승인자·브랜치 보호에 필요했고, 전환 전에 키 노출을 검사했다
  • 중간 과제(배포 결과 메신저 알림)와 도전 과제(내 앱에 CI)는 하지 않았다
  • 배포 후 모니터링·알림, 시간대 경계 테스트, 화면(브라우저) 자동 테스트는 만들지 않았다(문제 D를 CI에서 막으려면 필요)
  • UTC 재현을 로컬에서 직접 하지 못했다(Windows에서 TZ=UTC 불가) — CI 결과로 대신했다
  • 처음 누른 production 승인이 왜 반영되지 않았는지 확인하지 못했다
  • 정식 docx 검증기(validate.py)를 이 PC에서 찾지 못해 이 문서 세트의 docx는 XML 구조 검사와 LibreOffice 렌더링으로만 확인했다

10. 정리

  • 자동 배포는 맞는지 확인하지 않는다 → 기계가 보는 문(CI) · 사람이 먼저 써 보는 문(staging) · 직접 누르는 문(승인) · 우회를 막는 문(브랜치 보호)
  • CI는 알려 줄 뿐 막지 않는다. 막는 것은 PR 필수 + 필수 체크다
  • 로컬에서 통과한 것이 서버에서 통과한다는 보장은 없다. 테스트는 서버와 같은 환경에서, 사용자가 보는 값을, 일부러 깨뜨려 확인한다
  • CI가 못 보는 화면·말투·실제 AI의 답은 staging에서 사람이 본다
  • 교안 명령은 다른 방식으로 바꾸지 않고 그대로 먼저 돌려 본다
  • 다음: 배포 후 모니터링·알림, 화면 자동 테스트

11. 궁금했던 것

Q. python -m pytest로는 통과했는데 왜 CI에서만 실패했나?

  • python -m pytest는 현재 폴더를 import 경로에 넣고, pytest 명령은 넣지 않는다. 교안은 pytest -q였다
  • 교안 명령은 다른 방식으로 바꾸지 않고 그대로 먼저 돌려 봐야 한다

Q. staging이 production과 같은 키를 쓰면 의미가 있나?

  • 환경을 나누는 구조(이름·권한·변수·배너·승인)는 그대로 연습된다. 다만 비용·한도 분리 효과는 없다
  • 내 계정에서 발급한 키라면 staging용 키·월 사용 한도를 따로 거는 것이 맞다

Q. 비공개 저장소로는 이 실습이 안 되나?

  • 승인자(Required reviewers)와 브랜치 보호는 비공개 저장소에서 유료 플랜이 필요하다. 공개로 바꾸기 전에 커밋 기록의 키 패턴과 .env 커밋 이력을 검사한다
