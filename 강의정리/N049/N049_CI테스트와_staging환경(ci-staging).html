핵심 한 문장 요약 — 자동 배포는 "머지된 코드를 빠르게 내보낼 뿐" 맞는지는 확인하지 않는다 — 그래서 테스트(CI)가 코드를 자동으로 검사하고, staging이 사람이 먼저 써 보게 하고, 브랜치 보호와 배포 승인이 그 검사를 우회하지 못하게 막는, 세 겹의 품질 게이트를 직접 만들어 보는 것.

이번 강의는 N048에서 만든 자동 배포(main에 머지하면 GitHub Actions가 Cloud Run에 배포)를 이어받는다. 같은 AI 친구 에이전트 서비스(friend-agent, 줄여서 에이전트 서비스)에 ① 자동 테스트(CI), ② 사용자에게 나가기 전에 먼저 써 보는 별도 서버(staging), ③ 검사를 건너뛰지 못하게 하는 브랜치 보호와 배포 승인을 차례로 붙인다. 마지막에는 일부러 망가뜨린 변경 네 개를 올려, 어떤 게이트가 어떤 문제를 잡고 어떤 문제는 놓치는지 눈으로 확인한다.

💡 팁원문의 핵심 장면은 "내일 아침 8시에 알려 줘"라고 부탁한 약속이 오후 5시로 저장되는 변경이다. 앱은 멀쩡히 켜지고, 자동 배포는 그 변경을 그대로 사용자에게 내보낸다. 이번 강의 내내 이 한 장면이 반복해서 나온다.

1. 자동 배포만으로는 왜 부족한가

main 브랜치에 머지만 하면 몇 분 뒤 서비스가 새 버전으로 바뀌는 자동 배포는 편하지만, 머지된 변경을 그대로 사용자에게 내보낸다. 그 코드가 맞는지는 확인하지 않는다. 그래서 실제 서비스를 운영하는 팀은 두 가지를 둔다.

  • CI(지속적 통합, Continuous Integration): 코드를 합칠 때마다 정해 둔 테스트를 자동으로 돌리는 장치.
  • 별도의 환경(staging): 사용자에게 나가기 전에 먼저 써 볼 수 있는 또 하나의 서버.
🧪 예제[해설서 비유] 자동차를 만들 때마다 브레이크·라이트·핸들을 사람이 느낌으로 확인하면 위험하다. 그래서 공장에서는 기계가 같은 검사를 반복한다. 소프트웨어 테스트도 똑같다.

시작 질문: 9시간 어긋난 변경은 어디서 막을 수 있었을까

원문은 학습 시작 때 이런 질문을 던진다. "약속 시각이 9시간 어긋나는 변경이 사용자에게 나간다고 생각해 보세요. 이 변경이 사용자에게 닿기 전에 어디에서 누가 또는 무엇이 막을 수 있었을까요?" 해설서의 모범 답안은 다섯 지점이다.

지점하는 일
자동 테스트(CI)약속 시각을 저장했을 때 올바른 시간인지 자동 검사. 9시간 차이가 나면 실패
코드 리뷰다른 사람이 시간대 변환 로직에 오류가 없는지 확인
staging 환경운영과 비슷한 별도 환경에서 약속 등록·알림 기능을 먼저 확인
배포 승인 절차테스트가 실패했거나 검토가 끝나지 않았다면 운영 배포를 막음
모니터링·알림배포 후 잘못된 시각이 저장되는 현상을 감지해 빠르게 대응

이 답은 하루가 끝날 때 다시 꺼내 본다. "오늘 실제로 만든 게이트"와 "아침에 떠올렸지만 오늘 만들지 않은 지점"을 나눠 적는 것이 회고 질문이다(10장).

전체 흐름 — 품질 게이트

그림을 따라가면, 로컬 환경(dev)에서 고친 코드는 CI 테스트를 통과해야 staging 브랜치에 머지되고, 머지되면 staging 서버 friend-agent-staging에 자동으로 배포된다. staging 주소에서 직접 써 보고 문제가 없으면 staging에서 main으로 PR을 올리고, 같은 CI 테스트를 다시 통과해 머지된다. main에 들어온 변경은 바로 나가지 않고 배포 승인을 기다리며, 승인한 뒤에야 실제 사용자가 쓰는 friend-agent가 바뀐다.

📌 요약CI 테스트나 사람이 변경을 멈춰 세울 수 있는 자리 세 곳(테스트·staging 확인·배포 승인)이 품질 게이트(quality gate)다. 정해 둔 기준을 통과해야 다음 단계로 넘어가게 하는 지점을 말한다.

3. 테스트와 pytest — 기계가 대신 확인하게 하기

왜 테스트가 필요한가

지금까지는 무언가 고친 뒤 화면을 열어 직접 말을 걸어 보며 확인했다. 이 방식은 네 가지 약점이 있다.

  • 고칠 때마다 사람이 다시 해야 한다.
  • 바쁘면 건너뛰게 된다.
  • 이번에 고친 곳만 보게 된다.
  • 한 곳을 고치다 예전에 잘 되던 다른 기능이 깨지는 회귀(regression)를 알아차리기 어렵다.

테스트(test)는 "이 입력에는 이 결과가 나와야 한다"를 코드로 적어 두고 기계가 매번 같은 방식으로 확인하게 하는 것이다. 한 번 적어 두면 몇 초 만에 전부 다시 돌릴 수 있다.

pytest가 하는 일

테스트는 tests/ 폴더의 Python 파일에 함수로 적는다. 이 과정에서 쓰는 도구 pytest는 tests/에서 이름이 test_로 시작하는 파일과 함수를 찾아 하나씩 실행하고, 몇 개가 통과하고 몇 개가 실패했는지 모아 보여 준다. 템플릿 tests/test_app.py의 테스트 하나를 보면 모양을 알 수 있다.

def test_crisis_message_gets_fixed_safety_reply():
    events = chat("요즘 너무 죽고 싶어")
    text = "".join(e["text"] for e in events if e["type"] == "delta")
    assert "109" in text
코드의미
함수 이름확인하는 동작을 적은 것 — "위기 메시지에는 정해진 안전 응답이 간다"
chat("...")/api/chat에 위기 표현을 보냄
text = ...응답에서 글자만 모음
assert "109" in text뒤의 조건이 거짓이면 그 자리에서 테스트를 실패로 표시. 답에 109 안내가 없으면 실패

코드를 처음부터 다 읽지 못해도 함수 이름과 assert 줄만 보면 테스트가 무엇을 지키는지 알 수 있다.

페이크(fake) LLM — 실제 AI 없이 돌리는 이유

테스트에서 실제 LLM API를 부르면 ① 호출마다 비용이 나가고, ② 느리며, ③ 같은 메시지에도 답이 달라서 맞고 틀림을 정할 수 없다. 그래서 정해진 규칙으로만 답하는 테스트용 구현을 쓴다. 템플릿의 tests/conftest.py는 테스트를 시작하기 전에 페이크 LLM과 인메모리 저장소(데이터를 DB가 아니라 서버 메모리에만 두는 저장소)를 쓰도록 정해 두어서, 테스트는 LLM 제공사에 요청을 한 건도 보내지 않는다.

4. 약속 시각 테스트를 직접 추가하고, 버그를 잡는지 확인하기

4-1. 로컬에서 템플릿 테스트 돌리기

템플릿에는 서비스 동작을 확인하는 테스트 여섯 개(tests/test_app.py)와 Claude 제공사 연결을 확인하는 테스트 네 개(tests/test_claude.py)가 있다. 가상환경을 켠 상태에서 pip install -r requirements-dev.txt, pytest -q를 실행한다.

pytest 출력 읽는 법

  • 첫 줄에는 테스트마다 문자가 하나씩 찍힌다. 점(.)은 통과, F는 실패다.
  • 마지막 줄은 통과·실패 개수와 걸린 시간 요약이다. 지금은 10 passed가 나오면 성공이다.
  • 실패한 테스트가 있으면 위에 FAILURES 블록이 생긴다. 읽는 순서는 ① 테스트 이름(제목), ② >가 붙은 줄(실패한 assert, 즉 기대한 것), ③ E로 시작하는 줄(그때 실제로 나온 값)이다.

4-2. 약속 시각 테스트 추가하기

"내일 아침 8시에 알려 줘"라고 부탁하면 약속이 한국 시간 08:00으로 저장되는지 확인하는 테스트를 tests/test_reminder_time.py로 만든다. 템플릿 docs/examples.md에는 "이런 입력에는 이렇게 동작해야 한다"는 예시가 번호와 함께 적혀 있는데, 이 테스트는 그중 E07을 옮긴 것이다. 입력과 기대 동작을 한 쌍으로 적은 것이 테스트 케이스(test case)이고, 예시 번호를 주석에 남겨 두면 실패했을 때 어떤 동작이 깨졌는지 바로 찾을 수 있다. 코드 전문은 부록 A-2에 있다.

테스트는 메시지를 보낸 뒤 약속 목록 화면이 쓰는 /api/reminders를 읽어, 저장된 시각 표시가 08:00으로 끝나는지 본다. TestClient는 서버를 실제로 띄우지 않고 앱에 바로 요청을 보내는 테스트용 클라이언트다. 다시 pytest -q를 돌려 11 passed가 나오면 된다.

4-3. 테스트가 버그를 잡는지 확인하기 — "일부러 깨뜨려 보기"

새로 만든 테스트가 제 역할을 하는지는 통과하는 것만 봐서는 알 수 없다. 지키려는 동작을 일부러 깨뜨렸을 때 실제로 실패하는지까지 봐야 믿을 수 있다. 템플릿의 starter/incidents/reminder-timezone.patch는 약속 시각에서 시간대 정보를 빼는 한 줄짜리 변경이다. 연습용 브랜치 try/timezone에 이 패치를 넣고 테스트를 두 시간대로 돌려 본다.

  • 그냥 실행(내 컴퓨터의 한국 시간): 모두 통과
  • TZ=UTC pytest -q(서버와 같은 UTC): 약속 시각 테스트 하나가 실패. FAILURES 블록의 E 줄을 보면 08:00이어야 할 시각이 17:00으로 저장돼 있다
⚠️ 주의Windows의 PowerShell에서는 TZ=UTC를 이렇게 붙일 수 없다. 그 경우 이 비교는 5장의 CI 결과로 확인한다. 확인이 끝나면 git restore app/tools.py → git switch - → git branch -D try/timezone으로 되돌리고, 지우는 브랜치 이름을 한 번 더 확인한다.

왜 UTC에서만 실패할까 — 이번 강의 가장 중요한 대목

시간대 정보가 사라지면 컴퓨터는 현재 실행 중인 컴퓨터의 시간대를 기준으로 해석한다. 내 컴퓨터는 한국 시간으로 돌아서 시간대가 빠진 시각이 우연히 맞는 값으로 읽히지만, Cloud Run 서버와 GitHub Actions 러너는 UTC로 돌기 때문에 같은 코드가 9시간 늦은 시각을 저장한다. 로컬에서 평소처럼 돌려서는 이 버그가 보이지 않고, 테스트를 서버와 같은 환경에서 돌려야 보인다. 이것이 5장의 CI로 이어진다.

기존 테스트는 왜 이 버그를 못 잡았을까

템플릿에 원래 있던 test_reminder_is_saved_with_timezone은 두 시간대 모두에서 통과한다. "저장된 시각에 시간대 정보가 붙어 있는가"만 보는데, 저장소가 시간대가 빠진 시각에 실행 중인 컴퓨터의 시간대를 다시 붙이기 때문에 시각이 틀려도 조건은 맞는 것이다. 새로 만든 테스트는 사용자가 보게 되는 08:00을 확인해서 같은 버그를 잡았다.

4-4. 테스트 파일을 PR로 main에 올리기

지금 tests/test_reminder_time.py는 내 컴퓨터에만 있다. PR로 main에 넣어야 다른 사람도, 다음 장의 CI도 같은 테스트를 돌린다. 패치를 되돌린 상태(pytest -q가 11 passed)인지 확인한 뒤, 테스트 파일 하나만 커밋해 PR을 올리고 머지한다(명령은 부록 A-3). 머지하면 자동 배포가 한 번 돌지만 테스트 파일은 서비스 동작을 바꾸지 않는다.

5. 테스트를 main에 올리고 CI 붙이기

이제 main에는 테스트가 있지만 여전히 누군가 pytest를 실행해야만 돈다. 바쁠 때 잊어버리거나 로컬 시간대에서만 돌리면 서버에서 틀리는 변경도 통과한 것처럼 보인다. 그래서 PR이 올라올 때마다 GitHub Actions가 정해진 환경(Ubuntu, Python 3.13, UTC)에서 테스트를 돌리게 한다.

🧪 예제[해설서 비유] 과제를 제출한다고 생각해 보자. 로컬 테스트는 제출 전에 학생이 직접 답을 확인하는 것, CI는 제출할 때마다 자동 채점기가 검사하는 것, PR 상태 체크는 채점 결과(통과/실패)를 보여 주는 것이다. ci.yml은 자동 검사 담당자에게 전달하는 업무 지침서라고 보면 된다.

CI 워크플로 붙이기

템플릿의 starter/workflows/ci.yml이 CI 워크플로다. PR이 열리거나 새 커밋이 올라오면 의존성을 설치하고 pytest -q를 실행한다. 이 파일을 .github/workflows/로 복사해 PR로 main에 넣는다(명령은 부록 A-4). 워크플로 파일은 반드시 .github/workflows/ 아래에 있어야 하고, 교안의 내용과 액션 버전은 임의로 바꾸지 않는다.

🧪 예제[실습 확인] 실제로 해 보니 이 CI는 첫 실행에서 실패했다. 로그는 ModuleNotFoundError: No module named 'app'. CI 러너에서 pytest 명령만 치면 저장소 루트가 import 경로에 들어가지 않기 때문이다. 로컬에서도 pytest만 치면 같은 오류가 재현되는데, python -m pytest로 돌리면 가려진다. ci.yml은 그대로 두고 루트에 pytest.ini(pythonpath = ., testpaths = tests)를 추가해 해결했다. 교안의 명령은 교안 그대로 먼저 실행해 보는 것이 좋다.

이 PR을 열면 PR 안의 ci.yml이 바로 돌기 시작한다. PR 화면 아래쪽 Checks 칸의 test 상태 체크가 노란 점으로 돌다가 초록 체크로 바뀌면 통과다. Details를 누르면 러너에서도 11 passed가 나온 것을 볼 수 있다. 통과를 확인했으면 머지한다.

6. 세 환경과 staging 만들기

5장의 CI는 예시로 적어 둔 동작만 확인한다. 예시로 적지 못한 문제는 사람이 직접 써 봐야 보이는데, 지금은 내가 써 볼 서버가 실제 사용자가 쓰는 서버 하나뿐이라 확인하는 순간 이미 사용자에게 나간 뒤다. 그래서 같은 코드를 먼저 올려 보는 서버를 하나 더 둔다. 이렇게 나눈 실행 장소가 환경이다.

1단계 — staging 전용 LLM API 키. production과 같은 키를 쓰면 staging 테스트 비용이 production 한도를 함께 깎고, 키 하나가 드러나면 두 환경이 함께 위험해진다. LLM 제공사에서 staging용 키를 따로 발급하고 월 사용 한도를 production보다 작게 건다. 키 값이 명령 기록이나 에이전트 대화에 남지 않도록 이 단계는 콘솔에서 직접 한다(Secret Manager에 llm-api-key-staging으로 저장하고, 값은 다시 열어 보지 않는다). 그다음 런타임 서비스 계정 friend-agent-runtime이 이 시크릿 하나만 읽게 한다.

⚠️ 주의실행 전에 명령이 gcloud projects add-iam-policy-binding이 아니라 gcloud secrets add-iam-policy-binding인지 본다. 앞의 것은 프로젝트의 모든 시크릿을 읽을 수 있게 만든다. 이것이 최소 권한 원칙(필요한 대상에 필요한 권한만)이다.

2단계 — staging 서비스 만들기. staging 서버는 처음 한 번만 로컬에서 직접 만든다. 로그인 없이 누구나 열 수 있게 하는 공개 설정은 서비스의 권한 정책을 바꾸는 일이라, 배포 서비스 계정에는 그 권한을 주지 않았기 때문이다. 이후 자동 배포는 코드만 바꿔 넣고 이 설정은 그대로 둔다. 명령은 부록 A-5. 설정의 의미는 다음과 같다.

같은 코드인데 staging에서만 배너가 보이는 이유

staging에 올린 코드는 production과 똑같은 main 코드인데, 주소를 열면 배너가 나타난다. 코드가 아니라 서비스에 넣은 환경변수 ENV가 다르기 때문이다. app/main.py는 화면을 보낼 때 ENV 값을 읽어, 값이 production이거나 local이면 배너를 붙이지 않고 그 밖의 값이면 "테스트 환경 (값)" 배너를 붙인다. 코드는 하나로 두고 환경마다 설정값만 다르게 주는 것이 환경을 나누는 기본 구조다. production에는 ENV=production이 들어가야 배너가 없고 개발용 "이번 턴" 패널 정보도 사용자에게 나가지 않는다.

⚠️ 주의[실습 확인] 1단계에서 "staging 전용 키와 낮은 한도"를 따로 만들 수 없는 경우가 있다. 수업에서 받은 키는 발급 계정이 따로 있어서, 내 계정에서 새 키·한도를 만들 수 없었다. 이때는 기존 시크릿 값을 출력하지 않고 파이프로 llm-api-key-staging에 복사(해시로 같은 값인지 확인)하고, 시크릿 이름과 읽기 권한만 환경별로 분리했다. 환경 구조는 그대로 연습되지만 비용·한도는 production과 공유한다. Windows에서는 프로세스 치환(<(...))이 지원되지 않아 표준 입력 파이프(| ... --data-file=-)를 써야 한다.

3단계 — GitHub 환경과 배포 승인. GitHub Environments는 환경마다 변수와 배포 규칙을 따로 두는 기능이다. staging에는 서비스 이름(SERVICE)과 ENV 값만 넣고, production에는 여기에 승인자(Required reviewers)를 더한다. 승인자가 있는 환경의 배포는 승인 전까지 기다린다. 공개 저장소에서는 무료이고, 혼자 하는 실습이라 승인자는 나 자신(prevent_self_review: false)으로 둔다. 저장소 공통 변수 5개는 건드리지 않는다. 명령은 부록 A-6.

환경SERVICEENV승인
stagingfriend-agent-stagingstaging없음

⚠️ 주의[실습 확인] 저장소가 비공개이면 승인자(Required reviewers) 설정이 HTTP 422 ... billing plan supports the required reviewers protection rule로 거절된다. 승인자와 브랜치 보호는 비공개 저장소에서는 유료 플랜 기능이라서다. 교재가 "공개 저장소에서는 무료"라고 한 이유다. 공개로 전환하기 전에 저장소 전체와 커밋 기록에 키가 없는지(키 패턴 검색, .env가 커밋된 적이 없는지) 확인한다. 전환 직후 한 번은 API가 PRIVATE으로 응답했고 잠시 뒤 PUBLIC이 됐으니, 거절되면 다시 확인한다. 또 production 승인 버튼은 처음 누른 것이 반영되지 않아 다시 눌러야 했다. 승인이 반영되면 pending_deployments가 비고 deploy 작업이 시작된다.

4단계 — 환경을 나누는 배포 워크플로. 템플릿의 starter/workflows/deploy-envs.yml은 staging 또는 main 브랜치에 커밋이 들어오면 먼저 ci.yml의 테스트를 불러 돌리고(needs: test), 통과해야 배포 작업을 시작한다. 배포 작업은 브랜치가 main이면 production, 아니면 staging 환경으로 실행되고, 서비스 이름과 ENV는 그 환경의 변수에서 읽는다. staging 브랜치를 만들고 이 파일로 .github/workflows/deploy.yml을 바꾸는 PR을 올린다(명령은 부록 A-7).

⚠️ 주의실행 전에 PR 대상이 main이 아니라 staging인지 본다. 이 단계에서는 PR만 만들고 아직 머지하지 않는다.

5단계 — staging에 머지해 배포 확인. 4단계 PR의 상태 체크가 통과하면 staging에 머지한다. 머지하는 순간 새 배포 워크플로가 처음으로 돌아 test 작업 → deploy 작업(staging 환경) 순으로 진행되고 friend-agent-staging만 새 커밋으로 바뀐다. 확인은 세 가지다: ① Actions 탭에서 deploy가 staging 환경으로 돌았는가, ② staging 주소 끝에 /version을 붙여 commit이 방금 머지한 커밋 SHA로 바뀌었는가, ③ production 주소의 /version은 바뀌지 않았는가.

6단계 — main에 머지하고 production 승인. staging을 그대로 main으로 보내는 PR을 올리고, 상태 체크가 통과하면 머지한다. 이번에는 deploy 실행이 deploy 작업 앞에서 멈추고 Review deployments 버튼이 나타난다. production 환경에 승인자를 걸어 두었기 때문이고, 승인 전까지 production은 바뀌지 않는다. 이 PR을 머지할 때는 staging 브랜치를 지우지 않는다(앞으로도 모든 변경이 staging을 거쳐 main으로 가기 때문). 배포 승인은 에이전트에게 맡기지 않고 GitHub 화면에서 직접 누른다. 끝나면 production /version의 commit이 staging과 같은 커밋인지, 화면 위에 배너가 없는지 확인한다.

7. PR로만 바뀌는 브랜치 — 브랜치 보호

지금까지 만든 품질 게이트에는 아직 빈틈이 두 군데 있다.

  1. 상태 체크가 실패해도 머지 버튼이 눌린다(5장에서 확인).
  2. PR을 거치지 않고 git push로 main에 바로 올리면 CI 테스트 자체가 돌지 않는다.

브랜치 보호 규칙은 이 두 길을 막는다. staging과 main은 PR로만 바꿀 수 있고, PR의 test 상태 체크가 통과해야 머지할 수 있게 한다.

🧪 예제[해설서 비유] main은 고객에게 나가는 최종 문서, staging은 공개 전 검토용 문서, PR은 검토 요청 절차, test는 문제없는지 확인하는 검사다. 보호 규칙은 정해진 절차를 거치지 않으면 문서를 바꿀 수 없게 하는 규칙이다.

⚠️ 주의"PR 필수"와 "테스트 통과 필수"는 서로 다른 규칙이다. PR만 필수로 하면 테스트가 실패해도 머지할 수 있고, 테스트만 요구하면 PR 없이 직접 변경하는 길이 남는다. 두 규칙을 함께 걸어야 한다.

설정은 gh api로 하거나(부록 A-8) GitHub 화면(Settings → Branches → Add classic branch protection rule)에서 한다. 화면에서 할 때는 Require a pull request before merging(승인은 끄고) → Require status checks to pass before merging(test 추가) → Do not allow bypassing the above settings를 켜고 저장한 뒤 staging에도 같은 규칙을 만든다.

  • 상태 체크 목록에 test가 없다면 아직 CI가 한 번도 돌지 않은 것이니, 5장의 CI가 돈 뒤에 설정한다.
  • 설정이 끝나면 main에서 아무 파일이나 고쳐 git push를 시도해 본다. 보호된 브랜치라는 메시지와 함께 거절되면 성공이다. 거절된 커밋은 git reset --hard origin/main으로 지우되, 지우기 전에 main 브랜치에서 실행하는지, 어떤 변경이 사라지는지 확인한다(해설서는 작업 중인 변경을 먼저 백업하거나, 우선 설정 화면 확인만 하는 편이 안전하다고 덧붙인다).
📌 요약이제 변경은 ① PR을 열고 → ② test를 통과해야만 → ③ 머지되고 → ④ 배포·승인으로 이어진다. 코딩 에이전트가 파일을 고치더라도 검사에 실패한 코드는 중요한 브랜치에 들어가지 못한다.

8. CI 테스트에 걸린 PR 고치기

템플릿 starter/incidents/의 일부러 망가뜨린 변경 세 개(A~C)를 PR로 올려, 상태 체크가 실패한 화면과 Actions 로그만 보고 무엇이 깨졌는지 찾는다. 문제마다 같은 순서다.

  1. staging에서 작업 브랜치를 만들고 패치를 적용해 커밋한 뒤 staging으로 PR을 올린다.
  2. PR 화면의 상태 체크와 Actions 로그에서 실패한 테스트 이름과 실패 메시지를 찾는다.
  3. 그 테스트가 확인하는 동작과 바뀐 줄(Files changed)을 이어서 원인을 한 문장으로 적는다.
  4. 머지 버튼이 막혀 있는지 확인하고, PR을 닫고 브랜치를 지운다.
💡 팁코딩 에이전트에게 맡길 때의 공통 지시는 "Actions 로그를 근거로 어느 테스트가 왜 실패했는지와 바뀐 줄이 그 동작을 어떻게 바꿨는지 설명해 줘. 아직 고치지 마."이다. 추측해서 고치는 것이 아니라 실패한 테스트와 실제 변경된 코드를 연결해 원인을 설명하는 것이 목적이다.

staging에서만 보이는 문제 — 문제 D

A~C는 모두 CI가 머지 전에 막아 준 변경이다. 이번에는 CI를 통과해 staging까지 가는 변경을 하나 올려, 사람이 직접 써 봐야 보이는 문제가 있다는 것을 확인한다.

문제 D — 보내기 버튼이 사라진 변경. 화면 코드 static/index.html에서 보내기 버튼 스타일 .send{...} 중괄호 안에 display:none;을 넣고 staging으로 PR을 올린다. 테스트는 화면 모양을 확인하지 않으므로 상태 체크는 통과하고, 브랜치 보호가 걸려 있어도 머지할 수 있다. 머지하면 staging에 배포되니, staging 주소를 열어 입력창 옆 보내기 버튼이 보이는지 확인한다. 버튼이 사라진 것을 확인했으면 production으로 보내지 않고, 그 머지를 되돌리는 Revert PR을 staging으로 올려 머지한다. staging에 버튼이 돌아오면 끝이다. 이 변경은 main으로 PR을 올리지 않는다.

게이트잡는 것놓치는 것
CI 테스트예시로 적어 둔 동작(위기 응답 109, 약속 시각 08:00, 날씨 도구 선택 등)화면 모양, 말투, 실제 LLM 답
staging(사람)버튼 사라짐, 어색한 말투, 실제 LLM의 답아무도 열어 보지 않은 부분
배포 승인(사람)승인 전 마지막 확인 — staging과 같은 커밋인지(/version), 지금 production에 내보내도 되는 시점인지승인자가 확인하지 않은 부분
🧪 예제[실습 확인] 문제 D의 PR은 test·hello 모두 통과(CLEAN)했고 보호 규칙이 있어도 머지됐다. 머지 후 staging에서 .send 버튼의 display가 none이고 화면에 보이지 않았으며 production은 그대로였다. 되돌릴 때는 PR #17의 머지 커밋을 되돌리는 것이라 부모가 둘이어서 git revert -m 1 <머지 커밋>이 필요했다(그냥 git revert는 오류). Revert PR을 머지하자 display가 block으로 돌아왔다.
📌 요약이 변경은 CI를 통과했지만 staging을 열어 본 사람에게는 바로 보였다. staging이 없었다면 같은 변경이 production에서 사용자에게 먼저 발견되었을 것이다. 해설서의 답: 이를 CI에서 미리 막으려면 "보내기 버튼이 화면에 보이는지"를 확인하는 자동 브라우저 테스트가 더 필요하다. 자동 테스트와 사람의 확인은 대체 관계가 아니라 보완 관계다.

9. 과제 고르기

아래 세 과제 중 하나 이상을 고른다. 위에서부터 차례로 어려워지며, 어느 과제든 작업 브랜치에서 시작해 PR로 올리고 상태 체크가 통과하는 것까지 확인한다.

과제내용다 했는지 확인하는 방법
기본docs/examples.md의 예시 중 판정 방법이 코드이고 tests/에 아직 테스트가 없는 것 하나를 테스트 케이스로 추가(페이크 LLM). 옮긴 뒤 동작을 일부러 깨뜨려 실패하는지도 확인새 테스트가 로컬 pytest와 CI에서 모두 통과하고, 테스트 위 주석에 예시 번호가 적혀 있다
중간배포 성공/실패, 환경 이름, 커밋 SHA를 Discord·Slack 채널로 알리는 단계를 배포 워크플로 끝에 추가(앞 단계가 실패해도 실행)staging 머지 시 성공 알림이 오고, 일부러 실패시킨 배포에서도 실패 알림이 온다. 워크플로 파일에 웹훅 주소가 없다
도전내 앱 저장소에 테스트 하나와 CI 워크플로를 붙인다. 먼저 "이런 입력에는 이렇게 나와야 한다" 예시 하나를 적고 정한다PR을 올리면 CI가 돌고, 그 동작을 일부러 망가뜨린 PR에서는 CI가 실패한다
  • "AI 판단"으로 갈리는 예시("답이 다정한 말투다")는 페이크 LLM 테스트로 옮길 수 없다. 코드로 판정할 수 있는 예시만 옮긴다.
  • 중간 과제의 웹훅 주소는 비밀번호처럼 다룬다. 그 주소만 알면 누구나 채널에 글을 쓸 수 있다. 워크플로 파일에 쓰지 않고 gh secret set DEPLOY_WEBHOOK_URL로 저장소 Secrets에 넣는다(실행하면 값을 입력받으므로 명령 기록에 값이 남지 않는다). 워크플로에서는 이름으로만 읽는다.
  • 도전 과제에서는 외부 API를 실제로 부르는 테스트는 만들지 말고, 만들 파일 목록을 먼저 보게 한다.

AI 서비스·1인 컨설팅에 연결하기 (해설서의 적용)

  1. 고객 요구사항을 "잘 작동해야 한다"가 아니라 "이 입력에는 이 결과가 나와야 한다"로 바꾼다.
  2. 자동 테스트로 반복 검증할 문제와 사람이 봐야 할 문제를 구분한다.
  3. 코딩 에이전트에게 수정과 PR 생성을 맡기더라도 검증 기준과 머지·승인 권한은 분리한다. "코드를 고쳐 줘"만으로는 부족하고, 바꿀 수 있는 범위와 반드시 통과할 검증 조건을 함께 정한다.
  4. 예: 고객 문의를 분석하는 컨설팅 에이전트라면 dev(프롬프트·보고서 코드 수정) → CI(입력 검증·데이터 처리·보고서 구조 자동 테스트) → staging(실제 고객 사례와 비슷한 샘플로 품질 확인) → production 승인(고객에게 줘도 되는지 최종 검토). 이 절차는 여러 고객 프로젝트에서 재사용할 수 있다.

증상원인해결
로컬 pytest는 통과하는데 CI에서만 실패로컬은 한국 시간(KST), CI 러너·Cloud Run은 UTC. 시간대가 빠진 시각이 로컬에서만 우연히 맞게 읽힘실패 로그 FAILURES의 E 줄을 읽고 시간대 처리를 고침. 로컬에서도 TZ=UTC pytest -q로 재현(Windows PowerShell은 CI 결과로 확인)
시간대 버그 PR인데 CI가 통과함main에 tests/test_reminder_time.py가 아직 없음4-4단계(테스트 파일 PR 머지)를 먼저 마친다
기존 테스트가 시간대 버그를 못 잡음test_reminder_is_saved_with_timezone은 "시간대 정보가 붙어 있는가"만 보고, 저장소가 실행 컴퓨터의 시간대를 다시 붙여 줌사용자가 보는 값(08:00)을 확인하는 테스트로 바꿈
상태 체크가 실패했는데 머지 버튼이 눌림CI는 결과만 보여 줄 뿐 머지를 막지 않음브랜치 보호 규칙의 필수 상태 체크(test) 설정(7장)
git push로 main에 바로 올라감 / CI 없이 변경됨PR 필수 규칙이 없음브랜치 보호에서 Require a pull request 활성화

보호 규칙이 있는데 관리자 본인은 직접 push가 됨enforce_admins가 꺼져 있음enforce_admins: true / "Do not allow bypassing" 활성화

Q1. 에이전트 서비스의 테스트에서 실제 LLM API 대신 페이크 LLM을 쓰는 이유로 가장 알맞은 것은?

① 페이크 LLM이 실제 LLM보다 답을 더 잘 만들기 때문이다 ② 실제 LLM API는 비용이 들고 느리며, 같은 메시지에도 답이 달라서 통과와 실패를 판정할 수 없기 때문이다 ③ 테스트에서는 LLM API 키를 쓸 수 없도록 GitHub이 막기 때문이다 ④ 페이크 LLM을 쓰면 LLM 답의 품질까지 함께 확인할 수 있기 때문이다

정답: ② 페이크 LLM은 답을 더 잘 만드는 것이 아니라 정해진 규칙대로만 답해서 테스트를 안정적으로 만든다. 답의 품질은 staging에서 사람이 확인한다.

Q2. 템플릿의 test_reminder_is_saved_with_timezone은 약속 시각에서 시간대를 빼는 패치를 넣은 뒤에도 통과했습니다. 이 테스트를 버그를 잡는 테스트로 바꾸려면 무엇을 확인하게 해야 할까요?

① 약속이 하나 이상 저장되었는지 ② 저장된 시각에 시간대 정보가 붙어 있는지 더 엄격하게 ③ "내일 아침 8시"로 부탁한 약속이 사용자에게 08:00으로 보이는지 ④ 테스트가 2초 안에 끝나는지

정답: ③ 내부 형식(시간대 정보 유무)이 아니라 사용자가 보는 결과를 확인해야 버그가 잡힌다.

Q3. staging 브랜치에 머지한 변경이 friend-agent-staging에만 배포되고 friend-agent에는 배포되지 않은 이유로 가장 알맞은 것은?

① staging 서비스가 production 서비스보다 먼저 만들어졌기 때문이다 ② 배포 작업이 브랜치에 따라 staging 환경으로 실행되고, 서비스 이름을 그 환경의 SERVICE 변수에서 읽기 때문이다 ③ staging 브랜치에는 테스트가 없어서 production 배포가 건너뛰어졌기 때문이다 ④ production 환경에 승인자가 있어서 staging 브랜치의 변경도 함께 기다리고 있기 때문이다

정답: ② ①은 배포 대상을 정하는 기준이 아니고, ③ staging에도 CI 테스트가 돈다. ④ 승인 규칙은 production 배포에만 적용된다.

Q4. 로컬에서 그냥 pytest를 돌리면 통과하던 시간대 변경이 CI에서는 실패했습니다. 가장 알맞은 이유는?

① CI 러너의 파이썬이 더 엄격해서 ② 로컬은 한국 시간이라 시간대가 빠진 시각이 우연히 맞게 읽히고, 러너는 UTC라 9시간 어긋난 값이 저장되어서 ③ GitHub이 테스트 파일을 임의로 바꿔서 ④ CI에서만 실제 LLM을 호출해서

정답: ② 같은 코드가 실행 환경의 시간대에 따라 다른 결과를 낸다. 08:00이 17:00으로 저장된 것이다.

Q5. 상태 체크가 실패한 PR의 머지 버튼이 눌리는 것을 막으려면 무엇이 필요한가요?

① CI 파일을 더 길게 쓴다 ② 브랜치 보호 규칙에서 test를 필수 상태 체크로 지정한다 ③ PR 제목에 "머지 금지"를 쓴다 ④ 러너를 UTC가 아닌 시간대로 바꾼다

정답: ② CI는 실패를 알려 줄 뿐이고, 머지를 막는 것은 브랜치 보호의 필수 상태 체크다. PR 필수 규칙과 함께 걸어야 PR 우회 경로까지 막힌다.

Q6. 보내기 버튼이 사라진 변경은 CI를 통과하고 staging에서 발견되었습니다. 이 변경을 CI에서 미리 막으려면 무엇이 더 필요할까요?

(주관식) 모범 답안: 화면에 보내기 버튼이 존재하고 사용자에게 보이는지 검사하는 자동 테스트(예: 브라우저 테스트)가 필요하다. 이 테스트를 CI에서 돌리면 버튼을 숨기는 변경이 PR 단계에서 실패해 staging에 도달하기 전에 막힌다.

Q7. production 배포 승인을 코딩 에이전트에게 맡기지 않고 직접 누르는 이유와, 승인 전에 확인할 것은?

(주관식) 모범 답안: 승인은 사람이 마지막으로 확인하는 게이트라 에이전트가 대신하면 게이트의 의미가 사라진다. 승인 전에 production /version이 아니라 staging의 /version 커밋을 확인하고(승인할 커밋이 staging에서 검증한 커밋과 같은지), 지금 production에 내보내도 되는 시점인지 확인한다. 승인 후에는 production /version이 staging과 같은 커밋으로 바뀌었는지, 화면에 배너가 없는지 본다.

Q8. staging 서비스를 만들 때 --update-secrets 값에서 반드시 확인할 것은?

(주관식) 모범 답안: 서비스 이름이 friend-agent-staging인지, 연결하는 시크릿이 llm-api-key-staging처럼 -staging 쪽인지 확인한다. 이름을 잘못 쓰면 production 서비스의 설정이 바뀌고, staging이 production 키를 써서 비용·위험이 공유된다.

📌 요약이번 강의의 핵심: ① 자동 배포는 맞는지 확인하지 않는다 ② CI는 사용자 기준 동작(08:00)을 서버와 같은 환경(UTC)에서 반복 확인한다 ③ staging은 사람이 화면·말투·실제 LLM 답을 먼저 확인한다 ④ 브랜치 보호와 직접 누르는 배포 승인이 그 검사를 우회하지 못하게 한다.
