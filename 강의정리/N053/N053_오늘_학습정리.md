# N053 오늘 학습 정리 — 새 버전을 올려도 사용자가 끊기지 않게 하기

> 2026-10-29 · 강의 N053 「Cloud Run으로 무중단 배포하기」와 오늘 실습(3~7장)을 내 방식으로 한 장에 정리했다. 28년 기획·경영 경험에 빗대 쓰고, 숫자는 오늘 실습 기록에서 가져왔다. 확인하지 못한 것은 "추정"이라고 적었다.

## 오늘의 한 문장

> 📌 **요약** — 안전한 배포는 **새 버전을 올리는 일**과 **사용자에게 보내는 일**을 나누고, 보내기 전에 **검증**하고, 문제가 생기면 **바로 되돌릴 수 있게** 해 두는 것이다. 배포가 성공했다는 신호는 "사용자가 오류를 안 봤다"는 증거가 아니다.

## 1. 일곱 가지로 줄이면

| 오늘 배운 것 | 경영에 빗대면 | 오늘 내가 본 숫자 |
|---|---|---|
| **리비전과 트래픽 설정** — 배포할 때마다 한 벌(리비전)이 생기고, 요청을 어느 리비전에 몇 % 보낼지 따로 정한다 | 신제품 라인을 기존 라인과 **병행 가동**하고, 물량 배정표만 바꾸는 것 | 0% → 100% 전환 중 요청 실패 0건(staging) |
| **스타트업 프로브 `/health`** — 새 인스턴스가 정말 준비됐는지 묻는 검사. 기본값은 포트만 본다 | 신규 공장의 **시운전 합격 판정**. 전등이 켜졌다고 생산을 시작하면 안 된다 | 기본 프로브: 준비가 늦은 버전에서 503 54건 / `/health` 프로브: 0건(대신 배포가 더 오래 걸림) |
| **0% 배포와 태그 URL** — 새 리비전을 사용자에게 안 보낸 채 올리고, 전용 주소로 먼저 열어 본다 | 출시 전 **시제품 샘플 검수**. 새 메뉴를 만드는 일과 파는 일을 나눈다 | 태그 URL은 새 리비전, 원래 주소는 이전 리비전이 답함 |
| **트래픽 고정** — 롤백·카나리 뒤 특정 리비전에 박혀서 새 배포가 사용자에게 안 간다 | 업무 이관을 "최신 담당자에게"가 아니라 **"김 대리에게"라고 이름을 박아** 둔 지시 | 배포는 성공했는데 사용자는 옛 리비전(`--to-latest`로 풀기) |
| **머지 한 번 배포 자동화** — 0% 배포 → 스모크 테스트 → 통과해야 전환 | **결재선의 게이트**. 검증이 실패하면 다음 단계가 나가지 않는다 | 망가진 버전은 스모크 테스트에서 멈췄고 요청 735건 실패 0건 |
| **원클릭 롤백** — 버튼 하나로 이전 리비전으로 | **철수 기준을 미리 정해 둔** 비상 스위치 | production 15초. 단, 직후 약 9초 동안 4건 실패(콜드 스타트 **추정**) |
| **측정과 기록** — 숫자는 나온 대로 적는다 | 보고서의 **근거 자료**. 결과를 보고 기준을 바꾸지 않는다 | 첫 측정 6건 실패 → 깨워 둔 재측정 0건. 둘 다 기록 |

## 2. 가장 오래 남을 세 장면

1. **"배포 성공" 뒤에 54건이 실패했다.** 준비가 30초 늦는 버전을 기본 프로브로 배포하자 배포 명령은 성공으로 끝났는데 사용자 요청은 약 21초 동안 503이었다. `/health` 프로브로 바꾸면 같은 조건에서 0건이 됐다. 대가는 배포 시간이었다(27초 → 약 84초). **사용자가 오류를 보는 것보다 배포가 늦는 편이 낫다**는 판단이다.
2. **검증이 틀린 곳을 보면 아무것도 증명하지 못한다.** 새 리비전이 0%인 동안 원래 서비스 주소는 이전 리비전이 답한다. 스모크 테스트를 원래 주소로 하면 망가진 새 버전도 통과한다. 그래서 **태그 URL**을 본다. 일부러 `/version`의 커밋을 틀리게 만든 버전은 CI를 통과했지만 스모크 테스트가 전환을 막았다.
3. **롤백은 배포보다 약하다.** 배포 전환은 `/health` 프로브가 준비될 때까지 기존 리비전이 답해서 0건이었는데, 롤백은 준비 확인 없이 곧바로 트래픽을 옮겨 직후 몇 초가 가장 약했다. 되돌아갈 리비전이 한동안 쉬어 인스턴스가 줄어 있었던 것으로 추정한다(확인하지는 못했다).

## 3. 오늘 막혔던 곳 — 같은 교훈이 두 번 나왔다

- **로그인 실패**: 연결 명령이 성공했는데 화면에 "로그인을 시작하지 못했습니다"가 떴다. 저장된 키의 글자 구조를 확인하니 `sb_publishable_`이 두 번 붙어 있었다.
- **프로브 경로**: Git Bash가 `/health`를 `C:/Program Files/Git/health`로 바꿔 저장했다. 실험을 세 번 돌렸다.
- 두 일 모두 "명령이 성공했다"는 출력만 봤을 때는 몰랐고, **저장된 값을 조회**하고서야 원인이 보였다. 앞으로는 실행한 뒤 **저장된 값을 다시 읽어 본다.**

## 4. 시작 질문 다시 보기

교안의 시작 질문은 "한 번에 전환할 때와 10%만 보낼 때 문제 발견과 피해 범위가 어떻게 다른가"였다. 오늘 배운 것을 더하면 답이 이렇게 바뀐다.

- 한 번에 전환은 피해가 전체에 가지만, **0%로 올려 미리 확인하면** 한 명도 피해를 안 본다.
- 10% 카나리는 피해를 줄이지만 **요청이 적으면** 판단 근거가 약하다(하루 30건이면 10%는 약 3건). 요청이 적은 지금 서비스는 블루그린이 맞다.
- 어느 쪽이든 **롤백 기준은 배포 전에 정하고**, 롤백 직후의 약한 구간까지 계산에 넣는다.

## 6. 아직 모르는 것 (확인하지 못한 것)

- 롤백 직후 4건 실패의 정확한 원인(콜드 스타트 추정), 배포 시간이 교안의 "30초쯤"보다 훨씬 길었던 이유
- 카나리 각 단계의 실제 비율(스크립트가 응답 리비전이 바뀔 때만 기록해 세지 못했다)
- 배포 서비스 계정의 역할이 오늘 아침과 같은지(아침에 기록을 남기지 않았다)
- 스키마가 바뀌는 배포를 직접 시험하는 것(확장 → 호환 코드 → 코드 전환 → 정리는 아직 이론)
