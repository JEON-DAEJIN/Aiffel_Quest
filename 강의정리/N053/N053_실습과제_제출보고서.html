2-2. staging 연결과 막힌 곳 — publishable key 접두사 중복

  1. 사용자가 PowerShell에서 연결 명령을 실행했다. 첫 시도는 <staging 프로젝트 URL> 자리 표시를 통째로(꺾쇠 포함) 바꾸지 않았고, 쉼표가 들어간 값을 따옴표로 감싸지 않아(Claude의 안내가 틀렸다) unrecognized arguments로 실패했다. 변수($URL, $KEY)를 쓰고 값을 큰따옴표로 감싸는 방식으로 바꿨다.
  2. 두 번째 시도는 명령이 성공했다(리비전 friend-agent-staging-00012-2l9, /version에 storage: supabase). 그러나 브라우저에 "로그인을 시작하지 못했습니다" 창이 떴다(증거 03).
  3. Claude가 서비스에 저장된 키를 값은 출력하지 않고 글자 구조만 확인했다: 길이 61, sb_publishable_이 두 번 이어져 있었다. 같은 키로 Supabase 익명 가입 요청을 보내면 401이었다. 원인은 복사한 값에 이미 들어 있는 접두사를 $KEY = "sb_publishable_…"에 한 번 더 쓴 것이다(Claude의 예시가 오해를 만들었다). 익명 로그인 설정 문제가 아니었다.
  4. 사용자가 키를 다시 넣고 $KEY.Length로 확인(처음 32, 다시 46)한 뒤 재실행했다 → 리비전 00013-fs2. Claude가 저장된 값을 조회해 길이 46·접두사 1회, 익명 가입 요청 200을 확인했다. 중간에 사용자가 붙여 준 출력은 이전 실행(00012)의 글이었고, 실제 상태는 조회로 확인했다.

⚠️ 주의 — 교안 부록 B의 "로그인을 시작하지 못했습니다" 원인은 익명 로그인이 꺼져 있는 것이다. 이번 원인은 달랐다(키 접두사 중복). 같은 증상에서도 먼저 저장된 값의 구조(길이·접두사)를 조회해 보면 원인을 빨리 가른다.

11. 궁금했던 것

아래는 실습 중 사용자(DJ)가 실제로 한 질문이다(말투는 줄여 옮겼다). 진행기록에는 답변 원문이 남아 있지 않아, 각 질문과 연결되는 진행기록의 확인·결정을 요약했다.

Q1. "이건 이미 지난 시간에 한 것 아닌가?"

  • 지난 강의(N052)의 블루그린은 내 컴퓨터의 Docker·Nginx에서 직접 로드밸런서를 세운 것이고, 이번에는 같은 일을 Cloud Run이 맡는 구조에서 한 뒤 PR 머지 한 번으로 자동화했다. 또 시작 점검(1절)에서 Cloud Run 서비스에 Supabase 연결·시크릿이 없다는 것이 확인되어, 지난 시간 결과를 그대로 쓸 수 없는 부분(3장)부터 실습하기로 범위를 정했다. 지난 시간에 한 것이 이미 활용된 곳은 staging용 Supabase 프로젝트 하나였다.

Q2. "승인 없이 실행하는 게 과제 목적에 맞는가?"

  • rollback 워크플로에 production 승인을 붙일지의 문제로 정리했다(6-2절). 이 저장소는 본인 한 명이 승인자이자 실행자라 승인은 보호보다 지연이 크다고 보고 입력 형식·서비스 소속·Ready 검사를 안전장치로 두는 쪽을 사용자가 선택했다. 과제 문구가 이 선택을 직접 따져 정하라는 것이라 어느 쪽도 맞고, environment: production을 붙이면 바로 승인이 걸린다고 답했다.

Q3. 꺾쇠 <>도, 큰따옴표도 지워야 하나?

  • 자리 표시는 꺾쇠까지 포함해 통째로 실제 값으로 바꾼다. 첫 시도가 실패한 이유 중 하나가 <staging 프로젝트 URL> 자리 표시를 통째로 바꾸지 않은 것이었다(2-2절). 값 자체는 PowerShell에서 큰따옴표로 감싸고 변수($URL, $KEY)에 담아 쓰는 방식으로 바꿨다.

Q4. "staging 익명 로그인은 어디서 확인하나?"

  • Supabase 대시보드의 Authentication > Sign In / Providers에서 Allow anonymous sign-ins를 본다(교안 부록 B). 이번에는 Claude가 대시보드를 보지 않고 서비스에 설정된 키로 익명 가입 요청을 보내 200과 세션 토큰이 돌아오는 것으로 켜져 있음을 확인했다(2-1절).

Q5. "URL은 어디서 찾나?"

  • Supabase 프로젝트 URL은 각 프로젝트의 Project Settings > API Keys에서 찾는다(교안 3-4). URL 값은 보고서에 적지 않았다. Cloud Run 서비스 주소와 태그 URL은 서비스 조회(status.traffic[].url)로 얻는 값을 쓰는 편이 안전하다(4-1절).
