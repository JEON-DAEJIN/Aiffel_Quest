### 5-1. 막힌 곳 — 실험 ③을 세 번 돌린 이유

1. **첫 실행(무효)**: Git Bash가 `--startup-probe=httpGet.path=/health`의 `/health`를 윈도 경로로 바꿔, 서비스에 저장된 프로브 경로가 `C:/Program Files/Git/health`가 됐다(조회해서 발견, N052의 `MSYS_NO_PATHCONV` 함정과 같은 종류). 그런데도 이 상태에서 실패 0건·배포 약 65초가 나왔다. 왜 그랬는지는 확인하지 않았다(앱이 알 수 없는 경로에도 200으로 답했을 **가능성**). 근거로 쓰지 않고 로그만 `10_측정3_잘못된경로_GitBash변환.log`로 보존.
2. **두 번째(무효)**: `MSYS_NO_PATHCONV=1`을 켜자 이번에는 `gcloud`의 bash 래퍼가 자기 파이썬 파일 경로(`C:\c\Users\…\gcloud.py`)를 못 찾아 **배포가 실행되지 않았다**. 서비스는 그대로 `00017`·잘못된 경로. 로그는 `11_측정3_재실행_무효_gcloud경로오류.log`로 보존.
3. **세 번째(유효)**: `MSYS2_ARG_CONV_EXCL="--startup-probe"`로 그 옵션 하나만 변환에서 제외 → 저장된 프로브가 `httpGet.path=/health`임을 조회로 확인. 위 표의 ③은 이 실행 값.

> 교훈: Git Bash에서 `/`로 시작하는 옵션 값은 변환될 수 있으니 실행 후 **저장된 값을 조회해** 확인한다. 변환 전체를 끄면 `gcloud` 래퍼가 깨질 수 있어 해당 옵션만 제외한다(`MSYS2_ARG_CONV_EXCL`). PowerShell에서는 이 문제가 없다.

## 7. 5장 — 블루그린·롤백·카나리·트래픽 고정 (staging, 2026-10-29) [에이전트]

### 7-1. 0% 배포와 태그 URL

- 시작: `friend-agent-staging-00020-dc2`가 `latestRevision: true`로 100%.
- `gcloud run services update … --update-env-vars "BANNER=GREEN" --no-traffic --tag green` → 새 리비전 `00021-fup`이 0%, 태그 URL 생성. **배포 직후 100% 줄에서 `latestRevision: true`가 사라지고 `00020`에 고정**됨(`--no-traffic`의 부수 효과).
- 태그 URL `/version`: `00021-fup`, `banner: GREEN`. 원래 서비스 주소 `/version`: `00020-dc2`, `banner: ""`. 태그 URL `/health`: 200 `{"status":"ok"}`.
- 태그 URL은 두 형식 모두 열렸다: ① 조회(`status.traffic[].url`)가 돌려준 `https://green---<서비스>-<해시>-uc.a.run.app` ② 서비스 주소(프로젝트 번호 형식) 앞에 `green---`만 붙인 주소. 워크플로에서는 조회로 받은 값을 쓰는 편이 안전하다(형식이 바뀌어도 따라감).

### 7-3. 카나리 10% → 50% → 100% (로그 14) — 요청 503건, 실패 0건

- 설정: `--to-tags green=10`(`00020` 90 / `00021` 10) → `green=50` → `green=100`. 단계 사이 약 55~65초.
- 응답 수: `00020` 280건(56%), `00021` 223건(44%). 단계별 머문 시간(0%·10%·50%·100% 순으로 24·66·65·44초)으로 계산한 기대값은 약 42%로 관찰값과 비슷하다.
