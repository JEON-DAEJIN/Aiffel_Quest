## 2. Ch01 — 오리엔테이션: 과제 선정

학습서 Ch01은 "자주 쓰는 AI 서비스나 직접 만들어 본 AI 기능 하나를
떠올려, 사용자는 그 기능을 어떤 경로로 쓰고 있는지, 버튼 하나를 누르면
내부에서 어떤 호출이 어떤 순서로 일어날지 아는 만큼 적어 보라"는 시작
질문으로 열립니다.

저는 이 질문에 **ASP(AI Story Partner)**를 과제로 선택했습니다.
스토리위즈 대표 시절 "이거 뜨겠습니까?"라는 질문에 명확한 근거로 답하지
못했던 실제 경험에서 출발한 구상으로, 이미 브런치 칼럼 초고(미완)로
콘셉트는 정리해 두었지만 코드도 PRD도 전혀 없는 상태였습니다 — 학습서가
요구하는 다섯 가지 제공 채널 가운데 맞는 것을 고르는 과정(목표 ①)을
처음부터 제대로 밟아볼 수 있는 대상이라 판단했습니다.

## 3. Ch02 — 사용 맥락 분석

### 학습서가 요구한 것

<div class="callout example">

<span class="label">🧪 학습서 원문</span>

"오늘 하루 동안 설계할 AI 기능을 정합니다. ... 대상 사용자 무리 하나를
정하고 표의 다섯 항목을 채웁니다. 실제 사용자에게 확인하지 못한 칸은
'가정'이라고 표시해 두고, 아래 인터뷰와 데스크 리서치로 가정을 하나씩
줄입니다." / "실습: 제공 채널 — 앞에서 정한 사용자와 기능으로 제공 채널
후보를 두 개 고릅니다. 하나는 가장 빨리 사용자에게 써 보게 할 수 있는
채널, 다른 하나는 사용자가 늘었을 때 옮겨 갈 채널입니다."

</div>

### 제가 수행한 결과

1.  **사용 맥락 표 5항목**을 먼저 "가정"으로 채웠습니다(칼럼 초고 근거:
    대상 사용자는 신인 작가일 것).
2.  **데스크 리서치**: 웹 검색으로 ① "지인에게 원고를 보여주기도
    어렵다"는 작가의 글 ② 크몽의 유료 편집자 첨삭 상품 실재를 확인해
    "리서치"로 승격했습니다.
3.  **실제 인터뷰**: "스토리위즈 대표 시절 마지막으로 '이거 뜨겠습니까'
    질문을 받았던 장면"을 직접 질문드려, 다음 답변을 받았습니다 —
    "실제로 작가에게 가져온 파일을 PD가 보고 고민하는 순간, 항상 질문을
    던졌습니다." 이로써 **당초 가정(작가 본인이 자가진단)이 실제
    경험(PD가 내부 판단)과 다르다는 것**이 드러났습니다.
4.  **제공 채널 후보 2개 비교**(학습서 실습 그대로): 후보1 "가장 빨리 쓸
    수 있는 채널"=기성 AI 도구(Claude 프로젝트), 후보2 "사용자가 늘면
    옮겨 갈 채널"=독립형 웹앱. 전환 조건 4가지를 점검한 결과 전부
    미충족이어서, 후보1을 확정했습니다.

<div class="callout tip">

<span class="label">💡 팁</span>

이 단계에서 발견이 3개(대상 사용자, 판단 방식, 예측 포함 여부) 나왔고,
셋 다 제가 임의로 정하지 않고 전대진님께 직접 여쭤 결정을 받았습니다.

</div>

## 4. Ch03 — 처리 방식과 오류 대응

### 학습서가 요구한 것

<div class="callout example">

<span class="label">🧪 학습서 원문</span>

"실습: 내 기능의 처리 방식과 출력 형식을 정하고, 결과가 나오기까지
사용자가 보는 화면이나 메시지를 순서대로 적습니다. 그다음 발생할 수 있는
오류를 세 가지 적고, 영향도(낮음, 중간, 높음)와 대응 장치를 정합니다."

</div>

### 제가 수행한 결과

**처리 방식**: 기성 AI 도구는 대화형이라 본질적으로 **동기 처리**로
확정. 10화 분량처럼 처리 시간이 길어지는 경우의 비동기 처리는 웹앱 전환
시로 미뤘습니다.

**오류 대응**: 학습서는 세 가지 오류를 적으라고 했지만, 저는 **5가지
대응 장치 전체**를 실제 테스트에서 드러난 문제(유사 사례 비교의 근거
약함)에 대조해 점검했습니다.

<div class="table-scroll">

| 장치         | 적용       | 비고                                |
|--------------|------------|-------------------------------------|
| 출처 표시    | ✅         | "확신 없으면 '근거 약함' 명시" 규칙 |
| 폴백         | ✅         | 위 문구 자체가 폴백 응답            |
| HITL         | ✅         | PD가 최종 판단자 — 이미 구조에 내장 |
| 에스컬레이션 | 불필요     | 넘길 담당자가 없음                  |
| 피드백       | PoC는 충분 | 대화로 바로 되물으면 됨             |

</div>

## 5. Ch04 — 코드 없이 검증하기

### 학습서가 요구한 것

<div class="callout example">

<span class="label">🧪 학습서 원문</span>

"직접 확인할 곳: 오즈의 마법사 테스트 진행 — 1. 짝과 역할을 나눕니다...
2. 진행자는 상황 하나만 알려 줍니다... 3. 참여자는 정한 채널로 실제처럼
요청합니다... 4. 진행자는 정한 출력 형식대로 직접 응답을 작성해
돌려주고, 테스트 노트를 채웁니다."

</div>

### 제가 수행한 결과

짝을 지어 진행하는 오즈의 마법사 테스트 대신, 혼자 빠르게 확인할 수 있는
**기성 AI 도구 프로토타입** 방식을 선택했습니다(학습서가 제시한 두 방법
중 상황에 맞는 쪽).

1.  Ch02·03에서 정한 7개 평가 기준을 "약점 발견 → 근거 → 보정 제안" 3단
    구조로 출력하는 **시스템 프롬프트**를 작성했습니다.
2.  실제 로그라인("AI를 배우는 50대 퇴직자가 제한된 AI 노트북을 들고
    회귀하는 기업물")으로 **실제 테스트를 실행**했습니다. 정보가 부족한
    기준은 정직하게 "정보 부족"으로 표시했습니다.
3.  결과를 세 갈래(지침으로 풀리는 문제/채널을 바꿔야 하는 문제/추가
    개발이 필요한 문제)로 나눴습니다 — 6번 기준의 "근거 약함" 문제는 세
    번째로 분류해 파일럿 과제로 넘겼습니다.

<div class="callout summary">

<span class="label">📌 회고</span>

Ch01에서 저는 ASP를 "창작자가 자기 원고를 구조 분석으로 자가진단하는
도구"라고 막연히 그렸습니다. 그런데 Ch02의 인터뷰 한 번으로 **실제
사용자는 작가가 아니라 PD였다**는 것이 드러났고, 제 실제 판단 방식이
"구조 분석"보다는 "흥행실적과 유사 사례 비교"에 가까웠다는 것도 함께
드러났습니다. 이 두 발견 덕분에 최종 설계는 "구조 분석(칼럼 원안)"과
"유사 사례 포지셔닝(실제 경험)"을 결합한 7개 기준으로 완성됐습니다. 처음
생각과 가장 많이 바뀐 지점은 바로 이것입니다 — **AI 기능의 구현보다,
누가 왜 이 도구를 쓰는지를 실제로 확인하는 과정이 설계 전체를
바꿔놓았다는 것**입니다.
