N043 실습 설명자료 — 나만의 딥리서치 에이전트 프로젝트 (한류 콘텐츠 확산)

N043(N042를 나만의 주제로 다시 설계하는 프로젝트)을 논리적으로 상세히 풀어 정리한 문서. 강의의 취지, 실습이 검증하려는 것, 프로젝트에서 실제로 있었던 일, 향후 적용법, 동료에게 설명하는 법 순으로 구성했다.

💡 읽는 법: 코드를 몰라도 끝까지 읽을 수 있게 썼다. 어려운 용어는 그 자리에서 비유로 풀어준다. “개발자용”이라고 표시된 부분은 건너뛰어도 줄거리를 이해하는 데 지장 없다.

1. 이 수업(N043)의 취지 — 코드를 베끼는 게 아니라 설계 판단을 직접 내리는 것

N043은 완성된 코드를 따라치는 수업이 아니라, N042에서 배운 “코디네이터+조사관+편집자” 구조(기획→배치→조사→점검→종합→평가)를 나만의 주제로 처음부터 다시 설계해서 제출하는 과제입니다. 목적은 멀티에이전트 코드 자체가 아니라, “무엇을 나눌지·무엇을 보여줄지·무엇으로 판단할지”라는 세 가지 설계 판단을 학습자가 직접 내리게 하는 것입니다.

원문은 이렇게 마무리됩니다: “멀티에이전트를 만드는 것이 아니라, 업무에 필요한 만큼만 분업을 설계한다.”

2. 실습이 알아보고자 한 것

주제를 고를 때 지켜야 할 좋은 주제 3조건: “① 여러 자료가 필요함 ② 자료 총량이 모델이 한 번에 읽을 수 있는 양을 넘음 ③ 문서끼리 연결 관계가 있음.”

목차를 나눌 때는 형식이 아니라 내용으로 나눠야 합니다: “잘못된 예: A→개요 / B→연표 / C→분석 / D→결론… 좋은 방법은 내용으로 나누는 것입니다. 예: A→발생 배경 / B→주요 사건…” — 형식으로 나누면 조사관 전원이 같은 핵심 문서를 중복해서 읽게 됩니다.

대조군 비교의 공정성도 강조됩니다: “팀은 12개 문서를 읽는데 혼자 하는 시스템은 4개만 읽게 해놓고 ’팀이 더 좋았습니다’라고 하면… 상대방의 손발을 묶어 놓고 이긴 것”입니다.

3. 프로젝트에서 실제로 있었던 일 — 버그 5건

주제: “한류 콘텐츠 산업의 확산”

  1. 자료 중복·오염: 위키백과에서 자료를 모을 때 “위키백과란 무엇인가” 같은 허브 문서나, YG엔터테인먼트와 YG 엔터테인먼트처럼 같은 문서가 이름만 살짝 다르게 중복 저장되는 문제가 있었습니다 → 제외 목록과 중복 확인 절차로 정리했습니다.
  2. 시드 오타: 조사를 시작할 문서 제목 중 하나(“사드 배치 논란”)가 실제 위키백과 표제어와 정확히 일치하지 않아서, 프로그램은 에러 없이 “그런 문서 없음”만 반환하고 조용히 그 갈래가 통째로 비어버렸습니다 → 실행 후 특정 절이 부실한 걸 보고 역추적해서 정확한 제목(“대한민국의 사드 배치 논란”)으로 고쳤습니다.
  3. 너무 엄격한 기준: “절 주제와 정확히 겹치는 내용만 요약하라”는 지시가 너무 엄격해서, 9개 질문 중 7개에서 근거율이 0%로 나왔습니다 → “글자 그대로 안 겹쳐도 배경·근거로 도움되면 요약”하도록 기준을 완화했습니다(비교 대상에도 똑같이 적용).
  4. 핵심어가 문서 끝에 숨어있던 문제: 긴 문서에서 앞부분만 잘라 보여주는 방식을 썼는데, 정작 필요한 핵심어(“한한령”)가 문서의 22,763번째 글자(거의 끝부분)에 있어서 놓쳤습니다 → 핵심어 주변을 따로 찾아 발췌하는 방식을 추가했습니다.
  5. 채점 기준이 실제 로직을 모름: “부실하면 이전 결과를 유지한다”는 규칙을 나중에 추가했는데, 채점 프로그램은 이 규칙을 모른 채 그냥 “가장 마지막 결과”만 채점하고 있었습니다 → 실제로 채택된 결과와 채점 대상이 어긋나 있었던 걸 발견하고, 채점 로직이 같은 함수를 공유하도록 고쳤습니다.

4. 앞으로 내 프로젝트에 어떻게 적용하면 되는가

누구나 알아야 할 원칙

  • “오류 없이 끝났다”는 “내가 원하는 자료를 받았다”는 뜻이 아닙니다. 조용히 실패(문서 없음, 너무 엄격한 필터)하는 지점은 에러 로그가 아니라 결과물을 직접 읽어야만 보입니다.
  • 나중에 규칙을 하나 추가하면, 그 규칙을 모르는 다른 부분(채점·로그·데모)이 낡은 채로 남기 쉽습니다. 로직과 평가는 항상 같은 기준을 공유해야 합니다.
  • 한두 번의 실행 결과만으로 “이게 더 낫다”고 단정하지 마세요. 같은 설정으로 여러 번 돌려도 결과가 크게 흔들릴 수 있습니다.

개발자용 체크리스트 (코드를 직접 짤 때만 해당)

  • 목차를 나눌 때 “형식”이 아니라 “내용”으로 나눈다.
  • 시드 문서 제목은 실제 표제어와 정확히 일치하는지 확인한다.
  • 채점 로직과 실제 처리 로직이 같은 함수를 재사용하게 만든다(따로 구현하면 어긋남).

5. 동료에게 어떻게 설명하면 되는가

한 줄 엘리베이터 피치: > “’한류 콘텐츠 확산’을 주제로, 팀장 AI가 케이팝·영화·산업구조·위기대응 네 갈래로 일을 나눠 조사시키고 편집자 AI가 합치는 리서치 시스템을 처음부터 직접 설계했어요. 만드는 중에 코퍼스 오염부터 채점 버그까지 실제 함정 5개를 하나씩 잡아냈어요.”

좀 더 풀어서 설명할 때 순서: 1. “완성 코드를 베끼는 게 아니라, 제 주제로 처음부터 다시 설계하는 과제였어요.” (문제의식) 2. “주제 하나 고르는 것도 조건이 있더라고요 — 자료가 충분히 많고 서로 연결돼야 좋은 주제예요.” (구조) 3. “실제로 돌리다 보니 시드 문서 제목 오타 하나 때문에 한 갈래가 통째로 비어버리는 것도 겪었고요.” (경험담) 4. “제일 크게 배운 건, 오류 없이 끝났다고 안심하면 안 된다는 거예요 — 조용히 실패하는 지점은 결과를 직접 읽어야만 보여요.” (핵심 원칙)
