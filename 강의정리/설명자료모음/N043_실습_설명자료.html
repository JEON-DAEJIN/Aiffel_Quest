1. 이 수업(N043)의 취지 — 코드를 베끼는 게 아니라 설계 판단을 직접 내리는 것

N043은 완성된 코드를 따라치는 수업이 아니라, N042에서 배운 "코디네이터+조사관+편집자" 구조를 나만의 주제로 처음부터 다시 설계해서 제출하는 과제입니다. 목적은 "무엇을 나눌지·무엇을 보여줄지·무엇으로 판단할지"라는 세 가지 설계 판단을 학습자가 직접 내리게 하는 것입니다.

📌 요약

멀티에이전트를 만드는 것이 아니라, 업무에 필요한 만큼만 분업을 설계한다.

2. 실습이 알아보고자 한 것

좋은 주제 3조건: 여러 자료가 필요함 / 자료 총량이 모델이 한 번에 읽을 수 있는 양을 넘음 / 문서끼리 연결 관계가 있음.

💡 팁

잘못된 예: A→개요 / B→연표 / C→분석 / D→결론. 좋은 방법은 내용으로 나누는 것입니다. 예: A→발생 배경 / B→주요 사건. 형식으로 나누면 조사관 전원이 같은 핵심 문서를 중복해서 읽게 됩니다.

⚠️ 주의

팀은 12개 문서를 읽는데 혼자 하는 시스템은 4개만 읽게 해놓고 '팀이 더 좋았습니다'라고 하면… 상대방의 손발을 묶어 놓고 이긴 것입니다.

3. 프로젝트에서 실제로 있었던 일 — 버그 5건

주제: "한류 콘텐츠 산업의 확산"

  1. 자료 중복·오염: YG엔터테인먼트와 YG 엔터테인먼트처럼 같은 문서가 이름만 살짝 다르게 중복 저장 → 제외 목록과 중복 확인 절차로 정리.
  2. 시드 오타: 시작 문서 제목("사드 배치 논란")이 실제 위키백과 표제어와 안 맞아 그 갈래가 통째로 비어버림 → "대한민국의 사드 배치 논란"으로 정정.
  3. 너무 엄격한 기준: "정확히 겹치는 내용만" 요약하라는 지시로 9개 질문 중 7개에서 근거율 0% → 기준을 완화(비교 대상에도 동일 적용).
  4. 핵심어가 문서 끝에 숨어있던 문제: "한한령"이라는 단어가 문서의 22,763번째 글자(거의 끝)에 있어서 놓침 → 핵심어 주변 발췌 방식 추가.
  5. 채점 기준이 실제 로직을 모름: "부실하면 이전 결과 유지" 규칙을 나중에 추가했는데 채점 프로그램은 이를 모른 채 "가장 마지막 결과"만 채점 → 같은 함수를 공유하도록 수정.

4. 앞으로 내 프로젝트에 어떻게 적용하면 되는가

누구나 알아야 할 원칙

  • "오류 없이 끝났다"는 "내가 원하는 자료를 받았다"는 뜻이 아닙니다. 조용히 실패하는 지점은 결과물을 직접 읽어야만 보입니다.
  • 나중에 규칙을 하나 추가하면, 그 규칙을 모르는 다른 부분(채점·로그·데모)이 낡은 채로 남기 쉽습니다.
  • 한두 번의 실행 결과만으로 "이게 더 낫다"고 단정하지 마세요.

개발자용 체크리스트 (코드를 직접 짤 때만 해당)

  • 목차를 나눌 때 "형식"이 아니라 "내용"으로 나눈다.
  • 시드 문서 제목은 실제 표제어와 정확히 일치하는지 확인한다.
  • 채점 로직과 실제 처리 로직이 같은 함수를 재사용하게 만든다.

5. 동료에게 어떻게 설명하면 되는가

🧪 예제

한 줄 엘리베이터 피치: "'한류 콘텐츠 확산'을 주제로, 팀장 AI가 케이팝·영화·산업구조·위기대응 네 갈래로 일을 나눠 조사시키고 편집자 AI가 합치는 리서치 시스템을 처음부터 직접 설계했어요. 만드는 중에 코퍼스 오염부터 채점 버그까지 실제 함정 5개를 하나씩 잡아냈어요."

  1. "완성 코드를 베끼는 게 아니라, 제 주제로 처음부터 다시 설계하는 과제였어요." (문제의식)
  2. "주제 하나 고르는 것도 조건이 있더라고요 — 자료가 충분히 많고 서로 연결돼야 좋은 주제예요." (구조)
  3. "시드 문서 제목 오타 하나 때문에 한 갈래가 통째로 비어버리는 것도 겪었고요." (경험담)
  4. "오류 없이 끝났다고 안심하면 안 된다는 걸, 조용히 실패하는 지점을 직접 찾으며 배웠어요." (핵심 원칙)
