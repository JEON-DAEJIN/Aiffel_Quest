## 1. 배포가 성공했다는 것과 사용자가 오류를 안 봤다는 것은 다르다 — 요청 확인 스크립트 세 실험 {#1}

### 취지

지금까지 여러 번 배포했지만 그 순간 접속한 사용자가 오류를 봤는지는 확인한 적이 없습니다. 새 주방의 전등만 켜졌고 재료는 아직인데 손님을 안내하면 주문이 실패합니다. 이 절은 그 차이를 숫자로 봅니다.

### 검증 목표

- 요청 확인 스크립트(0.2초마다 `/version`에 요청을 보내 응답 리비전과 실패를 센다, 2초 안에 답이 없으면 실패)를 돌려 놓고 새 리비전을 만들어 실패를 센다.
- 포트만 열리고 앱은 준비 안 된 버전을 올려 실패를 재현하고, 프로브를 `/health`로 바꾸면 사라지는지 본다.

### 실제로 있었던 일

세 실험 모두 staging(`friend-agent-staging`)에서 도우미가 실행했습니다. 새 리비전은 이미지를 새로 만들지 않고 화면 문구 환경변수 `BANNER`만 바꿔 만들었고, 시작 전에 서비스를 한 번 호출해 콜드 스타트(쉬던 서비스가 첫 요청에 늦는 현상)를 피했습니다.

| 실험 | 프로브 | 전체 요청 | 실패 | 배포 명령 시간 | 관찰 |
|---|---|---|---|---|---|
| ① 기본 배포(`BANNER=측정1`) | 기본(포트만) | 285건 | 3건(`ReadTimeout`, 12:05:36~12:05:40) | 27초 | 옮겨 가는 막바지에 몰림. 교안의 "0건이거나 아주 적음" 범위 |
| ② 준비가 늦은 버전(`SLOW_START_SECONDS=30`) | 기본(포트만) | 295건 | **54건(전부 503**, 12:08:07~12:08:28, 약 21초) | 37초 | 배포 명령이 **성공으로 끝난 뒤에도** 약 19초 더 503 |
| ③ `/health` 프로브(5초 간격, 12회, 2초) | `/health` | 377건 | **0건** | 약 84초 | 이전 리비전이 12:17:11 무렵까지 답한 뒤 새 리비전으로 넘어감 |

②가 핵심 장면입니다. 앱이 포트는 바로 열고 30초 동안 "준비 중(503)"만 돌려주는 버전인데, 기본 프로브는 포트만 보므로 Cloud Run은 "준비됐다"며 사용자를 옮겼습니다. 화면에는 "새 리비전이 트래픽 100%를 받고 있다"는 성공 문구가 떴지만 503은 전체로 약 21초 이어졌고 배포 명령이 끝난 뒤에도 약 19초 더 이어졌습니다. 교안의 "30초 가까이"와 달리 약 21초였고, 지연이 컨테이너 시작부터 세어졌기 때문일 것으로 **추정**하지만 확인하지는 않았습니다. ③은 같은 30초 지연에서 실패가 0건이 됐고, 대가는 시간이었습니다(①의 27초보다 훨씬 긴 약 84초. 이유는 확인하지 못함). ①의 3건은 콜드 스타트로 **추정**합니다(미확인).

프로브 설정은 서비스에 직접 넣은 것이라, 도우미가 `deploy.yml`의 `flags` 한 줄만 바꾸는 PR #29를 만들었습니다(CI 통과). 제가 `staging`에 머지하자 staging 배포가 성공했고(리비전 `00020-dc2`, 커밋 `55734e4`), 도우미가 만든 `staging → main` PR #30을 제가 머지·승인해 production도 같은 프로브를 갖게 됐습니다(`friend-agent-00025-txp`, 커밋 `55734e4`).

> 🧪 **예제** — [해설서 비유] 새 주방의 전등이 켜졌다고 요리가 되는 것은 아닙니다. 기본 프로브는 전등만 보는 점검이고 `/health` 프로브는 재료와 도구까지 보는 점검입니다. ②의 54건이 준비 전에 손님을 안내한 결과입니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- "배포가 성공했습니다"는 Cloud Run의 준비 조건을 통과했다는 뜻일 뿐, 사용자가 오류를 안 봤다는 뜻이 아닙니다.
- "752건 중 실패 0건"처럼 숫자로 말하세요. 단 그 숫자는 잰 시간과 요청 범위 안에서만 의미가 있습니다.
- 포트가 열렸다는 것과 서비스가 준비됐다는 것은 다릅니다. 준비 기준은 사람이 정합니다.

**개발자에게 시킬 때 물어볼 것**
- 새 리비전의 준비를 무엇으로 확인하나요(포트인가, 실제로 준비됐을 때만 성공하는 `/health`인가)? 배포 중 실패를 숫자로 재 봤나요?
- 개발자용: `httpGet.path=/health,periodSeconds=5,failureThreshold=12,timeoutSeconds=2`는 5초마다 묻고 12번까지 기다리며, 그 안에 준비 안 되면 새 리비전은 실패로 끝나고 트래픽은 옮겨 가지 않는다.

### 동료에게 설명하기

"도우미에게 시켜 배포 중에 사용자가 오류를 보는지 0.2초마다 요청을 보내 세어 봤어요. 준비가 30초 늦는 버전을 올리니 배포 명령은 '성공'으로 끝났는데도 503이 약 21초 이어졌고(명령이 끝난 뒤에도 약 19초) 54건이 실패했어요. 준비 확인을 `/health`로 바꾸니 같은 조건에서 0건이 됐고 대신 배포가 더 오래 걸렸어요. 배포 성공과 사용자 무사는 다른 얘기예요."

## 2. 새 버전을 올리는 일과 사용자에게 보내는 일을 나눈다 — 0% 배포, 태그 URL, 전환, 롤백, 카나리, 트래픽 고정 {#2}

### 취지

N052에서는 Nginx로 직접 블루그린을 했고, 이번에는 같은 일을 Cloud Run이 맡습니다. 식당 입구의 안내 직원(로드밸런서)을 Cloud Run이 하니 저는 "어느 리비전에 몇 %"라는 지시만 내립니다. 다만 새 주방이 정말 준비됐는지는 직원이 판단해 주지 않으므로 1절의 프로브로 제가 기준을 정해야 합니다.

### 검증 목표

- 0% 배포와 태그 URL로 새 버전만 따로 열어 본다. 한 번에 전환·롤백하는 시간과 실패를 잰다. 카나리를 해 본다. 트래픽 고정을 재현한다.

### 실제로 있었던 일

모두 staging에서 도우미가 실행했습니다. 시작 때 `friend-agent-staging-00020-dc2`가 "최신 리비전에 100%"로 트래픽을 받고 있었습니다.

**0% 배포와 태그 URL** `BANNER=GREEN`으로 `--no-traffic --tag green` 배포를 하자 새 리비전 `00021-fup`이 0%로 생겼습니다. 태그 URL의 `/version`은 `00021-fup`과 `banner: GREEN`, 원래 서비스 주소는 `00020-dc2`와 빈 배너를 돌려줬습니다. 같은 서비스인데 주소에 따라 다른 버전이 답한 것입니다. 태그 URL은 조회로 받은 주소와 서비스 주소 앞에 `green---`만 붙인 주소가 모두 열렸고, 워크플로에서는 조회로 받은 값이 형식 변경에도 안전합니다. 부수 효과도 있었습니다. `--no-traffic` 배포 직후 100% 줄에서 `latestRevision: true`가 사라지고 `00020`에 **고정**됐습니다.

**전환과 롤백(로그 13, 요청 281건)**

| 동작 | 시각(KST) | 결과 |
|---|---|---|
| 전환(`--to-tags green=100`) | 12:41:19.4~12:41:37.9(명령 18.5초) | 전환 중 **실패 0건**, 첫 `00021` 응답 12:41:35.2 |
| 롤백(`--to-revisions 00020-dc2=100`) | 12:42:13.0~12:42:24.5(명령 11.5초) | `ReadTimeout` **4건**(12:42:22.9~12:42:29.8), `00020` 첫 응답 12:42:32.2 |

교안은 "모두 실패 0건, 몇 초"를 예상했는데 롤백에서 4건이 나왔습니다. `00020` 인스턴스가 약 35초 트래픽이 없어 줄었다 다시 켜지는 콜드 스타트로 **추정**합니다(인스턴스 수는 확인 안 함). 명령 시간이 교안보다 긴 이유도 확인하지 못했습니다.

**카나리(로그 14, 요청 503건, 실패 0건)** `green=10`(90 대 10) → `50` → `100`으로 단계마다 약 55~65초 머물렀습니다. 응답은 `00020` 280건(56%), `00021` 223건(44%)이었고 단계별 머문 시간으로 계산한 기대값(약 42%)과 비슷했습니다. 한계로, 스크립트가 응답 리비전이 바뀔 때만 한 줄씩 찍어 단계별 건수를 따로 세지 못했습니다. 교안은 비율이 요청 하나하나에 확률로 적용되므로 요청이 적을수록 10%가 8%나 13%처럼 흔들린다고 설명하는데, 이번 로그로 그것을 증명하지는 못했습니다.

**트래픽 고정 재현** 카나리가 끝났을 때 트래픽은 `green` 태그(`00021`)에 고정돼 있었습니다. 이 상태에서 `BANNER=고정확인`으로 새 리비전을 만들었더니 명령은 성공인데 출력이 계속 `00021-fup`을 가리켜 새 리비전이 안 생긴 것처럼 보였습니다. 조회하니 `00022-tvw`는 준비(Ready)돼 있었지만 트래픽 0%·인스턴스 없음(`Retired`)이었고, 서비스 주소의 `/version`은 `00021`(`banner: GREEN`) 그대로였습니다. **배포는 성공했는데 사용자는 옛 리비전**입니다. `update-traffic --to-latest`를 실행하자 100%가 `00022-tvw`로 옮겨 가 `banner: 고정확인`이 떴고, 태그와 `BANNER`를 정리해(`00023-jrk`) `latestRevision: true` 100%로 돌렸습니다.

> 🧪 **예제** — [보충 비유] 업무 이관 지시를 "김 대리에게"라고 이름을 박아 두면 새 담당자가 와도 서류는 계속 김 대리 책상으로 갑니다. 롤백이나 카나리를 한 번 하면 트래픽 설정이 이 "이름 박힌 지시"가 되고, 새 리비전 `00022-tvw`가 일을 시작하지 못하는 것이 그 장면입니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 새 버전을 **만드는 일**과 **보내는 일**을 분리하세요. 0%로 올려 직원 전용 출입구로 확인하고, 괜찮을 때만 옮깁니다.
- 교안은 롤백이 빠른 이유를 이전 리비전을 지우지 않았고 트래픽 표만 바꾸기 때문이라고 설명합니다.
- 롤백이나 카나리를 한 번 하면 트래픽이 고정됩니다. 그 뒤 배포가 "성공"해도 서비스 주소의 `/version`으로 새 버전이 보이는지 따로 확인해야 합니다.

**개발자에게 시킬 때 물어볼 것**
- 롤백 뒤 다음 배포에서 고정을 풀고 있나요? 배포 뒤 `/version`으로 새 커밋을 확인하나요?
- 롤백은 프로브를 다시 돌리지 않습니다. 되돌아갈 리비전이 지금 정상인지는 누가 보나요?
- 개발자용: 서비스가 공개돼 있으면 태그 URL도 누구나 열 수 있어, 민감한 서비스는 접근 통제를 고려한다.

### 동료에게 설명하기

"새 버전을 0%로 올리니 원래 주소는 옛 버전이, `green---` 주소는 새 버전이 답했어요. 사용자에게 보내기 전에 새 버전만 먼저 확인할 수 있었어요(도우미가 두 주소를 조회해 비교했어요). 전환은 실패 0건, 롤백은 명령 하나인데 4건이 실패했어요. 제일 놀란 건 트래픽 고정이에요. 배포는 성공인데 사용자는 계속 옛 버전을 보니까, 배포 뒤에는 서비스 주소에서 새 버전이 보이는지 꼭 확인해야 해요."

## 3. 대화가 남는 서비스 — Supabase 연결, 키 세 개, 시험 환경과 운영 환경 분리, 같은 서비스 계정을 쓰는 한계 {#3}

### 취지

시작 상태를 보니 두 서비스 모두 `storage: memory`, `auth: none`, 즉 대화가 인스턴스 메모리에 있었습니다. 이 상태로 블루그린을 하면 교안 설명대로 새 리비전이 뜰 때마다 대화가 사라집니다(지난 N052에서 다룬 "전환 성공과 무중단은 다르다"와 같은 이야기이며, 이번 실습에서 대화가 사라지는 장면을 직접 본 것은 아닙니다). 그래서 먼저 대화를 모든 리비전이 함께 보는 데이터베이스(Supabase)로 옮겼습니다. 상담 기록을 직원 책상에서 중앙 기록실로 옮기는 일입니다.

### 검증 목표

- staging과 production을 각자의 Supabase 프로젝트에 연결하고, 비밀 키는 시크릿으로만 연결한다. 새 리비전 뒤에도 대화가 남는지 본다.

### 실제로 있었던 일

**준비** staging Supabase는 N052에서 만든 것이 있었고, production용은 제가 새로 만들어(East US Ohio, 무료) `0001_init.sql`을 실행해 테이블 6개를 확인하고 익명 로그인을 켰습니다. Secret Manager의 `supabase-secret-staging`·`supabase-secret-production`은 **제가 콘솔에서 직접** 만들었고 값은 대화에 나오지 않았습니다. 도우미는 런타임 서비스 계정에 시크릿 **각각에 대해서만** 읽기 권한을 주고 정책을 다시 조회해 확인했습니다.

**staging 연결** 제가 PowerShell로 연결 명령을 실행했습니다. 첫 시도는 `unrecognized arguments`로 실패했고(7절), 두 번째는 성공(`friend-agent-staging-00012-2l9`, `storage: supabase`)했지만 "로그인을 시작하지 못했습니다" 창이 떴습니다. 도우미가 값 없이 글자 구조만 보니 키 길이가 61이고 접두사 `sb_publishable_`이 두 번 이어져 있었고, 같은 키로 익명 가입을 요청하면 401이었습니다. 제가 키를 다시 넣어(제가 `$KEY.Length`로 확인한 길이는 처음 32, 다시 넣은 뒤 46) 리비전 `00013-fs2`를 만들었고, 도우미가 길이 46·접두사 1회·가입 요청 200을 확인했습니다.

| 확인 | 결과 |
|---|---|
| ① "게스트로 사용 중" | 제 캡처에서 문구가 잘려 "…용 중"만 보임(게스트 표시로 **추정**, 전체 글자는 확인 못 함). 로그인 실패 창은 키를 고친 뒤 안 뜸 |
| ② `messages` 표에 행 생성 | 제 캡처: 오늘(UTC 02:52~02:53) 새 사용자로 5행. 1~6행은 어제 N052 기록 |
| ③ 새 리비전 뒤에도 대화 유지 | 도우미가 `BANNER=저장확인`으로 `00014-vbd`를 만들었고, 제가 새로고침하니 띠에 `저장확인`과 기존 대화가 그대로 |
| ④ 다른 브라우저에서 앞 대화가 안 보임 | 제 시크릿 모드(비공개) 창은 캐릭터 만들기부터 시작(다른 게스트) |

**production 연결** 제가 변수 `$PURL`·`$PKEY`(길이 46 확인)로 연결해 리비전 `friend-agent-00024-62j`가 만들어졌고, 도우미가 `/version`에서 `env: production`·`storage: supabase`·`auth: supabase`, 시크릿 참조, staging과 다른 프로젝트 URL, 가입 요청 200을 확인했습니다. 이번엔 코드를 바꾸지 않아 연결 전 커밋 그대로(production `8243335`, staging `1010a7d`)였습니다. production에서 직접 대화해 `messages` 표를 확인하는 단계는 **하지 않았습니다.**

**키 세 개**

| 값 | 용도 | 넣는 곳 |
|---|---|---|
| 프로젝트 URL | 브라우저 로그인 | 일반 환경변수 |
| 공개 키(publishable) | 브라우저 로그인(화면 코드로 전달) | 일반 환경변수, 공개되는 값 |
| 비밀 키(secret) | 서버 전용, RLS를 건너뛰어 모든 데이터 접근 | **시크릿.** 명령에는 이름만 씀 |

**같은 서비스 계정의 한계** 강의노트는 두 환경이 같은 런타임 서비스 계정을 쓰고 그 계정이 두 시크릿을 모두 읽으면 staging의 실수가 production 데이터에 닿을 수 있다고 짚습니다. 오늘 도우미의 IAM 변경은 시크릿 각각의 읽기 권한 2개가 전부였고 환경별 계정 분리는 하지 않았습니다. 두 서비스가 같은 계정을 쓰는지 서비스별로 조회한 기록은 작업 기록에 없으니, **데이터는 환경별로 나눴어도 권한은 나누지 않았을 가능성**이 있다고 읽어 주세요.

### 적용 원칙

**누구나 알아야 할 원칙**
- 서버를 마음껏 바꾸려면 사용자 기록이 서버 밖에 있어야 합니다.
- 시험과 운영의 데이터베이스는 따로 두고, 권한 분리는 별도의 일로 챙기세요.
- 비밀 키는 채팅·명령·코드에 붙이지 않고, 시크릿 입력은 사람이 콘솔에서 직접 합니다.

**개발자에게 시킬 때 물어볼 것**
- 시험·운영이 서로 다른 데이터베이스와 시크릿, 서비스 계정을 쓰나요? 두 리비전이 같은 표를 쓰는 동안 표 구조를 바꿔도 동작하나요?
- 개발자용: 환경변수는 기존 값을 지우는 `--set-env-vars`가 아니라 `--update-env-vars`, 서비스 이름과 시크릿 이름의 환경(`-staging`)을 맞춘다.

### 동료에게 설명하기

"대화를 서버 메모리에서 Supabase로 옮겼어요. 운영용을 새로 만들어 시험용과 나누고 비밀 키는 제가 콘솔에서 직접 금고에 넣었어요. 새 버전을 만들어도 대화가 남았고 시크릿 모드(비공개) 창은 다른 사용자였어요. 다만 두 서비스가 같은 서비스 계정을 쓰는 한계는 아직 안 풀었어요."

## 4. 머지 한 번으로 저절로 — 워크플로 6단계 {#4}

### 취지

2절까지는 명령을 손으로 쳤습니다. 이제 PR 머지 한 번으로 돌게 만듭니다. 이번 과제에는 정답 파일이 없었고, 만들어진 각 단계를 제가 설명할 수 있어야 클리어였습니다. 자동화의 핵심은 명령을 자동으로 치는 것이 아니라 **각 단계의 성공 여부로 다음 단계의 실행 여부를 통제하는 것**입니다.

### 검증 목표

- 기존 배포 단계를 0% 배포 → 스모크 테스트 → 전환으로 나누어 staging과 production 둘 다에 적용하고, 머지 뒤 손대지 않아도 끝까지 도는지 본다.

### 실제로 있었던 일

설계는 도우미가 쓰고, 저는 "staging과 production 둘 다", "전환은 `--to-latest`", "태그는 고정 이름 `green`"을 확인했습니다. 도우미가 `deploy.yml`에 **67줄만 추가**(기존 줄은 그대로)해 PR #31(→ `staging`)을 만들었고, 푸시 전에 YAML과 모든 실행 블록의 문법을 검사했습니다.

| 단계 | 하는 일(비개발자 말) | 왜 필요한가 |
|---|---|---|
| ⓪ 동시 실행 방지 | 같은 브랜치 배포는 한 번에 하나만 | 두 배포가 동시에 트래픽을 만지는 혼란 방지 |
| ① 기록 | 지금 요청을 받는 리비전 이름을 로그에 남김 | 롤백 때 돌아갈 곳. 콘솔을 못 보는 워크플로가 눈 대신 쓰는 기록 |
| ② 0% 배포 | 새 리비전을 트래픽 없이 올리고 `green` 태그 부착 | 올리는 일과 보내는 일의 분리 |
| ③ 스모크 테스트 | 태그 URL의 `/health`와 `/version` 커밋이 이번 커밋인지 6초 간격, 최대 10번 확인 | 막 올라온 리비전의 콜드 스타트를 감안한 재시도 |
| ④ 전환 | 최신 준비 리비전이 테스트한 리비전과 같을 때만 `--to-latest`로 100% 이동 | 테스트한 것과 다른 리비전의 전환을 막고 고정도 풀어 둠 |
| ⑤ 전환 확인 | 서비스 주소 `/version`의 커밋이 새 커밋인지 확인 | "배포는 성공했는데 사용자는 옛 버전"을 잡음 |

**왜 태그 URL로 보는가** 새 리비전이 0%인 동안 원래 주소로 물으면 **옛 리비전이 대답**하므로, 정상이어도 새 버전의 증명이 아닙니다. 납품받은 신제품이 아니라 창고의 옛 재고를 검수한 격입니다. 그래서 새 리비전만 열리는 태그 URL을 봅니다.

**왜 `--to-latest`로 전환하는가** 태그나 리비전 이름으로 옮기면 트래픽이 거기에 고정돼 2절의 사고가 다음 배포에서 되풀이됩니다. `--to-latest`는 "가장 최근 리비전을 따라가는" 상태로 돌려놓습니다.

**staging 첫 실행(run #25, 커밋 `1a4819e`, 제가 머지)** 전 단계 성공. 전환 전 리비전 `00023-jrk`, 새 리비전 `00031-wod`, 스모크 시작까지 약 2분 30초(이미지 빌드·준비 대기 포함). 스모크 테스트와 전환 확인은 첫 시도에 통과했고 전환 로그는 `0%  00031-wod` → `100% LATEST (currently 00031-wod)`였습니다. 최종 `latestRevision: true` 100%(고정 아님), `green` 태그는 같은 리비전에 남았습니다. 리비전 번호가 `00023`에서 `00031`로 건너뛴 이유는 확인하지 못했고 동작에는 영향이 없어 보였습니다.

**production 반영(PR #32 → run #26, 제가 머지·승인)** staging 이미지를 찾아 승격하고(이미지 빌드는 건너뜀) 기록·배포·스모크 테스트·전환·전환 확인이 모두 성공했습니다. 최종 `friend-agent-00026-vis`가 `latestRevision: true` 100%, 커밋 `1a4819e`로 staging과 같았습니다.

## 5. 무중단을 숫자로 증명하고, 문제가 생기면 버튼 하나로 — production 752건 실패 0건, 원클릭 롤백 15초 {#5}

### 취지

워크플로가 성공했다는 것은 작업이 정상 종료됐다는 뜻이지 사용자에게 장애가 없었다는 뜻이 아닙니다. 병원 접수 시스템을 바꿀 때 물어야 할 것은 "설치됐나요"가 아니라 "전환하는 동안 접수가 실패하지 않았나요"입니다. 이 절은 production에서 그것을 증명하고 되돌리는 버튼을 만듭니다.

### 검증 목표

- production 배포 중 이전·새 리비전 응답이 모두 보이고 실패가 0건인지 본다. 버튼으로 이전 리비전에 돌아가고 `/version`이 바뀔 때까지의 시간을 잰다.

### 실제로 있었던 일

**첫 측정: 6건 실패(로그 15)** 제가 승인해 `deploy` 작업이 시작되는 순간(KST 14:10:22)을 도우미가 감지해 production에 5분간 요청을 보냈습니다. **전체 723건, 실패 6건**(`ReadTimeout`, 14:10:23~14:10:35), 이전 `friend-agent-00025-txp` 152건, 새 `friend-agent-00026-vis` 565건이었습니다. 새 리비전의 첫 응답은 14:11:39이고 **이 전환 구간의 실패는 0건**이었습니다. 6건은 감시 직후 15초 안에 몰렸고 14:10:37에 이전 리비전의 첫 응답이 왔으니 새 리비전이 받기 약 1분 전, 즉 배포 전환이 원인은 아닙니다. 감시 전에 production을 깨워 두지 않아 이전 리비전의 콜드 스타트였을 것으로 **추정**할 뿐 확인은 안 했습니다. 이 로그만으로는 "실패 0건" 조건을 엄밀히 충족하지 못했습니다.

**재측정: 752건 실패 0건(로그 16, run #28)** 이번에는 승인을 기다리는 동안 production을 20초마다 깨워 둔 뒤, 승인으로 `deploy` 작업이 시작되는 순간(14:28:12)부터 5분간 요청을 보냈습니다. **전체 752건, 실패 0건**, 이전 `00026-vis` 195건(26%) → 새 `friend-agent-00028-rum` 557건(74%), 새 리비전 첫 응답 14:29:32. 배포 run은 전체 2분 13초, 최종 커밋 `8d549df`였습니다. 6건이 사라진 것은 콜드 스타트 추정과 일관되지만 깨워 두기만 바꾼 한 번의 비교일 뿐 원인을 직접 확인한 것은 아닙니다. 첫 측정 6건도 기록에서 지우지 않았습니다.

**원클릭 롤백과 승인 선택** 롤백에도 production 승인을 걸지는 제가 정했고, **걸지 않는 쪽**을 골랐습니다. 이 저장소는 저 혼자 승인자이자 실행자라 승인은 보호보다 지연이 크기 때문이고, 대신 입력 형식(리비전 이름 모양)·서비스 소속·준비(Ready) 상태를 검사하는 안전장치를 뒀습니다. **반대 위험**은 급할 때도 아무나 누를 수 있다는 점이고, `environment: production`을 붙이면 바로 막을 수 있습니다. 과제는 이 선택을 직접 따져 정하라는 것이라 어느 쪽도 정답이 아닙니다.

도우미가 만든 `rollback.yml`은 새 파일 하나입니다. 버튼을 누를 때 `target`(staging·production)과 `revision`(돌아갈 리비전 이름)을 입력받아 인증 → 입력·리비전 확인 → `--to-revisions 리비전=100` → 서비스 주소 `/version` 확인과 걸린 초를 요약 표에 기록합니다. 입력값은 환경변수로만 셸에 넘겨 이상한 문자열이 명령이 되지 않게 했습니다. PR #33(→ staging)과 #34(→ main)를 제가 머지·승인해 Actions에 등록됐습니다.

| # | 대상 | 되돌아갈 리비전 | 실행 | 롤백 명령부터 `/version` 확인까지 |

| #1 | staging | `friend-agent-staging-00031-wod` | 도우미 | 32초(확인 3번째 시도) |

## 6. 일부러 망가뜨려 안전장치를 시험하다 — CI는 통과, 스모크 테스트가 전환을 막음, 735건 실패 0건, Revert {#6}

### 취지

안전장치는 정상일 때만 확인해서는 부족합니다. [보충 비유] 소방 훈련에서 실제로 알람을 울려 보듯 일부러 망가뜨려 막아 내는지 봐야 합니다. 시험은 격리된 staging에서만 했고 production은 건드리지 않았습니다.

### 검증 목표

- 망가진 버전을 머지하면 워크플로가 실패하고 전환이 건너뛰어지는지, 그동안 사용자는 이전 버전을 받아 실패가 0건인지, Revert 뒤 정상 배포가 도는지 본다.

### 실제로 있었던 일

**망가뜨리는 방식** 교안은 "`/health`가 항상 실패하는 버전"을 말하지만, `/health`를 검사하는 테스트가 있고 `staging` 브랜치는 `test` 체크를 필수(관리자에게도 적용)로 요구해 그 PR은 CI에서 막힙니다. 제가 **A 방식**을 골랐습니다. `/version`이 틀린 커밋 값을 돌려주게 해(`app/main.py` 한 줄, `"commit": "broken-" + ...`), `/health`는 정상이라 프로브는 통과하고 **스모크 테스트의 커밋 비교에서만** 걸리게 했습니다. 로컬 테스트 15개와 실제 CI가 통과했고 PR #35(→ `staging`)를 제가 머지했습니다. `/health`를 실패시키는 B 방식은 하지 않았습니다.

**시험 결과(run #29, 병합 커밋 `b50cc5c`)**

| 단계 | 결과 |
|---|---|
| test(CI) | success(19초). CI는 통과했다 |
| 이미지 만들기·올리기, 리비전 기록(`00033-bas`) | success |
| 0% 배포(새 리비전 `00037-duy`) | success. `/health`가 정상이라 프로브는 통과 |
| **스모크 테스트(태그 URL)** | **failure.** 기대 커밋과 달리 10번 모두 `broken-b50cc5c` |
| 전환 / 전환 확인 / 배포 결과 | **skipped** |

로그의 마지막 줄은 "스모크 테스트 실패. 전환하지 않는다. 사용자는 계속 friend-agent-staging-00033-bas 을 쓴다"였습니다. 시험 뒤 staging은 `00033-bas` 100%, `/version` 커밋 `8d549df` 그대로였고, 망가진 `00037-duy`는 0%에 `green` 태그만 달고 있었습니다.

**요청 확인(로그 19)** 도우미가 deploy 시작(14:59:24)을 감지해 5분간 요청을 보냈습니다(대기 중 staging을 20초마다 깨움). **전체 735건, 실패 0건**이었고 응답은 전부 `00033-bas`(100%)였습니다. 측정한 `/version` 요청은 전부 이전 버전이 답했습니다(실제 사용자의 경험을 잰 것은 아닙니다).

**Revert와 정상 배포(PR #36 → run #30)** 도우미가 `git revert -m 1 b50cc5c`로 브랜치 `revert-broken-version`에서 PR #36을 만들고 `app/main.py`가 시험 전 커밋 `8d549df`와 같음을 diff로 확인했습니다(교안은 GitHub Revert 버튼이지만 같은 결과). 제가 머지했고 run #30(커밋 `412a785`)은 전 단계 success였으며, 스모크 테스트는 첫 시도에 통과하고 전환 로그는 `0%  00038-veg` → `100% LATEST (currently 00038-veg)`였습니다. 최종 staging은 `00038-veg`가 `latestRevision: true` 100%였고, **롤백(#1·#2)으로 고정돼 있던 트래픽도 이 전환 단계(`--to-latest`)가 풀었습니다.** 클리어 네 조건(실패한 단계와 건너뛴 전환 / 트래픽이 이전 리비전 그대로 / 실패 0건 / Revert 뒤 정상 배포)이 모두 충족됐습니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- CI 통과는 "코드 시험이 통과했다"이지 "사용자에게 보내도 된다"가 아닙니다. 이번에 CI는 초록이었고 스모크 테스트가 막았습니다.
- 안전장치는 일부러 망가뜨려 확인하고, 시험은 격리된 환경에서 하며, 되돌리는 경로(Revert)까지 해 보세요.
- 이 시험은 한 가지 고장(커밋 값 불일치)만 봤습니다. 스모크 테스트가 통과해도 모든 기능이 완벽한 것은 아닙니다.

**개발자에게 시킬 때 물어볼 것**
- 망가진 버전을 일부러 올려 어느 단계에서 멈추고 그동안 사용자가 어느 버전을 받는지 확인했나요? 스모크 테스트가 로그인·메시지 전송·저장 같은 핵심 기능까지 보나요?
- 개발자용: 필수 체크 때문에 `/health` 고장 방식은 쓰지 못했고, 프로브가 먼저 막는 경로(B)는 시험하지 않았다.

### 동료에게 설명하기

"커밋 값이 틀린 버전을 일부러 staging에 올렸어요. CI는 통과했는데 스모크 테스트가 10번 모두 실패해서 전환 단계는 건너뛰었어요. 그 5분 동안 도우미가 `/version` 요청 735건을 보냈는데 실패 0건이었고 전부 이전 버전이 답했어요. Revert 뒤에는 정상 배포가 끝까지 돌았고, 롤백 때문에 고정돼 있던 트래픽도 풀렸어요."

## 7. 실습 중 부딪힌 일과 교안과 달랐던 점 {#7}

### 취지

부딪힌 일은 실패가 아니라 다음에 미리 막을 함정 목록입니다. 무슨 일이 있었는지, 교안과 달랐던 점, 하지 못한 것을 그대로 남깁니다.

### 검증 목표

- 원인과 대응을 기록하고, 교안과 달랐던 점과 확인하지 못한 것을 숨기지 않고 모은다.

### 실제로 있었던 일

**① 키 접두사가 두 번 들어간 사고** 복사한 공개 키에 이미 `sb_publishable_`이 들어 있는데 제가 `$KEY = "sb_publishable_…"`에 한 번 더 썼습니다. 도우미의 예시가 만든 오해였습니다. 증상은 "로그인을 시작하지 못했습니다" 창이라 처음엔 익명 로그인 설정 문제처럼 보였지만, 값 없이 길이와 구조만 보고(서비스에 저장된 값의 길이 61 → 다시 넣은 값 46) 가입 요청 401로 원인을 좁혔습니다. 중간에 제가 붙여 준 출력은 이전 실행(00012)의 것이어서 실제 상태는 조회로 확인했습니다. 교훈은 키를 보지 않고도 길이와 구조로 점검할 수 있다는 것, 화면 증상이 가리키는 곳과 실제 원인이 다를 수 있다는 것입니다.

**② PowerShell의 쉼표·꺾쇠·따옴표** 첫 연결 시도는 `<staging 프로젝트 URL>`의 꺾쇠 자리 표시를 통째로 바꾸지 않았고, 쉼표가 든 값을 따옴표로 감싸지 않아 쉼표가 인자 구분으로 해석돼 `unrecognized arguments`로 실패했습니다. 도우미의 안내가 틀렸고, 변수(`$URL`, `$KEY`)와 큰따옴표 방식으로 바꿨습니다. 교안의 줄 끝 `\`도 macOS·Linux 기준이라 Windows에서는 맞지 않습니다.

**③ Git Bash가 `/health`를 윈도 경로로 바꾼 일(실험 무효 2번)** 실험 ③을 세 번 돌렸습니다. 첫 실행은 Git Bash가 `/health`를 `C:/Program Files/Git/health`로 바꿔 저장했는데(조회로 발견) 실패 0건(376건)·배포 약 65초가 나왔습니다. 이유는 확인하지 않았고(앱이 모르는 경로에도 200으로 답했을 **가능성**) 근거로 쓰지 않고 로그만 보존했습니다. 두 번째는 변환을 끄려 `MSYS_NO_PATHCONV=1`을 켜자 `gcloud` 래퍼가 자기 파이썬 파일 경로를 못 찾아 **배포가 실행되지 않았습니다**(로그의 371건·실패 1건은 배포가 없던 구간). 세 번째는 `MSYS2_ARG_CONV_EXCL="--startup-probe"`로 그 옵션만 제외하고 저장값이 `/health`임을 조회로 확인해 1절의 ③ 값이 됐습니다. 교훈은 Git Bash에서는 실행 뒤 **저장된 값을 조회해** 확인하라는 것이고, PowerShell에는 이 문제가 없습니다.

### 교안과 달랐던 점

| 항목 | 교안 | 이번 실습 |
|---|---|---|
| ② 준비 늦은 버전의 실패 | 30초 가까이 | 약 21초, 54건 |
| ③ 프로브의 배포 시간 | 30초쯤 더 | ①의 27초보다 훨씬 긴 약 84초(원인 확인 못 함) |
| 롤백 | 실패 0건, 몇 초 | staging 4건(롤백 명령 11.5초, 워크플로로 잰 확인까지 32초), production 4건(워크플로로 잰 확인까지 15초), 복귀는 0건·4초 |
| 전환 명령 시간 | 몇 초 | 18.5초 |
| 카나리 10% 비율 | 8%·13%처럼 나옴 | 이번 로그로 증명 못 함 |
| `--no-traffic` 부수 효과 | 교안에 없음 | `latestRevision`이 사라지고 현재 리비전에 고정됨 |
| 리비전 번호 | 언급 없음 | 번호가 여러 번 건너뜀(staging `00023`→`00031`, `00033`→`00037`, production `00026`→`00028`→`00032`, 이유 미확인) |
| 망가진 버전 | `/health`가 항상 실패 | 필수 체크 때문에 `/version` 커밋 불일치로 대체 |

### 하지 못한 것과 추정으로 남긴 것

| 항목 | 상태 |
|---|---|
| production에서 직접 대화해 `messages` 확인, "게스트로 사용 중" 전체 문구 | 하지 않음 / 캡처가 잘려 확인 못 함 |
| ① 3건·롤백 4건·production 첫 6건·확인 첫 시도의 5초 초과 | 콜드 스타트로 **추정**, 확인 안 함 |
| ③의 긴 배포 시간, ②가 21초였던 이유, 무효 첫 실행에서 0건이었던 이유 | 확인하지 못함 |
| 카나리 10% 단계의 새 리비전 응답 수 | 따로 세지 못함 |
| 환경별 서비스 계정 분리, 같은 계정 사용 여부 조회 | 하지 않음 / 기록 없음 |
| 오늘 아침의 배포 서비스 계정 역할 | 스냅샷을 남기지 않아 비교 못 함. 지금은 프로젝트 수준 역할 2개(`run.sourceDeveloper`, `serviceusage.serviceUsageConsumer`), 넓은 기본 역할은 없음 |
| 프로브가 먼저 막는 경로(B), 스키마 변경 배포 호환성 | 시험하지 않음(교안 설명만) |
| 단계별 설명 발표 연습, 선택 과제(결과 알림·카나리 자동 승격) | 제 몫 / 진행기록에 시도한 기록 없음 |

### 적용 원칙

**누구나 알아야 할 원칙**
- 막힌 이유는 값이 노출되지 않는 점검(길이·구조·저장된 설정 조회)으로 좁히세요.
- 도구(도우미)도 안내를 틀립니다. 화면과 조회 결과를 믿고 바로 정정하세요.
- 무효가 된 실험은 지우지 말고 무효라고 표시해 보존하세요. 교안과 숫자가 달라도 나온 대로 적으세요.

**개발자에게 시킬 때 물어볼 것**
- 설정을 넣은 뒤 저장된 값을 조회해 의도대로인지 확인했나요(특히 Windows)? 무효가 된 실험의 이유가 기록돼 있나요?
- 개발자용: Git Bash에서는 옵션 하나만 제외하려면 `MSYS2_ARG_CONV_EXCL`을 쓴다. 전체를 끄는 `MSYS_NO_PATHCONV=1`은 `gcloud` 래퍼를 깰 수 있다.

### 동료에게 설명하기

"세 군데서 막혔어요. 공개 키 접두사를 제가 한 번 더 붙여 로그인이 안 됐고, PowerShell에서 쉼표 든 값을 따옴표로 안 감싸 명령이 실패했고, Git Bash가 `/health`를 윈도 경로로 바꿔 실험을 두 번 버렸어요. 교안과 다른 숫자는 그대로 적었고 확인 못 한 건 전부 '추정'이나 '확인하지 못함'으로 남겼어요."

## 8. 내 서비스에 적용하면 {#8}

### 취지

강의노트(1-7·5-8·8-3절)는 이 구조가 직접 운영할 1인 AI 사업의 신뢰도를 높이는 사업 역량이라고 말합니다. 이 절은 그 내용을 옮긴 것이며, **제가 이 서비스들에 적용해 본 것은 아닙니다.**

### 검증 목표 (적용할 때 확인할 것)

- 새 버전으로 바뀌어도 사용자 기록이 남고, 문제가 생기면 빨리 이전 버전으로 돌아갈 수 있는가.

### 적용 원칙

| 서비스 | 적용하면 | 새 리비전에서 확인할 것 |
|---|---|---|
| My-Story-Maker(MSM) | 글·이야기 분석 기능이 잘못 배포돼도 서비스 중단과 데이터 손실 위험을 줄인다. 새 분석·웹소설 생성 기능을 카나리로 일부 사용자에게 먼저 제공할 수 있다 | 분석 결과, 문체 유지, 저장 기능. 기존 버전을 남겨 두면 빨리 되돌린다 |
| 뉴스레터 에이전트 | 예약 실행되는 서비스의 새 버전을 먼저 시험하고, 발행 오류가 발견되면 이전 버전으로 되돌린다 | 수집·선별·근거 검증·발행 중 한 단계가 바뀌어도 모두에게 즉시 영향 주지 않게 확인. 실제 발행·외부 전송은 테스트 환경과 분리 |
| AI 컨설팅 서비스 | 고객별 에이전트의 배포 절차를 표준화해 운영 위험과 유지보수 비용을 관리하고, 상담 기록이 사라지지 않게 데이터베이스에 저장해 테스트 실패 시 이전 버전으로 복구한다 | 진단 질문·보고서 로직을 바꿀 때 테스트 사례로 품질을 확인하고 이전 버전과 비교한 뒤 전환. 고객 데이터와 운영 환경 분리 |

**누구나 알아야 할 원칙**
- 고객 대화를 저장하는 AI 서비스는 코드뿐 아니라 **데이터 안전성, 버전 간 호환성, 오류 시 복구 방법**까지 설계해야 합니다.
- 방식은 요청량에 맞춰 고릅니다. 하루 30건이면 10%는 하루 평균 약 3건이라 문제를 발견하기 어려우니 블루그린이 맞고, 요청이 늘면 카나리로 넘어갑니다. 이번 자동화도 블루그린으로 했습니다.
- 롤백 기준(오류율, 지연, 핵심 기능, 인스턴스 상태, 사용자와 비용)은 배포하기 **전에** 정하세요.

**개발자에게 시킬 때 물어볼 것**
- 새 버전이 표 구조를 바꿀 때 두 리비전이 함께 도는 동안과 롤백 뒤에도 동작하나요(확장 → 호환 코드 배포 → 코드 전환 → 정리)? 롤백해도 데이터베이스 구조는 자동으로 돌아가지 않습니다.
- 스모크 테스트가 로그인·메시지 전송·저장 같은 핵심 기능을 보나요? 운영 데이터와 테스트 데이터는 분리돼 있나요?

### 동료에게 설명하기

"무중단 배포를 볼 때 저는 세 가지를 같이 봐요. 새 버전을 사용자에게 보내기 전에 먼저 확인했는지, 배포 중 실패가 몇 건인지 숫자가 있는지, 문제가 생기면 버튼 하나로 돌아가는지요. 이번에 production 배포 중 752건에 실패 0건이었고, 망가진 버전은 전환 전에 멈췄어요. 고객 기록을 다루는 서비스면 기록이 데이터베이스에 있는지도 먼저 물어요."

> 📌 **요약** — 이번 실습의 한 줄 교훈은 **"배포 성공은 사용자가 오류를 안 봤다는 뜻이 아니다. 새 버전을 0%로 올려 확인한 뒤에만 보내고, 문제가 생기면 돌아가게 하며, 모두를 숫자로 증명한다"**입니다. 준비가 늦은 버전의 54건 실패, 배포는 성공했는데 옛 버전을 본 트래픽 고정, production 752건 실패 0건, 롤백 직후 4건, 망가진 버전이 735건 실패 0건으로 멈춘 전환을 직접 보았습니다.

## 9. 용어 사전 {#9}

| 용어 | 쉬운 설명 |
|---|---|
| 리비전 · 트래픽 설정 · 0% 배포 · 태그 URL · 스타트업 프로브 · 스모크 테스트 · 트래픽 고정 · 원클릭 롤백 · 시크릿 · 블루그린과 카나리 | 위 "미리 보는 용어" 표 참고 |
| Cloud Run | 컨테이너를 서비스로 돌려 주는 구글 클라우드. 로드밸런서와 트래픽 분배를 대신 운영한다 |
| 콜드 스타트 | 쉬던 서비스(인스턴스 0개)의 첫 요청이 인스턴스를 새로 켜느라 늦거나 실패하는 현상 |
| 요청 확인 스크립트 | 0.2초마다 `/version`에 요청을 보내 응답 리비전과 실패를 세는 도구 |
| `/health` · `/version` | 서비스가 살아 있는지 알려 주는 주소 · 어느 리비전이 어떤 커밋으로 답하는지 알려 주는 주소 |
| `--no-traffic` · `--tag` | 새 리비전에 사용자 요청을 안 보냄 · 그 리비전만 열리는 태그 URL을 만듦 |
| `--to-tags` · `--to-revisions` · `--to-latest` | 트래픽을 태그·특정 리비전·가장 최근 리비전으로 옮김. `--to-latest`가 고정을 푼다 |
| 그레이스풀 셧다운 | 이전 인스턴스가 종료 신호를 받은 뒤 처리하던 요청을 마치는 것(기본 10초) |
| 워크플로 · `workflow_dispatch` | 정해진 순서로 자동 실행되는 작업 묶음(`deploy.yml`, `rollback.yml`) · 버튼으로 직접 실행하게 하는 트리거 |
| 환경 승인(`environment: production`) | production 배포 전 사람이 승인하게 하는 GitHub 설정. 이번 롤백에는 붙이지 않았다 |
| CI · Revert | 코드를 합칠 때마다 자동으로 도는 테스트 · 이미 합친 변경을 되돌리는 새 변경 |
| 스키마 마이그레이션 | 데이터베이스 표 구조를 바꾸는 작업. 롤백해도 자동으로 되돌아가지 않는다 |
| 익명 로그인 · RLS | 가입 없이 브라우저마다 사용자 한 명을 만드는 방식 · 표의 행마다 읽기·쓰기를 제한하는 기능 |
| 공개 키 · 비밀 키 | 브라우저용 노출 가능한 키 · 서버 전용으로 RLS를 건너뛰는 높은 권한의 키 |
| `MSYS2_ARG_CONV_EXCL` | Git Bash가 `/`로 시작하는 인자를 윈도 경로로 바꾸는 것을 옵션 하나만 막는 설정 |
| KST · UTC | 한국 시간 · 세계 표준시(KST가 9시간 빠름). 로그는 KST, GitHub Actions 화면은 UTC |
| staging · production | 시험용 서비스(`friend-agent-staging`)와 실제 사용자가 쓰는 서비스(`friend-agent`) |
| 커밋 | 코드 변경 한 건의 기록과 그 고유 번호. `/version`의 커밋은 "지금 어떤 코드가 돌고 있나"를 알려 준다 |
| PR · 머지 | 코드 변경을 합쳐 달라는 요청(PR)과 그 요청을 받아들여 합치는 행동(머지) |
| 인스턴스 · 콜드 스타트 | 서비스를 실제로 돌리는 한 대의 실행 단위 · 줄어 있던 인스턴스를 다시 켜느라 첫 요청이 늦어지는 것 |
| 환경변수 | 서비스에 값을 넘기는, 이름이 붙은 설정(예: 저장소 종류) |
| 서비스 계정 | 사람이 아니라 프로그램이 쓰는 계정과 그 권한 |
| 503 · ReadTimeout | 서버가 "아직 준비 중"이라고 답한 오류 · 정해 둔 시간(2초) 안에 답이 안 와서 실패로 센 것 |
| `/version` · `/health` | 서비스가 "지금 어떤 코드·리비전인가"를 알려 주는 주소 · "일할 준비가 됐나"를 알려 주는 주소 |
| RLS | 데이터의 행 단위 접근 제한. 다른 사용자의 기록을 못 보게 한다 |
| 시크릿 모드(비공개) 창 | 브라우저의 비공개 창. 이 문서의 "시크릿"(키를 보관하는 금고)과는 다른 말이다 |
