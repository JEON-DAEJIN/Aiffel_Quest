취지

4. 머지 한 번으로 저절로 — 워크플로 6단계

취지

2절까지는 명령을 손으로 쳤습니다. 이제 PR 머지 한 번으로 돌게 만듭니다. 이번 과제에는 정답 파일이 없었고, 만들어진 각 단계를 제가 설명할 수 있어야 클리어였습니다. 자동화의 핵심은 명령을 자동으로 치는 것이 아니라 각 단계의 성공 여부로 다음 단계의 실행 여부를 통제하는 것입니다.

검증 목표

  • 기존 배포 단계를 0% 배포 → 스모크 테스트 → 전환으로 나누어 staging과 production 둘 다에 적용하고, 머지 뒤 손대지 않아도 끝까지 도는지 본다.

실제로 있었던 일

설계는 도우미가 쓰고, 저는 "staging과 production 둘 다", "전환은 --to-latest", "태그는 고정 이름 green"을 확인했습니다. 도우미가 deploy.yml에 67줄만 추가(기존 줄은 그대로)해 PR #31(→ staging)을 만들었고, 푸시 전에 YAML과 모든 실행 블록의 문법을 검사했습니다.

단계하는 일(비개발자 말)왜 필요한가
⓪ 동시 실행 방지같은 브랜치 배포는 한 번에 하나만두 배포가 동시에 트래픽을 만지는 혼란 방지
① 기록지금 요청을 받는 리비전 이름을 로그에 남김롤백 때 돌아갈 곳. 콘솔을 못 보는 워크플로가 눈 대신 쓰는 기록
② 0% 배포새 리비전을 트래픽 없이 올리고 green 태그 부착올리는 일과 보내는 일의 분리
③ 스모크 테스트태그 URL의 /health와 /version 커밋이 이번 커밋인지 6초 간격, 최대 10번 확인막 올라온 리비전의 콜드 스타트를 감안한 재시도
④ 전환최신 준비 리비전이 테스트한 리비전과 같을 때만 --to-latest로 100% 이동테스트한 것과 다른 리비전의 전환을 막고 고정도 풀어 둠
⑤ 전환 확인서비스 주소 /version의 커밋이 새 커밋인지 확인"배포는 성공했는데 사용자는 옛 버전"을 잡음

왜 태그 URL로 보는가 새 리비전이 0%인 동안 원래 주소로 물으면 옛 리비전이 대답하므로, 정상이어도 새 버전의 증명이 아닙니다. 납품받은 신제품이 아니라 창고의 옛 재고를 검수한 격입니다. 그래서 새 리비전만 열리는 태그 URL을 봅니다.

왜 --to-latest로 전환하는가 태그나 리비전 이름으로 옮기면 트래픽이 거기에 고정돼 2절의 사고가 다음 배포에서 되풀이됩니다. --to-latest는 "가장 최근 리비전을 따라가는" 상태로 돌려놓습니다.

staging 첫 실행(run #25, 커밋 1a4819e, 제가 머지) 전 단계 성공. 전환 전 리비전 00023-jrk, 새 리비전 00031-wod, 스모크 시작까지 약 2분 30초(이미지 빌드·준비 대기 포함). 스모크 테스트와 전환 확인은 첫 시도에 통과했고 전환 로그는 0% 00031-wod → 100% LATEST (currently 00031-wod)였습니다. 최종 latestRevision: true 100%(고정 아님), green 태그는 같은 리비전에 남았습니다. 리비전 번호가 00023에서 00031로 건너뛴 이유는 확인하지 못했고 동작에는 영향이 없어 보였습니다.

production 반영(PR #32 → run #26, 제가 머지·승인) staging 이미지를 찾아 승격하고(이미지 빌드는 건너뜀) 기록·배포·스모크 테스트·전환·전환 확인이 모두 성공했습니다. 최종 friend-agent-00026-vis가 latestRevision: true 100%, 커밋 1a4819e로 staging과 같았습니다.

6. 일부러 망가뜨려 안전장치를 시험하다 — CI는 통과, 스모크 테스트가 전환을 막음, 735건 실패 0건, Revert

취지

안전장치는 정상일 때만 확인해서는 부족합니다. [보충 비유] 소방 훈련에서 실제로 알람을 울려 보듯 일부러 망가뜨려 막아 내는지 봐야 합니다. 시험은 격리된 staging에서만 했고 production은 건드리지 않았습니다.

검증 목표

  • 망가진 버전을 머지하면 워크플로가 실패하고 전환이 건너뛰어지는지, 그동안 사용자는 이전 버전을 받아 실패가 0건인지, Revert 뒤 정상 배포가 도는지 본다.

실제로 있었던 일

7. 실습 중 부딪힌 일과 교안과 달랐던 점

취지

부딪힌 일은 실패가 아니라 다음에 미리 막을 함정 목록입니다. 무슨 일이 있었는지, 교안과 달랐던 점, 하지 못한 것을 그대로 남깁니다.

검증 목표

  • 원인과 대응을 기록하고, 교안과 달랐던 점과 확인하지 못한 것을 숨기지 않고 모은다.

실제로 있었던 일

① 키 접두사가 두 번 들어간 사고 복사한 공개 키에 이미 sb_publishable_이 들어 있는데 제가 $KEY = "sb_publishable_…"에 한 번 더 썼습니다. 도우미의 예시가 만든 오해였습니다. 증상은 "로그인을 시작하지 못했습니다" 창이라 처음엔 익명 로그인 설정 문제처럼 보였지만, 값 없이 길이와 구조만 보고(서비스에 저장된 값의 길이 61 → 다시 넣은 값 46) 가입 요청 401로 원인을 좁혔습니다. 중간에 제가 붙여 준 출력은 이전 실행(00012)의 것이어서 실제 상태는 조회로 확인했습니다. 교훈은 키를 보지 않고도 길이와 구조로 점검할 수 있다는 것, 화면 증상이 가리키는 곳과 실제 원인이 다를 수 있다는 것입니다.

② PowerShell의 쉼표·꺾쇠·따옴표 첫 연결 시도는 <staging 프로젝트 URL>의 꺾쇠 자리 표시를 통째로 바꾸지 않았고, 쉼표가 든 값을 따옴표로 감싸지 않아 쉼표가 인자 구분으로 해석돼 unrecognized arguments로 실패했습니다. 도우미의 안내가 틀렸고, 변수($URL, $KEY)와 큰따옴표 방식으로 바꿨습니다. 교안의 줄 끝 \도 macOS·Linux 기준이라 Windows에서는 맞지 않습니다.

③ Git Bash가 /health를 윈도 경로로 바꾼 일(실험 무효 2번) 실험 ③을 세 번 돌렸습니다. 첫 실행은 Git Bash가 /health를 C:/Program Files/Git/health로 바꿔 저장했는데(조회로 발견) 실패 0건(376건)·배포 약 65초가 나왔습니다. 이유는 확인하지 않았고(앱이 모르는 경로에도 200으로 답했을 가능성) 근거로 쓰지 않고 로그만 보존했습니다. 두 번째는 변환을 끄려 MSYS_NO_PATHCONV=1을 켜자 gcloud 래퍼가 자기 파이썬 파일 경로를 못 찾아 배포가 실행되지 않았습니다(로그의 371건·실패 1건은 배포가 없던 구간). 세 번째는 MSYS2_ARG_CONV_EXCL="--startup-probe"로 그 옵션만 제외하고 저장값이 /health임을 조회로 확인해 1절의 ③ 값이 됐습니다. 교훈은 Git Bash에서는 실행 뒤 저장된 값을 조회해 확인하라는 것이고, PowerShell에는 이 문제가 없습니다.
