## 1. 전환했는데 사용자는 끊기지 않았다 — 설정 한 줄, reload, 실패 0건 {#1}

### 취지

지난 시간(N050~N051)까지 우리 서비스(friend-agent, 줄여서 에이전트 서비스)는 한 번 만든 이미지를 컨테이너로 돌리는 데까지 왔습니다. 이번 시간의 질문은 이것입니다. **새 버전으로 바꿀 때 지금 쓰고 있는 사용자가 끊기지 않게 하려면 어떻게 하나요?** 가게를 리모델링한다면 문을 닫지 않고 옆에 새 매장을 완성해 놓은 뒤 안내판만 바꾸는 방법이 있습니다. 서비스에서는 그 안내판 역할을 로드밸런서(Nginx)가 맡습니다.

### 검증 목표

- 같은 서비스를 두 벌(blue·green) 띄우고, Nginx 설정 **한 줄**로 요청 목적지를 바꿀 수 있는지 본다.
- 바꾸는 동안 요청이 실패하는지 **숫자로 측정**하고, 문제가 생기면 같은 방식으로 되돌릴 수 있는지(롤백) 확인한다.
- 서버 목록에 가중치를 주면 요청이 3 대 1로 나뉘는지 본다(카나리 배포의 원리).

### 실제로 있었던 일

**준비 (09:15, 도우미가 실행)** 서비스 컨테이너 두 개(`blue`, `green`)와 Nginx 컨테이너(`bg-nginx`)를 같은 Docker 네트워크에 띄웠습니다. 서비스 두 개는 일부러 바깥으로 문을 열지 않았고(포트 연결 없음), 내 컴퓨터의 8080 포트는 Nginx에만 연결했습니다. 확인 결과 `docker ps`에서 `bg-nginx`에만 `0.0.0.0:8080->80/tcp`가 보였고, `blue`·`green`을 직접 두드리면 연결이 되지 않았습니다. 사용자가 서비스에 닿는 길은 Nginx 하나뿐입니다. 이것이 리버스 프록시(대신 받아서 뒤로 넘겨 주는 문지기)의 모습입니다. 도우미의 내장 브라우저로 `http://localhost:8080`을 열자 화면 맨 위에 **BLUE 배너**가 보였고, `/version`은 `revision: blue`, `storage: memory`, `auth: none`을 돌려줬습니다. 이 시점에는 대화가 서버 메모리에 저장됩니다(3절).

**실험 ① blue→green 전환과 롤백 (09:16~09:17, 도우미가 실행)** 요청 확인 스크립트(0.2초마다 요청을 보내 어느 쪽이 응답했는지, 실패했는지 기록)를 한쪽 터미널에서 돌리고, 다른 쪽에서 전환했습니다.

| 시각 | 한 일 | 결과 |
|---|---|---|
| 09:16:43 | 스크립트 시작 | 첫 응답 `blue` |
| 09:16:54 | 전환 전 확인: `green`이 살아 있는지 Nginx 안에서 물어봄 | `{"status":"ok"}`, `revision: green` |
| 09:16:55 | 설정의 서버 줄을 `server blue:8080;` → `server green:8080;`로 수정 | 한 줄만 바뀜 |
| 09:16:56 | `nginx -t` (설정 문법 검사) | `syntax is ok` |
| 09:16:56~57 | `nginx -s reload` | `signal process started` |
| **09:16:57.257** | 스크립트가 처음으로 `green` 응답 기록 | reload와 같은 초 |
| 09:17:09~10 | 롤백: 같은 줄을 `green` → `blue`, 검사, reload | 서버 줄이 처음 상태로 |
| **09:17:10.999** | 스크립트가 다시 `blue` 응답 기록 | reload의 1초 뒤 |

측정 요약은 **전체 요청 341건, 실패 0건**, 70초, blue 274건(80%), green 67건(20%)이었습니다. green이 응답한 구간은 약 14초(09:16:57~09:17:11)인데, 0.2초 간격이면 약 70건이고 실제 67건과 맞습니다. 80%와 20%는 "green이 응답한 시간이 70초 중 20%였다"는 뜻이지 분배 규칙이 아닙니다. 교안의 예시 화면(1013건, 실패 0건, 215초)과 건수·비율이 다른 것은 전환 시각을 제가 정했기 때문이고, 실패가 0건이라는 점은 같았습니다. 도우미의 내장 브라우저 화면의 배너도 전환하자 **GREEN**으로 바뀌었습니다.

설정 파일 수정은 노트 부록 A-6에 "미실행"으로 적어 두었던 PowerShell 방식(`(Get-Content …) -replace "server blue:8080;","server green:8080;" | Set-Content … -Encoding ascii`)을 처음으로 써 봤습니다. 전환과 롤백 두 번 모두 의도한 한 줄만 바뀌었고 Nginx가 문제없이 읽었습니다. 즉 **이 방식은 동작합니다.**

reload가 요청을 한 건도 놓치지 않은 이유는, Nginx가 껐다 켜지는 것이 아니라 이전 작업 프로세스는 하던 요청을 끝내고 새 작업 프로세스가 새 설정으로 새 요청을 받기 때문입니다(교안 설명). 그리고 순서를 지켰습니다. **수정 → 검사 → reload**, 그리고 이전 서버(blue)는 끄지 않고 남겨 뒀기 때문에 롤백이 1초 만에 가능했습니다.

**실험 ② 가중치 3 대 1 (09:18, 도우미가 실행)** 설정 파일은 편집기로 `server blue:8080 weight=3;`과 `server green:8080;`으로 바꾸고, 같은 방식으로 30초를 측정했습니다. 결과는 **전체 147건, 실패 0건**, blue 110건(75%), green 37건(25%)이었습니다. 110 대 37은 2.97 대 1로 3 대 1에 가깝습니다. 로그의 응답이 바뀐 시각을 보면 green이 약 0.6~0.8초(요청 4개)마다 한 번 나오고 그 사이에 blue가 세 번 응답하는 모양이어서, "4개마다 3개가 blue로" 가는 순서 세기가 그대로 보입니다. 이 숫자를 90 대 10, 99 대 1로 바꾸면 카나리 배포가 됩니다. 다만 이번에는 설정에 `zone` 줄을 둔 상태로만 실험했기 때문에, 그 줄을 뺐을 때 어긋나는지는 확인하지 못했습니다.

> 🧪 **예제** — [해설서 비유] 학교 급식실에 배식대가 두 개 있습니다. blue는 지금 학생들이 쓰는 배식대, green은 새로 준비해 둔 배식대, Nginx는 학생들을 어느 쪽으로 보낼지 정하는 안내 직원입니다. 새 배식대를 준비하는 동안에도 기존 배식대는 계속 쓰고, 준비가 끝나면 안내 직원의 지시만 바꿉니다. 서비스를 새로 만드는 일과 사용자의 목적지를 바꾸는 일을 **분리**하는 것이 핵심입니다.

> 🧪 **예제** — [보충 비유] 신규 생산라인을 병행 가동한 뒤 물량 배정표만 바꾸는 것과 같습니다. 문제가 생기면 배정표를 되돌리면 되니, 기존 라인을 바로 철거하지 않는 것이 롤백의 조건입니다. 가중치 3 대 1은 시범 판매 지점에 물량 일부만 먼저 배정해 보는 것과 같습니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 무중단 배포의 뼈대는 "새 것을 옆에 세워 두고, 목적지만 바꾸고, 옛것은 바로 치우지 않는다"입니다. 이 순서를 지키면 되돌리기가 쉬워집니다.
- 측정하세요. "끊기지 않았을 것 같다"가 아니라 요청 341건 중 실패 0건처럼 숫자로 말해야 합니다. 단, 이 숫자는 **그 측정 구간의 결과**일 뿐 모든 경우의 보증이 아닙니다.
- 새 버전으로 보내는 비율을 처음에는 작게 잡는 카나리 방식은 같은 장치(가중치)로 만듭니다.

**개발자에게 시킬 때 물어볼 것**
- 전환 전에 새 서버가 살아 있는지 확인했나요? 설정은 수정 → 검사 → reload 순서였나요?
- 이전 서버를 reload 직후 바로 끄지 않고 롤백용으로 남겨 뒀나요?
- 개발자용: 이 실습에서는 `nginx -t` 검사 뒤 `nginx -s reload`를 썼고, 컨테이너를 다시 띄우면 서버 주소가 바뀔 수 있어 다시 reload했다. 가중치 실험에서는 `zone active_app 64k;`로 작업 프로세스들이 순서를 함께 센다.

### 동료에게 설명하기

"서비스를 두 벌 띄워 놓고 앞에 문지기(Nginx)를 세웠어요. 설정 파일에서 서버 이름 한 줄만 blue에서 green으로 바꾸고 reload했더니, 0.2초마다 보낸 요청 341건이 하나도 실패하지 않았고 응답이 1초 안에 green으로 바뀌었어요. 되돌릴 때도 같은 한 줄만 바꾸면 됐고요. 서버 목록에 비율(3 대 1)을 주면 새 버전에 일부 요청만 보내 보는 카나리 배포도 같은 장치로 돼요."

## 2. 서버 하나가 멈추면 누가 비용을 내나 — 연결 대기 시간 기본값과 1초 {#2}

### 취지

1절은 모든 서버가 멀쩡할 때의 이야기였습니다. 현실에서는 서버가 갑자기 멈춥니다. 무료 Nginx에는 서버가 살아 있는지 **미리 점검하는 기능(능동 헬스체크)이 없습니다.** 그러면 서버 하나가 멈췄을 때 이를 알아채는 데 드는 비용을 누가 낼까요? 이 절은 그 답을 숫자로 봅니다.

### 검증 목표

- 가중치 3 대 1 상태에서 green을 멈추고, 기본 설정과 연결 대기 시간 1초 설정에서 **사용자 실패 수**를 비교한다.
- 교안이 말한 "연결 대기 시간(`proxy_connect_timeout`, 기본 60초)"이 이 PC에서 그대로 재현되는지 확인한다.

### 실제로 있었던 일

**③-a 기본 설정 (09:19~09:20, 도우미가 실행)** 스크립트를 60초 돌리고 약 10초 뒤인 09:19:28에 `docker stop green`을 실행했습니다(종료까지 약 4초). 09:19:31의 마지막 green 응답 이후, **09:19:32.482에 첫 실패**(`ReadTimeout`, 스크립트의 2초 제한 안에 답이 없음)가 찍혔고, 그 뒤 약 2.83초마다 한 번씩, 총 13번 실패했습니다. 마지막 실패는 09:20:06.439입니다. 요약은 **전체 159건, 실패 13건**, blue 130건(82%), green 16건(10%)이었습니다.

실패 간격 2.83초는 "green 차례 요청 하나가 2초 제한에 걸려 실패하는 시간 + 그 사이 blue 차례 요청 세 개(각 약 0.2초) + 간격" 한 바퀴의 길이와 맞습니다. 즉 **네 번에 한 번(green 차례)** 요청이 멈춘 채 기다리다 실패로 센 것이고, 나머지 blue 요청은 정상이었습니다.

그러다 09:20:10(Nginx 로그의 UTC 표기로는 00:20:10)에 Nginx 에러 로그에 두 줄이 남았습니다. `connect() failed (113: Host is unreachable) while connecting to upstream`, 그리고 `upstream server temporarily disabled`. 두 번째 줄은 Nginx가 한 번 실패한 green을 잠시 목록에서 뺐다는 뜻이고(기본 동작: 한 번 실패하면 10초 제외), 그 뒤로는 실패가 이어지지 않았습니다.

**교안과 달랐던 점**: 교안은 "Nginx는 연결 대기 시간(기본 60초)이 지나야 실패로 보고 다른 서버로 넘긴다"고 설명합니다. 이번에는 첫 실패(09:19:32)부터 Nginx가 그 서버를 빼는 로그(09:20:10)까지가 **60초가 아니라 약 38초**였고(사용자가 본 마지막 실패는 09:20:06, 약 34초 시점), 로그의 원인도 타임아웃이 아니라 `113: Host is unreachable`이었습니다. 멈춘 컨테이너의 주소로 가는 연결이 Docker 네트워크에서 응답을 못 받다가 운영체제가 도달 불가로 판정한 것으로 **추정**하지만, 확인한 것은 로그의 오류 문구와 시각까지이고 **38초가 정확히 왜 나왔는지는 확인하지 못했습니다.** Docker Desktop·Windows 11 환경 때문일 수 있습니다. 그래도 교안의 핵심("알아채는 비용을 사용자 요청이 낸다")은 그대로 재현됐습니다. 실패 13건이 곧 알아채는 데 쓰인 요청들입니다.

**③-b 연결 대기 1초 (09:21~09:23, 도우미가 실행)** green을 다시 켠(`docker start green`) 뒤, `location /` 안에 `proxy_connect_timeout 1s;` 한 줄만 더하고 검사·reload(green을 다시 켰으니 이름을 다시 찾게 하려고)했습니다. 같은 실험을 반복했고(09:21:33 green 정지, 09:21:37 종료), 결과는 **전체 272건, 실패 0건**, blue 257건(94%), green 15건(6%)이었습니다. 에러 로그는 정지가 끝난 1초 뒤인 09:21:38에 `upstream timed out (110: Operation timed out) while connecting to upstream`과 `upstream server temporarily disabled`가 남았습니다. 이어서 약 12초 간격으로 같은 두 줄이 반복되는데, Nginx가 제외 시간(기본 10초)이 지나면 실제 요청 하나를 green에 다시 보내 보고, 1초 만에 실패하면 다시 빼기 때문입니다.

이 대가를 따로 쟀습니다(09:22:46부터 30초, green 정지 상태에서 0.2초 간격 52건). 0.5초를 넘긴 요청은 **2건**이었고, 둘 다 약 1초(1.006초, 1.015초)에 상태 코드 200으로 끝났습니다(09:22:49, 09:23:04, 약 15초 간격). 나머지 50건은 0.5초 이하였습니다.

| 항목 | ③-a 기본값 | ③-b 1초 |
|---|---|---|
| 요청 수 (60초) | 159 | 272 |
| **실패 수** | **13건** | **0건** |
| Nginx가 멈춘 서버를 알아챈 시점 | 멈춘 뒤 약 38초(`113 Host is unreachable`) | 멈춘 뒤 1초(`110 Operation timed out`, 설정한 1초) |
| 사용자가 겪은 것 | 네 번에 한 번 멈췄다가 2초 제한에서 실패 | green 차례 요청이 약 1초 늦게 200 |
| green을 뺀 뒤 | 더 이상 실패 없음 | 12~15초마다 요청 하나가 1초씩 더 기다림 |

1초 설정에서 실패가 0건이 된 이유는, Nginx가 1초 안에 실패로 보고 **같은 요청을 blue로 다시 보냈고** 스크립트의 2초 안에 blue 응답이 돌아왔기 때문입니다. 세 가지가 재현됐습니다. 대기 시간을 줄이면 실패가 사라지고(13 → 0), 대신 green 차례 요청은 1초 늦어지며, green을 뺀 뒤에도 일정 간격마다 한 요청이 1초를 더 기다립니다. 또 ③-a에서는 교안의 60초가 재현되지 않은 것과 달리 ③-b에서는 **설정한 1초가 그대로 동작**했습니다.

한계도 있습니다. 대기 시간을 너무 짧게 잡으면 잠깐 바빠서 늦게 연결된 정상 서버까지 실패로 볼 수 있다고 교안이 경고하지만, **이번에는 그런 오판을 시험하지 않았습니다.** 또 `proxy_connect_timeout`은 연결을 맺는 단계에만 적용되어서, 연결된 뒤 응답이 늦어지는 경우는 이 값으로 다루지 못합니다(별도 읽기 제한을 봐야 함).

> 🧪 **예제** — [보충 비유] 키맨 리스크입니다. 핵심 업무를 한 사람만 알고 있다가 그 사람이 휴가를 가면 부서가 멈춥니다. 대체 인력(이중화)만으로는 부족하고 결근을 알아채는 체계와 업무를 넘기는 절차가 있어야 합니다. 무료 Nginx는 출근부 없이, 전화를 넘겨 보고 안 받으면 그제야 결근으로 아는 안내 직원입니다. 그 "넘겨 보는 전화"가 사용자의 실제 요청이라서 비용을 사용자가 냅니다. 연결 대기 시간 1초는 "안 받으면 1초만 기다리고 옆 상담원에게 넘겨라"는 지침이고, 60초나 38초 설정은 한참 기다린 뒤에야 넘기는 지침입니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 서버 이중화의 가치는 "고장을 얼마나 빨리 알아채고 넘기느냐"로 결정됩니다. 서버를 두 대 둔 것만으로는 사용자가 겪는 고장 시간이 줄지 않을 수 있습니다.
- 알아채는 방식에는 두 가지가 있습니다. 실제 요청이 실패하는 것을 보고 알아채는 방식(수동)과, 따로 주기적으로 점검하는 방식(능동)입니다. 무료 Nginx는 앞의 것뿐이고, 그 비용은 사용자 요청이 냅니다.
- 이 실습의 숫자(38초, 13건)는 이 PC 환경의 결과입니다. 교안의 60초와 달랐던 것은 오류가 아니라 환경 차이일 수 있으니, 자기 환경에서 직접 재 보세요.

**개발자에게 시킬 때 물어볼 것**
- 서버 하나가 멈췄을 때 사용자 실패가 몇 건 나는지, 연결 대기 시간을 몇 초로 두었는지 알려 주세요. 기본값 그대로인가요?
- 능동 헬스체크가 필요한 서비스인가요(필요하면 로드밸런서 선택부터 다시 봐야 합니다)?
- 개발자용: `proxy_connect_timeout`은 연결 시도에만 적용된다. 응답이 늦어지는 경우는 읽기 타임아웃을 따로 보고, 너무 짧게 잡으면 정상 서버를 잘못 뺄 수 있어 오판 시험이 필요하다(이번에는 하지 않았다).

### 동료에게 설명하기

"서버 두 대 중 하나를 일부러 멈춰 봤어요. 기본 설정에서는 60초 동안 요청 159건 중 13건이 실패했어요. 문지기가 '저 서버 죽었네'를 요청이 실패해야 알기 때문이에요. 연결 대기 시간을 1초로 줄이니 272건 중 실패가 0건이 됐고, 대신 죽은 서버로 갈 차례였던 요청이 1초씩 늦게 응답했어요. 교안은 60초라고 했는데 제 PC에서는 약 38초였어요. 왜 38초인지는 확인 못 했고요. 어쨌든 알아채는 비용을 사용자가 낸다는 건 같았어요."

## 3. "전환 성공"과 "무중단"은 다르다 — 메모리에 있던 대화가 사라지는 장면 {#3}

### 취지

1~2절에서는 "요청이 끊기는가"만 봤습니다. 그런데 사용자는 요청 하나하나보다 **하던 일이 이어지는지**를 느낍니다. 이 절은 실패 0건이었던 바로 그 전환이 사용자에게는 어떤 일이었는지를 봅니다.

### 검증 목표

- blue에서 한 대화·약속이 green으로 전환했을 때 보이는지, 롤백하면 어떻게 되는지, blue를 재시작하면 어떻게 되는지 확인한다.

### 실제로 있었던 일

이때는 서비스가 `storage: memory`로, 두 서버가 각자 자기 메모리에 대화·약속을 두고 있었습니다. 도우미는 브라우저 대신 같은 API를 파이썬(`httpx`)으로 호출해 단계마다 대화 메시지·약속·기억의 개수를 셌습니다(한글 JSON을 `curl -d`로 보내면 깨지는 문제를 피하려는 선택이었습니다).

| 단계 | 시각 | 한 일 | 응답한 쪽 | 대화 메시지 | 약속 | 기억 |
|---|---|---|---|---|---|---|
| 0 | 09:24:06 | 시작 상태 | blue | 0 | 0 | 0 |
| 1 | 09:24:07 | "내일 아침 8시에 물 마시라고 알려 줘" 전송 | blue | **2** | **1** | 0 |
| 2 | 09:24:19 | **green으로 전환** | green | **0** | **0** | 0 |
| 3 | 09:24:30 | **blue로 롤백** | blue | **2** | **1** | 0 |
| 4 | 09:24:40 | `docker restart blue` + reload | blue | **0** | **0** | 0 |

1단계에서는 가짜 AI가 규칙으로 약속 저장 도구를 골라 "약속을 저장했습니다: 10월 29일(목) 08:00에 '물 마시기'."라고 답했고, 약속은 `pending` 상태로 저장됐습니다. 2단계에서 요청은 성공했지만 green에는 그 대화도 약속도 **없었습니다.** 3단계에서 롤백하자 2개·1개가 **그대로 다시 나타났습니다.** 데이터가 지워진 것이 아니라 blue 서버의 메모리에만 있었던 것입니다. 4단계에서 blue를 다시 시작하자 **완전히 사라졌습니다.** 컨테이너가 새로 시작하면 메모리가 비워집니다. 교안 5-6의 결과 해석이 숫자까지 그대로 재현됐습니다.

즉 1절의 전환(실패 0건)은 사용자에게 "대화가 사라진 것"이었습니다. **"전환 성공"과 "무중단"은 다릅니다.** 교안은 이런 구조에서는 새 버전을 배포할 때마다 대화가 사라지고, 컨테이너가 둘일 때는 새로고침마다 보이는 대화가 달라질 수 있다고 설명합니다. 뒤의 것은 이번에 직접 시험하지는 않았습니다.

> 🧪 **예제** — [해설서 비유] 상담실이 두 개 있습니다. 새 상담실로 안내를 바꿨는데 고객이 기다리지 않고 상담을 받았다면 요청은 성공입니다. 그런데 새 상담원이 고객의 이전 상담 내용을 모른다면, 고객은 연결은 됐어도 같은 설명을 처음부터 다시 해야 합니다. 상담원마다 자기 수첩에만 기록하던 방식에서는, 고객이 다른 상담원에게 가는 순간 이력이 끊깁니다. 그 상담원이 퇴근(재시작)하면 수첩도 사라집니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 무중단은 한 가지가 아니라 다섯 가지 질문입니다. 요청이 실패했나(가용성), 얼마나 기다렸나(지연), 하던 일이 이어지나(상태 연속성), 재시작해도 남나(데이터 지속성), 되돌릴 수 있나(롤백). 실패 건수는 첫 번째 질문의 답일 뿐입니다.
- 서버 메모리에만 있는 기록은 전환·재시작에서 사라집니다. 이것은 버그가 아니라 구조입니다.
- 사용자에게 중요한 기록이 어디에 저장되는지를 먼저 물으세요.

**개발자에게 시킬 때 물어볼 것**
- 사용자의 대화·약속·설정은 서버 메모리에 있나요, 외부 저장소에 있나요? 새 버전 배포나 재시작 때 이 기록이 남는지 시험해 봤나요?
- 개발자용: `/version`이 `storage` 값을 보여 줘서 메모리 모드인지 바로 확인할 수 있다. 환경변수 `STORAGE`·`AUTH`가 이를 정한다.

### 동료에게 설명하기

"전환할 때 요청은 하나도 안 실패했는데, 전환해 보니 방금 한 대화랑 약속이 안 보였어요. 대화가 blue 서버 메모리에만 있었거든요. blue로 되돌리면 다시 보이고, blue를 재시작하면 영영 사라졌어요. 그래서 '전환 성공'과 '무중단'은 다르다고 말해요. 실패 건수만 보면 놓치는 거예요."

## 4. 대화를 서버 밖으로 — Supabase, 무상태 서버, 키 세 개, RLS, 게스트 로그인 {#4}

### 취지

3절의 해결책은 하나입니다. **서버가 대화의 유일한 사본을 자기 메모리에 두지 않게** 하는 것입니다. 그렇다고 서비스에 기록이 없어지는 것이 아니라, 기록을 서버 메모리에서 서버 밖 데이터베이스로 옮기는 것입니다. 이번 실습은 Supabase(데이터베이스와 로그인 기능을 함께 빌려 주는 서비스)를 썼습니다. 개인 수첩에 쌓아 둔 고객 이력을 모두가 쓰는 공용 CRM으로 옮기는 일과 같습니다.

### 검증 목표

- 사용자(저)가 Supabase 프로젝트를 직접 만들고, 테이블을 만들고, 게스트 로그인을 켠다.
- `.env`로 서버 두 개를 Supabase에 연결해 시작 로그에서 저장소 스위치가 바뀐 것을 확인한다.

### 실제로 있었던 일

이 절의 대시보드 작업과 `.env` 편집은 모두 제가 직접 했습니다. 계정·키·비밀번호를 다루는 일은 도우미가 대신하지 않는다는 원칙이어서, 도우미는 여기까지의 기록을 정리하고 제가 할 단계를 안내한 뒤 거기서 멈췄습니다.

**프로젝트 만들기 (09:39)** 무료(Free) 조직에서 시험용임을 알 수 있는 이름으로 만들었습니다. 조직에 이전 프로젝트 3개가 있었지만 모두 일시정지(Paused) 상태여서 아무것도 멈추거나 지우지 않고 새로 만들 수 있었습니다. 만든 뒤 리전은 East US (Ohio) · us-east-2로 배정된 것을 확인했고(교안이 권한 리전), 컴퓨트는 Nano(무료), 상태는 Healthy였습니다.

**테이블 만들기 (09:42)** SQL Editor에 템플릿의 `0001_init.sql` 전체를 붙여 넣고 실행했더니 테이블이 **6개**(`characters`, `memories`, `messages`, `reminders`, `summaries`, `user_settings`) 생겼습니다. 교안 본문은 5개(캐릭터·대화·요약·기억·약속)로 말하지만 실제로는 `user_settings`가 하나 더 있습니다. 이 SQL은 `create table if not exists`라 다시 실행해도 안전하고, 각 테이블에 RLS를 켜기만 할 뿐 허용 규칙(정책)은 하나도 만들지 않습니다. 그래서 허용 정책이 0개라 브라우저의 publishable key로는 표를 직접 읽고 쓸 수 없는 구조이고, 서버(secret key)만 접근합니다(이 키로 직접 읽기를 시험해 본 것은 아니고, 정책이 없다는 사실에서 나온 설명입니다).

**게스트 로그인 켜기 (09:45)** `Authentication > Sign In / Providers`에서 `Allow anonymous sign-ins`를 켰다고 제가 알렸습니다. 이 단계는 도우미가 화면으로 확인하지 못했고, 실제로는 나중에 브라우저가 "게스트로 사용 중"으로 뜬 것으로 확인했습니다. 교안은 익명 로그인 한도(기본 IP당 시간당 30건)도 확인하라고 하는데, 이번 실습에서 그 값을 확인했다는 기록은 없습니다.

**키 세 개의 역할** `.env`에 넣는 값은 다섯 줄입니다. `STORAGE=supabase`와 `AUTH=supabase`는 저장소와 로그인을 Supabase로 바꾸는 스위치이고, 나머지 세 줄이 프로젝트 주소(URL)와 키 두 개입니다.

| 값 | 용도 | 취급 원칙 |
|---|---|---|
| `SUPABASE_URL` | 어떤 프로젝트에 연결할지 | 앱 설정에 사용 |
| `SUPABASE_PUBLISHABLE_KEY` | 브라우저에서 인증과 공개 API 접근 | 드러나도 RLS 때문에 표를 직접 읽을 수 없다(교안 설명, 이번에 직접 시험하지는 않음). 단, RLS가 제대로 켜져 있어야 한다 |
| `SUPABASE_SECRET_KEY` | 서버에서 높은 권한으로 접근 | RLS를 건너뛰어 모든 사용자의 행을 읽고 쓸 수 있다. **서버에만 두고** 브라우저·채팅·문서에 노출하지 않는다 |

도우미는 `.env`의 내용을 읽거나 출력하지 않는다는 규칙을 지켰습니다. 변수 이름은 `.env.example`로만 확인했고, 값이 맞게 들어갔는지는 컨테이너 시작 로그의 `"storage": "supabase"`, `"auth": "supabase"`로만 확인하기로 했습니다. 이 규칙 때문에 일이 한 번 돌아갔는데, 그 이야기는 6절에 있습니다.

**왜 게스트 로그인이 필요한가** 앱은 접속하는 브라우저마다 가입 없이 게스트 사용자를 한 명 만들고, 서버는 모든 조회에 그 사용자의 ID 조건을 붙여 대화를 사용자별로 나눕니다. 로그인 없이 데이터베이스만 켜면 모든 방문자의 대화가 한 사람 것으로 섞이므로, 템플릿은 그런 설정이면 앱이 시작하지 않게 막아 뒀습니다.

**무상태가 되었다** 마지막으로 서버 두 개를 `.env`로 다시 띄운 결과(6절의 `.env` 일을 겪은 뒤)는 두 컨테이너의 시작 로그가 `"storage": "supabase", "auth": "supabase"`, `Uvicorn running`이었습니다(09:55). 앱이 시작을 거부하지 않았으므로 코드의 검사(`STORAGE=supabase`이면 인증·URL·두 키가 모두 있어야 함)를 통과한 것입니다. 이제 blue와 green은 대화의 유일한 사본을 들고 있지 않는, 언제 꺼지고 새로 켜져도 되는 **무상태 서버**입니다. 환경변수는 컨테이너를 새로 만들어야 반영된다는 것도 알게 됐습니다(`docker restart`로는 안 됩니다).

> 🧪 **예제** — [해설서 비유] 이전에는 상담원마다 자기 수첩에 대화를 기록했습니다. 이번에는 상담 내용을 모두가 함께 쓰는 중앙 고객 기록 시스템에 저장합니다. blue도 green도 같은 기록을 읽고 상담하니, 한 명이 퇴근(재시작)해도 기록은 남습니다.

> 🧪 **예제** — [보충 비유] publishable key는 건물 로비의 방문증이고, secret key는 서류 보관실 마스터키입니다. 방문증이 노출돼도 서류함(RLS)이 잠겨 있으면 서류를 볼 수 없지만, 마스터키가 노출되면 모든 사용자의 기록이 열립니다. 그래서 마스터키는 서버 담당자만 갖습니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 서버가 언제 꺼져도 사용자 기록이 남게 하려면, 기록을 서버 밖 저장소로 옮기는 구조가 먼저입니다. 서버를 늘리고 바꾸는 자유는 그다음에 따라옵니다.
- 키는 두 종류입니다. 노출돼도 되는 것(publishable)과 절대 노출되면 안 되는 것(secret)을 구분해서 다루세요. 비밀 값은 채팅·문서에 붙여 넣지 않습니다.
- 여러 사용자의 기록이 한 표에 쌓이는 서비스라면 "남는가"만큼 "다른 사람 것이 섞이지 않는가"가 중요합니다.

**개발자에게 시킬 때 물어볼 것**
- 사용자 기록의 저장소는 어디이고, 접근 제한(RLS 같은)은 켜져 있나요? 브라우저용 키로 표를 직접 읽을 수 있는지 시험해 봤나요?
- 비밀 키는 어디에 보관하나요(로컬은 커밋하지 않는 `.env`, 배포 환경은 시크릿 저장소)?
- 개발자용: 템플릿 SQL은 `GRANT` 없이 RLS만 켠다. 새 Supabase 화면의 보안 옵션과 맞물리는 부분은 6절에 적었다.

### 동료에게 설명하기

"서버 메모리에 있던 대화를 Supabase라는 외부 데이터베이스로 옮겼어요. 환경변수 두 줄(STORAGE, AUTH)을 바꾸고 컨테이너를 새로 띄우니, 서버가 대화를 자기 메모리에 들고 있지 않게 됐어요. 키는 두 종류라서, 브라우저용(publishable)은 노출돼도 되지만 서버용(secret)은 서버에만 둬요. 사용자별로 대화가 안 섞이게 하려고 가입 없는 게스트 로그인을 켰고요."

## 5. 직접 확인한 세 가지 — green 전환·blue 재시작·시크릿 창 {#5}

### 취지

데이터를 밖으로 옮겼다고 해서 끝이 아닙니다. 3절에서 사용자가 겪은 세 장면(전환·재시작·다른 사용자)이 이번에는 어떻게 되는지 같은 방식으로 다시 봐야 합니다. 이 절의 브라우저 확인과 Supabase 화면 확인은 제가 직접 했습니다.

### 검증 목표

- 대화·약속이 Supabase에 쌓이는지(①), green으로 전환해도 이어지는지(②), blue를 재시작해도 이어지는지(②-b), 다른 브라우저(시크릿 창)에서는 앞의 대화가 보이지 않는지(③)를 확인한다.

### 실제로 있었던 일

**① 데이터가 Supabase에 쌓였다 (14:19)** Docker 재시작 직후(6절) blue가 활성인 상태에서, 제가 브라우저에서 `http://localhost:8080`을 열고 게스트로 접속해 캐릭터를 저장한 뒤 "내일 아침 8시에 물 마시라고 알려 줘"를 보냈습니다. Supabase `Table Editor`의 `messages` 테이블에는 행이 **3개**(모두 같은 사용자 ID) 있었습니다. 순서대로 앱이 열릴 때 캐릭터가 먼저 건넨 인사(`greeting`, 14:15:45), 제 문장(14:16:00), 약속을 저장했다는 답(14:16:01)입니다. 3절에서는 메시지가 2개였는데 이번에 3개인 것은 인사 메시지가 하나 더 있기 때문입니다(도우미의 API 확인은 화면을 거치지 않아 인사가 없었습니다). `reminders` 테이블에는 행이 1개 있었습니다. 내용은 "물 마시기", 시각은 데이터베이스에 UTC로 2026-10-28 23:00:00로 저장돼 있고 앱이 한국 시간 10월 29일(목) 08:00으로 바꿔 보여 줍니다. 상태는 `pending`입니다. 3절에서 메모리에 있던 약속이 이번에는 데이터베이스 행으로 남았습니다.

화면에 `Add RLS policy` 버튼이 보여서 RLS가 켜져 있고 정책이 0개인 상태와 맞았고, `id`가 1부터 시작했으며, `messages`와 `reminders`의 사용자 ID가 같은 값이었습니다(사용자별 분리의 근거).

**② green으로 전환해도 이어진다 (14:19~14:24)** 도우미가 14:19에 Nginx를 green으로 바꿨고(`/version`이 `revision: green`, `storage: supabase`), 제가 브라우저를 새로고침했습니다. 맨 위 배너가 **GREEN**으로 바뀌었고, 대화창에 인사 → 제 문장 → 약속 저장 답, 3개가 **그대로** 보였으며, 캐릭터 카드와 "게스트로 사용 중" 표시도 그대로였습니다. 3절에서는 같은 전환 뒤에 0개였습니다. 오른쪽 "이번 턴(개발용)" 패널이 비어 있는 것은, 새로 보낸 메시지가 없으면 비는 화면이기 때문에 정상입니다.

**②-b blue를 재시작해도 이어진다 (14:24~14:26)** green이 활성인 동안 도우미가 `docker restart blue`로 blue만 재시작했고(blue 메모리가 비워짐), 설정을 `server blue:8080;`으로 되돌린 뒤 reload했습니다(14:25:01). 재시작한 blue의 시작 로그도 `storage: supabase, auth: supabase`였습니다. 제가 새로고침하자 배너 **BLUE**에 대화 3개가 **그대로** 있었고, 새로고침해도 인사 메시지가 또 생기지 않았습니다(인사는 대화가 비어 있을 때 처음 한 번만 만들기 때문입니다). 3절의 마지막 장면(재시작하면 0/0)과 같은 조작인데 결과가 반대입니다.

| | 3절 (메모리) | 이 절 (Supabase) |
|---|---|---|
| blue → green 전환 후 | 대화·약속 **0개** | 대화·약속 **그대로** |
| blue 재시작 + reload 후 | **0/0** (완전히 사라짐) | 대화 3개·약속 **그대로** |

**③ 시크릿 창에서는 다른 사람이다 (14:33)** 제가 Chrome 시크릿 창에서 `http://localhost:8080`(blue 활성)을 열었습니다. 첫 번째 게스트를 "게스트 A", 시크릿 창의 게스트를 "게스트 B"라고 부르겠습니다.

1. 시크릿 창의 대화 화면은 **비어 있었습니다.** 배너 BLUE, "게스트로 사용 중", 기본 캐릭터 카드. 게스트 A의 대화 3개는 보이지 않았습니다.
2. 게스트 B로 "내 약속 뭐 있어?"를 보내자 답이 "(가짜 응답) 저장된 약속이 없습니다."였습니다. 게스트 A의 약속 "물 마시기"는 게스트 B에게 나오지 않았습니다.
3. Supabase `messages` 테이블이 **6개 행**이 됐습니다. 1~3번은 게스트 A의 것(그대로), **4~6번은 다른 사용자 ID**(앞 8자리가 게스트 A와 다름)로 쌓였습니다. 인사 → "내 약속 뭐 있어?" → "저장된 약속이 없습니다." 순입니다.

즉 사용자 분리를 "화면에서 앞의 대화가 안 보인다"와 "표에 서로 다른 사용자 ID로 나뉘어 쌓인다"라는 **두 가지 증거**로 함께 확인했습니다. 교안의 설명대로 시크릿 창이 새 게스트가 됐고, 서버가 그 사용자 ID로만 조회해 앞의 대화가 보이지 않았습니다. 화면의 "이 브라우저에만 저장됩니다" 문구도 같은 뜻으로 읽힙니다. 같은 사람이 브라우저를 바꾸면 다른 게스트가 됩니다. 확인하지 못한 것도 있습니다. 게스트 B는 약속을 만들지 않았으니 `reminders`는 1행 그대로일 것으로 예상하지만 **그 표는 캡처하지 않아 확인하지 못했습니다.**

새로 관찰한 것도 하나 있습니다. 시크릿 창 화면의 "걸린 시간" 패널이 도구 선택·첫 글자·답 전체 모두 **3.0초**였습니다. 가짜 AI는 외부 AI를 부르지 않는데도 3초가 걸린 것입니다. 저장소가 한국이 아닌 미국 동부(Ohio)의 데이터베이스라서 요청 하나에 데이터베이스를 여러 번 왕복하는 시간이 든 것으로 **추정**합니다. 서울 리전에서 같은 요청을 재 보지 않았기 때문에 확인된 것은 아닙니다. 기록을 서버 밖으로 옮기면 지연이 늘 수 있다는 점과, 리전 선택이 중요하다는 교안의 이유가 이어집니다.

> 🧪 **예제** — [해설서 비유] 이제 blue 상담원이 퇴근해도, green 상담원이 새로 투입돼도, 고객 이력은 중앙 기록 시스템에 남아 있어 상담이 이어집니다. 그리고 그 시스템은 고객별로 이력을 따로 보관해서, 다른 고객이 와도 앞 고객의 이력은 보이지 않습니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 같은 조작(전환, 재시작)을 구조 변경 전후로 반복해서 결과를 비교하세요. "전에는 0개, 지금은 그대로"가 가장 설득력 있는 증거입니다.
- 사용자 분리는 화면 증거 하나로 끝내지 말고 **데이터 증거**(표에 서로 다른 사용자 ID로 쌓였는지)까지 같이 보세요.
- 기록을 서버 밖에 두면 거리(지연)라는 새 비용이 생길 수 있습니다. 어디에 두느냐(리전)도 선택입니다.

**개발자에게 시킬 때 물어볼 것**
- 사용자별로 기록이 나뉘는 것을 화면과 데이터 두 쪽에서 확인했나요? 비밀 키로 접근하는 서버 코드가 모든 조회에 사용자 조건을 붙이고 있나요(RLS를 건너뛰는 키이기 때문입니다)?
- 데이터베이스의 리전은 서버와 가까운가요? 왕복이 느릴 때를 측정해 봤나요?

## 6. 실습 중 부딪힌 일과 교안과 달랐던 점 {#6}

### 취지

계획대로만 되는 실습은 없습니다. 부딪힌 일은 실패가 아니라 **다음 번에 미리 막을 함정 목록**입니다. 이 절은 구체적으로 무슨 일이 있었는지를 남깁니다.

### 검증 목표

- 부딪힌 일의 원인과 대응을 기록하고, 교안(v1.0 노트)과 달랐던 점을 숨기지 않고 모은다.

### 실제로 있었던 일

**① Docker Desktop이 꺼져 있었다 (두 번)** 시작 때(09:15)는 `docker`가 엔진에 연결하지 못했고(`failed to connect to the docker API`), 도우미가 Docker Desktop을 실행하자 약 20초 뒤 엔진이 올라왔습니다. 두 번째는 14:14에 제 Chrome에서 `http://localhost:8080`이 `ERR_CONNECTION_REFUSED`로 열리지 않을 때였습니다. 마지막 재기동(09:55) 이후 시간이 지나 Docker Desktop이 꺼져 있었고, 엔진이 다시 올라오자 컨테이너 3개가 모두 `Exited (255)`로 남아 있었습니다. 컨테이너를 `--restart` 옵션 없이 띄웠기 때문에 Docker가 꺼지면 같이 멈추고 자동으로 돌아오지 않습니다. 도우미가 `docker start blue green bg-nginx`와 reload(재시작하면 서버 주소가 바뀔 수 있어서)로 살렸고, `docker start`는 컨테이너를 새로 만들지 않아 처음 줄 때의 환경변수(Supabase 설정)가 그대로 유지됐습니다(`/version`이 `storage: supabase`). 서버는 언제든 꺼질 수 있다는 4절의 주제를 우연히 한 번 더 겪은 셈입니다. 운영 서버에서는 재시작 정책이나 관리 도구가 이 일을 합니다.

**② `.env`에서 기존 줄을 고쳐야 했다 (09:50~09:55)** 첫 재기동(09:50)의 시작 로그가 `"storage": "memory", "auth": "none"`이었습니다. 앱이 시작을 거부하지도 않았습니다. 기대한 `supabase`가 아니었습니다. 컨테이너에는 `STORAGE=supabase`가 전달되지 않았다는 뜻입니다. 그런데 도우미는 `.env`를 읽지 않는 규칙이라 원인을 직접 볼 수 없어서, 가능한 이유 다섯 가지(저장 안 됨, 다른 위치의 `.env`, 주석 처리, 같은 이름의 중복 줄, 공백·특수문자)를 들고 제가 직접 실행할 **값이 나오지 않는 점검 명령**을 안내했습니다. 제가 실행한 결과는 이랬습니다. 파일은 09:49:54에 저장돼 있었고(재기동 직전), `STORAGE`·`AUTH` 줄은 각각 한 줄뿐인데 값이 **10번 줄 `STORAGE=memory`, 11번 줄 `AUTH=none`**이었습니다. 원인은 새 줄을 더하면서 **원래 있던 줄의 값을 바꾸지 않은 것**이었습니다. 교안은 "다섯 줄을 넣는다"고만 해서, 이미 있는 줄을 **고치는** 일이라는 점이 빠지기 쉽습니다. 이어서 점검한 세 값은 각 줄이 한 개씩이고 글자 수가 URL 40자, publishable 46자, secret 41자로 형식과 맞아서 값이 제대로 들어 있다고 판단했고, 값 자체는 보지 않았습니다. 두 줄이 `supabase`로 바뀐 뒤(고쳐 저장했다는 별도 보고 없이 재기동 로그로 확인했습니다) 두 번째 재기동(09:55)이 성공했습니다. 같은 명령인데 두 줄만 `memory`·`none` → `supabase`로 바뀌어 결과가 달라졌으니 "설정은 코드가 아니라 환경변수 한 줄로 바뀐다"는 장면이 오히려 선명하게 재현됐습니다. 그리고 값이 맞는지 보는 방법은 시작 로그 첫 줄의 `storage`·`auth`였습니다.

**③ Git Bash가 경로를 바꿔 버렸다** `docker exec bg-nginx cat /etc/nginx/conf.d/default.conf`를 Git Bash에서 실행하자 `cat: can't open 'C:/Program Files/Git/etc/nginx/conf.d/default.conf'`가 나왔습니다. Git Bash가 `/etc/...`를 윈도 경로로 바꿔서 컨테이너에 넘긴 것입니다(교안의 PowerShell에서는 일어나지 않음). 명령 앞에 `MSYS_NO_PATHCONV=1`을 붙이자 정상이었고, 이후 실습의 `docker exec` 명령은 모두 그렇게 실행했습니다. N050 때와 같은 증상입니다. 한글 JSON을 `curl`로 보내면 깨지는 문제는 처음부터 피해서, 3절의 확인은 파이썬(`httpx`)으로 했습니다.

**④ 지구본 아이콘은 RLS 표시가 아니었다 (09:42 직후)** 테이블을 만든 뒤 이름 옆에 지구본 모양 아이콘이 보였습니다. 앞서 도우미가 "이름 옆에 RLS 표시가 있어야 한다"고 안내했는데, **그것은 틀린 설명**이었습니다. 지구본은 RLS가 아니라 "Data API에 노출된 테이블"이라는 표시였고(프로젝트를 만들 때 "Automatically expose new tables"를 켜 둬서 붙은 것), RLS가 켜졌는지는 각 테이블을 열었을 때 상단 표시로 확인해야 합니다. 5절에서 `messages` 화면의 `Add RLS policy` 버튼으로 확인했습니다. 안내가 틀렸을 때 바로 정정해 기록으로 남겼다는 점이 이 일의 요점입니다.

## 7. 내 서비스에 적용하면 (선택) {#7}

### 취지

이번 실습의 대상은 AI 친구 에이전트였지만, 사용자의 개인 기록이 쌓이는 모든 서비스에 같은 질문이 적용됩니다. 노트는 MSM(My-Story-Maker)처럼 사용자의 개인 기록을 다루는 서비스라면 데이터가 사라지지 않는 것뿐 아니라 **다른 사용자의 기록이 섞이지 않는 것**이 매우 중요하다고 짚습니다. 이 절은 그 점을 실제로 적용한다면 무엇을 확인할지를 정리합니다. **MSM에 적용해 본 것은 아니고**, 이번 실습에서 확인한 방법을 옮겨 놓은 것입니다.

### 검증 목표 (적용할 때 확인할 것)

- 사용자 기록이 서버 메모리가 아닌 외부 저장소에 있는가, 그리고 기록이 사용자별로 분리되는가.

### 적용 원칙

**누구나 알아야 할 원칙**

**개발자에게 시킬 때 물어볼 것**
- 사용자 기록은 서버 메모리에만 있는 부분이 없나요? 있다면 어디까지가 재시작에서 사라지나요?

### 동료에게 설명하기

"무중단 배포를 확인할 때 저는 세 가지를 같이 봐요. 요청이 끊기는지(실패 건수), 하던 일이 이어지는지(대화가 남는지), 되돌릴 수 있는지(롤백)요. 이번 실습에서 실패는 0건이었는데도 대화는 사라졌었어요. 그래서 사용자 기록이 서버 메모리에 있는지부터 물어봐요. 개인 기록 서비스면 사용자끼리 안 섞이는지도 시크릿 창으로 꼭 확인하고요."

> 📌 **요약** — 이번 실습의 한 줄 교훈은 **"무중단은 요청이 안 끊기는 것만이 아니라, 사용자가 하던 일이 이어지는 것이다. 기록은 서버 밖에 두고, 서버는 언제든 바꿀 수 있게 만든다"**입니다. 설정 한 줄로 전환하고(341건, 실패 0건), 서버가 멈추면 알아채는 비용을 사용자 요청이 내며(13건 대 0건), 메모리의 대화는 전환·재시작에서 사라진다는 것(0/0)을 숫자로 봤고, 기록을 Supabase로 옮긴 뒤 같은 조작에서 대화 3개가 그대로 남는 것까지 직접 확인했습니다.

## 8. 용어 사전 {#8}

| 용어 | 쉬운 설명 |
|---|---|
| 로드밸런서 · 블루-그린 · reload · 가중치와 카나리 · 헬스체크 · 무상태 서버 · Supabase · RLS | 위의 "미리 보는 용어" 표 참고 |
| 리버스 프록시 | 사용자 요청을 대신 받아 뒤의 서버로 넘기고 응답을 돌려주는 문지기. 이번 실습의 Nginx가 이 역할 |
| upstream | Nginx가 요청을 넘길 뒤쪽 서버들의 목록. 이번에는 `blue` 또는 `green` |
| `nginx -t` | Nginx 설정 파일의 문법을 미리 검사하는 명령. reload 전에 먼저 한다 |
| 롤백 | 문제가 생겼을 때 이전 상태로 되돌리는 것. 이번에는 설정의 서버 줄을 다시 `blue`로 바꾸기 |
| `proxy_connect_timeout` | Nginx가 뒤쪽 서버에 연결을 시도하며 기다리는 최대 시간. 기본 60초, 이번 실험에서 1초로 줄임. 연결을 맺는 단계에만 적용된다 |
| 수동 헬스체크 · 능동 헬스체크 | 실제 요청이 실패한 뒤에야 서버를 빼는 방식(무료 Nginx) · 따로 주기적으로 서버 상태를 점검하는 방식 |
| `113: Host is unreachable` | 연결 시도가 운영체제 수준에서 "도달할 수 없음"으로 실패했다는 오류 코드. 이번 약 38초 관찰에서 Nginx 로그에 남음 |
| `110: Operation timed out` | 연결 대기 시간이 지나 실패했다는 오류 코드. 1초 설정 실험에서 남음 |
| 단일 장애점 | 그것 하나가 멈추면 전체가 멈추는 부분. 비유하면 키맨 리스크 |
| 무중단 배포의 다섯 점검 영역 | 요청 가용성 · 응답 지연 · 상태 연속성 · 데이터 지속성 · 롤백 |
| 환경변수 `STORAGE`·`AUTH` | 서비스의 저장소와 로그인 방식을 정하는 스위치. `memory`·`none`이면 메모리 모드, `supabase`·`supabase`이면 Supabase 모드 |
| `.env` | 환경변수를 한 파일에 모아 둔 설정 파일. 커밋하지 않고, 키 같은 비밀을 넣되 화면·채팅에 출력하지 않는다 |
| publishable key · secret key | 브라우저에서 쓰는 노출 가능한 키(RLS가 지켜 줘야 함) · 서버에서만 쓰는 높은 권한의 비밀 키(RLS를 건너뜀) |
| 게스트(익명) 로그인 | 가입 없이 접속하는 브라우저마다 사용자 한 명을 만들어 주는 방식. 브라우저를 바꾸면 다른 사용자가 된다 |
| `--env-file` | 파일의 환경변수를 컨테이너에 전달하는 Docker 옵션. 같은 변수를 `-e`로도 주면 `-e`가 우선 |
| `docker restart` · `docker start` · 컨테이너 새로 만들기 | 재시작은 메모리를 비우되 환경변수는 유지 · 멈춘 컨테이너를 다시 켬(환경변수 유지) · 환경변수를 바꾸려면 컨테이너를 지우고 새로 띄워야 함 |
| `MSYS_NO_PATHCONV=1` | Windows Git Bash가 `/`로 시작하는 인자를 윈도 경로로 바꾸지 않게 하는 설정 |
| UTC · KST | 데이터베이스가 쓰는 세계 표준시 · 한국 시간(UTC보다 9시간 빠름) |
