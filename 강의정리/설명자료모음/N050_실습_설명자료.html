1. 같은 코드인데 서버에서만 안 됐다 — staging의 500 오류와 로그 한 줄 {#1}

취지

지난 시간(N049)까지 AI 친구 에이전트 서비스(friend-agent, 줄여서 에이전트 서비스)에는 자동 검사·시험 서버(staging)·승인 절차가 붙었습니다. 이번 시간은 그 위에 새 기능 하나를 켜면서 시작합니다. 동아리 공지나 일정표 사진을 보내면 글자를 읽어 입력창에 넣어 주는 기능(OCR)입니다. 기능의 코드는 이미 서비스에 들어가 있고 환경변수 OCR_ENABLED로 켜고 끕니다. 첫 질문은 이것입니다. "내 컴퓨터에서는 되는데 서버에서는 안 돼요"라는 말이 나올 때, 코드가 한 글자도 다르지 않다면 무엇이 다른 걸까요?

검증 목표

  • 로컬에서 되는 기능이 staging에서 실패하는 장면을 직접 재현하고, 서버 로그의 같은 시각 오류 줄로 원인을 정한다.
  • 문제를 코드 / 환경 / 배포 중 어디에 속하는지 판정한다.

실제로 있었던 일

먼저 제 PC를 "정상 환경"으로 만들었습니다. 시작할 때 PC의 글자 읽기 프로그램(tesseract)은 영어(eng)와 방향 감지(osd) 데이터만 있고 한국어(kor)가 없었습니다. 11시 28분에 한국어 데이터(1.6MB)를 받았고, 관리자 권한으로 설치 폴더에 복사하고 프로그램 경로를 등록하는 일은 제가 직접 했습니다. 그 뒤 tesseract --list-langs로 eng, kor, osd를 확인했습니다. 이 상태에서 산책 동아리 10월 일정 사진(schedule.png)을 보내자 HTTP 200과 함께 153글자가 읽혔습니다.

11시 34분에 staging에 OCR_ENABLED=true를 추가했습니다. 기존 값은 그대로 두고 하나만 더하는 옵션(--update-env-vars)을 썼고, production은 건드리지 않았습니다. 새 리비전(friend-agent-staging-00006-dst)이 뜬 뒤 같은 사진을 보내자 HTTP 500이 돌아왔고, 화면에는 "사진에서 글자를 읽는 프로그램이 서버에 없습니다."라는 안내가 보였습니다.

핵심은 그다음입니다. 안내문은 결과만 말해 줍니다. 같은 시각(11시 35분 05초)의 Cloud Run 로그에는 오류 한 줄이 있었습니다.

ERROR  tesseract 프로그램을 찾을 수 없습니다. 실행 환경에 tesseract 가 설치되어 있지 않습니다.
POST /api/ocr  500

두 줄을 합치면 상황이 정리됩니다. 서비스는 정상적으로 시작했고, 사진 요청이 들어온 순간에야 프로그램을 부르다 실패했습니다. 그래서 배포는 성공으로 끝났고 대화 같은 다른 기능은 멀쩡했습니다. 코드는 같았고(코드 문제 아님), 서버라는 주방에 tesseract라는 도구가 없었던 것입니다(환경 문제). 이 문제는 같은 날 Dockerfile 한 파일로 풀렸고(3절), 풀린 뒤에는 같은 사진이 staging에서 200으로 읽혔습니다. 사용자가 직접 📷 버튼으로 사진을 골라 입력창에 일정 세 줄이 들어오는 것도 확인했습니다.

🧪 예제 — [해설서 비유] 요리하는 상황으로 생각해 보세요. 내 컴퓨터는 도구가 다 갖춰진 주방이고, 서버는 같은 요리사가 있지만 필요한 도구 하나가 없는 주방이며, 코드는 두 곳에서 똑같이 따르는 레시피입니다. 레시피가 같아도 도구가 없으면 요리를 완성할 수 없습니다.

적용 원칙

누구나 알아야 할 원칙

  • "내 컴퓨터에서 됐다"는 서버에서 된다는 증거가 아닙니다. 코드가 같아도 코드가 돌아가는 방(실행 환경)은 다를 수 있습니다.
  • 문제가 생기면 먼저 코드 / 환경 / 배포 셋 중 어디인지 가르세요. 이번 건은 환경이었습니다.
  • 배포 성공은 "실행 환경이 맞다"는 증거가 아닙니다. 화면 안내가 아니라 로그의 같은 시각 줄에서 원인을 찾으세요.

개발자용

  • 기능을 켜는 환경변수는 기존 값을 지우는 --set-env-vars가 아니라 추가하는 --update-env-vars로 넣고, 로그는 ERROR로 거른 뒤 요청 시각 근처의 오류 메시지와 상태 코드를 함께 대조한다.

동료에게 설명하기

"사진 속 글자를 읽어 주는 기능을 만들었는데, 제 컴퓨터에서는 잘 읽히고 시험 서버에서는 오류가 났어요. 코드는 똑같은데요. 로그를 열어 보니 '글자 읽는 프로그램이 서버에 없다'고 한 줄 적혀 있었어요. 레시피는 같은데 그 주방에 도구가 없었던 거예요. 그래서 제가 처음 한 일은 코드를 의심하는 대신 로그를 보고, 문제가 코드인지 환경인지 배포인지부터 가른 거였어요."

2. 이미지와 컨테이너 — 컨테이너를 지우면 대화가 사라진다 {#2}

취지

환경 문제를 풀려면 "실행 환경"이 정확히 무엇인지부터 알아야 합니다. Docker는 실행 환경을 이미지로 묶고 그 이미지를 컨테이너로 실행합니다. 둘을 혼동하면 "컨테이너 안에서 고친 것이 왜 다음에 사라지지?" 같은 의문이 생깁니다. 이 절은 둘을 손으로 만져 보며 구분합니다.

검증 목표

  • 공식 Python 이미지에 tesseract가 없고, 같은 이미지의 컨테이너끼리 파일을 나누지 않음을 확인한다.
  • 컨테이너를 지우면 메모리 속 대화는 사라지지만 이미지는 그대로임을 확인한다.

실제로 있었던 일

Docker Desktop을 이번에 처음 설치했습니다. 설치 뒤 공식 Python 이미지(python:3.13-slim-bookworm)를 받아 컨테이너 안에서 확인하자 Python 3.13은 있지만 tesseract는 없었습니다. Python이 들어 있다고 OCR에 필요한 프로그램이 모두 들어 있는 것은 아닙니다. 이 이미지는 디스크를 183MB 차지했습니다.

컨테이너 note-a 안에서 /tmp/note.txt에 "메모"를 쓴 뒤, 같은 이미지로 새 컨테이너를 띄워 그 파일을 읽자 "파일 없음"이었습니다. Docker Desktop 화면에는 이미지가 한 줄, 종료된 컨테이너가 따로 한 줄 보였습니다.

과제 1에서는 에이전트 서비스로 같은 개념을 확인했습니다. 컨테이너에 두 번 말을 걸자 저장된 메시지가 4개(내 발언 2 + 가짜 응답 2)였습니다. 이 컨테이너를 지우고 같은 이미지로 새로 띄우자 메시지는 0개였습니다. 컨테이너 ID는 e6f131713f90에서 8ed3418b358a로 바뀌었고 이미지 ID(90cbc2725f5f)는 그대로였습니다. 이 확인은 브라우저 대신 API로 했습니다.

이 실험이 보여 주는 것은 하나입니다. 컨테이너의 메모리는 영속 저장소가 아니라서, 컨테이너를 지우면 그 안의 대화도 사라진다는 점입니다. Cloud Run의 새 리비전도 새 컨테이너를 띄우므로 같은 이유로 대화가 사라질 것으로 보이지만, 이는 추정이고 Cloud Run에서는 시험하지 않았습니다.

🧪 예제 — [해설서 비유] 붕어빵(컨테이너)을 먹어 치워도 틀과 재료(이미지)는 그대로 남고, 같은 준비물로 몇 개든 새로 구울 수 있습니다.

🧪 예제 — [보충 비유] 이미지는 인수인계 매뉴얼, 컨테이너는 그날 투입된 임시 직원입니다. 임시 직원이 머릿속에 적어 둔 메모는 퇴근(컨테이너 삭제)과 함께 사라지고, 다음 날 새 직원은 같은 매뉴얼에서 처음부터 시작합니다. 남겨야 할 기록은 직원 머릿속이 아니라 본사 장부(외부 저장소)에 있어야 합니다.

적용 원칙

누구나 알아야 할 원칙

  • 이미지는 설계된 환경, 컨테이너는 그걸 실행한 것입니다. 환경을 고치려면 설계도(이미지)를 고치고, 실행 중인 컨테이너 안을 고치지 않습니다.
  • 오래 남아야 하는 데이터를 컨테이너 메모리에만 두면 컨테이너와 함께 사라집니다. 이것은 버그가 아니라 구조입니다.
  • 키 같은 비밀은 이미지에 넣지 않고 실행할 때 건넵니다. 이미지는 여러 곳에 퍼질 수 있는 파일이기 때문입니다.

개발자용

  • docker rm은 컨테이너만 지우고 이미지는 남긴다. 지우기 전에 대상이 무엇인지 확인한다.
  • 터미널(Git Bash)이 /app 같은 인자를 윈도 경로로 바꾸거나 한글 JSON을 curl로 보내 400이 나는 일이 있었다. Docker가 아니라 셸·인코딩 문제였고 MSYS_NO_PATHCONV=1과 UTF-8 전송으로 해결했다.

동료에게 설명하기

"Docker 이미지는 '이 서비스가 돌아가려면 이런 환경이 필요해'라고 묶어 둔 준비물이고, 컨테이너는 그걸로 실제로 돌리는 거예요. 제가 컨테이너에서 대화를 두 번 하고, 그 컨테이너를 지운 뒤 같은 이미지로 다시 띄웠더니 대화 4개가 0개가 됐어요. 이미지 번호는 그대로인데요. 그러니까 컨테이너 메모리는 오래 남길 곳이 아니에요. 서버에서도 같은 일이 생길 걸로 보이지만 거기서는 아직 시험해 보지 않았어요."

3. Dockerfile을 읽고 검토하는 법 — 다섯 기준과 __pycache__ 17개 {#3}

취지

이제 서버라는 주방에 도구를 갖추는 방법을 적을 차례입니다. 그 문서가 Dockerfile입니다. 템플릿의 예시 파일을 복사해 쓸 수 있지만, 복사한 파일이 우리 서비스에 맞는지 검토하는 눈이 이 절의 주제입니다. 코딩 에이전트에게 맡겨도 어떤 버전을 고정할지, 누구 권한으로 돌릴지 같은 판단은 사람의 몫입니다.

검증 목표

  • Dockerfile을 다섯 기준으로 검토해 통과 여부를 판정한다.
  • 로컬에서 빌드한 이미지 안의 tesseract가 사진을 읽는지, 들어가면 안 되는 것이 없는지 이미지를 열어 확인한다.
  • 이미지를 기존 자동 배포로 staging에 올려, 빌드 기록에서 Dockerfile이 쓰였는지 확인한다.

취지

5. 새 기능(PDF)을 붙일 때는 시스템 프로그램이 먼저 {#5}

취지

1~4절은 고장 난 뒤에 고치는 이야기였습니다. 이 절은 반대로 새 기능을 붙이면서 같은 사고를 미리 피하는 이야기입니다. 도전 과제는 사진뿐 아니라 PDF 공지문도 읽게 하는 것이었습니다. 새 기능마다 던질 질문은 하나입니다. "이 기능은 파이썬 라이브러리 말고 운영체제에 설치할 프로그램이 따로 필요한가?"

검증 목표

  • 새 기능에 필요한 시스템 프로그램을 찾아내고, 로컬에서 되던 기능이 컨테이너에서는 실패할 수 있음을 확인한다.
  • Dockerfile에 한 줄만 더해 네 곳에서 같은 결과가 나오는지 본다.

실제로 있었던 일

후보는 PDF 읽기, QR 코드 읽기, HEIC 사진, 동영상 음성 변환(ffmpeg)이었습니다. PDF를 골랐고 QR은 2순위, HEIC와 ffmpeg는 난이도 때문에 권하지 않았습니다(구현은 하지 않았습니다). PDF를 읽으려면 먼저 PDF의 각 쪽을 그림으로 바꿔야 하고, 그 일을 하는 pdftoppm이 poppler라는 운영체제 프로그램에 들어 있습니다. 파이썬 쪽에는 이를 부르는 pdf2image 라이브러리만 추가했습니다.

로컬 PC에는 winget으로 poppler를 설치했습니다(비공식 빌드, 압축 파일 약 16.0MB). 코드는 앞 3쪽만, 200dpi로, 시간 제한 30초 안에서 읽도록 했고, poppler가 없으면 "PDF를 읽는 프로그램이 서버에 없습니다."라는 안내와 오류 로그를 남기게 했습니다. 변경은 5파일이었는데 Dockerfile은 처음에 건드리지 않은 채 먼저 로컬에서 시험했습니다. 로컬에서는 사진·PDF 1쪽·4쪽·깨진 PDF가 모두 기대대로였고, 자동 테스트는 기존 12개에 새 3개를 더한 15개가 통과했습니다. 3쪽 제한 값을 일부러 99로 깨뜨리자 assert 99 == 3으로 실패했고, 되돌리자 다시 통과했습니다.

문제는 그다음입니다. poppler 줄이 없는 Dockerfile로 만든 컨테이너에 같은 PDF를 보내자, 사진은 200으로 읽혔는데 PDF만 500이었습니다. 화면에는 "PDF를 읽는 프로그램이 서버에 없습니다.", 로그에는 "poppler 프로그램을 찾을 수 없습니다."가 남았습니다. 컨테이너 안에는 tesseract는 있고 pdftoppm은 없었습니다. 로컬에서는 되던 PDF가 컨테이너에서 처음 실패한 것이고, 1절의 사건이 다른 얼굴로 되풀이된 장면입니다.

해결은 Dockerfile의 설치 줄 끝에 poppler-utils 한 단어를 더하는 것이었습니다. 이미지는 460MB에서 473MB(+13MB)가 됐고, 사진·PDF 1쪽·4쪽·깨진 PDF 결과가 로컬과 모두 같아졌습니다. PR #22로 staging에 올리자 Cloud Build aa4d5d58이 성공했고(로그에 Setting up poppler-utils 확인) staging에서도 같은 결과가 나왔으며, PR #23으로 production에도 반영했습니다. 이 한 줄이 필요한 이유는 한 문장입니다. PDF를 이미지로 바꾸는 pdftoppm이 운영체제 프로그램이라 pip로는 설치되지 않기 때문입니다. 이번에는 staging에 올리기 전에 로컬 컨테이너에서 문제를 먼저 잡았습니다.

⚠️ 주의 — 새 PDF 테스트 3개는 PDF를 그림으로 바꾸는 함수를 가짜로 바꿔 놓고 검사합니다. 그래서 15개가 통과해도 "서버에 poppler가 실제로 있는가"는 검증하지 못합니다. N049의 자동 검사가 가진 한계와 같은 구멍이고, 이 확인은 컨테이너와 staging의 몫이었습니다.

  • 새 기능을 계획할 때 "파이썬 라이브러리 말고 운영체제에 설치할 프로그램이 있나?"를 먼저 물으세요.

  • 테스트를 믿기 전에 일부러 깨뜨려(3 → 99) 실패하는지 확인한 뒤 되돌린다. 샘플 PDF는 저장소에 커밋하지 않고 임시 폴더에서 만들어 썼다.

동료에게 설명하기

"PDF를 읽는 기능을 새로 붙였는데, 이번에는 서버에 올리기 전에 컨테이너에서 먼저 터졌어요. 제 컴퓨터에서는 PDF가 잘 읽혔는데, 서버와 같은 환경의 컨테이너에서는 'PDF 읽는 프로그램이 없다'고 나왔거든요. PDF를 그림으로 바꾸는 프로그램이 운영체제에 따로 깔려야 하는 거라서요. 설명서에 한 줄만 더했더니 해결됐어요. 그래서 이제는 새 기능을 붙일 때 '운영체제에 따로 깔 게 있나?'를 제일 먼저 물어요."

6. 같은 Dockerfile이어도 같은 이미지는 아니다 {#6}

취지

Dockerfile을 도입하면 "staging에서 검증한 것이 그대로 production에 나간다"고 믿고 싶어집니다. 하지만 staging과 production은 각각 따로 빌드합니다. 같은 설계도로 두 번 만들면 같은 제품일까요? 이 절은 그 믿음을 시험하고 풀리지 않은 숙제를 솔직히 적습니다.

검증 목표

  • 같은 Dockerfile로 캐시 없이 두 번 빌드한 것(과제 2)과 실제 staging·production 빌드의 패키지·이미지 ID를 비교해, "검증한 이미지 = 배포한 이미지"라고 말할 수 있는지 판정한다.

실제로 있었던 일

과제 2에서 docker build --no-cache로 try-a, try-b를 연달아 만들었습니다. 각각 약 31초, 30초가 걸렸습니다(교재는 "몇 분"이라 했지만 이 PC에서는 30초대였습니다). 결과는 이렇습니다. 이미지 ID는 8d665740853b와 3a23685075fb로 달랐고, 크기는 둘 다 460MB였습니다. 파이썬 패키지(30줄)와 apt 패키지(159개)는 같았습니다. 레이어 10개 중 베이스 4개와 COPY . . 1개는 같고 나머지 5개는 달랐습니다. 레이어와 Dockerfile 줄의 대응은 docker history 줄 수가 레이어 수와 같다는 점에서 추정한 것이며, 무엇이 정확히 달라졌는지 원인 파일은 확인하지 않았습니다.

실제 배포 기록에서도 같은 모양이 나왔습니다. staging 빌드 615ce1d8(이미지 ID a31820f7a6bf)과 production 빌드 4718e203(a3c0f9af949f)은 베이스 이미지 digest, 파이썬 패키지 30개, apt 패키지 62개가 모두 같았지만 이미지 ID는 달랐습니다. 빌드마다 붙는 build_id 라벨이 달랐고, 두 빌드의 간격은 약 1시간 33분이었습니다. PDF 반영 빌드(staging aa4d5d58의 7cd90c50e99a, production 057dbfd2의 cb253b448e50)도 패키지는 같고(파이썬 31개·apt 67개) 이미지 ID가 달랐으며 간격은 약 18분이었습니다. 이미지 ID가 달라지는 이유로는 이 라벨과 빌드 시각이 거론되지만, 어느 것이 얼마나 영향을 줬는지는 확인하지 않았습니다.

그러니 이렇게 말해야 정확합니다. staging에서 검증한 이미지와 production에 나간 이미지는 서로 다른 이미지입니다. 패키지 내용이 같다는 것까지만 확인했고 "같은 이미지"라고는 말할 수 없습니다. 이번 비교는 모두 몇 시간 안이라 패키지 버전이 같았습니다. 며칠 간격으로 빌드하면 목록까지 달라질 수 있다고 하나 직접 재현하지는 않았습니다.

🧪 예제 — [보충 비유] 시제품 검수(staging)를 통과한 뒤 납품(production) 때 공장에서 다시 양산하는 구조입니다. 같은 도면이라 거의 같겠지만, 검수한 바로 그 제품이 나가는 것은 아닙니다. 성분표(패키지)가 같다고 확인했을 뿐, 제조번호(이미지 ID)가 같다고 한 적은 없습니다. 검수한 제품을 그대로 납품하려면 출하 절차 자체를 바꿔야 합니다.

적용 원칙

누구나 알아야 할 원칙

  • "같은 설계도"와 "같은 제품"은 다릅니다. 검증한 것과 내보낸 것이 같다고 말할 때는 무엇이 같은지(설계도인지 완성품인지)를 구분해 말하세요.
  • 확인한 만큼만 말하세요. 이번에는 "패키지 목록은 같다"까지가 확인한 범위입니다.
  • 이 숙제는 오늘 끝내지 않았습니다. 해결하려면 이미지를 한 번만 만들어 두 환경에 보내는 흐름이 필요합니다.

개발자용

  • 이미지 비교는 이미지 ID, 베이스 digest, pip freeze, dpkg -l, 레이어 해시를 함께 본다. 이번에는 베이스를 FROM python:3.13-slim-bookworm 태그로 고정했고(digest 고정은 하지 않았다), 두 빌드에서 베이스 digest는 같았다. 만든 이미지의 태그·digest 관리와 승격, 배포마다 쌓이는 400MB대 이미지의 저장 공간 관리는 교안이 남긴 다음 숙제다.

동료에게 설명하기

"Dockerfile로 환경을 적어 뒀으니 시험 서버에서 검증한 게 운영에도 그대로 나간다고 생각하기 쉬운데요, 사실 시험 서버와 운영은 각각 새로 빌드해요. 제가 비교해 봤더니 설치된 프로그램 목록은 똑같은데 이미지 번호는 달랐어요. 같은 도면으로 두 번 찍은 거라서요. 그러니까 '같은 설계도'까지는 맞지만 '같은 제품'은 아니에요. 같은 제품이라고 말하려면 한 번 찍은 걸 양쪽에 보내야 하는데, 그건 아직 숙제로 남겨 뒀어요."
