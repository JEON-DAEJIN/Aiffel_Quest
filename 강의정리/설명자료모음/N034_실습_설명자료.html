N034 실습 설명자료 — 카드뉴스 에이전트 만들기

N034 강의와 card-news-agent 프로젝트를 논리적으로 상세히 풀어 정리한 문서. 강의의 취지, 실습이 검증하려는 것, 프로젝트에서 실제로 있었던 일, 향후 적용법, 동료에게 설명하는 법 순으로 구성했다.

💡 읽는 법: 코드를 몰라도 끝까지 읽을 수 있게 썼다. 어려운 용어는 그 자리에서 비유로 풀어준다. “개발자용”이라고 표시된 부분은 건너뛰어도 줄거리를 이해하는 데 지장 없다.

1. 이 수업(N034)의 취지 — 왜 카드뉴스 자동화에 사람이 필요한가

N034는 “AI가 카드뉴스를 다 만들어주는 것”이 아니라, 조사·선택·제작·검수처럼 사람이 매번 반복하는 업무에서 AI가 후보를 조사해 제시하고, 사람이 결정하면 AI가 다음 단계를 이어가는 사람-AI 협업 흐름(에이전틱 워크플로)을 설계하는 문제의식에서 출발했습니다. 기획서(PRD) 한 장을 개발 도우미에게 건네고, 실제로 동작하는 웹앱까지 완성하는 것이 목표였습니다.

2. 실습이 알아보고자 한 것

이 실습이 확인하려던 건 “AI가 질문하고 사람이 답할 때까지 웹앱이 정확히 멈춰 있을 수 있는가”였습니다. 원문의 표현을 빌리면:

“waiting_for_user는 오류가 아니라 정상적인 작업 상태입니다. AI가 질문하면 웹앱은 반드시 멈춰야 하며, 사용자가 답하기 전에 다음 단계로 자동 진행해서는 안 됩니다.”

그리고 더 미묘한 함정도 있었습니다: “세션 ID 저장 ≠ 작업 상태 자동 복구” — 즉 “지금 이 대화”를 가리키는 표(세션 ID) 하나만 저장해서는 안 되고, 어디까지 진행했는지·무엇을 물었는지·사람이 뭐라고 답했는지까지 따로 저장해야 새로고침이나 서버 재시작 후에도 이어갈 수 있습니다.

3. 프로젝트에서 실제로 있었던 일

  1. 예산(budget) 버그: AI 호출 예산을 하루 0.5달러로 낮게 잡고 시작했더니, 실제 웹검색 조사 도중 예산을 다 써버려 첫 실행이 그대로 실패했습니다. 게다가 실패하면 무조건 한 번 다시 시도하도록 되어 있어서, 재시도가 예산을 두 배로 태우고도 또 실패하는 것까지 실제로 확인됐습니다. → 예산을 2.0달러로 올리고, “재시도해도 반드시 다시 실패할 오류(예산초과·시간초과)는 재시도하지 않는다”는 규칙을 추가했습니다.
  2. AI가 실제 상표 로고를 그린 사건: “경쟁사 로고를 흐릿하게 표시”라는 지시만으로 이미지를 만들었더니, AI가 원문과 아무 상관 없는 실제 유명 브랜드 로고를 그려냈습니다. “경쟁사 로고”라는 추상적인 지시만 주면, AI가 자기가 학습한 데이터에서 가장 흔한 실제 브랜드로 빈칸을 채워버린 것입니다. → 모든 이미지 생성 지시에 “실제 브랜드명·로고·상표를 그리지 말 것”이라는 전역 안전장치를 넣었습니다.
  3. 검증을 합쳐서 하면 착시가 생긴다: 다른 강의(N036) 실습에서 배운 교훈을 이 프로젝트에도 그대로 적용했습니다 — 두 항목(제목+본문)을 합쳐서 “한국어인지” 검사하면, 한쪽만 한국어여도 “문제없음”으로 착시가 생깁니다. 실제로 이 프로젝트도 처음엔 AI에게 “한국어로 쓰라”고 프롬프트로만 지시했을 뿐, 코드로 확인하는 절차가 없었다는 걸 발견하고, 항목별로 따로 검사하고 실패한 항목만 다시 요청하는 절차를 추가했습니다.

4. 앞으로 내 프로젝트에 어떻게 적용하면 되는가

누구나 알아야 할 원칙

  • “그럴듯해 보인다”와 “실제로 된다”는 다릅니다. 코드를 눈으로 읽고 “이러면 되겠지”라고 넘기지 말고, 실제로 실행해서 결과를 확인해야 예산 버그나 상표 로고 사건 같은 문제가 눈에 보입니다.
  • AI에게 추상적인 지시(“경쟁사 로고”, “적당히 예쁘게”)만 주면, AI는 가장 흔한 답으로 빈칸을 채웁니다. 구체적인 금지 사항(“실제 브랜드는 안 됨”)을 명시해야 안전합니다.
  • 검증은 합쳐서 하지 말고 쪼개서 하세요. 여러 항목을 한 번에 검사하면 일부만 통과해도 “전체 통과”로 착각하기 쉽습니다.

개발자용 체크리스트 (코드를 직접 짤 때만 해당)

  • 실패를 무조건 재시도하지 말고, “재시도해도 다시 실패할 오류(예산초과·타임아웃)”와 “재시도하면 나아질 오류”를 구분한다.
  • 세션 ID와 작업 상태(현재 단계·질문·답변)는 서로 다른 곳에 각각 저장한다.
  • 필드별 개별 검증 후, 실패한 항목만 지목해 재요청하는 방식을 쓴다(전체 재생성 아님).

5. 동료에게 어떻게 설명하면 되는가

한 줄 엘리베이터 피치: > “AI가 조사하고 사람이 결정하면 AI가 이어받는 카드뉴스 제작 워크플로를 만들어봤어요. 만드는 중에 예산 폭주, AI가 실제 상표를 그려내는 문제, 검증 착시 같은 진짜 문제를 실행해보고서야 발견해서 고쳤어요.”

좀 더 풀어서 설명할 때 순서: 1. “카드뉴스 만들기처럼 사람이 매번 반복하는 일을, AI가 조사해서 후보를 보여주고 사람이 고르면 이어가는 방식으로 만들었어요.” (문제의식) 2. “핵심은 ’AI가 질문하고 멈춰 있는 상태’가 고장이 아니라 정상이라는 걸 웹앱이 정확히 알아야 한다는 거예요.” (구조) 3. “실제로 만들어보니 예산을 너무 적게 잡아서 첫 실행이 실패했고, 심지어 재시도까지 예산을 또 태웠어요.” (경험담 1) 4. “더 놀라운 건, ‘경쟁사 로고’ 그려달라고 했더니 AI가 진짜 유명 브랜드 로고를 그려버린 거예요 — 추상적으로 지시하면 AI가 흔한 답으로 채운다는 걸 몸으로 확인했어요.” (경험담 2) 5. “이런 문제들은 코드만 봐서는 안 보이고, 실제로 돌려봐야 보였어요.” (핵심 원칙)
