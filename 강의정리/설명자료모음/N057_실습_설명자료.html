1. 왜 노트북 백엔드였나

취지

오늘 실습의 목표는 이미 잘 돌아가는 웹 서비스 "하루친구"에 폰 화면(앱)만 새로 붙이는 것이다. 그런데 앱을 만들기도 전에, 붙일 대상인 백엔드가 열리지 않았다. 본사 시스템이 멈춘 날 지점 개업식을 하는 것과 같다. 교안은 "앱에서 문제가 생기면 앱부터 의심하지 말고 백엔드가 정상인지 먼저 본다"고 하는데, 이 원칙이 앱을 만들기도 전에 쓰였다.

검증 목표

  • 시작 상태(Node.js, GitHub 로그인, 열리는 백엔드, 폰과 Expo Go)가 갖춰졌는지 본다.
  • 백엔드가 안 열리면 원인을 찾고, 오늘 실습을 할 수 있는 대안을 정한다.

실제로 있었던 일

시작 상태 점검. Node.js는 v24.18.0, npm은 11.16.0이었고 GitHub에도 로그인되어 있었다. 폰은 Android이고 Expo Go 설치와 SDK 58 확인이 대기 상태였다. Expo 계정은 오늘 빌드를 하지 않으므로 필요 없다고 정리했다(교안 표에는 있음) [확인].

교안은 공개 주소의 백엔드를 기대하지만 실제로는 둘 다 500이었다. 브라우저 대신 명령으로 확인 주소(/health)를 부르니 staging과 production 모두 500이 왔다(0.45초, 구글 앞단의 "30초 뒤 다시 시도" 화면) [확인]. 클라우드 로그(경고 이상, 최근 2시간)에 한 줄이 남아 있었다. "이 프로젝트는 결제가 꺼져 있어서 요청이 실패했다"는 뜻의 문구였다. 조회해 보니 결제 사용이 꺼져 있었고 연결된 결제 계정도 닫혀 있었다 [확인]. 지난 실습(N053, 2026-10-29)에서 "무료 체험 6일 남음"이던 것이 끝난 것으로 보인다 [추론]. 서버 코드의 문제가 아니라 요금 계정의 문제였다 [확인].

선택지는 세 가지였다.

선택지내용결정
① 결제 다시 켜기사용자가 콘솔에서 유료 계정으로 전환(도우미는 하지 않음). 교안 그대로 공개 주소 사용선택하지 않음
② 노트북에서 백엔드 실행같은 와이파이의 폰이 노트북 주소의 8080번으로 접속. 무료이고 오늘 실습 전부 가능선택
③ 강사 시연용 주소교안이 적어 둔 대안선택하지 않음

선택 ②의 이유는 기록에 "무료, 오늘 실습 전부 가능"이다. 도우미가 세 선택지를 묻고 학습자가 "노트북에서 돌리기"를 골랐으며, 이후 학습자가 폰·방화벽 조치를 해 주었다 [확인].

도커 대신 가상환경으로 띄웠다. 도커 데스크톱은 꺼져 있었고, 설치 위치가 기본 위치가 아니라 사용자 폴더라서 처음 켜려던 명령이 실패했다. 대신 노트북에 글자 읽기 프로그램(tesseract, 한국어 데이터 포함)과 백엔드 가상환경이 이미 있어서, 도커 없이 가상환경에서 바로 실행했다. .env는 도우미가 열지 않았고 프로그램이 그대로 읽게 했다 [확인].

적용 원칙

누구나 알아야 할 원칙

  • 앱이 안 될 때는 앱부터 의심하지 않고 바깥(백엔드)부터 본다. 오늘은 앱을 만들기도 전에 이 원칙이 맞았다.
  • 임시 대안을 쓸 때는 교안과 달라지는 점(주소 종류, 켜 둬야 하는 것)을 적어 둔다.
  • 원인은 서버 코드가 아니라 요금 계정일 수 있다. 로그의 한 줄을 읽기 전에는 모른다.

  • 이 서비스는 어느 요금 계정에 묶여 있고, 무료 기간이 언제 끝납니까?

"앱을 만들려고 보니 붙일 본사 시스템이 먼저 꺼져 있었어요. 코드 문제가 아니라 무료 체험이 끝나서 결제가 꺼진 거였어요. 그래서 오늘은 내 노트북에 임시 본사를 차리고 폰을 같은 와이파이에 붙였어요. 공짜라서 좋은데 노트북이 꺼지거나 와이파이가 바뀌면 길을 잃는다는 약점이 있어요."

2. 템플릿으로 앱을 만들고 폰에 띄우기

취지

템플릿(기본 틀)에서 앱 저장소를 만들고, 백엔드 주소 하나만 넣어 내 폰에서 띄웠다. 교안은 이때 "백엔드는 한 줄도 바뀌지 않는다"고 한다. 지점 창구를 새로 열어도 본사 시스템은 그대로 쓰는 것과 같다. 이 절에서 교안의 시퀀스(앱이 켜질 때부터 답을 받을 때까지 무엇이 오가는지)를 실제 로그로 대조했다.

검증 목표

  • 템플릿에서 저장소를 만들고 SDK 버전이 폰의 Expo Go와 맞는지 본다.
  • 앱이 켜진 뒤 백엔드 로그가 교안의 순서와 같은지 본다.
  • 답이 글자 단위로 흘러오는지, 앱을 완전히 껐다 켜도 같은 손님으로 이어지는지 본다.

실제로 있었던 일

저장소 만들기. 학습자가 '공개로 만들기'를 골랐다(교안대로). 템플릿 저장소에서 내 계정에 friend-agent-mobile을 만들어 내려받고 설치했다(49초). 첫 커밋은 a97aa36이다. 부품 판은 expo ~58.0.21, react-native 0.88.0, expo-router ~58.0.28로 폰의 Expo Go SDK 58과 맞았다. app.json에는 이름 하루친구, 패키지 이름 com.example.harufriend, 세로 고정이 들어 있었고 카메라 권한 설명은 아직 없었다. 화면 파일과 연결 파일의 목록은 교안 표와 같았다 [확인].

교안과 다른 점 ① 설정 파일 내용. Expo 도우미 스킬(플러그인)을 앱 폴더에 설치했다(학습자 승인 뒤, 버전 1.13.9, 스킬 24개). 교안은 "설치가 끝나도 .claude/settings.json에 새로 바뀌는 내용은 없다"고 했다. 실제로는 git이 이 파일을 수정됨으로 표시했다. 비교해 보니 같은 블록의 위치가 파일 맨 위에서 맨 아래로 옮겨졌을 뿐 내용은 같았다. 되돌렸다 [확인]. 즉 교안의 말은 내용 기준으로는 맞고, git은 순서 변경도 수정으로 보여 준다.

스킬이 이 세션에 읽히지 않았다. 이 대화 세션은 강의정리 폴더에서 열려 있어 앱 폴더의 프로젝트 범위 스킬이 바로 읽히지 않았다. 그래서 화면 수정은 도우미가 AGENTS.md와 SDK 58 문서를 근거로 했다 [확인].

.env와 개발 서버는 학습자가 직접 했다. 도우미의 권한 설정이 .env 읽기·쓰기를 막고 있어(비밀값 보호 규칙) 학습자가 직접 복사해서 EXPO_PUBLIC_API_URL에 노트북 주소(8080번)를 넣었다. 교안 예시는 공개 주소(https://…run.app)다. 개발 서버(npx expo start)도 학습자가 자기 터미널에서 실행했다(QR 코드가 학습자 화면에 떠야 하므로). 학습자가 "로그인부터 해야 할까?"라고 묻자, Expo 계정 로그인은 빌드·계정 프로젝트용이라 오늘은 필요 없고 앱 안의 익명 로그인은 앱이 스스로 한다고 답했다 [확인].

폰에서 열기. QR을 찍자 "하루친구 / SDK version: 58.0.0" 화면이 나왔고 app.json의 이름·SDK와 일치했다. 개발자 메뉴에는 개발 서버 주소(8081번)가 연결됨으로 보였고 Fast Refresh가 켜져 있었다. 8081은 개발 서버(화면 코드), 8080은 백엔드(데이터)다 [확인].

3. 같은 백엔드 다른 손님

취지

앱과 웹을 같은 백엔드에 붙이면 두 곳의 대화가 같이 보일까. 교안은 "안 보인다"고 한다. 폰과 브라우저가 각각 다른 게스트로 로그인하기 때문이다. 지점마다 따로 받은 임시 출입증이 서로 다른 고객으로 취급되는 것과 같다. 이 절은 그것을 DB 기록으로 증명한 부분이다.

검증 목표

  • 같은 백엔드를 노트북 브라우저로 열었을 때 무엇이 보이는지 예상하고 실제와 비교한다.
  • 폰의 대화가 사라진 것이 아니라 다른 손님의 것임을 DB 기록으로 보인다.

실제로 있었던 일

예상. 같은 백엔드를 노트북 브라우저(localhost:8080)로 열면 앱의 대화가 보이거나(같은 사람) 캐릭터 만들기 화면이 나온다(새 손님) 둘 중 하나로 예상했다 [확인: 기록의 예상].

실제는 둘 다 아니었다. 학습자의 화면에는 예전(N052~N056) 실습 때의 화면이 떴다. 곰 캐릭터 "하루", 크레딧 30, 예전 날씨 대화였다. 이 브라우저가 그때 받은 게스트 토큰을 저장소에 간직하고 있어서, 같은 주소를 열자 예전 손님으로 다시 로그인한 것이다. 폰에서 오늘 만든 캐릭터는 이름은 같은 "하루"지만 강아지였다(학습자) [확인].

4. 저장하면 바로 바뀌는가

취지

교안은 "코드를 저장하면 몇 초 안에 폰 화면이 바뀐다"고 한다. 일부러 괄호를 하나 지우면 폰에 빨간 오류 화면이 뜬다고도 한다. 이 두 가지를 실제로 해 보았고, 교안과 달랐던 점이 하나 나왔다. 양식을 고치고 저장하면 지점 화면이 자동으로 바뀐다는 설명이 첫 시도에서는 맞지 않았다.

검증 목표

  • 문구를 바꾸고 저장했을 때 폰이 바뀌는지 본다.
  • 일부러 괄호를 지웠을 때 오류가 어디에 어떻게 보이는지 본다.

실제로 있었던 일

① 문구 바꾸기: 저장했는데 폰이 안 바뀌었다. 교안이 말한 "첫 메시지를 보내 보세요."는 대화가 없을 때만 보이는 문구(index.tsx 100행)다. 이미 대화가 있어서 바꿔도 화면 변화가 없으므로, 지금 보이는 입력창 안내 문구(113행)로 바꿨다. 새 문구는 학습자가 정했다("오늘 같은 날 커피는 어떤 걸로 마실까?"). 저장 뒤 학습자가 계속 지켜봤는데 폰에 변화가 없었다 [확인].

도우미가 확인한 순서는 이렇다. 파일 저장됨 → 개발 서버 상태 running → 학습자 터미널에 Android Bundled 76ms … (1 module)가 찍힘 → 개발자 메뉴의 Reload를 누르자 Android Bundled 103ms … (1 module)가 다시 찍히고 그제야 폰에 새 문구가 떴다 [확인]. 첫 번째 변경에서 자동 반영이 안 된 이유는 확인하지 못했다. 일시적 연결 문제로 정리했다 [미확인].

② 일부러 괄호 지우기: 빨간 화면이 저절로 떴다. 66행의 닫는 괄호 하나를 지우고 저장했다(Reload 없이 지켜봄). 학습자 터미널에는 SyntaxError … Unexpected token, expected "," (66:104)와 코드 발췌(지운 자리를 가리키는 표시), 그 아래 내부 경로 수십 줄이 찍혔다. 폰에는 TransformError: SyntaxError가 저절로 떴다. 파일 감지와 자동 반영(Fast Refresh)이 모두 살아 있다는 뜻이다. 괄호를 되돌려 저장했다 [확인].

교안과 다른 점. 교안은 "몇 초 안에 폰 화면이 바뀐다"고 했지만 첫 번째 변경은 Reload를 해야 바뀌었고, 두 번째(오류)부터는 자동으로 반영되었다 [확인].

💡 팁 — 앱이 빨간 화면이 되면 오류 문구를 그대로 도우미에게 붙여 주는 것이 가장 빠른 해결 방법이다(교안과 해설서). 이번에도 터미널과 폰에 같은 오류 문구가 떴다.

  • 빨간 오류 화면에 나온 파일 이름과 줄 번호를 도우미에게 그대로 전달했습니까?

"양식을 고치고 저장하면 지점 화면이 바로 바뀐다고 했는데, 첫 번째는 제가 수동으로 '새로 받기'를 눌러야 바뀌었어요. 일부러 괄호를 하나 지웠더니 폰에 빨간 화면이 저절로 뜨면서 몇 번째 줄인지 알려 줬고요. 오류 문구를 그대로 도우미에게 주면 가장 빨리 고쳐요."

5. 답 아래 메모와 폰에서만 보인 문제

취지

웹 화면에는 있는데 앱에는 없는 기능을 하나 붙였다. 답 아래에 "이번 턴에 기억한 것"과 "잡거나 취소한 약속"을 작은 글씨로 보여 주는 메모다. 코드를 맡기기 전에 "어떤 정보를 어디서 가져와 어떤 모양으로 보여 줄지"를 먼저 정했다. 보고서 양식을 바꾸기 전에 데이터 출처부터 확인하는 일과 같다. 그리고 폰에서 직접 써 보다가 교안에 없던 문제 두 가지가 나왔다.

검증 목표

  • 해설서의 "기획자가 정할 네 가지"를 실제로 정하고, 백엔드가 보내는 순서를 코드로 읽어 확인한다.
  • 기억 메모와 약속 메모가 답 아래에 붙는지, 앱을 껐다 켜면 어떻게 되는지 본다.
  • 폰에서 직접 써 보고 드러나는 문제를 찾는다.

실제로 있었던 일

적용 원칙

누구나 알아야 할 원칙

  • 앱에 새 정보를 보이고 싶을 때 먼저 "백엔드가 이 정보를 이미 보내고 있는가"를 본다. 안 보내면 앱만 고쳐서는 안 된다.
  • 안내 문구에는 칸의 용도를 쓰고, 예시 질문처럼 입력된 글로 오해될 문장은 넣지 않는다.
  • 실험하려고 바꾼 것은 되돌렸는지 확인한다. 이번에는 실험 문구가 진짜 불편을 만들었다.
  • 화면 문제는 직접 써 봐야 보인다. 코드 검사(타입 검사)는 자판 가림을 잡지 못한다.

  • Android와 iOS에서 자판이 올라올 때 입력창이 가려지지 않는지 실제 폰으로 확인했습니까?

동료에게 이렇게 설명한다

"답 아래에 '이번에 기억한 것, 잡은 약속'을 작은 글씨로 보여 주는 기능을 붙였어요. 앱을 껐다 켜면 메모가 사라지는데, 메모는 그때그때 오는 신호로만 그린 거라 정상이에요. 그리고 폰으로 직접 써 보니 자판이 올라오면 입력창이 가려지는 문제가 있었어요. 코드 검사로는 안 나오고 손으로 써 봐야 보이는 문제였어요."

6. 사진으로 약속 만들기 카메라 경로가 막힌 이유

취지

일정표 사진을 찍어 글자를 읽고 약속으로 만드는 기능이다. 백엔드에는 이미 글자 읽기(POST /api/ocr)가 있어서 앱에서는 사진을 받아 보내는 화면만 만든다. 교안은 이것을 "앱으로 만든 이유가 가장 잘 드러나는 기능"이라고 한다. 이 절은 같은 업로드 함수가 사진첩에서는 되고 카메라에서는 안 되었을 때 원인을 찾아가는 과정이다.

검증 목표

  • 사진첩 경로와 카메라 경로 모두 사진이 백엔드에 도착하는지 본다.
  • 막힌 경로가 있으면 오류 문구를 근거로 원인을 하나씩 가른다.

실제로 있었던 일

설계(학습자가 "이 설계대로 진행하자. 권한 설명도 넣어두자"라고 승인).

  • 입력창 왼쪽에 카메라 버튼을 둔다. 백엔드 설정의 ocr_enabled가 true일 때만 보인다. 누르면 "사진첩에서 고르기 / 카메라로 찍기 / 취소" 선택 창이 뜬다.
  • 카메라는 앱 안 화면(src/app/camera.tsx)이다. 안내 "글자가 화면 안에 들어오게 찍어 주세요", 셔터와 닫기 버튼이 있고, 권한이 없으면 다시 묻거나(가능할 때) "설정 열기"를 보여 준다.
  • 사진은 photo 칸으로 보내고 Content-Type은 직접 넣지 않는다. 받은 글은 입력창에 "사진에서 읽은 글이야. 여기 있는 일정 중에 알려 줘야 할 게 있으면 약속으로 저장해 줘."와 함께 넣고, 자동으로 보내지 않는다(HITL) [확인].
  • 설치는 npx expo install expo-camera expo-image-picker(SDK 58에 맞는 판 각각 ~58.0.14, ~58.0.10)로 했다. app.json에는 카메라 권한 문구("일정표나 안내문을 찍어 글자를 읽고 약속으로 만들려고 카메라를 사용합니다.", 마이크는 끔)와 사진 권한 문구를 넣었다 [확인].

카메라 경로가 세 번 막혔고 네 번째에 성공했다.

시도방법화면에 뜬 오류원인
1fetch에 {uri, name, type} 객체를 담음"unsupported fromdatapart implementation"(학습자 표기)SDK 58은 expo/fetch가 전역 fetch이고 그 방식의 폼 조각을 받지 않음
2파일 시스템 라이브러리로 파일을 직접 읽음"call to function 'FileSystemFile.bytes' has been rejected. -> caused by missing 'READ' permission for accessing the file."Expo Go 안에서 JS가 파일을 직접 읽는 것이 막힘
3XMLHttpRequest로 바꿈"/api/ocr 요청 실패: 네트워크 오류(백엔드 주소 와이파이 확인)". 사진첩은 성공, 카메라만 실패백엔드에는 요청이 오지 않음(요청이 폰 밖으로 나가기도 전에 실패)
4찍은 사진 주소를 화면 이동 주소에 싣지 않고 앱 안의 작은 보관함(src/lib/photoHandoff.ts)으로 넘김없음, 성공사진 주소를 넘기는 방법이 카메라 경로의 문제였음

2번 오류는 학습자가 "카메라로 찍었을 때 일어났어. 처음에는 카메라를 허용할 것이냐고 물어봤는데, 두번 째는 … 묻지 않았어"라고 덧붙였다. 한 번 허용하면 다시 묻지 않는 것이 정상이다. 3번 때 학습자는 "사진에서 읽기는 정상 동작해 대신 글을 제대로 못 읽어 엉뚱한 문장으로 뱉어"라고 했는데, 이는 사진첩 경로가 이미 되는 상태이고 글 인식 품질은 별개라는 말이다(7장). 1번 오류가 사진첩과 카메라 중 어느 경로에서 났는지는 기록에 없다 [미확인].

성공. 4번째 방법으로 학습자가 인쇄물을 찍자 "정확히 읽었어"라고 확인했다. 백엔드에 POST /api/ocr 200이 기록되었다(카메라 경로로는 처음 도착). 그때 찍은 인쇄물의 글은 "CONRAD / SEOUL / NEVER JUST STAY. STAY INSPIRED"로, 날짜·시각이 없는 영어 글이었다 [확인]. 한글 인쇄물을 찍어 본 기록은 없다 [미확인].

교안과 다른 점. 교안은 "400 오류 함정"(공통 헤더 때문에 사진을 못 찾음)을 경고했다. 이번에 만난 오류는 그것이 아니라 SDK 58의 폼 방식, Expo Go의 파일 읽기 제한, 화면 이동 때 사진 주소를 싣는 방법 세 가지였다 [확인]. 또한 앱의 오류 문구 "백엔드 주소·와이파이 확인"은 이번에는 틀린 힌트였다. 요청이 폰 밖으로 나가기도 전에 실패했기 때문이다 [확인].

💡 팁 — 같은 함수가 한 경로(사진첩)에서는 되고 다른 경로(카메라)에서만 안 될 때는 함수가 아니라 두 경로의 차이를 의심한다. 이번 차이는 사진 주소를 넘기는 방법이었다.

적용 원칙

누구나 알아야 할 원칙

  • 사진을 받아 보내는 일과 글자를 읽는 일은 나뉜다. 앱은 앞쪽(받기, 전달, 입력창에 넣기)만 맡고, 읽기는 백엔드가 한다.
  • 오류 문구는 정확한 문장을 그대로 기록한다. 문구마다 원인이 다르다.
  • 오류 안내 문구 자체가 틀릴 수 있다. 백엔드 로그에 요청이 0건이면 문제는 폰 쪽이다.
  • 시도 순서와 폐기한 방법(지운 파일 시스템 라이브러리)을 적어 두면 같은 길을 다시 가지 않는다.

개발자에게 시킬 때 물어볼 것

  • 이 오류가 났을 때 백엔드 로그에 요청이 찍혔습니까, 안 찍혔습니까?
  • 사진첩과 카메라 두 경로가 같은 코드로 가는지, 다르다면 무엇이 다릅니까?

동료에게 이렇게 설명한다

"사진 기능을 붙이는데 사진첩은 되는데 카메라만 안 됐어요. 같은 업로드 함수인데 말이에요. 세 번을 고쳐도 안 되다가, 문제가 업로드 함수가 아니라 '찍은 사진의 위치를 다음 화면에 넘기는 방법'에 있다는 걸 알았어요. 서버 로그에 요청이 한 건도 없었던 게 힌트였어요."

7. OCR은 사진 종류에 따라 갈린다

취지

글자 읽기(OCR)는 사진이 어떤 사진이냐에 따라 결과가 크게 갈린다. 오늘은 같은 엔진으로 손글씨, 인쇄물, 화면을 찍은 사진, 화면 캡처 이미지를 비교할 수 있었다. 같은 문서를 손으로 쓴 것, 스캔한 것, 모니터를 사진 찍은 것, 파일로 저장한 것으로 나누어 읽혀 본 것과 같다.

검증 목표

  • 사진 종류별로 읽은 결과가 어떻게 다른지 본다.
  • 잘못 읽었을 때 원인이 코드인지 사진인지 가른다.
  • 읽은 글을 사람이 고쳐서 보내는 설계(HITL)가 실제로 필요한지 확인한다.

실제로 있었던 일

8. 앱이 멈췄을 때 와이파이

취지

1장에서 정한 "노트북 백엔드와 같은 와이파이" 방식의 약점이 실제로 터졌다. 앱은 정상인데 길이 사라진 상황이다. 이 절은 증상에서 원인으로 바깥부터 좁힌 기록이다.

검증 목표

  • 앱이 멈춘 것처럼 보일 때 앱 코드 탓인지 연결 탓인지 가른다.
  • 앞에서 만난 비슷한 증상(원만 계속 돎)과 같은 원인인지 본다.

실제로 있었던 일

증상이 두 번 있었다.

  1. 사진첩 OCR 시험 뒤, Expo Go에서 하루친구를 다시 열자 원만 계속 돌고 열리지 않았다. 노트북 쪽은 정상(개발 서버 running, 안드로이드 묶음 약 6MB 정상 생성)이었고 폰 요청은 백엔드에 0건이었다. 다시 열자 풀렸다 [확인]. 그때는 폰이 묶음을 받아 오는 연결 구간 문제로 판단했다 [추론].
  2. 카메라로 찍은 인쇄물 글을 보낸 직후 "앱이 멈췄어"라고 학습자가 알렸다. 보낸 글은 "사진에서 읽은 글이야. 여기있는 일정 중에 알려줘야 할 게 있으면 약속으로 저장해줘 / CONRAD / SEOUL / NEVER JUST STAY. STAY INSPIRED"였다. 다시 열자 fetch failed: java.net.ConnectException: Failed to connect to /<노트북 주소>:8080이라는 오류가 떴다 [확인].

원인. 백엔드에 채팅 요청이 0건이었다. 노트북이 저장된 다른 와이파이로 자동 전환되어 주소가 바뀌어 있었다. 앱의 .env 주소는 옛 주소 그대로였다 [확인]. 해결은 폰과 노트북을 원래 와이파이에 다시 연결하는 것이었다. 학습자가 "둘다 … 연결했어"라고 했고 노트북 주소가 원래대로 돌아와 8080과 8081이 모두 응답했다 [확인]. 이 글에 날짜·시각이 없으므로 약속이 생기지 않은 것은 정상이다 [추론].

앞 증상의 원인은 확정되지 않았다. 기록은 처음에 "폰에서 다시 열어 해결"이라고 적었다가 나중에 바로잡았다. 원인은 확인하지 못했고 와이파이 전환과 같은 원인이었을 가능성이 크다 [추론, 진행기록 11-4의 정정을 따름].

⚠️ 주의 — 노트북 백엔드와 같은 와이파이로 붙이는 방식은 노트북 주소가 바뀌면 앱이 길을 잃는다. 클라우드 배포(고정 주소)가 필요한 이유 하나를 직접 확인했다(교안의 연결 점검 순서 ③ 노트북과 폰이 통신할 수 있는가에 해당).

적용 원칙

누구나 알아야 할 원칙

  • "앱이 멈췄다"는 증상은 앱 코드 오류가 아닐 수 있다. 백엔드 로그에 요청이 0건이면 연결 구간을 본다.
  • 원인을 확정하지 못했으면 "가능성이 크다"라고 적는다.
  • 임시로 쓰는 노트북 백엔드는 "노트북이 켜져 있고, 같은 와이파이이고, 주소가 안 바뀐다"는 세 조건 위에서만 돈다.

개발자에게 시킬 때 물어볼 것

  • 앱이 멈췄을 때 백엔드에는 요청이 도착했습니까? 안 왔으면 어느 구간에서 막혔습니까?
  • 이 서비스는 고정 주소의 클라우드로 언제 옮깁니까?

동료에게 이렇게 설명한다

"앱이 갑자기 멈춰서 코드를 의심했는데, 백엔드 로그에 요청이 한 건도 없었어요. 노트북이 저장된 다른 와이파이로 자동 전환되어 주소가 바뀐 거였어요. 사무실 전화번호가 바뀌었는데 지점은 옛 번호로 계속 거는 상황이에요. 그래서 고정 주소의 클라우드가 필요하다고 몸으로 알았어요."

9. 말은 증거가 아니다 백엔드 안전장치의 빈칸 세 개

취지

폰에서 사진 약속 기능을 시험하다가 백엔드의 빈칸 세 개가 연달아 나왔다. 코드 시험이 220개 통과하던 백엔드였다. 앱 문제가 아니라 원래 있던 문제를 폰으로 직접 써 보다가 찾은 것이다. 이 절에서 가장 중요한 교훈은 "친구의 말은 증거가 아니고, 서버가 실제로 한 일이 증거"라는 것이다.

검증 목표

  • 약속 메모의 날짜가 입력과 다르게 나온 원인을 추적한다.
  • 약속이 저장되었다고 답했는데 메모가 없는 경우의 원인을 가른다.
  • 일정 조회 답이 실제 데이터와 맞는지 본다.
  • 고친 뒤 시험 수와 폰 확인으로 결과를 확인한다.

실제로 있었던 일

빈칸 ① 날짜가 하루 앞당겨짐(달력 날짜를 모르는 규칙). 학습자가 OCR로 읽은 글을 다듬어 보냈다. 보낸 글은 "제목 / 11월 7일 / 오전 10시30분 / 미용실 예약"이었다. 메모는 "약속을 저장했습니다: 11월 6일(금) 10:30에 '미용실 예약'"이었다. 시각은 맞고 날짜가 하루 이른 것이다. 학습자가 "그런데 이건 서버 문제인지 / 나는 11월7일 오전1030분으로 예약했는데 / 아래 메모에는 11월6일로 약속을 예약했어"라고 물었다 [확인].

도우미가 백엔드의 날짜 해석 함수(parse_when)에 같은 글을 넣어 재현했다. 결과가 2026-11-06 10:30이었다. 원인은 세 단계였다 [확인: 재현].

  1. 날짜 규칙이 "내일·금요일" 같은 말로 된 날짜만 알고 "11월 7일" 같은 달력 날짜는 모른다. 날짜를 못 찾으면 "오늘"로 본다.
  2. 오늘(11/5) 10:30은 이미 지났으니 "다음 날"로 밀어 11월 6일이 된다.
  3. N054에서 넣은 안전장치(fix_reminder_date)가 모델이 정한 날짜가 규칙과 다르면 규칙 쪽으로 덮어쓴다. 그래서 모델이 11월 7일로 맞게 정했더라도 틀린 규칙이 이겼을 가능성이 크다(로그에는 모델이 정한 create_reminder) [추론].

학습자가 "네, 고쳐 주세요"라고 승인했다. 백엔드에 새 브랜치 n057-date-fix(N056 브랜치에서 분기)를 만들어 app/when.py에 달력 날짜 해석(month_day_offset)을 추가했다. "11월 7일"을 며칠 뒤인지로 바꾸고, 지난 날짜면 내년으로, 없는 날짜(2월 30일)면 무시한다. 새 시험 9개를 더했다(틀린 그 글 그대로 11/7 10:30, 띄어쓰기 없는 "11월7일", 해 넘김 1월 2일이 2027, "11월 7일 전날 밤", 없는 날짜, 안전장치가 모델의 맞는 날짜를 더는 덮어쓰지 않는지). 전체 229개 통과(기존 220 + 새 9). 앱은 손대지 않았다 [확인].

빈칸 ② 저장했다고 말하는데 약속이 없다(안전장치가 "저장해 줘"를 모름). 고친 뒤 폰에서 세 가지를 확인했다.

  1. "미용실 약속 취소해 줘" → 로그에 취소 도구가 실행되었고 취소 메모가 붙었다. 학습자는 "메모에서 잘 붙어 있어"라고 했다. 11/6의 잘못된 약속이 정리되었다 [확인].
  2. "11월 7일 오전 10시 30분 미용실 예약 알려 줘" → 친구는 "완료했다"고 답했지만 메모가 없었다. 로그에 도구 호출이 0건이었다. 모델이 도구를 고르지 않았으니 약속은 저장되지 않았다. 날짜 수정과는 무관하다(규칙은 도구가 골라진 뒤에만 쓰인다). 추정 원인은 바로 앞 대화("이미 저장되어 있습니다", "이미 취소되었습니다")가 섞여 모델이 "이미 처리된 일"로 본 것이다 [확인: 로그] [추론: 원인]. 학습자는 "미용실 예약은 완료했는데 이번에 메모는 붙지 않네"라고 알렸다.
  3. "새 약속 저장해 줘: 11월 7일 오전 10시 30분 미용실" → 이번에도 메모 없음, 도구 호출 0건 [확인].

6장에서 메모를 붙인 설계가 거짓 "완료"를 잡아냈다. 말은 "완료"였지만 메모(서버가 실제로 도구를 돌린 결과)가 없었다.

재현으로 두 원인을 나누었다. 노트북에서 백엔드 함수를 직접 불러 모델이 고른 것과 안전장치 뒤 최종을 비교했다.

메시지모델이 고른 것안전장치 뒤 최종판단
"…미용실 예약 알려 줘"(3회)약속 저장, 날짜 11/7 10:30(3/3)그대로실제 앱에서의 "도구 0건"은 재현되지 않음. 모델이 그때그때 다르게 고르는 흔들림으로 봄 [추론]
"새 약속 저장해 줘: …"(2회)약속 저장, 11/7 10:30빠짐 ("알려 달라는 부탁이 없는데 모델이 약속 저장을 골라서 뺐습니다")안전장치의 낱말 목록에 빈칸이 있음 [확인]

이 안전장치는 "나 다음 주 토요일에 이사 가" 같은 그냥 일정 이야기에 약속이 생기는 것을 막으려고 넣은 것(N054)이다. 그런데 "알려·알림·리마인드·깨워·잊지·말해 줘"만 알고 "저장해 줘"는 모른다. 또 하나의 "안전장치가 정답을 막는" 사례다 [확인].

학습자가 "네, 고쳐 주세요"라고 승인했다. app/router.py의 부탁하는 말 목록(REMINDER_REQUEST)에 "저장해 줘, 등록해 줘, 약속으로 …, 약속 잡아·만들어·넣어 줘"를 추가했다. "저장"만 있는 말("어제 사진 저장했어")은 부탁이 아니므로 "저장해 줘·주" 꼴만 본다. 새 시험 9개(부탁 6가지는 약속이 남고 날짜 유지, 그냥 일정 이야기 3가지 "이사 가", "미용실 다녀올 거야", "사진 저장했어"는 여전히 빠짐). 전체 238개 통과(229 + 9). 폰에서 같은 메시지를 보내자 메모에 "약속을 저장했습니다: 11월 7일(토) 10:30에 '미용실 예약'"이 붙었다. 날짜 수정과 부탁 낱말 수정이 실제 대화에서 모두 동작한 것이다. 앱은 한 번도 다시 빌드하거나 Reload하지 않았다 [확인].

빈칸 ③ 일정 조회가 대화 기억으로 지어짐. 부품을 올리고(10장) 난 뒤 학습자가 "일주일 내 나의 일정을 한번 알려줘"라고 물었다. 친구의 답은 "11월 7일(토) 오전 10시30분: 미용실 예약" 하나만이었다. 로그에는 도구 호출이 0건이었다. 약속 목록 조회 도구를 쓰지 않고 대화에 나온 내용만으로 답을 지은 것이다 [확인].

실제 데이터(reminders 표, 오늘 만든 행, 사용자 앞 8자만)는 이랬다.

10. 권한 거부 부품 올리기 커밋과 push

취지

기능이 끝난 뒤 마무리 점검 단계다. 카메라 권한을 껐을 때 앱이 멈추지 않는지(교안 마지막 확인), 부품 판을 맞추면 대화가 남아 있는지, 커밋과 올리기(push)를 학습자의 승인 아래 어떻게 나누었는지를 정리했다.

검증 목표

  • 카메라 권한이 거부된 상태에서도 앱이 멈추지 않는지 본다.
  • 부품 판을 SDK에 맞춘 뒤 대화와 사진 기능이 그대로인지 본다.
  • 무엇을 어느 저장소에 어떤 순서로 올렸는지 정리한다.

실제로 있었던 일

권한 거부. 학습자가 폰 설정에서 Expo Go의 카메라 권한을 "허용 안 함"으로 바꾼 뒤 카메라로 찍기를 눌렀다. 앱이 꺼지지 않고 권한 안내 화면이 나왔고, 그 화면의 버튼으로 다시 허용했다. 학습자의 확인 말은 "확인했고, 카메라 권한을 다시 허용으로 돌렸어"였다 [확인]. 교안 8-9의 확인 다섯 가지(카메라가 입력창으로, 저절로 안 보냄, 고쳐 보내면 약속 메모, 사진첩, 권한 거부에도 안 멈춤)가 모두 끝났다 [확인].

마무리 점검. npx tsc --noEmit은 통과했다. npx expo-doctor(1.21.6)는 20개 중 19개 통과, 1개 경고였다. SDK 58이 기대하는 것보다 조금 옛 판의 부품이 6개 있었다(react-native-safe-area-context, expo, expo-constants, expo-linking, expo-router, react-native). 모두 같은 SDK 58 안의 작은 판 차이이고 템플릿을 받을 때부터 있던 차이였다 [확인].

적용 원칙

누구나 알아야 할 원칙

  • 권한 거부는 사용자가 흔히 하는 행동이다. 거부해도 앱이 멈추지 않고 안내와 다시 허용 길이 있어야 한다.
  • 부품 판을 맞춘 뒤에는 빌드·검사만 보지 말고 실제 폰에서 대화와 주요 기능이 그대로인지 본다.
  • 커밋과 push를 나누고, 각각 사용자의 승인을 받는다. 오늘의 일이 아닌 변경은 커밋에서 뺀다.
  • 기록의 "push 전" 같은 시점 표현은 나중에 바뀐 것을 반영한다. 틀린 채 남기지 않는다.

  • 권한이 거부되었을 때 앱은 어떤 화면을 보여 줍니까? 실제로 꺼 본 결과가 있습니까?
  • 이 브랜치에는 이번 작업 말고 다른 커밋도 들어 있습니까? PR로 낼 때 무엇이 함께 가나요?

"카메라 허가를 꺼 봤는데 앱이 꺼지지 않고 '허가가 필요해요' 안내가 떴고, 버튼으로 다시 켤 수 있었어요. 부품 판을 올린 뒤에도 대화가 그대로였어요. 기억은 본사에 있으니까요. 커밋은 따로, 올리기는 제 승인 뒤에 했고, 오늘 일이 아닌 변경은 일부러 뺐어요."

11. 회고 아침 답과 저녁에 본 것

취지

검증 목표

  • 시작 질문의 답이 어디까지 맞았고 무엇이 빠졌는지 본다.
