## 1. 메시지 한 건의 원가는 얼마인가

### 취지

실습의 시작 질문은 이랬다. "무료로 열어 둔 서비스에서 사용자 한 명이 하루에 메시지 300개를 보내면 어떤 문제가 생기고, 막으려면 무엇을 정해야 하는가." 학습자는 "목적 외 사용, 다른 사용자가 못 쓸 만큼 자원을 소진, 로그인 사용자만·하루 개수 제한·유료화가 방안"이라고 적었다 [확인]. 그런데 이 답에는 "메시지 한 건이 실제로 얼마인가"가 없었다. 장사에서 단가를 모르고 가격과 증정 수량을 정하는 것과 같다. 그래서 먼저 원가를 재었다.

### 검증 목표

- 최근 7일 실제 메시지 한 건의 비용을 Langfuse 기록에서 읽어 평균·상위 10%·최대를 구한다.
- 가장 비싼 단계가 어디인지 본다.
- 대화가 길어지면 메시지 비용이 얼마나 느는지 본다.

### 실제로 있었던 일

**방법.** 화면을 눌러 보는 대신 Langfuse API로 같은 일을 했다. 이 도구(langfuse 5.1.0)에는 트레이스 목록 API가 없어서, 이름이 `chat-turn`인 맨 위 관찰 단위로 메시지를 찾고 같은 트레이스의 생성(GENERATION) 비용을 더했다 [확인].

**비용 칸은 이미 채워져 있었다.** Langfuse 가격표가 `gpt-4o-mini`를 알고 있어서(입력 100만 토큰당 0.15달러·출력 0.60달러, 교안의 단가와 같다) 모델 정의를 따로 추가할 필요가 없었다 [확인].

**최근 7일, 실제 91건.** `chat-turn` 96건 중 생성 호출이 있는 95건에서 가짜 AI가 섞인 4건(비용 0)을 뺀 91건이다(환경별로 default 45·local 36·staging 10, 모두 gpt-4o-mini) [확인].

| 값 | 달러 | 원(1,400원/달러 가정) |
|---|---|---|
| 평균 | 0.000435 | 약 0.61원 |
| 중앙값 | 0.000411 | 약 0.58원 |
| 상위 10% | 0.000519 | 약 0.73원 |
| 최댓값 | 0.000760 | 약 1.06원 |
| 최솟값 | 0.000336 | 약 0.47원 |

**교안과 다른 점 ① 호출 횟수.** 교안은 메시지 한 건의 AI 호출을 세 가지(도구 고르기·답 만들기·기억 정리)로만 적는다. 실제로는 91건 중 3건이 4번 호출했다. 대화가 쌓이면 "요약" 호출이 하나 더 붙기 때문이다. 그 3건이 0.00067~0.00076달러로 가장 비쌌다 [확인].

**교안과 다른 점 ② 가장 비싼 단계.** 교안은 "대개 답 만들기가 가장 비싸다"고 한다. 내 서비스에서는 **도구 고르기가 비용의 42.2%**(답 만들기 34.4%·기억 정리 21.9%·요약 1.5%)였고 91건 중 67건에서 가장 비쌌다. 도구 고르기는 도구 설명서를 매번 같이 보내느라 입력이 처음부터 약 1,000토큰이고, 답은 짧아서(출력 평균 36토큰) 출력 단가가 4배여도 답 만들기가 덜 나왔다 [확인: 단계별 비용·토큰] [추론: 이유 설명].

**긴 대화의 첫 메시지와 열 번째 이후.** 최근 기록에 15턴 넘는 실제 대화가 없었다(세션당 최대 11턴이었고 그마저 이전 실습의 확인 스크립트가 턴마다 새 대화로 보낸 것). 그래서 한 대화 안에서 16턴을 실제 AI로 직접 보냈다(로컬, 저장소 메모리, 인사·날씨·고민·공휴일·알림·기억할 정보·앞 대화 참조를 섞음) [확인]. 16턴 합계는 0.007246달러(약 10원)였다.

| 턴 | 메시지 비용(달러) | 답 만들기 입력 토큰 | 도구 고르기 입력 토큰 |
|---|---|---|---|
| 1 | 0.000342 | 519 | 988 |
| 5 | 0.000416 | 742 | 1,096 |
| 8 | 0.000483 | 1,038 | 1,119 |
| 10 | 0.000480 | 1,106 | 1,107 |
| 13 | 0.000506 | 1,222 | 1,093 |
| 16 | 0.000474 | 1,204 | 1,121 |

첫 메시지는 0.000342달러, 열 번째 이후 평균은 0.000484달러로 **1.42배**였다. 답 만들기 입력이 519토큰에서 11턴째 약 1,200토큰까지 늘다가 멈췄다. 지난 대화를 최근 10턴까지만 넣기 때문이라는 교안의 설명과 맞는다. 도구 고르기 입력은 끝까지 약 1,100토큰이었다. 그래서 긴 대화 뒤쪽에서는 답 만들기가 도구 고르기보다 조금 비싸져 교안의 설명에 가까워진다 [확인].

**사용자 유형별 한 달 원가.** 교안 방식(원가 × 하루 메시지 × 30)으로 계산했다. 많이 쓰는 사용자·악용 계정은 "열 번째 이후" 비용(약 0.68원)을 넣었다 [추론].

| 사용자 유형 | 하루 메시지 | 메시지 한 건 원가 | 한 달 원가 |
|---|---|---|---|
| 보통 사용자 | 20 | 약 0.61원(평균) | 약 365원 |
| 많이 쓰는 사용자 | 300 | 약 0.68원 | 약 6,100원 |
| 자동화 악용 계정 | 3,000 | 약 0.68원 | 약 6만 1,000원 |

교안의 예(메시지당 1.5원 기준)보다 내 서비스는 절반 아래다. 작은 모델을 쓰고 답이 짧기 때문이다. 그래도 악용 계정 하나가 보통 사용자 약 167명분을 쓴다는 구조는 같다 [추론].

> ⚠️ **주의** — 원 단위는 모두 1,400원/달러라는 임시 가정이다. 오늘 고시 환율은 찾지 못했다. 환율이 확인되면 원 단위를 다시 계산해야 한다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 원가는 교안의 숫자를 빌리지 말고 내 서비스 기록에서 읽는다. 같은 구조(사용량에 비례)라도 크기는 절반이었다.
- "가장 비싼 단계는 어디인가"는 짐작하지 말고 단계별로 본다. 교안과 내 서비스의 답이 달랐다.
- 숫자 옆에는 조건(몇 건, 어느 기간, 어느 환경, 환율 가정)을 붙인다.

**개발자에게 시킬 때 물어볼 것**
- 이 숫자는 실제 호출 몇 건의 평균이고, 가짜 호출이나 시험 호출이 섞이지 않았나요?
- 단계별로 나누면 어느 호출이 가장 비싼가요? 대화가 길어지면 그 순서가 바뀌나요?

### 동료에게 이렇게 설명한다

"메시지 한 건이 평균 0.6원쯤 들어요. 최근 일주일 실제 91건 기준이고, 환율은 1,400원으로 가정했어요. 교안은 답 만들기가 제일 비싸다고 했는데 제 서비스는 도구를 고르는 단계가 제일 비쌌어요. 도구 설명서를 매번 같이 보내기 때문이에요. 대화가 길어지면 첫 메시지보다 1.4배쯤 되다가 멈춰요."

## 2. 같은 메시지를 두 모델에 보냈더니

### 취지

원가를 줄이려면 작은 모델이 좋고, 품질을 올리려면 큰 모델이 좋다. 그런데 얼마나 다른가. 같은 메시지 열 개를 두 모델에 보내 비용과 답을 나란히 놓았다. 소형차와 고급차를 같은 길에서 한 번씩 몰아 보는 일이다.

### 검증 목표

- 같은 열 개 메시지를 gpt-4o-mini와 gpt-4o에 보내 비용 배수를 잰다.
- 답이 얼마나 달랐는지 학습자가 직접 판정한다.
- 차이가 "어느 단계에서 처음 갈렸는지" 본다.

### 실제로 있었던 일

**방법.** 교안은 `.env`의 모델 이름을 바꾸고 서버를 껐다 켜라고 한다. 이번에는 `.env`를 열지도 고치지도 않고, 스크립트가 실행되는 동안에만 모델 이름을 정했다(앱이 이미 정해진 환경변수를 덮어쓰지 않기 때문). 같은 메시지 10개(인사 1·날씨 1·공휴일 1·고민 2·약속 1·맞장구 1·앞 말 이어받기 3)를 같은 순서로, 모델마다 새 대화로 보냈다. 로컬, 실제 AI였다 [확인].

| 항목 | 지금 모델 | 큰 모델 |
|---|---|---|
| 모델 | gpt-4o-mini | gpt-4o |
| 메시지 10개 합계 | 0.004424달러(약 6.2원) | 0.073555달러(약 103원) |
| 메시지 한 건 평균 | 약 0.62원 | 약 10.3원 |
| 비용 배수 | 1 | **×16.6** |
| 답이 더 나았던 것(학습자 판정, 10개 중) | 3 | **7** |

배수 ×16.6은 교안의 단가 차(약 16.7배)와 거의 같다. 답 만들기 출력이 평균 46토큰과 45토큰으로 비슷해서 비용 차이가 단가 차이를 그대로 따랐다. 큰 모델로 10개를 보낸 비용은 약 103원으로, 교안의 "대개 몇십 원 안쪽"보다 조금 넘었다. 메시지당 세 호출이 모두 큰 모델로 바뀌기 때문이다 [확인].

**사람 판정 7:3.** 학습자는 메시지마다 a/b로 골랐다(a = 작은 모델, b = 큰 모델). 큰 모델이 나은 것이 7개(1·2·4·5·6·7·8번), 작은 모델이 나은 것이 3개(3·9·10번)였다. 3번은 작은 모델 답에 영어가 섞였는데도 작은 모델이 낫다고 봤다 [확인].

**도우미가 트레이스로 확인한 사실(판정은 학습자 몫).**

| # | 메시지 | 작은 모델 | 큰 모델 | 처음 갈린 단계 |
|---|---|---|---|---|
| 4 | 이번 달에 쉬는 날 있어? | 도구를 **고르지 않고** "11월 11일이 임시공휴일"이라고 **지어냄** | 공휴일 조회 도구를 불러 "이번 달 공휴일 없음, 다음은 12월 25일" | 도구 고르기 |
| 7 | 토요일 오후 2시 점심 약속, 전날 밤에 알려 줘 | 알림은 맞게 저장(11-06 금 21:00)하고 결과도 "저장했습니다"인데 답은 "알림 기능은 없어서 알릴 수 없어" | 같은 저장 뒤 "이미 저장되어 있어… 새로 저장해 줄까?"(방금 저장한 것을 기존 것으로 읽음) | 답 만들기(둘 다) |
| 3 | 그럼 뭐 입고 나가면 좋을까? | 한국어 중간에 영어가 섞임 | 자연스러움 | 답 만들기 |

1·2·8·9·10번(인사·날씨·맞장구)은 두 답의 차이가 작았다. 교안의 "가벼운 인사나 맞장구에서는 가르기 어렵다"와 같다 [확인].

**4번은 이전 실습과 이어지는 발견이다.** 이전 실습(N055)에서 "다음 공휴일" 질문은 고쳤지만 "이번 달" 질문은 시험지에 없었다. 도구가 공휴일을 주지 않았는데 지어내는 같은 모양의 실패가 "이번 달"에서 다시 나왔다. 7번은 도구 결과("저장했습니다")와 답이 어긋나는 답 만들기 실패이고 작은 모델에서 더 심했다. 둘 다 이번 실습 범위(원가·결제) 밖이라 **고치지 않고 적어만 뒀다**. 나중에 N055의 시험지에 넣을 후보다 [확인].

**판정 해석.** 교안 기준으로는 차이가 드러난 메시지가 7/10이므로 "작은 모델 그대로"가 아니라 "답 만들기 호출에만 큰 모델"을 검토할 차례다. 다만 4번은 도구 고르기에서 갈렸으므로 답 만들기만 큰 모델로 바꿔서는 안 고쳐진다. 7번은 답 만들기 단계라 바꾸면 나아질 수 있지만 큰 모델도 완벽하지 않았다. 교안대로 열 개 비교는 감을 잡는 정도일 뿐이고, 모델을 실제로 바꾸려면 평가 데이터셋으로 실험해야 한다 [추론]. 이번 실습은 원가·가격을 정하는 단계까지 **지금 모델(gpt-4o-mini)로 진행**했다 [확인].

### 적용 원칙

**누구나 알아야 할 원칙**
- 비용 배수는 단가표로 거의 정해진다(×16.6). 어려운 것은 "그 값을 내고 얻는 품질 차이"를 재는 일이다.
- 답의 차이는 "어느 단계에서 처음 갈렸나"까지 본다. 단계를 모르고 모델만 바꾸면 안 고쳐지는 곳이 있다.
- 열 개 비교는 감을 잡는 수준이다. 결정은 시험지로 한다.

**개발자에게 시킬 때 물어볼 것**
- 모델을 바꾸면 세 호출 모두 바뀌나요, 일부만 바꿀 수 있나요? 비용은 각각 얼마로 달라지나요?
- 답이 갈린 곳이 도구 고르기인가요, 답 만들기인가요?

### 동료에게 이렇게 설명한다

"같은 질문 10개를 소형차와 고급차에 태워 봤어요. 기름값은 16.6배였고 제가 읽어 보니 10개 중 7개에서 고급차가 나았어요. 그런데 하나는 아예 길을 잘못 든 거라 차를 바꿔도 안 고쳐져요. 그래서 모델을 바꾸는 결정은 열 개로 하지 않고 시험지로 하기로 했어요."

## 3. 손익 계산기와 무료 한도

### 취지

원가를 알았으니 "무료를 얼마나 주고 얼마에 팔면 남는가"를 정해야 한다. 교안의 손익 계산기를 내 원가로 다시 돌려, 상품표와 무료 크레딧을 정하는 근거로 삼았다. 사업계획서의 손익분기 점검과 같다.

### 검증 목표

- 교안의 기본값으로 먼저 돌려 교안 문장을 재현하는지 확인한다.
- 내 원가로 돌려 무료 한도와 가격 중 무엇이 손익을 더 크게 바꾸는지 본다.
- 정할 것 표(차감 단위·상품표·무료 크레딧)를 채운다.

### 실제로 있었던 일

**방법.** 학습서의 웹 계산기는 PDF에 남아 있지 않아서, 강의노트에 옮긴 검산식을 코드로 옮겼다. 교안 계산기 기본값을 빌렸다: 사용자 1,000명·하루 20개·무료 하루 10개·유료 전환 5%·크레딧 10원·수수료 3.74%·고정비 7만 5,000원, 무료 사용자는 한도까지 다 쓴다고 가정했다. **먼저 교안 기본값(원가 1.5원)으로 돌려** 손익이 −40만 3,110원(가격 2배 −25만 8,720원, 무료 3개 −2,787원)으로 강의노트의 검산 표와 같음을 확인했다 [확인]. 그다음 메시지 원가는 교안대로 "비싼 쪽"(상위 10%, 약 0.73원)을 넣었다.

| 경우 | 한 달 손익 |
|---|---|
| 기본(무료 10개·크레딧 10원) | **−15만 9,489원** |
| 가격 2배(20원) | −1만 5,099원 |
| 무료 5개 | +1만 6,246원 |
| 무료 3개 | **+8만 6,541원** |
| 무료 0개 | +19만 1,982원 |

- 손익이 0이 되는 하루 무료 한도는 약 5.5개(전환율 5%일 때)다. 교안 기본값(1.5원)에서는 약 3개였다. 원가가 절반이라 무료를 두 배 가까이 줄 수 있다는 교안의 말과 같은 결과다 [추론].
- **가격 2배(−1만 5,099원)보다 무료 한도 10개→3개(+8만 6,541원)가 손익을 더 크게 바꾼다.** 교안의 결론이 내 원가에서도 그대로다 [확인].
- 모든 호출을 gpt-4o로 바꾸면(메시지당 약 10.3원) 크레딧 10원에서 **1개 팔 때마다 0.67원 손해**이고, 무료 0개여도 −9만 5,130원이다. 교안의 "큰 모델을 쓰는 메시지에도 크레딧 1개만 받는다면 이 확인이 가장 먼저 깨진다"를 숫자로 확인했다 [확인].

> ⚠️ **주의** — 이 손익은 **교안 계산기 기본값을 빌린 가정**이다. 사용자 1,000명·전환율 5%·고정비 7만 5,000원은 내 서비스의 실제 값이 아니다. 지금 실제 사용자는 거의 없다(이전 실습에서 30일 94건). 이 표는 "무료 한도가 가격보다 더 큰 손잡이"라는 구조를 확인하는 용도이고, 매출 예측이 아니다.

**정할 것 표(학습자 결정).**

| 정할 것 | 내 서비스의 값 | 근거 |
|---|---|---|
| 차감 단위 | 메시지 1건 = 크레딧 **1개** | 긴 대화에서도 메시지 원가가 0.48~0.76원 안쪽이라 고정 1개로 원가에서 크게 벗어나지 않음 |
| 크레딧을 더 받는 기능 | 없음(지금은) | 사진 읽기는 호출 원가를 재기 전이라 보류 |
| 상품표 | credits_100 1,000원/100개 · credits_550 5,000원/550개 · credits_1200 10,000원/1,200개(교안의 예) | 가장 큰 묶음의 1개 가격 약 8.3원이 비싼 쪽 원가 0.73원 + 수수료 0.31원을 넉넉히 넘음. 단 모든 호출을 gpt-4o로 바꾸면 깨짐 |
| 처음 받는 무료 크레딧 | **30개**(가입 때 한 번) | 보통 사용자(하루 20개) 하루 반 분량. 게스트를 새로 만들어도 계정당 원가 약 22원(30 × 0.73원)에서 멈춤 |
| 하루 무료 메시지 | **없음** | 구현이 단순함. 하루 무료가 5.5개를 넘으면 적자라는 것을 확인함 |

무료를 "하루 몇 개"가 아니라 "가입 때 한 번 30개"로 정한 것이 이 절의 핵심 결정이다. 하루 무료는 매일 원가가 나가고, 가입 무료는 계정당 상한이 있기 때문이다 [추론].

### 적용 원칙

**누구나 알아야 할 원칙**
- 가격표를 만들기 전에 원가와 수수료로 "한 개 팔면 얼마 남는가"를 계산한다.
- 손익이 크게 움직이는 손잡이(여기서는 무료 한도)부터 정한다.
- 가정으로 만든 표는 "가정"이라고 표에 붙인다.

**개발자에게 시킬 때 물어볼 것**
- 이 손익표의 전환율·사용자 수·고정비는 실제 값인가요, 빌린 값인가요?
- 모델을 바꾸면 이 표의 어느 칸이 가장 먼저 깨지나요?

### 동료에게 이렇게 설명한다

"하루 무료 10개를 주면 한 달에 15만 원 넘게 적자인데, 무료를 3개로 줄이면 8만 원 넘게 흑자예요. 가격을 2배로 올려도 그만큼은 안 움직여요. 다만 사용자 1,000명, 전환율 5%는 교안 계산기의 기본값을 빌려 온 가정이라, 방향만 보는 표예요. 그래서 하루 무료 대신 가입 때 한 번 30개만 주기로 했어요."

## 4. 크레딧 원장

### 취지

돈을 받기 전에 먼저 "크레딧을 어떻게 세고 막을지"를 만들었다. 잔액 숫자 하나가 아니라, 늘고 준 이유를 한 줄씩 쌓는 원장이다. 통장이 잔액만 적지 않고 입출금 내역을 남기는 것, 회계가 지우지 않고 분개를 쌓는 것과 같다.

### 검증 목표

- 새 사용자에게 30개가 한 번만 들어가고, 메시지마다 1개가 줄고, 0이면 거절되는지 본다.
- 화면을 건너뛰고 서버를 직접 불러도 거절되는지 본다.
- 구현 전에 정할 것(언제 차감하나, 실패하면 어떻게 하나, 데이터 삭제 때 원장은)을 정한다.

### 실제로 있었던 일

**구현 전에 학습자가 정한 것.**

| 질문 | 정한 것 | 이유 |
|---|---|---|
| 언제 차감하나 | 메시지를 받자마자 | 답은 스트리밍이라 흘려 보내기 시작하면 상태 코드를 바꿀 수 없다. 402는 답을 만들기 전에만 돌려줄 수 있다 |
| 답을 만들다 실패하면 | 되돌리는 줄(+1)을 쌓는다 | 실패한 사실과 돌려준 사실이 원장에 모두 남는다 |
| 크레딧이 0이면 | 402와 "크레딧을 다 썼어요. 충전하면 바로 이어서 이야기할 수 있어요." | 친구 말투, 이후 충전 팝업으로 이어짐 |
| 어디서 차감하나 | 서버에서만 | 화면은 서버가 준 잔액을 보여 주기만 |
| (교안에 없음) '내 데이터 삭제'를 누르면 원장은 | **남긴다** | 원장에는 대화 내용이 없다(변화량·이유·참조). 지우면 삭제할 때마다 무료 30개를 다시 받고, 산 크레딧도 사라진다 |

**도우미가 구현 중에 더한 판단(교안에 없음).**

1. **위기 표현은 크레딧을 받지도 거절하지도 않는다.** 크레딧이 0인 사용자가 "죽고 싶어"를 보냈을 때 402가 나가면 안전 안내를 못 받는다. 안전장치를 약하게 하는 변경이 아니라, 결제가 안전장치를 막지 않게 하는 변경이다 [확인: 테스트].
2. **가입 무료 크레딧은 차감할 때도 먼저 쌓는다.** 화면을 거치지 않고 서버를 바로 불러도 30개가 먼저 쌓인 뒤 빠진다 [확인].
3. **동시에 두 메시지가 와도 잔액을 넘겨 쓰지 못하게 DB 함수 하나로 묶었다.** 사용자별 잠금을 건 뒤 가입분 확인 → 잔액 확인 → 줄 추가를 한다. 잔액이 1인데 동시에 10개를 보내는 테스트에서 1개만 통과했다 [확인].
4. **두 DB 함수는 브라우저 쪽 역할의 실행 권한을 회수하고 서버 역할에만 줬다.** Supabase는 새 함수를 브라우저 역할도 부를 수 있게 하는 기본 설정이라, 막지 않으면 공개 키로 남의 잔액을 빼는 함수를 부를 수 있다 [확인].

**테스트와 일부러 깨 보기.** 새 테스트 9개(가입 30개 한 번만, 메시지마다 −1 줄, 잔액 0이면 402와 답 안 만듦, 가입분 먼저, 위기 표현은 0이어도 통과, 답 실패면 되돌리는 줄, 데이터 삭제해도 원장 유지, 같은 참조 두 번 안 쌓임, 동시 10개에 1개만 통과)를 더해 204개가 통과했다(기존 195 + 9). 402를 내는 조건문을 일부러 꺼 보니 해당 테스트가 실패했고 되돌리자 다시 통과했다 [확인].

**실제 환경 확인(시험용 Supabase + 실제 AI).**

| 확인 | 결과 |
|---|---|
| 서버 열쇠로 잔액 함수·원장 조회 | 성공 |
| 브라우저 열쇠로 차감 함수·잔액 함수 호출 | **401, 권한 없음 코드(42501)** |
| 브라우저 열쇠로 원장 조회 | 200이지만 `[]` — 행 보안 정책(정책 없음)으로 아무 행도 안 보임 |
| 새 브라우저로 열기 | 머리줄 '크레딧 30', 로그 "가입 무료 크레딧 지급" |
| 메시지 하나 | '크레딧 29', 원장 `chat −1`·`signup +30` |
| 잔액을 0으로 만든 뒤 메시지 | 거절 문구 + 입력창에 원문 남음. 같은 게스트로 서버를 직접 불러도 **402** |

잔액 0 만들기는 원장을 고치지 않고 `adjust −29` 줄을 더해서 했다. 실제 AI는 답 뒤에 기억 정리까지 해서 숫자가 몇 초 늦게 바뀌었다(화면은 `done` 뒤에 다시 읽는다) [확인]. 교안의 해석대로 거절은 서버에서 일어나므로 화면을 건너뛰어도 크레딧 없이는 답을 받을 수 없다. **다만 이 시점에는 크레딧이 줄기만 하고 늘릴 방법이 없었다.** 결제가 필요한 이유다 [확인].

> 📌 **요약** — 4장의 핵심은 세 가지다. 원장은 지우지 않고 줄을 더한다. 거절은 서버에서만 한다. 그리고 "남의 잔액을 빼는 함수"는 권한을 회수해 브라우저가 못 부르게 한다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 잔액 숫자 하나만 두지 말고 이유가 붙은 줄을 쌓는다. 잘못된 줄은 지우지 않고 되돌리는 줄을 더한다.
- 돈과 관련된 판단(차감·거절)은 화면이 아니라 서버가 한다. 화면은 서버가 준 숫자를 보여 줄 뿐이다.
- 안전을 위한 기능(위기 안내)이 결제 때문에 막히지 않는지 따로 점검한다.

**개발자에게 시킬 때 물어볼 것**
- 동시에 두 요청이 같은 잔액을 읽으면 어떻게 되나요? 이를 어떤 테스트로 확인했나요?
- 브라우저 열쇠로 이 함수를 직접 부르면 거절되나요? 직접 불러 본 결과가 있나요?
- 사용자가 "내 데이터 삭제"를 누르면 원장은 어떻게 되나요?

### 동료에게 이렇게 설명한다

"크레딧을 선불 카드로 만들었어요. 잔액만 적지 않고 통장처럼 줄마다 이유를 남겨요. 줄이 늘기만 하고 지우지 않아서, 잘못 빠진 것도 '돌려준 줄'을 더해요. 브라우저에서 몰래 부르면 안 되는 함수는 권한을 회수했고, 실제로 브라우저 열쇠로 불러 보니 401이 나왔어요."

## 5. 테스트 키를 찾은 과정

### 취지

결제 대행사 연동에는 키가 필요하다. 교안은 "연동 문서의 코드 예제에서 문서용 테스트 키를 찾으라"고 한다. 그런데 오늘 문서에는 키가 없었다. 이 절은 교안과 오늘의 현실이 어긋났을 때 어디서 근거를 다시 찾았는지의 기록이다.

### 검증 목표

- 교안이 가리키는 곳에서 문서용 테스트 키를 찾는다.
- 못 찾으면 공식 출처 안에서 다른 곳을 찾고, 그 근거를 적는다.

### 실제로 있었던 일

**교안은 "문서에 키가 있다"고 하지만 오늘은 자리표시자뿐이었다.** 연동 문서를 로그인하지 않은 브라우저로 열어 화면이 다 그려진 뒤에도 키 자리에는 `{WIDGET_CLIENT_KEY}`·`{WIDGET_SECRET_KEY}`라는 자리표시자만 보였다. 학습자도 같은 화면을 붙여 보냈고, 도우미가 내장 브라우저로 키 모양 문자열이 0건임을 확인했다. 공식 AI 안내(LLM Quick Reference)도 "문서에 실제 시크릿 키는 나오지 않는다"고 적는다. 반면 API 키 안내 문서는 여전히 "전자결제 신청 전에는 문서에 있는 테스트 키로 연동해 보라"고 한다. 문서끼리도 어긋나 있었다 [확인].

**찾은 곳은 공식 샘플 저장소였다.** 결제 대행사의 공식 샘플 저장소(V2 샘플, 2026-04-30 갱신, 보관 처리 안 됨)에 결제위젯 문서용 테스트 키가 **한 세트로** 공개돼 있었다. 같은 저장소의 PHP+자바스크립트 샘플이 두 키를 함께 쓴다. 공개된 키라도 값은 기록에 적지 않았다. 교안대로 시크릿과 똑같이 `.env`에만 둔다 [확인].

학습자가 이 키 한 세트를 `.env`에 넣었다. 도우미는 `.env`를 열지 않고 앱이 읽는 방식으로 접두사와 길이만 확인했다(클라이언트 키 `test_gck_` 38자, 시크릿 키 `test_gsk_` 38자, 앞뒤 공백 없음) [확인].

**AI 연동 안내에서 쓴 것.** 학습자가 AI 연동 안내 링크를 줬다. 거기서 MCP 서버(이 세션에는 연결 안 됨, 추가해도 다음 세션부터), 전체 문서 목록(`llms.txt`), Quick Reference(결제 흐름·결정 룰·자주 틀리는 패턴 21개), 주소 끝에 `.md`를 붙이면 원문이 나오는 규칙이 있음을 알았다. 이번에는 MCP 대신 이 문서들을 직접 읽어 근거로 썼다. 6장에 바로 쓴 사실은 다음과 같다 [확인].

- 승인 API 호출 때 `Authorization: Basic base64(시크릿키:)`처럼 **콜론이 필수**다.
- 주문 번호는 영문·숫자·`-_=` 6~64자다.
- 결제창에서 실패하면 실패 주소로 오고, 이때는 승인 API를 부르지 않는다.
- 승인 요청에 `Idempotency-Key`를 붙인다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 교안의 "여기서 찾으라"가 현실과 어긋나면, 같은 공식 출처 안에서 대체 경로를 찾고 어디서 찾았는지 적는다.
- 테스트 키라도 값은 문서에 쓰지 않는다. 습관이 되어야 실제 키에서 사고가 안 난다.
- 키는 `.env`에만 둔다. 도우미에게도 `.env`를 열어 달라고 하지 않고, 앞 글자·길이만 확인한다.

**개발자에게 시킬 때 물어볼 것**
- 이 키는 어느 공식 문서·저장소에서 가져왔나요? 테스트용이 맞나요?
- 코드나 로그에 키가 남지 않는지 어떻게 확인하나요?

### 동료에게 이렇게 설명한다

"교안은 '연동 문서에 테스트 키가 있다'고 했는데 오늘 가 보니 자리표시자만 있었어요. 같은 회사의 공식 샘플 저장소에서 한 세트를 찾았고, 값은 기록에 안 적고 금고(.env)에만 넣었어요. 교안과 현실이 다르면 어디서 근거를 다시 찾았는지를 적어 두는 게 중요해요."

## 6. 결제위젯과 실행 확인

### 취지

크레딧을 늘리는 길을 만들었다. 결제위젯 화면, 주문 저장, 서버의 승인 처리다. 그리고 교안의 "실행 확인" 1~6번을 따라 실제로 돌려 보았다. 이 절에는 교안에 없던 발견이 둘 있다. 결제창을 닫으면 실패 주소로 오지 않는 것, 그리고 접속 로그에 결제 키 전체가 남던 것이다.

### 검증 목표

- 상품 고르기 → 결제위젯 → 성공 페이지 → 서버 승인 → 원장 +줄 → 충전한 크레딧으로 메시지까지 한 번 끝까지 간다.
- 토스페이먼츠·주문 표·원장의 세 곳이 맞는지 본다.
- 로그에 시크릿 키나 결제 키 전체가 남지 않는지 본다.

### 실제로 있었던 일

**구성(교안 구조 표를 그대로 따름).**

| 구성 요소 | friend-agent에서 |
|---|---|
| 상품표 | 서버 한 곳(`PRODUCTS`)에만 있고 화면 코드에는 금액이 없다 |
| 주문 만들기 | 화면은 상품 ID만 보내고, 금액·크레딧은 서버 상품표에서 정한다. 주문 번호는 `ord_` + 무작위 32자 |
| 결제위젯 | 크레딧 팝업 안에서 결제위젯을 띄운다. 금액은 서버가 준 주문 금액 |
| 성공 페이지 | 주소의 결제 키·주문 번호·금액을 서버로 보내기만 하고 **크레딧을 직접 늘리지 않는다** |
| 서버 승인 | 내 주문인가 → 이미 완료인가 → 대기인가 → **금액이 저장된 금액과 같은가(다르면 400, 승인 API 안 부름)** → 시크릿 키로 승인 → 성공하면 주문 완료 + 원장에 `order:주문번호` + 줄 |
| 실패 페이지 | 오류 코드·문구를 보여 주고 주문을 실패로 바꿈 |

- 화면이 `amount=100, credits=1200`을 덧붙여 보내도 주문은 1,000원/100개로 만들어졌다 [확인: 테스트].
- 시크릿 키는 서버 설정과 승인 호출에서만 읽고, 화면에 주는 설정 응답에는 없다 [확인: 테스트].
- 크레딧을 늘리는 곳은 코드에서 세 곳뿐이다(가입 지급·답 실패 되돌림·승인 성공 뒤 구매) [확인].
- 새 테스트 7개를 더해 211개가 통과했다.

교안의 객관식(성공 페이지가 열리자마자 크레딧을 늘리는 설계의 문제)에 학습자는 "1번, 인증과 결제는 서로 다른 개념이다"라고 답했고 정답이었다. 성공 주소가 열렸다는 것은 인증이 끝났다는 뜻이지 승인이 끝났다는 뜻이 아니다. 화면 코드가 크레딧 지급을 부를 수 있으면 결제 없이 API를 직접 불러 크레딧을 늘릴 수 있으므로, 크레딧을 늘리는 코드는 서버의 승인 처리 한 곳에만 둔다 [확인].

**실행 확인 1~3번.** 크레딧 표시를 누르면 팝업에 남은 크레딧 30·차감 규칙·상품 3개(1개 10원·9.1원·8.3원)·안내 문구·게스트 경고가 보였다. 잔액 0에서 메시지를 보내자 거절 문구와 함께 팝업이 열리고 입력창에 원문이 남았다. 상품을 고르면 결제위젯이 뜨고 결제 전에 주문 대기 줄이 저장됐다 [확인].

**실행 확인 4번에서 막혔다.** 신용·체크카드는 카드사가 실제 앱 인증(우리 WON카드 앱 결제코드)을 요구했고, 토스페이는 실제 가입 휴대폰 번호와 생년월일을 요구했다. 교안은 "테스트 카드로 끝까지"를 기대하지만, 문서용 키로 열어도 카드사·토스페이의 본인 확인 창은 실제로 떴다. 개인정보라서 입력하지 않고 닫았다 [확인].

**발견 ① 결제창을 닫으면 실패 주소로 오지 않는다.** 교안은 "결제를 진행하다 취소하면 실패 페이지에 오류 문구가 뜨고 주문은 실패가 된다"고 적는다. 실제로 PC에서 토스페이 창을 닫으니 토스가 실패 페이지로 보내지 않고, 결제위젯이 **화면 안에서 오류("취소되었습니다")만 돌려줬다**. 서버 로그에 실패 처리 호출이 없었고 **주문이 '대기'로 남았다**. 그래서 화면을 고쳤다. 결제 요청이 오류를 던지면 실패 페이지와 똑같이 서버에 실패를 알려 주문을 실패로 바꾸고, 결제 화면을 닫아 상품 고르기로 돌아가며, 다음 결제는 **새 주문**으로 시작한다. 고친 뒤 현대카드 창을 닫아 보니 화면에 "결제가 끝나지 않았어요: 취소되었습니다."가 뜨고 주문은 실패(`USER_CANCEL`)가 됐다. 승인이 없었으니 크레딧도 그대로였다. 고치기 전에 생긴 대기 주문 1건은 시험용 프로젝트라 그대로 뒀다 [확인].

**서버가 토스 승인 API와 통신하는지 따로 확인.** 존재하지 않는 결제 키로 승인을 요청했다(돈·카드·개인정보 없음). 우리 코드 그대로는 404와 "결제 진행 데이터가 존재하지 않습니다"가 왔다. 열쇠는 통과했고 결제만 없다는 뜻이다. 비교로 콜론을 뺀 헤더를 보내자 401(인증되지 않은 키)이 왔다. 문서가 "자주 틀리는 패턴 1번"이라 한 것이 실제로 401이 됨을 확인했다 [확인].

**실제 테스트 결제 승인 1건.** 도우미(Claude)가 토스 환경 가이드의 "유효한 카드 번호로 테스트해도 실제 결제는 되지 않고 가상으로 승인"을 근거로 "볼 수 있다"고 바로잡은 뒤, 학습자가 크롬에서 크레딧 100개·1,000원을 골라 **본인 카드 앱으로 카드사 인증**을 끝까지 했다. 인증은 학습자가 휴대폰에서 직접 했고 도우미는 어떤 값도 보거나 입력하지 않았다. 성공 페이지 팝업에 "100개를 충전했어요. 지금 잔액 130개예요."가 떴다(11:53) [확인]. 앞에서 "어렵다"고 좁게 말한 것을 학습자의 질문으로 바로잡았다.

**세 곳의 기록이 맞았다.**

| 곳 | 기록 |
|---|---|
| 토스페이먼츠 | 결제 조회 API로 조회됨. 상태 `DONE`, 1,000원, 카드, 승인 시각 11:53:47(KST), 주문 번호 일치 |
| 주문 표 | credits_100 · 1,000원 · 100개 · **paid** · 승인 시각 11:53:47 KST(= 02:53:47 UTC) · 결제 키 저장 |
| 크레딧 원장 | `signup +30` → `purchase +100`(참조 = `order:` + 이 주문 번호) · 합계 130 |

발주서·납품서·대금 지급을 맞춰 보는 대사에 해당하는 일이다. 문서용 테스트 키라 개발자센터 화면에는 안 나오고 조회 API로만 확인했다 [확인].

**충전한 크레딧으로 메시지.** 팝업을 닫고 "내일 아침 8시에 물 마시라고 해줘"를 보내자 답을 받은 뒤 '크레딧 129', 원장은 `signup +30` → `purchase +100` → `chat −1` 합계 129였다. 곁가지 관찰: 이 메시지에서 캐릭터가 기억 메모만 남기고 약속 알림은 만들지 않았다(알림 0개). 이번 범위 밖이라 고치지 않았고, 2절의 7번과 함께 이전 실습 시험지에 넣을 후보다 [확인].

**발견 ② 접속 로그에 결제 키 전체가 남았다.** 확인 목록의 "서버 로그에 시크릿 키와 결제 키 전체가 없음"은 처음엔 **실패**였다. 시크릿 키는 0건이었지만, 웹 서버(uvicorn)의 접속 로그에 토스가 돌려보낸 주소가 그대로 찍혀 `…/payments/success?paymentType=NORMAL&orderId=…&paymentKey=(전체)&amount=1000`처럼 결제 키 전체가 남았다. 우리 코드가 직접 남기는 로그는 금액·크레딧 수·오류 코드만이었는데, 앱 코드가 아닌 접속 로그는 보지 못했다. 교안의 "서버 터미널 로그에서 결제 키를 검색"으로만 잡혔다 [확인]. 이전에 "로그는 금액·크레딧 수·오류 코드만"이라 적은 것은 **우리 코드의 로그**에 대한 말이었고 접속 로그까지는 아니었다는 정정도 함께 기록했다.

고침은 접속 로그 필터다. 주소의 `paymentKey=` 값을 **앞 4자만 남기고 `***`로 가린다**. 테스트 1개를 더해 212개가 통과했고, 서버를 다시 띄워 가짜 키로 성공 주소를 불러 보니 로그에 `paymentKey=tgen***`으로 찍혔다 [확인].

> ⚠️ **주의** — 이 필터는 우리 앱이 남기는 접속 로그만 가린다. Cloud Run에 배포하면 앱 앞단(Google 프런트엔드)의 요청 로그가 주소 전체를 따로 남기므로 이 필터로는 가리지 못한다. 그 로그의 보존 기간과 열람 권한은 **아직 확인하지 않았다** [미확인].

### 적용 원칙

**누구나 알아야 할 원칙**
- 상품 가격과 크레딧 수는 서버의 표 한 곳에만 둔다. 화면이 보낸 금액은 믿지 않고 서버가 저장한 금액과 비교한다.
- 크레딧을 늘리는 코드는 서버의 승인 처리 한 곳에만 둔다. 성공 페이지가 열렸다는 것은 인증이지 승인이 아니다.
- "결제가 끝났다"는 한 곳의 말만 믿지 않고 세 곳(대행사·주문·원장)의 기록을 맞춰 본다.
- 교안의 기대 결과와 실제 화면이 다르면(결제창을 닫았을 때) 실제를 적고 고친다.
- 로그에는 결제 키를 남기지 않는다. 우리 코드의 로그뿐 아니라 서버·배포 환경의 접속 로그까지 본다.

**개발자에게 시킬 때 물어볼 것**
- 결제 성공 페이지가 열리면 크레딧이 바로 늘어나나요, 서버 승인 뒤에만 늘어나나요?
- 결제창을 닫거나 네트워크가 끊겼을 때 주문은 어떤 상태로 남나요? 실제로 해 본 결과가 있나요?
- 서버·배포 환경의 접속 로그에 결제 키가 찍히지 않나요? 앱 앞단의 로그는 누가, 얼마나 보나요?

### 동료에게 이렇게 설명한다

"결제는 식당 카드 결제와 같아요. 손님이 카드를 꽂고 확인받는 게 인증이고, 식당이 카드사에 확정을 요청해 승인받는 게 진짜 결제예요. 그래서 크레딧은 서버가 승인을 받은 뒤에만 늘려요. 오늘 본인 카드로 1,000원짜리 테스트 결제를 한 번 해서 토스·주문 표·원장 세 곳이 맞는 것을 봤어요. 하다가 결제창을 닫으면 주문이 대기로 남는 것, 접속 로그에 결제 키가 통째로 찍히는 것 두 가지를 찾아 고쳤어요."

## 7. 같은 결제를 두 번 받지 않기

### 취지

새로고침, 더블클릭, 네트워크 끊김 때문에 같은 승인 요청이 두 번 갈 수 있다. 그때 크레딧이 두 번 들어가거나, 돈은 빠졌는데 우리 서버가 실패로 표시하는 어긋남이 생기면 안 된다. 엘리베이터 1층 버튼처럼 한 번 누르든 세 번 누르든 결과가 같아야 한다.

### 검증 목표

- 지금의 승인 처리가 멱등키를 보내는지부터 확인한다.
- 세 겹 장치가 각각 무엇을 막는지 테스트로 보인다.
- 일부러 깨 보고, 새로고침으로 실제 확인한다.

### 실제로 있었던 일

**먼저 확인: 멱등키를 보내고 있지 않았다.** 코드에서 멱등키 관련 문자열이 0건이었다. 교안이 "짧게 요청하면 에이전트가 넣지 않고 지나가기 쉽다"고 한 자리다. 6장에서 일부러 뺀 것이지만, 짧은 요청이었다면 실제로 빠졌을 곳이다 [확인].

**세 겹 장치.**

| 겹 | 장치 | 막는 것 |
|---|---|---|
| ① | 주문 상태 확인(이미 완료된 주문이면 승인 API를 다시 부르지 않음) | 새로고침 같은 느린 중복 |
| ② | 원장 참조 유일(`order:주문번호`) | **우리 원장**에 크레딧이 두 번 쌓이는 것 |
| ③ | 멱등키(`Idempotency-Key`) | **대행사에서** 승인이 두 번 처리되는 것 |

멱등키 값은 학습자가 **주문 번호 그대로**로 정했다. 이미 추측할 수 없는 무작위 값이고 주문마다 하나라서, 칸을 더하지 않아도 된다 [확인].

**바뀐 것.** 승인 요청 헤더에 멱등키를 넣었다. 승인 API를 부를 때마다 로그에 주문 번호·멱등키·시도 횟수를 남기되 시크릿 키와 결제 키는 남기지 않는다. 대행사가 "처리 중"(409)이라 답하면 **키를 바꾸지 않고** 1초 뒤 같은 키로 다시(최대 3번) 보내고, 그래도 처리 중이면 "잠시 뒤 새로고침"을 돌려주며 주문은 대기로 둔다. 교안에 없던 것으로, 이미 완료된 주문에도 원장 줄을 한 번 더 시도한다(참조가 유일해서 이미 있으면 안 쌓인다). 승인 뒤 주문은 완료로 바꿨는데 크레딧 기록 직전에 멈춘 경우를 새로고침으로 복구하기 위해서다. 화면에는 중복 시 "이미 충전된 결제예요(100개). 지금 잔액 129개예요."라는 문구를 더했다 [확인].

**테스트 8개.**

| 구분 | 테스트 | 결과 |
|---|---|---|
| 교안 4가지 | 같은 승인 요청 두 번 | 크레딧 1번, 가짜 승인 API 1번 호출 |
| | 금액을 바꾼 요청 | 400, **승인 API 0번**, 주문 대기, 크레딧 그대로 |
| | 다른 사용자의 주문 | 404, **승인 API 0번** |
| | 승인 실패 | 주문 실패, 크레딧 없음 |
| 더한 4가지 | 거의 동시에 두 번(둘 다 '대기'를 읽음) | 호출 2번·같은 키·실제 승인 1번·원장 1줄 |
| | 409 뒤 같은 키로 다시 | 통과 |
| | 응답 없음(502, 대기 유지) 뒤 다시 보내 완료 | 통과 |
| | 완료인데 원장이 없는 주문을 두 번 새로고침 | 한 번만 채움 |

가짜 승인 API는 실제 대행사처럼 같은 멱등키면 첫 응답을 돌려주게 만들었다 [확인].

**일부러 깨 보기.** ⓐ 멱등키를 요청마다 새 무작위 값으로 바꾸자 4개 테스트(두 번·동시·409·네트워크)가 실패했다. ⓑ 주문 상태 확인(①)을 끄자 2개가 실패했다(두 번 요청에서 승인 API가 2번 불림, 복구 테스트). 이때도 크레딧은 ②·③ 덕에 한 번만 들어갔다. 겹쳐 둔 이유다. 되돌려 **220개가 통과**했다(212 + 8) [확인].

**직접 확인(사용자 크롬).** 결제를 끝낸 성공 화면을 학습자가 새로고침하자 "이미 충전된 결제예요(100개). 지금 잔액 129개예요."가 떴다. 서버 로그에는 새로고침 2번이 승인 요청으로 2번 들어왔지만 **토스 호출은 0번**이었다. ①이 대행사까지 가기 전에 멈춘 것이다. 원장은 `signup +30`·`purchase +100`·`chat −1` 그대로이고 purchase 줄은 1개, 합계 129였다. 접속 로그의 결제 키는 `tgen***`이었다 [확인]. 결제 취소는 6장에서 확인했다.

한계: 실제 토스로 같은 멱등키를 두 번 보내 첫 응답을 돌려받는 것은 **하지 않았다**. 새로고침은 ①에서 멈춰 토스까지 가지 않는다. ③은 가짜 승인 API 테스트(동시 두 번·409·네트워크)까지가 근거다 [미확인].

**이해 점검(주관식).** 질문은 "같은 결제 요청이 거의 동시에 두 번 오면 어떤 장치가 막아 주고, 그 장치가 없었다면 어떤 일이 생길까."였다. 학습자는 "원장 참고 또는 멱등키가 막아 줄 것이다."라고 답했다. 막는 장치를 ②와 ③으로 정확히 짚었다(해설서 모범 답안도 같다). 빠진 것은 뒷부분, "없었다면 어떤 일이 생기나"였다. ②가 없으면 두 요청이 각각 크레딧을 지급해 **같은 결제로 크레딧이 두 번** 들어간다(550개 상품이면 550개가 두 번). ③이 없으면 두 번째 요청이 대행사에서 "이미 처리된 결제" 같은 오류를 받아, 돈은 빠졌는데 우리 서버가 그 주문을 실패로 표시하는 어긋남이 생길 수 있다 [확인: 학습자의 답과 해설서] [추론: ③의 어긋남 시나리오].

### 적용 원칙

**누구나 알아야 할 원칙**
- 돈과 관련된 요청은 "두 번 와도 한 번과 같게" 만든다. 하나의 장치에 기대지 않고 서로 다른 장치를 겹친다. 하나를 끄고도 결과가 지켜졌다.
- 판단은 화면 문구가 아니라 잔액과 원장으로 한다.
- 에이전트가 짧은 요청에서 빠뜨리기 쉬운 것(멱등키)은 먼저 "넣었는가"를 확인한다.
- 일부러 한 장치를 꺼서 테스트가 실제로 실패하는지 본다. 안 깨지는 테스트는 아무것도 지키지 않는다.

**개발자에게 시킬 때 물어볼 것**
- 승인 요청이 같은 주문에 대해 두 번 가면 어떤 장치가 막나요? 그 장치를 끄면 어떤 테스트가 실패하나요?
- 금액이 바뀐 요청이나 남의 주문일 때 승인 API는 몇 번 불리나요(0번이어야 합니다)?

### 동료에게 이렇게 설명한다

"같은 결제가 두 번 와도 크레딧은 한 번만 들어가게 세 겹을 쳤어요. 주문 상태를 보는 현장 점검, 원장에서 같은 번호를 거르는 장부 대조, 대행사에 같은 이름표를 붙이는 외부 확인이에요. 그중 둘(현장 점검과 대행사 이름표)을 일부러 꺼 봤더니 테스트가 깨졌고, 그래도 크레딧은 한 번만 들어갔어요. 결제를 끝낸 화면을 새로고침하니 토스까지 가지 않고 '이미 충전된 결제예요'로 멈췄어요."

## 8. 회고: 1장에서 적은 답과 실제로 만든 것

### 취지

처음에 적은 "하루 300개 사용자" 답을 다시 꺼내, 오늘 만든 것이 그 문제를 어디까지 막는지, 못 막는 것이 무엇인지 본다. 기획서의 "처음 목표 대 결과" 비교와 같다.

### 검증 목표

- 1장 답의 세 제안(유료화·하루 개수 제한·로그인 사용자만)이 오늘 어떻게 되었는지 본다.
- 아직 못 막는 것을 적는다.

### 실제로 있었던 일

**학습자의 회고 답.** "일정부분 무료체험분을 주고 나머지는 유료화함으로써 고객이용 편의성은 높이고 무분별한 사용으로 인한 다른 이용자 불편과 수익성 저하를 막을 수 있었습니다." [확인]

**세 제안 대 실제.**

| 1장에서 제안 | 오늘 | 근거 |
|---|---|---|
| 유료화 | ✅ 만들었다. 메시지 1개 = 크레딧 1개, 상품표 3개, 실제 테스트 결제 승인 1건까지 | 4·6·7절 |
| 사용자당 하루 이용 개수 제한 | △ 다른 모양으로. **가입 때 무료 30개 한 번**(하루 무료는 두지 않음). 하루 상한 자체는 없다 | 3·4절 |
| 로그인 사용자만 | ✕ 그대로 게스트도 쓴다. 게스트를 새로 만들 때마다 무료 30개를 다시 받을 수 있다(계정당 원가 약 22원에서 멈춤) | 3절 |

**막는 것.** 무료분을 다 쓰면 402로 거절되고 더 쓰려면 사야 한다. 하루 300개 사용자는 이제 쓴 만큼 낸다(메시지 1개 10원 안팎, 원가 약 0.7원). 원가가 사용량에 비례하는 문제를 가격 구조로 막았다 [추론].

**아직 못 막는 것(학습자 답에 빠진 것).** 해설서의 모범 답안과 실습에서 확인한 것을 합쳤다.

- 여러 게스트 계정으로 무료 30개를 반복해서 받는 것. 1장의 "로그인 사용자만" 제안이 아직 남은 일이다.
- 자동화 프로그램의 대량 요청. 요청 속도 제한·하루/월 사용량 상한·동시 실행 수 제한이 없다. 돈을 내는 사용자라도 한꺼번에 몰리면 다른 사용자의 응답이 느려질 수 있다. 1장의 "다른 이용자 불편"은 유료화만으로는 다 막히지 않는다.
- 예상 밖으로 긴 입력, 비싼 기능(사진 읽기)의 원가. 작업별 최대 토큰·기능별 차감은 보류했다.
- 이상 사용 탐지·알림, 환불·유효기간 정책, Cloud Run 앞단 요청 로그의 결제 키.

해설서의 결론은 이렇다. 원가표는 비용을 파악하고, 크레딧 한도는 비용을 통제하며, 결제 시스템은 정당한 과금과 중복 지급을 막는다. 여기에 비정상 사용 탐지와 요청 제한까지 결합해야 안정적으로 운영된다 [확인].

**내부통제 3선으로 읽으면 [보충 비유].** 현장 통제(서버의 크레딧 차감·금액 대조)는 만들었고, 중복 방지(세 겹 장치)도 만들었다. 이상 사용을 감시하는 두 번째 선(탐지·알림·요청 제한)은 아직 없다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 유료화는 "얼마나 쓰느냐"를 가격으로 연결한다. 그러나 "누가 몇 번 만들 수 있느냐"(계정 반복 생성)와 "한꺼번에 몰리는 속도"는 다른 문제라서 따로 막아야 한다.
- 처음에 적은 답과 마지막에 만든 것을 대조하면 무엇이 남았는지 보인다.
- "막았다"고 쓸 때는 어디까지인지(무엇을 아직 못 막는지)를 같이 쓴다.

**개발자에게 시킬 때 물어볼 것**
- 같은 사람이 계정을 계속 새로 만들어 무료 크레딧을 받는 것은 어떻게 막나요?
- 한 사용자가 짧은 시간에 요청을 몰아 보내면 다른 사용자에게 영향이 가나요? 요청 속도 제한이 있나요?

### 동료에게 이렇게 설명한다

"하루 300개 쓰는 사람 문제는 '쓴 만큼 내게 하는 구조'로 막았어요. 그런데 계정을 계속 새로 만들어 무료분을 받는 것, 프로그램으로 한꺼번에 몰아 보내는 것은 아직 못 막았어요. 문은 달았는데 문지기는 아직 없는 상태예요."

## 9. 이번에 하지 않은 것과 한계

### 취지

이 절은 실패 목록이 아니라 "이 문서가 말하는 것의 경계"다. 이번 실습의 숫자와 결론은 아래 한계 안에서만 맞다.

### 하지 않은 것

| 항목 | 상태 |
|---|---|
| 실제 토스로 같은 멱등키 두 번 보내 첫 응답 받기 | 하지 않았다. 가짜 승인 API 테스트까지가 근거다 |
| 큰 모델로 바꾸기, 평가 시험지로 모델 비교 | 하지 않았다. 지금 모델(gpt-4o-mini)로 진행했다 |
| 2절의 4번(이번 달 공휴일 지어냄)·7번(저장했는데 알림 기능이 없다고 답함), 6절의 알림 안 만든 건 | 고치지 않고 적어만 뒀다. 이번 실습 범위 밖이다 |
| 사진 읽기 기능의 크레딧 차감 | 보류했다. 호출 원가를 재기 전이다 |
| 요청 속도 제한·이상 사용 탐지·환불 정책 | 하지 않았다(8절) |

### 확인하지 못한 것

- **[미확인]** 오늘 고시 환율. 1,400원/달러는 학습자와 정한 임시 가정이다.
- **[미확인]** Cloud Run 앞단 요청 로그의 결제 키 보존 기간·열람 권한(6절).
- **[미확인]** 실제 토스에서 같은 멱등키를 두 번 보냈을 때의 응답(7절).

### 한계(그대로 적는다)

- **가정으로 만든 손익표.** 3절의 사용자 1,000명·전환율 5%·고정비 7만 5,000원은 교안 계산기 기본값을 빌린 가정이다. 방향(무료 한도가 가격보다 큰 손잡이)은 확인했지만 매출 예측이 아니다.
- **실제 결제는 1건.** 실제 승인은 사용자가 본인 카드 앱으로 카드사 인증을 한 1건뿐이다. 이 1건으로 세 곳 기록이 맞는 것을 확인했지만 다양한 경우(실패·부분 취소 등)를 대표하지는 않는다.
- **표본이 작다.** 원가는 최근 7일 91건과 16턴 한 대화, 모델 비교는 10개 메시지다. 모델 비교는 감을 잡는 수준이다.
- **원 단위는 1,400원/달러 가정**이다.
- **교안 상품표.** 상품 가격 3개는 교안의 예를 그대로 썼다. 원가가 절반이라 더 낮은 가격도 가능하지만 이번에 정하지 않았다.
- **도우미의 실수와 학습자의 교정.** 화면 확인용 서버 설정을 엉뚱한 폴더에 넣어 다른 설정이 떠 버렸고(바로 멈추고 맞는 파일에 다시 넣었다), 승인 확인이 "어렵다"고 좁게 말한 것은 학습자의 질문으로 바로잡았다. 접속 로그의 결제 키는 교안의 확인 항목으로 잡혔다 [확인].

> 📌 **요약** — 이번 실습의 한 줄 교훈은 **"원가를 내 기록에서 재고, 쓴 만큼 받는 구조를 서버에 만들고, 같은 결제가 두 번 와도 한 번으로 끝나게 겹겹이 막되, 아직 못 막는 것(계정 반복 생성·요청 몰림)은 그대로 적는다"**이다. 메시지 한 건은 평균 약 0.61원(실제 91건, 1,400원/달러 가정)이고 가장 비싼 단계는 교안과 달리 도구 고르기였으며, 큰 모델은 ×16.6, 손익은 무료 한도가 가격보다 더 크게 움직였다. 실제 테스트 결제 승인 1건이 토스·주문 표·원장 세 곳에 맞게 남았고, 결제창 닫기와 접속 로그의 결제 키 두 가지를 찾아 고쳤으며, 테스트는 195개에서 220개가 되었다.

| 결제위젯 | 결제 대행사가 제공하는 결제 수단 선택 화면 |
| successUrl / failUrl | 결제 인증이 끝났을 때 / 실패했을 때 대행사가 사용자를 보내는 우리 주소 |

| 일부러 깨 보기 | 한 장치를 일부러 끄고 테스트가 실제로 실패하는지 보는 확인 |
