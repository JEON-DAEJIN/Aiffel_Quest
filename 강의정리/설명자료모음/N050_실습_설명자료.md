| 용어 | 무엇을 하는가 | 비유 |
|---|---|---|
| **Dockerfile (설계도)** | 서비스가 돌아갈 실행 환경을 처음부터 끝까지 한 파일에 적어 둔 것 | [보충 비유] 프랜차이즈 본사가 내려보내는 "주방 설비 목록 + 표준 조리 순서" — 어느 지점이든 같은 주방이 꾸려진다 |
| **이미지 (준비물 묶음)** | 설계도대로 만든, 실행에 필요한 것을 모두 담은 묶음. 한 번 만들면 내용이 바뀌지 않는다 | [해설서 비유] 붕어빵 틀과 재료를 갖춰 놓은 준비물 |
| **컨테이너 (실행 중인 것)** | 이미지를 실제로 돌린 것. 컨테이너가 사라져도 이미지는 그대로 남는다 | [해설서 비유] 그 준비물로 실제로 구워 낸 붕어빵 — 먹어 치워도 틀은 남는다 |
| **시스템 패키지 (운영체제 프로그램)** | 파이썬 라이브러리가 아니라 컴퓨터 운영체제에 따로 설치하는 프로그램 | [해설서 비유] 레시피(코드)가 같아도 주방에 도구가 없으면 요리가 안 된다 |
| **OCR (사진 속 글자 읽기)** | 사진·PDF 속 글자를 텍스트로 바꾸는 기능. 파이썬 쪽은 "통역을 부탁하는 사람", 실제로 읽는 `tesseract`는 "통역사" | [해설서 비유] 통역을 부탁하는 사람만 있고 통역사가 없으면 번역이 안 된다 |
| **이미지 ID (제조번호)** | 이미지 하나하나에 붙는 고유 번호. 같은 설계도로 따로 만들면 다를 수 있다 | [보충 비유] 같은 도면으로 따로 찍어 낸 제품에 붙는 제조번호 |
| **결과 해시** | 읽어 낸 글 전체를 짧은 문자열로 줄인 값. 글이 한 글자라도 다르면 값이 달라져서, 눈으로 읽지 않고 "결과가 같은가"만 비교하는 데 쓴다. 이미지 ID와는 별개의 값이다 | 성분 분석표 — 맛이 비슷해 보이는지가 아니라 성분이 같은지를 본다 |

## 1. 같은 코드인데 서버에서만 안 됐다 — staging의 500 오류와 로그 한 줄 {#1}

### 취지

지난 시간(N049)까지 AI 친구 에이전트 서비스(friend-agent, 줄여서 에이전트 서비스)에는 자동 검사·시험 서버(staging)·승인 절차가 붙었습니다. 이번 시간은 그 위에 새 기능 하나를 켜면서 시작합니다. 동아리 공지나 일정표 **사진을 보내면 글자를 읽어 입력창에 넣어 주는 기능(OCR)**입니다. 기능의 코드는 이미 서비스에 들어가 있고 환경변수 `OCR_ENABLED`로 켜고 끕니다. 첫 질문은 이것입니다. "내 컴퓨터에서는 되는데 서버에서는 안 돼요"라는 말이 나올 때, 코드가 한 글자도 다르지 않다면 무엇이 다른 걸까요?

### 검증 목표

- 로컬에서 되는 기능이 staging에서 실패하는 장면을 **직접 재현**하고, **서버 로그**의 같은 시각 오류 줄로 원인을 정한다.
- 문제를 **코드 / 환경 / 배포** 중 어디에 속하는지 판정한다.

### 실제로 있었던 일

먼저 제 PC를 "정상 환경"으로 만들었습니다. 시작할 때 PC의 글자 읽기 프로그램(tesseract)은 영어(eng)와 방향 감지(osd) 데이터만 있고 한국어(kor)가 없었습니다. 11시 28분에 한국어 데이터(1.6MB)를 받았고, 관리자 권한으로 설치 폴더에 복사하고 프로그램 경로를 등록하는 일은 제가 직접 했습니다. 그 뒤 `tesseract --list-langs`로 `eng`, `kor`, `osd`를 확인했습니다. 이 상태에서 산책 동아리 10월 일정 사진(`schedule.png`)을 보내자 HTTP 200과 함께 **153글자**가 읽혔습니다.

11시 34분에 staging에 `OCR_ENABLED=true`를 추가했습니다. 기존 값은 그대로 두고 하나만 더하는 옵션(`--update-env-vars`)을 썼고, production은 건드리지 않았습니다. 새 리비전(`friend-agent-staging-00006-dst`)이 뜬 뒤 같은 사진을 보내자 **HTTP 500**이 돌아왔고, 화면에는 "사진에서 글자를 읽는 프로그램이 서버에 없습니다."라는 안내가 보였습니다.

핵심은 그다음입니다. 안내문은 결과만 말해 줍니다. 같은 시각(11시 35분 05초)의 Cloud Run 로그에는 오류 한 줄이 있었습니다.

```
ERROR  tesseract 프로그램을 찾을 수 없습니다. 실행 환경에 tesseract 가 설치되어 있지 않습니다.
POST /api/ocr  500
```

두 줄을 합치면 상황이 정리됩니다. 서비스는 **정상적으로 시작**했고, 사진 요청이 들어온 순간에야 프로그램을 부르다 실패했습니다. 그래서 배포는 성공으로 끝났고 대화 같은 다른 기능은 멀쩡했습니다. 코드는 같았고(코드 문제 아님), 서버라는 주방에 tesseract라는 도구가 없었던 것입니다(환경 문제). 이 문제는 같은 날 Dockerfile 한 파일로 풀렸고(3절), 풀린 뒤에는 같은 사진이 staging에서 200으로 읽혔습니다. 사용자가 직접 📷 버튼으로 사진을 골라 입력창에 일정 세 줄이 들어오는 것도 확인했습니다.

> 🧪 **예제** — [해설서 비유] 요리하는 상황으로 생각해 보세요. 내 컴퓨터는 도구가 다 갖춰진 주방이고, 서버는 같은 요리사가 있지만 필요한 도구 하나가 없는 주방이며, 코드는 두 곳에서 똑같이 따르는 레시피입니다. 레시피가 같아도 도구가 없으면 요리를 완성할 수 없습니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- "내 컴퓨터에서 됐다"는 서버에서 된다는 증거가 아닙니다. 코드가 같아도 **코드가 돌아가는 방(실행 환경)**은 다를 수 있습니다.
- 문제가 생기면 먼저 **코드 / 환경 / 배포** 셋 중 어디인지 가르세요. 이번 건은 환경이었습니다.
- 배포 성공은 "실행 환경이 맞다"는 증거가 아닙니다. 화면 안내가 아니라 **로그의 같은 시각 줄**에서 원인을 찾으세요.

**개발자용**
- 기능을 켜는 환경변수는 기존 값을 지우는 `--set-env-vars`가 아니라 추가하는 `--update-env-vars`로 넣고, 로그는 ERROR로 거른 뒤 요청 시각 근처의 오류 메시지와 상태 코드를 함께 대조한다.

### 동료에게 설명하기

"사진 속 글자를 읽어 주는 기능을 만들었는데, 제 컴퓨터에서는 잘 읽히고 시험 서버에서는 오류가 났어요. 코드는 똑같은데요. 로그를 열어 보니 '글자 읽는 프로그램이 서버에 없다'고 한 줄 적혀 있었어요. 레시피는 같은데 그 주방에 도구가 없었던 거예요. 그래서 제가 처음 한 일은 코드를 의심하는 대신 로그를 보고, 문제가 코드인지 환경인지 배포인지부터 가른 거였어요."

## 2. 이미지와 컨테이너 — 컨테이너를 지우면 대화가 사라진다 {#2}

### 취지

환경 문제를 풀려면 "실행 환경"이 정확히 무엇인지부터 알아야 합니다. Docker는 실행 환경을 **이미지**로 묶고 그 이미지를 **컨테이너**로 실행합니다. 둘을 혼동하면 "컨테이너 안에서 고친 것이 왜 다음에 사라지지?" 같은 의문이 생깁니다. 이 절은 둘을 손으로 만져 보며 구분합니다.

### 검증 목표

- 공식 Python 이미지에 **tesseract가 없고**, 같은 이미지의 컨테이너끼리 **파일을 나누지 않음**을 확인한다.
- 컨테이너를 지우면 **메모리 속 대화는 사라지지만 이미지는 그대로**임을 확인한다.

### 실제로 있었던 일

Docker Desktop을 이번에 처음 설치했습니다. 설치 뒤 공식 Python 이미지(`python:3.13-slim-bookworm`)를 받아 컨테이너 안에서 확인하자 Python 3.13은 있지만 **tesseract는 없었습니다.** Python이 들어 있다고 OCR에 필요한 프로그램이 모두 들어 있는 것은 아닙니다. 이 이미지는 디스크를 183MB 차지했습니다.

컨테이너 `note-a` 안에서 `/tmp/note.txt`에 "메모"를 쓴 뒤, **같은 이미지로 새 컨테이너**를 띄워 그 파일을 읽자 "파일 없음"이었습니다. Docker Desktop 화면에는 이미지가 한 줄, 종료된 컨테이너가 따로 한 줄 보였습니다.

과제 1에서는 에이전트 서비스로 같은 개념을 확인했습니다. 컨테이너에 두 번 말을 걸자 저장된 메시지가 **4개**(내 발언 2 + 가짜 응답 2)였습니다. 이 컨테이너를 지우고 같은 이미지로 새로 띄우자 메시지는 **0개**였습니다. 컨테이너 ID는 `e6f131713f90`에서 `8ed3418b358a`로 바뀌었고 이미지 ID(`90cbc2725f5f`)는 그대로였습니다. 이 확인은 브라우저 대신 API로 했습니다.

이 실험이 보여 주는 것은 하나입니다. **컨테이너의 메모리는 영속 저장소가 아니라서, 컨테이너를 지우면 그 안의 대화도 사라진다**는 점입니다. Cloud Run의 새 리비전도 새 컨테이너를 띄우므로 같은 이유로 대화가 사라질 것으로 보이지만, 이는 **추정이고 Cloud Run에서는 시험하지 않았습니다.**

> 🧪 **예제** — [해설서 비유] 붕어빵(컨테이너)을 먹어 치워도 틀과 재료(이미지)는 그대로 남고, 같은 준비물로 몇 개든 새로 구울 수 있습니다.

> 🧪 **예제** — [보충 비유] 이미지는 인수인계 매뉴얼, 컨테이너는 그날 투입된 임시 직원입니다. 임시 직원이 머릿속에 적어 둔 메모는 퇴근(컨테이너 삭제)과 함께 사라지고, 다음 날 새 직원은 같은 매뉴얼에서 처음부터 시작합니다. 남겨야 할 기록은 직원 머릿속이 아니라 본사 장부(외부 저장소)에 있어야 합니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 이미지는 **설계된 환경**, 컨테이너는 **그걸 실행한 것**입니다. 환경을 고치려면 설계도(이미지)를 고치고, 실행 중인 컨테이너 안을 고치지 않습니다.
- 오래 남아야 하는 데이터를 컨테이너 메모리에만 두면 컨테이너와 함께 사라집니다. 이것은 버그가 아니라 구조입니다.
- 키 같은 비밀은 이미지에 넣지 않고 실행할 때 건넵니다. 이미지는 여러 곳에 퍼질 수 있는 파일이기 때문입니다.

**개발자용**
- `docker rm`은 컨테이너만 지우고 이미지는 남긴다. 지우기 전에 대상이 무엇인지 확인한다.
- 터미널(Git Bash)이 `/app` 같은 인자를 윈도 경로로 바꾸거나 한글 JSON을 `curl`로 보내 400이 나는 일이 있었다. Docker가 아니라 셸·인코딩 문제였고 `MSYS_NO_PATHCONV=1`과 UTF-8 전송으로 해결했다.

### 동료에게 설명하기

"Docker 이미지는 '이 서비스가 돌아가려면 이런 환경이 필요해'라고 묶어 둔 준비물이고, 컨테이너는 그걸로 실제로 돌리는 거예요. 제가 컨테이너에서 대화를 두 번 하고, 그 컨테이너를 지운 뒤 같은 이미지로 다시 띄웠더니 대화 4개가 0개가 됐어요. 이미지 번호는 그대로인데요. 그러니까 컨테이너 메모리는 오래 남길 곳이 아니에요. 서버에서도 같은 일이 생길 걸로 보이지만 거기서는 아직 시험해 보지 않았어요."

```arrow
Dockerfile(설계도) → 이미지(재료와 틀을 묶은 준비물) → 컨테이너(실제로 실행 중인 것) → Cloud Run 서비스(staging·production)
```

## 3. Dockerfile을 읽고 검토하는 법 — 다섯 기준과 `__pycache__` 17개 {#3}

### 취지

이제 서버라는 주방에 도구를 갖추는 방법을 적을 차례입니다. 그 문서가 Dockerfile입니다. 템플릿의 예시 파일을 복사해 쓸 수 있지만, 복사한 파일이 우리 서비스에 맞는지 **검토하는 눈**이 이 절의 주제입니다. 코딩 에이전트에게 맡겨도 어떤 버전을 고정할지, 누구 권한으로 돌릴지 같은 판단은 사람의 몫입니다.

### 검증 목표

- Dockerfile을 **다섯 기준**으로 검토해 통과 여부를 판정한다.
- 로컬에서 빌드한 이미지 **안의** tesseract가 사진을 읽는지, **들어가면 안 되는 것이 없는지** 이미지를 열어 확인한다.
- 이미지를 기존 자동 배포로 staging에 올려, 빌드 기록에서 Dockerfile이 쓰였는지 확인한다.

### 실제로 있었던 일

검토 다섯 기준은 다음과 같았고, 이번 파일은 모두 통과했습니다.

| 확인할 것 | 이번 결과 |
|---|---|
| 베이스 이미지·Python 버전이 고정돼 있는가 | `python:3.13-slim-bookworm`. 기존 `Procfile`·`.python-version`(3.13)과 같은 버전 |
| tesseract와 한국어 데이터를 설치하는 줄이 있는가 | `tesseract-ocr`, `tesseract-ocr-kor` 설치 |
| `.dockerignore`에 `.env`가 들어 있는가 | 들어 있음 |
| 실행 명령이 `PORT` 환경변수를 쓰는가 | `${PORT:-8080}` |
| 일반 사용자로 실행하는가 | `USER appuser` |

첫 빌드는 성공했고 이미지는 **460MB**였습니다. 줄별로는 tesseract 설치가 **94.9MB**, 라이브러리 설치가 **120MB**, 우리 코드 복사가 **442kB**였습니다(라이브러리 쪽이 교재 그림보다 큰 것은 패키지 버전 차이로 추정합니다). 이 이미지로 컨테이너를 띄워 같은 사진을 보내자 200, 153글자가 읽혔습니다. 이번에는 **이미지 안의** tesseract가 읽은 것입니다.

가장 값진 발견은 이미지를 열어 본 순간에 나왔습니다. `/app` 안에 `.env`·`tests`·`docs`는 없어 정상이었지만, `app` 폴더 안에 **`__pycache__` 폴더와 `.pyc` 파일 17개**가 들어 있었습니다(모두 `cpython-314`, 제 PC의 가상환경이 만든 것). 템플릿 `.dockerignore`의 `__pycache__/`와 `*.pyc` 규칙은 **맨 위 폴더에만** 적용되고 하위 폴더는 거르지 못했던 것입니다. 빌드가 성공해도 서비스가 잘 돌아도 눈에 띄지 않는 함정이고, 이미지를 직접 연 사람만 찾습니다.

두 줄을 `**/__pycache__/`와 `**/*.pyc`로 고쳐 다시 빌드하자 이미지 안 `__pycache__`와 `.pyc`는 **0개**가 됐습니다. 재빌드는 약 0.5초였습니다. 시간이 걸리는 설치 단계는 `CACHED`로 건너뛰고 코드 복사와 사용자 만들기만 새로 실행했기 때문입니다.

이어 PR #20으로 Dockerfile과 `.dockerignore`, 배포 설정(`deploy.yml`)을 staging에 올렸습니다. 배포 설정에서 바꾼 것은 `flags:` 줄 끝에 `--clear-base-image` 한 단어를 더한 것뿐입니다(+1/−1줄). 이 옵션이 없으면 배포가 오류로 멈춘다고 교재가 안내했지만, 저는 처음부터 넣었기 때문에 **그 오류를 직접 본 적은 없습니다.** 사용자가 머지를 승인한 뒤 Cloud Build `615ce1d8`이 약 1분 14초 만에 성공했고, 빌드 로그에는 `Step 1/11 FROM python:3.13-slim-bookworm`과 tesseract 설치가 보였으며 **buildpacks라는 단어는 한 번도 나오지 않았습니다.** 새 리비전(`friend-agent-staging-00007-94j`)이 100%를 받았고 1절에서 실패했던 바로 그 요청이 **200**으로 돌아왔습니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 실행 환경은 "누군가 기억하는 것"이 아니라 **저장소의 파일**로 남겨야 합니다. 내 컴퓨터에 프로그램을 설치한 기록은 저장소에 자동으로 들어가지 않습니다.
- 만든 이미지는 **열어서 확인**하세요. 빌드 성공은 "들어가면 안 되는 것이 안 들어갔다"는 증거가 아닙니다.
- 판단은 사람이 합니다. 어떤 버전을 고정할지, 누구 권한으로 돌릴지, 무엇을 뺄지는 에이전트가 대신 정해 주지 않습니다.

**개발자용**
- `.dockerignore`는 `.gitignore`와 달리 하위 폴더에 저절로 적용되지 않으므로 `**/__pycache__/`처럼 `**/`를 붙인다.
- 의존성 파일(`requirements.txt`)을 먼저 복사해 설치한 뒤 코드를 복사하면, 코드만 바뀔 때 `apt`·`pip` 단계가 `CACHED`로 재사용된다.
- Dockerfile 배포에는 `--clear-base-image`가 필요하다(교재 안내). 대신 베이스 이미지 보안 패치는 `FROM` 줄을 바꿔 다시 빌드해야 들어온다.

### 동료에게 설명하기

"서버에 도구가 없어서 안 됐으니까, 서버가 쓸 환경을 적은 설명서(Dockerfile)를 저장소에 넣었어요. 근데 제일 재밌었던 건 설명서가 아니라 확인이었어요. 만든 이미지를 직접 열어 보니 제 컴퓨터에서 생긴 임시 파일 17개가 같이 들어가 있었어요. '무시할 파일' 규칙이 맨 위 폴더에만 적용되고 있었거든요. 빌드는 성공했고 서비스도 잘 돌았을 거예요. 열어 보지 않았다면 모르고 지나갔을 거고요. 규칙을 한 줄 고치니 0개가 됐어요."

## 4. 같은 입력을 네 곳에 보내 같은 결과를 확인하기 {#4}

### 취지

"고쳤다"는 말을 어떻게 증명할까요? 이번 실습은 **같은 입력**을 여러 곳에 보내 **같은 결과가 나오는지** 대조하는 방식으로 증명했습니다. 곳이 많을수록 "내 컴퓨터에서만 되는" 상태가 아님이 분명해집니다.

### 검증 목표

- 같은 샘플을 로컬, 로컬 컨테이너, staging, production **네 곳**에 보내 결과를 비교한다.
- 눈으로 읽지 않고 **글자 수와 결과 해시**로 비교하며, production 승인·OCR 켜기 절차를 직접 거친다.

### 실제로 있었던 일

앞 10자만 쓴 결과 해시로 비교했고, 사진 `schedule.png`를 읽은 결과 해시는 `e61b2db05f`였습니다. production에는 PR #21(staging에서 검증한 변경을 main으로 올리는 요청)로 Dockerfile이 올라갔습니다. 머지 뒤 배포가 **승인 대기**에서 멈췄고, 에이전트가 아니라 제가 직접 승인했습니다(승인 화면은 캡처해 둠). 승인 뒤 Cloud Build `4718e203`이 성공했고 새 리비전(`friend-agent-00018-klq`)이 100%를 받았습니다.

이때 production에는 OCR이 꺼져 있어서 사진을 보내자 **404**("사진 글자 읽기가 꺼져 있습니다")가 돌아왔습니다. 오류가 아니라 의도된 상태입니다. `OCR_ENABLED=true`를 추가해 새 리비전(`00019-nlc`)을 만들자 사진이 읽혔습니다. 이후 PDF 읽기를 반영한 리비전(`00020-clm`)에서는 켜는 값이 그대로 유지돼 다시 켤 필요가 없었습니다. 아래 표의 production 열은 PDF 반영 뒤 리비전 00020에서 잰 값입니다.

| 입력 | 로컬(Windows) | 로컬 컨테이너 | staging | production |
|---|---|---|---|---|
| 사진(PNG) | 200, 153글자, e61b2db05f | 200, 153글자, e61b2db05f | 200, 153글자, e61b2db05f | 200, 153글자, e61b2db05f |
| PDF 1쪽 | 200, 153글자, e61b2db05f | 200, 153글자, e61b2db05f | 200, 153글자, e61b2db05f | 200, 153글자, e61b2db05f |
| PDF 4쪽(앞 3쪽만) | 200, 461글자, 4ba6dbbc32 | 200, 461글자, 4ba6dbbc32 | 200, 461글자, 4ba6dbbc32 | 200, 461글자, 4ba6dbbc32 |
| 깨진 PDF | 500 "PDF 파일을 읽을 수 없습니다." | 500 같음 | 500 같음 | 500 같음 |

PDF 1쪽의 결과 해시는 사진과 같습니다(같은 그림을 PDF로 바꾼 것이니 맞아야 합니다). 4쪽 PDF의 461글자는 앞 3쪽만 읽은 결과로 153×3에 줄바꿈 2개를 더한 값과 맞고, 깨진 PDF는 네 곳 모두 같은 안내와 500으로 실패했습니다(의도한 결과). 로컬 poppler(PDF를 이미지로 바꾸는 프로그램)는 25.07.0, 컨테이너는 22.12.0으로 버전이 달랐는데도 결과는 같았습니다.

> 🧪 **예제** — [보충 비유] 본사 품질팀이 같은 샘플 주문서를 네 개 지점 주방에 동시에 넣어 같은 맛이 나오는지 보는 교차 검수입니다. "맛있어 보인다"가 아니라 성분 분석표(결과 해시)를 대조하니 누가 봐도 같은지 다른지 가려집니다. 한 곳의 결과 해시만 달랐다면 그곳의 실행 환경이 다르다는 단서가 됩니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- "고쳐졌다"는 느낌이 아니라 **같은 입력으로 곳곳에서 같은 결과**가 나오는지로 확인하세요.
- 정상 입력뿐 아니라 **일부러 틀린 입력**(깨진 파일)도 보내서, 틀렸을 때의 반응이 곳곳에서 같은지 보세요.
- production은 **사람이 승인한 뒤** 바꿉니다. 승인과 기능 켜기는 별개의 단계입니다.

**개발자용**
- 결과 비교는 상태 코드, 글자 수, 결과 해시(앞 10자)를 같은 형식으로 기록해 두면 비교가 쉽다.
- 기존 환경변수는 새 리비전에도 유지되므로(`OCR_ENABLED`), 배포 뒤 환경변수 이름 목록으로 값이 빠지지 않았는지 확인한다.

### 동료에게 설명하기

"고쳤다는 걸 어떻게 믿을 수 있냐면, 같은 사진과 같은 PDF를 네 군데에 보내서 결과를 비교했어요. 제 컴퓨터, 제 컴퓨터 안의 컨테이너, 시험 서버, 실제 서버. 네 곳이 전부 글자 수도 결과 해시도 같았고, 일부러 보낸 깨진 PDF도 네 곳 모두 같은 안내로 실패했어요. 눈으로 읽어 보는 게 아니라 숫자로 비교한 거라서 '비슷해 보인다'는 말이 안 나와요."

## 5. 새 기능(PDF)을 붙일 때는 시스템 프로그램이 먼저 {#5}

### 취지

1~4절은 고장 난 뒤에 고치는 이야기였습니다. 이 절은 반대로 **새 기능을 붙이면서 같은 사고를 미리 피하는** 이야기입니다. 도전 과제는 사진뿐 아니라 **PDF 공지문**도 읽게 하는 것이었습니다. 새 기능마다 던질 질문은 하나입니다. "이 기능은 파이썬 라이브러리 말고 **운영체제에 설치할 프로그램**이 따로 필요한가?"

### 검증 목표

- 새 기능에 **필요한 시스템 프로그램**을 찾아내고, 로컬에서 되던 기능이 **컨테이너에서는 실패할 수 있음**을 확인한다.
- Dockerfile에 한 줄만 더해 네 곳에서 같은 결과가 나오는지 본다.

### 실제로 있었던 일

후보는 PDF 읽기, QR 코드 읽기, HEIC 사진, 동영상 음성 변환(ffmpeg)이었습니다. PDF를 골랐고 QR은 2순위, HEIC와 ffmpeg는 난이도 때문에 권하지 않았습니다(구현은 하지 않았습니다). PDF를 읽으려면 먼저 PDF의 각 쪽을 그림으로 바꿔야 하고, 그 일을 하는 `pdftoppm`이 poppler라는 **운영체제 프로그램**에 들어 있습니다. 파이썬 쪽에는 이를 부르는 `pdf2image` 라이브러리만 추가했습니다.

로컬 PC에는 `winget`으로 poppler를 설치했습니다(비공식 빌드, 압축 파일 약 16.0MB). 코드는 앞 3쪽만, 200dpi로, 시간 제한 30초 안에서 읽도록 했고, poppler가 없으면 "PDF를 읽는 프로그램이 서버에 없습니다."라는 안내와 오류 로그를 남기게 했습니다. 변경은 5파일이었는데 **Dockerfile은 처음에 건드리지 않은 채** 먼저 로컬에서 시험했습니다. 로컬에서는 사진·PDF 1쪽·4쪽·깨진 PDF가 모두 기대대로였고, 자동 테스트는 기존 12개에 새 3개를 더한 **15개가 통과**했습니다. 3쪽 제한 값을 일부러 99로 깨뜨리자 `assert 99 == 3`으로 실패했고, 되돌리자 다시 통과했습니다.

문제는 그다음입니다. **poppler 줄이 없는 Dockerfile**로 만든 컨테이너에 같은 PDF를 보내자, 사진은 200으로 읽혔는데 **PDF만 500**이었습니다. 화면에는 "PDF를 읽는 프로그램이 서버에 없습니다.", 로그에는 "poppler 프로그램을 찾을 수 없습니다."가 남았습니다. 컨테이너 안에는 tesseract는 있고 `pdftoppm`은 없었습니다. **로컬에서는 되던 PDF가 컨테이너에서 처음 실패한 것**이고, 1절의 사건이 다른 얼굴로 되풀이된 장면입니다.

해결은 Dockerfile의 설치 줄 끝에 `poppler-utils` 한 단어를 더하는 것이었습니다. 이미지는 460MB에서 **473MB(+13MB)**가 됐고, 사진·PDF 1쪽·4쪽·깨진 PDF 결과가 로컬과 모두 같아졌습니다. PR #22로 staging에 올리자 Cloud Build `aa4d5d58`이 성공했고(로그에 `Setting up poppler-utils` 확인) staging에서도 같은 결과가 나왔으며, PR #23으로 production에도 반영했습니다. 이 한 줄이 필요한 이유는 한 문장입니다. **PDF를 이미지로 바꾸는 `pdftoppm`이 운영체제 프로그램이라 `pip`로는 설치되지 않기 때문입니다.** 이번에는 staging에 올리기 **전에** 로컬 컨테이너에서 문제를 먼저 잡았습니다.

> ⚠️ **주의** — 새 PDF 테스트 3개는 PDF를 그림으로 바꾸는 함수를 **가짜로 바꿔 놓고** 검사합니다. 그래서 15개가 통과해도 "서버에 poppler가 실제로 있는가"는 검증하지 못합니다. N049의 자동 검사가 가진 한계와 같은 구멍이고, 이 확인은 컨테이너와 staging의 몫이었습니다.

> 🧪 **예제** — [보충 비유] 신메뉴를 지점에 풀기 전에 "필요한 설비 목록"을 먼저 뽑는 출시 체크리스트입니다. 본사 시연장에서 성공했어도 지점과 같은 설비를 갖춘 시험 지점(로컬 컨테이너)에서 먼저 돌려 보면, 실제 지점에 나가기 전에 빠진 설비를 찾을 수 있습니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- 새 기능을 계획할 때 **"파이썬 라이브러리 말고 운영체제에 설치할 프로그램이 있나?"**를 먼저 물으세요.
- 로컬에서 되는 것으로 끝내지 말고 **서버와 같은 환경(컨테이너)**에서 한 번 더 돌려 보세요. 실패가 서버가 되기 전에 컨테이너에서 잡힙니다.
- 자동 테스트의 통과가 "서버에 필요한 프로그램이 있다"를 뜻하지는 않습니다. 테스트가 무엇을 가짜로 바꿨는지 알아 두세요.

**개발자용**
- 시스템 프로그램은 `requirements.txt`가 아니라 Dockerfile의 `apt-get install` 줄에 적는다. 이번에는 `poppler-utils` 하나였다.
- 시스템 프로그램을 부르는 코드는 **없을 때의 안내와 로그**를 미리 만든다. 이번에는 원인 찾기가 로그 한 줄로 끝났다.
- 테스트를 믿기 전에 일부러 깨뜨려(`3 → 99`) 실패하는지 확인한 뒤 되돌린다. 샘플 PDF는 저장소에 커밋하지 않고 임시 폴더에서 만들어 썼다.

### 동료에게 설명하기

"PDF를 읽는 기능을 새로 붙였는데, 이번에는 서버에 올리기 전에 컨테이너에서 먼저 터졌어요. 제 컴퓨터에서는 PDF가 잘 읽혔는데, 서버와 같은 환경의 컨테이너에서는 'PDF 읽는 프로그램이 없다'고 나왔거든요. PDF를 그림으로 바꾸는 프로그램이 운영체제에 따로 깔려야 하는 거라서요. 설명서에 한 줄만 더했더니 해결됐어요. 그래서 이제는 새 기능을 붙일 때 '운영체제에 따로 깔 게 있나?'를 제일 먼저 물어요."

## 6. 같은 Dockerfile이어도 같은 이미지는 아니다 {#6}

### 취지

Dockerfile을 도입하면 "staging에서 검증한 것이 그대로 production에 나간다"고 믿고 싶어집니다. 하지만 staging과 production은 **각각 따로 빌드**합니다. 같은 설계도로 두 번 만들면 같은 제품일까요? 이 절은 그 믿음을 시험하고 풀리지 않은 숙제를 솔직히 적습니다.

### 검증 목표

- 같은 Dockerfile로 **캐시 없이 두 번** 빌드한 것(과제 2)과 실제 staging·production 빌드의 **패키지·이미지 ID**를 비교해, "검증한 이미지 = 배포한 이미지"라고 말할 수 있는지 판정한다.

### 실제로 있었던 일

과제 2에서 `docker build --no-cache`로 `try-a`, `try-b`를 연달아 만들었습니다. 각각 약 31초, 30초가 걸렸습니다(교재는 "몇 분"이라 했지만 이 PC에서는 30초대였습니다). 결과는 이렇습니다. 이미지 ID는 `8d665740853b`와 `3a23685075fb`로 **달랐고**, 크기는 둘 다 460MB였습니다. 파이썬 패키지(30줄)와 apt 패키지(159개)는 **같았습니다.** 레이어 10개 중 베이스 4개와 `COPY . .` 1개는 같고 나머지 5개는 달랐습니다. 레이어와 Dockerfile 줄의 대응은 `docker history` 줄 수가 레이어 수와 같다는 점에서 **추정**한 것이며, 무엇이 정확히 달라졌는지 원인 파일은 확인하지 않았습니다.

실제 배포 기록에서도 같은 모양이 나왔습니다. staging 빌드 `615ce1d8`(이미지 ID `a31820f7a6bf`)과 production 빌드 `4718e203`(`a3c0f9af949f`)은 베이스 이미지 digest, 파이썬 패키지 30개, apt 패키지 62개가 **모두 같았지만 이미지 ID는 달랐습니다.** 빌드마다 붙는 `build_id` 라벨이 달랐고, 두 빌드의 간격은 약 1시간 33분이었습니다. PDF 반영 빌드(staging `aa4d5d58`의 `7cd90c50e99a`, production `057dbfd2`의 `cb253b448e50`)도 패키지는 같고(파이썬 31개·apt 67개) 이미지 ID가 달랐으며 간격은 약 18분이었습니다. 이미지 ID가 달라지는 이유로는 이 라벨과 빌드 시각이 거론되지만, 어느 것이 얼마나 영향을 줬는지는 확인하지 않았습니다.

그러니 이렇게 말해야 정확합니다. **staging에서 검증한 이미지와 production에 나간 이미지는 서로 다른 이미지입니다.** 패키지 내용이 같다는 것까지만 확인했고 "같은 이미지"라고는 말할 수 없습니다. 이번 비교는 모두 몇 시간 안이라 패키지 버전이 같았습니다. 며칠 간격으로 빌드하면 목록까지 달라질 수 있다고 하나 **직접 재현하지는 않았습니다.**

> 🧪 **예제** — [보충 비유] 시제품 검수(staging)를 통과한 뒤 납품(production) 때 공장에서 다시 양산하는 구조입니다. 같은 도면이라 거의 같겠지만, 검수한 바로 그 제품이 나가는 것은 아닙니다. 성분표(패키지)가 같다고 확인했을 뿐, 제조번호(이미지 ID)가 같다고 한 적은 없습니다. 검수한 제품을 그대로 납품하려면 출하 절차 자체를 바꿔야 합니다.

### 적용 원칙

**누구나 알아야 할 원칙**
- "같은 설계도"와 "같은 제품"은 다릅니다. 검증한 것과 내보낸 것이 같다고 말할 때는 **무엇이 같은지**(설계도인지 완성품인지)를 구분해 말하세요.
- 확인한 만큼만 말하세요. 이번에는 "패키지 목록은 같다"까지가 확인한 범위입니다.
- 이 숙제는 오늘 끝내지 않았습니다. 해결하려면 이미지를 **한 번만 만들어 두 환경에 보내는** 흐름이 필요합니다.

**개발자용**
- 이미지 비교는 이미지 ID, 베이스 digest, `pip freeze`, `dpkg -l`, 레이어 해시를 함께 본다. 이번에는 베이스를 `FROM python:3.13-slim-bookworm` 태그로 고정했고(digest 고정은 하지 않았다), 두 빌드에서 베이스 digest는 같았다. 만든 이미지의 태그·digest 관리와 승격, 배포마다 쌓이는 400MB대 이미지의 저장 공간 관리는 교안이 남긴 다음 숙제다.

### 동료에게 설명하기

"Dockerfile로 환경을 적어 뒀으니 시험 서버에서 검증한 게 운영에도 그대로 나간다고 생각하기 쉬운데요, 사실 시험 서버와 운영은 각각 새로 빌드해요. 제가 비교해 봤더니 설치된 프로그램 목록은 똑같은데 이미지 번호는 달랐어요. 같은 도면으로 두 번 찍은 거라서요. 그러니까 '같은 설계도'까지는 맞지만 '같은 제품'은 아니에요. 같은 제품이라고 말하려면 한 번 찍은 걸 양쪽에 보내야 하는데, 그건 아직 숙제로 남겨 뒀어요."

## 7. 이번 실습에서 하지 않은 것과 남은 숙제 {#7}

이 문서는 실제로 한 것만 썼습니다. 하지 않았거나 한계가 있는 것을 따로 모아 둡니다.

| 항목 | 상태 |
|---|---|
| `--clear-base-image` 누락 오류 | 처음부터 옵션을 넣어 그 오류를 직접 재현하지 않음 |
| 새 리비전 배포 때 대화가 사라지는지 | Cloud Run에서는 시험하지 않음(컨테이너를 지우는 실험만 함) |
| 며칠 간격 빌드로 패키지 버전이 달라지는 현상 | 재현하지 않음(이번 비교는 모두 몇 시간 이내) |
| 이미지 태그·digest 관리, 검증한 이미지를 그대로 승격하는 흐름, 저장 공간 관리 | 교안이 남긴 다음 실습 숙제, 하지 않음 |
| 과제 1의 브라우저 직접 대화 | API로 대체(화면 캡처 없음) |
| QR·HEIC·ffmpeg | 후보로 비교만, 구현하지 않음 |
| 수업 키 공유(staging·production이 같은 LLM 키를 씀), 한도 분리 | 이번에 다루지 않음(N049 상태 그대로) |
| 새 PDF 테스트가 poppler 설치를 검증하는지 | 검증하지 못함(함수를 가짜로 바꿈), 확인은 컨테이너·staging 몫 |
| 원격 브랜치 `add-dockerfile`·`add-pdf-ocr` | 삭제하지 않고 남김 |

> 📌 **요약** — 이번 실습의 한 줄 교훈은 **"실행 환경은 코드가 아니라 설계도(Dockerfile)에 적어 저장소에 넣고, 서버와 같은 환경에서 한 번 더 돌려 확인한다"**입니다. 새 기능을 붙일 때는 운영체제에 설치할 프로그램이 있는지 먼저 묻고, 같은 설계도라도 따로 만든 이미지는 같은 제품이 아니라는 점을 기억합니다.

## 8. 용어 사전 {#8}

| 용어 | 쉬운 설명 |
|---|---|
| Dockerfile · 이미지 · 컨테이너 · 시스템 패키지 · 이미지 ID · 결과 해시 | 위의 "미리 보는 용어" 표 참고 |
| 베이스 이미지 | Dockerfile이 출발점으로 삼는 이미지. 이번에는 `python:3.13-slim-bookworm` |
| OCR · tesseract | 사진·PDF 속 글자를 텍스트로 바꾸는 기술 · 그 일을 실제로 하는 프로그램(`kor`는 한국어 데이터) |
| poppler (`pdftoppm`) | PDF를 쪽별 이미지로 바꾸는 운영체제 프로그램 |
| buildpacks | 코드를 보고 이미지를 알아서 만들어 주는 방식. 시스템 패키지는 알 수 없다 |
| 레이어 (layer) | Dockerfile 줄 하나가 만든 변경을 묶은 단위. 바뀌지 않은 줄은 캐시로 재사용된다 |
| `.dockerignore` | 이미지에 넣지 않을 파일을 적는 목록. 하위 폴더까지 거르려면 `**/`를 붙인다 |
| digest | 이미지 내용을 가리키는 고정 식별값. 이름표(태그)보다 엄밀하다 |
| 리비전 | 이미지와 설정(환경변수 등)을 묶은 Cloud Run의 배포 버전 |
| staging / production | 사용자에게 내보내기 전에 써 보는 시험 서버 / 실제 사용자가 쓰는 운영 서버 |
