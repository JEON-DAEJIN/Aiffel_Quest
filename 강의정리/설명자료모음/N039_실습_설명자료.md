# N038·N039 실습 설명자료 — 고객응대 에이전트(라우팅·그라운딩)

> N038(고객응대 에이전트 강의)과 N039(나만의 고객응대 에이전트 프로젝트)를 논리적으로 상세히 풀어 정리한 문서. 강의의 취지, 실습이 검증하려는 것, 프로젝트에서 실제로 있었던 일, 향후 적용법, 동료에게 설명하는 법 순으로 구성했다.
>
> 💡 **읽는 법**: 코드를 몰라도 끝까지 읽을 수 있게 썼다. 어려운 용어는 그 자리에서 비유로 풀어준다. "개발자용"이라고 표시된 부분은 건너뛰어도 줄거리를 이해하는 데 지장 없다.

| **가드레일 (검증)** | 답변이 실제 근거와 맞는지 사후에 대조하는 것 | 영수증과 실제 구매 내역을 대조하는 것 |

## 1. 이 수업(N038·N039)의 취지 — 왜 "알아서 잘 답해"로는 안 되는가 {#1}

N038·N039는 "AI가 그럴듯하게 지어낸 말(환각)을 못 하게 막으면서도 정확히 답하게 하려면 어떻게 시스템을 설계해야 하는가"라는 문제의식에서 출발합니다. AI에게 "알아서 잘 답해"라고 통째로 맡기는 대신, **판단(분류)·조회(근거 확보)·검증(사실 대조)**을 각각 독립된 부품으로 쪼개 따로 테스트할 수 있게 만드는 것이 핵심 설계 철학입니다. N038은 강사가 만든 정답 예시를, N039는 학생이 자기 주제로 직접 설계·제출하는 프로젝트입니다.

## 2. 실습이 알아보고자 한 것 {#2}

원문의 표현을 빌리면:

> "판단(라우팅) → 조회(그라운딩) → 검증(가드레일) 세 단계를 거쳐야, 그럴듯하지만 틀린 답을 하는 대신 매뉴얼과 실제 데이터에 발을 딛고 서 있는 답을 할 수 있습니다."

라우팅은 이렇게 비유합니다: "공항에서 모든 승객을 한 줄로 세우는 것이 아니라, 국내선→국내선 창구, 국제선→국제선 창구처럼 목적에 따라 적절한 창구로 보내는 것." 그리고 "OTHER(범위 밖)"라는 분류는 **분류 실패를 담는 쓰레기통이 아니라, "네 유형 중 어느 것도 아님이 확인된 상태"라는 분명한 판정**입니다.

가장 중요한 원칙은 이것입니다: "정책은 데이터이고 코드가 아닙니다" — 즉 배송비 같은 규칙을 프로그램 안에 고정값으로 박아두지 않고, 실제 매뉴얼 문서에서 그때그때 조회해서 답하게 만듭니다. 그래야 규칙이 바뀌어도 코드를 안 고치고 문서만 바꾸면 됩니다.

## 3. 프로젝트에서 실제로 있었던 일 {#3}

1. **규칙 방식에서 AI 방식으로 바꿔 큰 개선을 봄**: 처음엔 키워드를 미리 정해두고 그걸로 분류하는 방식(규칙 기반)을 썼는데, 정확도가 낮았습니다(100점 만점에 약 68점). AI에게 직접 분류를 맡기는 방식으로 바꾸자 약 95점까지 올랐습니다. 그런데 실제 고객 질문 40건으로 테스트했더니, 정작 최종 답변까지 도달한 게 0건이었습니다 — 원인은 AI 성능이 아니라, 고객이 말한 상품명("그 파란색 셔츠")을 실제 상품 목록의 정확한 이름과 연결해주는 부품이 아예 없었기 때문이었습니다.
2. **문구 하나를 고쳤더니 다른 문제가 생김**: 나만의 프로젝트(실제 서비스 챗봇 대상)에서 도구 호출 정확도가 85%(20건 중 17건)에서 90%(18건)로 좋아졌습니다. 그런데 카테고리 설명 문구 하나를 더 명확하게 고쳤더니, 기존에 틀렸던 3건은 고쳐졌지만 **새로 2건이 틀리기 시작**했습니다 — "과잉보정"입니다. 문구 하나를 세게 강조하면 원래 안 걸릴 질문까지 그쪽으로 끌려가는 현상입니다.
3. **분류가 틀려도 안전하게 거절한 사례**: 어떤 질문은 분류(라우팅)가 틀렸는데도, "근거 자료에 정확한 설명이 없어 답변드릴 수 없습니다"라고 정직하게 답을 거부했습니다. 분류가 틀려도 그라운딩(근거 확인) 단계가 안전판 역할을 해서, AI가 아무 말이나 지어내지 않고 "모른다"고 답한 것입니다.

## 4. 앞으로 내 프로젝트에 어떻게 적용하면 되는가 {#4}

### 누구나 알아야 할 원칙

- **AI에게 "그렇게 하지 마라"는 말 한 줄만으로는 부족합니다.** 실제로 지켰는지 별도로 대조하고 검사하는 단계가 있어야 합니다.
- **성능이 좋아졌다는 판단은 "느낌"이 아니라 미리 정해둔 정답 목록으로 재야 합니다.** 그리고 한 번에 하나씩만 바꾸고 다시 재야, 무엇이 효과가 있었는지 알 수 있습니다.
- **"모르면 모른다고 답하는" 경로를 반드시 만들어 두세요.** 지시만으로는 AI가 지어내는 걸 막을 수 없습니다 — 구조적으로 "근거 없으면 거절"하는 장치가 있어야 합니다.

### 개발자용 체크리스트 (코드를 직접 짤 때만 해당)

- 라우팅(분류)·그라운딩(조회)·가드레일(검증)을 하나의 프롬프트에 뭉치지 말고 별도 단계로 분리해서 각각 테스트한다.
- 고객이 쓰는 자연어 표현과 실제 상품/데이터 ID를 연결하는 "엔티티 링킹" 부품을 빠뜨리지 않는다 — 분류가 완벽해도 이게 없으면 답변에 도달 못 한다.
- 프롬프트 문구를 강화할 때는 기존 통과 케이스도 함께 재검사한다(과잉보정 확인).

## 5. 동료에게 어떻게 설명하면 되는가 {#5}

**한 줄 엘리베이터 피치**:
> "AI 상담봇이 그럴듯한 거짓말을 하지 않도록, 질문을 먼저 분류하고 필요한 자료만 찾아보게 한 뒤 답변을 그 자료와 대조해 검증하는 시스템을 만들었어요. 정확도를 85%에서 90%로 실제로 끌어올린 것까지 숫자로 확인했습니다."

**좀 더 풀어서 설명할 때 순서**:
1. "AI 상담봇이 위험한 이유는, 모르는 것도 그럴듯하게 지어내서 답한다는 거예요." (문제의식)
2. "그래서 판단·조회·검증 세 단계로 쪼갰어요 — 질문 분류하고, 실제 자료 찾아서, 답변이 그 자료와 맞는지 확인." (해법)
3. "실제로 만들어보니 분류 정확도는 85%에서 90%로 좋아졌는데, 문구 하나를 더 세게 고쳤더니 다른 문제가 새로 생기더라고요." (경험담)
4. "제일 인상 깊었던 건, 분류가 틀렸는데도 AI가 '근거가 없어서 답 못 드립니다'라고 정직하게 거절한 순간이었어요 — 안전장치가 진짜로 작동한 거죠." (핵심 원칙)

## 6. 용어 사전 {#6}

| 용어 | 쉬운 설명 |
|---|---|
| 라우팅 | 질문을 알맞은 처리 경로로 분류하는 것 |
| 그라운딩 | 답을 지어내지 않고 실제 자료를 조회해서 답하는 것 |
| 가드레일 | 답변이 근거 자료와 일치하는지 사후에 검사하는 장치 |
| OTHER | 어떤 분류에도 해당하지 않는다는 명확한 판정 (실패가 아님) |
| 엔티티 링킹 | 고객의 자연어 표현을 실제 상품/데이터 항목과 연결하는 작업 |
| 과잉보정 | 한 문제를 고치려다 다른 곳에서 새 문제가 생기는 현상 |
