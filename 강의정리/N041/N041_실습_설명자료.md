# N041 실습 설명자료 — 지식그래프 에이전트 프로젝트 (K-pop GraphRAG)

> N041(N040을 나만의 주제로 다시 설계하는 프로젝트)을 논리적으로 상세히 풀어 정리한 문서. 강의의 취지, 실습이 검증하려는 것, 프로젝트에서 실제로 있었던 일, 향후 적용법, 동료에게 설명하는 법 순으로 구성했다.
>
> 💡 **읽는 법**: 코드를 몰라도 끝까지 읽을 수 있게 썼다. 어려운 용어는 그 자리에서 비유로 풀어준다. "개발자용"이라고 표시된 부분은 건너뛰어도 줄거리를 이해하는 데 지장 없다.

## 미리 보는 용어 4개

| 용어 | 무엇을 하는가 | 비유 |
|---|---|---|
| **지식 그래프 (Knowledge Graph)** | AI가 찾아볼 지도 — 정보를 미리 점과 선으로 이어둔 것 | 여행 가기 전 미리 그려둔 지도 |
| **LangGraph** | 그 지도를 이용해 AI가 실제로 움직이는 절차 | 지도를 보고 실제로 짠 여행 일정 |
| **멀티홉** | 여러 관계를 연속해서 따라가야 답이 나오는 질문 | 지하철 환승 횟수 |
| **근거 기반 답변** | 근거가 없으면 답하지 않고 "모른다"고 말하는 것 | 시험에서 확신 없으면 답을 비워두는 것 (틀린 답 쓰는 것보다 나음) |

## 1. 이 수업(N041)의 취지 — 지식을 "저장"하는 법에서 "찾아 답하는" 법으로

N041은 완성 코드를 따라 치는 수업이 아니라, N040에서 배운 GraphRAG(그래프 기반 검색·답변) 파이프라인을 학습자가 스스로 고른 주제로 처음부터 다시 설계·제출하는 프로젝트입니다. 목표는 "지식을 저장하는 법"에서 한발 더 나아가, **그 지식을 찾아서 근거 있게 답하는 법**을 익히는 것입니다.

가장 중요한 조언은 이것입니다: "**멋있는 주제를 선택하는 것보다 관계가 잘 만들어지는 주제를 선택하는 것입니다.**" 화려한 주제를 고르는 게 아니라, 점(개체)과 선(관계)이 실제로 촘촘하게 만들어질 수 있는 주제를 고르는 게 성공의 열쇠라는 뜻입니다.

<a id="2"></a>
## 2. 실습이 알아보고자 한 것

이 프로젝트가 확인하려는 핵심은 원문의 이 문장에 담겨 있습니다:

> "AI가 항상 답을 만들어내는 것이 목표가 아닙니다. 오히려 **근거가 없으면 답하지 않는 AI**를 만드는 것이 목표입니다."

멀티홉(여러 단계를 거쳐야 나오는 질문)은 "지하철 환승 횟수"에 비유됩니다 — 한 번에 안 가고 여러 번 갈아타야 목적지에 도착하는 질문이라는 뜻입니다. 지식 그래프(Knowledge Graph)와 LangGraph는 이름이 비슷해서 헷갈리기 쉬운데, "Knowledge Graph = AI가 찾아볼 지도, LangGraph = AI가 그 지도를 사용해서 움직이는 여행 일정"이라는 비유로 구분합니다.

<a id="3"></a>
## 3. 프로젝트에서 실제로 있었던 일

**주제**: K-pop 4개 레이블(SM/YG/JYP/HYBE)을 중심으로 아티스트·앨범·시상식 지식 그래프를 만들었습니다.

1. **엉뚱한 문서가 섞여 들어온 사건**: 위키백과에서 60건을 수집할 때, 처음엔 "숨은 분류"까지 같으면 관련 문서로 인정하는 방식을 썼더니, 대한민국·미국·경기도처럼 K-pop과 무관한 문서가 섞여 들어왔습니다 → 필터를 고쳐서 해결했습니다.
2. **주인공을 잘라버린 사건**: 연결이 너무 많은 노드(허브)를 피하려고 "연결 개수 제한" 규칙을 넣었더니, 정작 질문의 주인공인 ENHYPEN(직접 연결 56개)까지 20개로 잘려버려 "ENHYPEN이 발매한 앨범은?"이라는 질문에 "확인할 수 없습니다"라고 잘못 거부하는 일이 생겼습니다 → 질문의 시작점이 되는 개체는 자르지 않도록 수정했습니다.
3. **최종 결과**: 골든셋 12문항에서 GraphRAG는 100%(12/12) 정답, 기본 검색(키워드 기반)은 33%(4/12)에 그쳤습니다. 특히 3~4단계를 거쳐야 하는 어려운 질문에서는 기본 검색이 0%까지 떨어진 반면, GraphRAG는 100%를 유지했습니다.
4. **거부가 오히려 좋은 신호였던 사건**: "데뷔 앨범"이나 "발라드 솔로 아티스트"처럼 그래프에 없는 표현이 들어간 질문을, AI가 답을 지어내지 않고 거부했습니다. 처음엔 버그로 의심했지만, 확인해보니 **AI가 자기 사전지식으로 빈칸을 채우지 않고 정직하게 거부한 것**으로 확인됐습니다.

<a id="4"></a>
## 4. 앞으로 내 프로젝트에 어떻게 적용하면 되는가

### 누구나 알아야 할 원칙

- **"돌아간다"와 "믿을 수 있다"는 다른 질문입니다.** 코드가 에러 없이 끝까지 실행됐다고 결과가 맞다는 뜻은 아닙니다. 매 단계 산출물을 직접 열어봐야 진짜 문제가 보입니다.
- **AI의 "거부"나 "모른다"는 답이 항상 실패는 아닙니다.** 정해둔 근거 범위 밖의 질문에 정직하게 답을 안 하는 것은, 오히려 신뢰할 수 있는 설계라는 증거일 수 있습니다.
- **주제를 고를 때는 "멋"보다 "관계가 잘 만들어지는가"를 먼저 보세요.** 화려한 주제라도 개체와 개체 사이 연결이 빈약하면 이 방식의 장점을 살릴 수 없습니다.

### 개발자용 체크리스트 (코드를 직접 짤 때만 해당)

- 허브 노드 회피 규칙을 넣을 때는 "질문의 시작점이 되는 개체"는 예외로 둔다.
- 평가(채점) 프롬프트의 문구 하나가 실제 성능과 무관하게 점수를 왜곡할 수 있으니, 채점 기준 문구가 내부 기술 용어인지 사람이 읽을 말인지 구분한다.
- 노드 병합 시 "이름+타입" 복합키를 쓴다.

<a id="5"></a>
## 5. 동료에게 어떻게 설명하면 되는가

**한 줄 엘리베이터 피치**:
> "K-pop 아티스트·앨범·레이블 데이터로 지식 그래프를 만들어, 여러 단계를 거쳐야 하는 질문에 근거를 대며 답하거나, 근거가 없으면 솔직하게 모른다고 말하는 AI를 직접 만들고 검증했어요. 어려운 질문에서 기본 검색은 33%, 이 방식은 100% 정답이었습니다."

**좀 더 풀어서 설명할 때 순서**:
1. "K-pop 아티스트·앨범 관계를 지도처럼 미리 그려두고, 그 지도를 따라가며 답하는 AI를 만들었어요." (문제의식)
2. "만들다 보니 연결 너무 많은 걸 자르는 규칙이 오히려 질문의 주인공까지 잘라버리는 문제가 있었어요." (경험담)
3. "재밌었던 건, AI가 답을 못 찾겠다고 거부한 게 버그가 아니라 오히려 정직한 답이었다는 걸 확인한 순간이었어요." (핵심 원칙)
4. "결과는 어려운 질문에서 기본 검색 33% vs 이 방식 100%로 확실히 갈렸어요." (규모감·범위 명시)

## 6. 용어 사전

| 용어 | 쉬운 설명 |
|---|---|
| 지식 그래프 (Knowledge Graph) | AI가 찾아볼 지도 — 정보를 점과 선으로 미리 이어둔 것 |
| LangGraph | 그 지도를 이용해 AI가 실제로 움직이는 절차를 짜는 도구 |
| 멀티홉 | 여러 관계를 연속으로 따라가야 답이 나오는 질문 |
| 허브 노드 | 연결이 지나치게 많은 노드 |
| 근거 기반 답변 | 근거가 없으면 지어내지 않고 "모른다"고 답하는 방식 |
