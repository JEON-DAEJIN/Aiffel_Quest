N047 · Cloud Run에서 AI서비스 운영하기

1. 공개한 뒤에는 질문이 바뀝니다

에이전트 서비스가 공개 주소에서 돌아가기 시작하면 질문이 "올라갔나?"에서 "계속 잘 돌아가나?"로 바뀝니다. 답이 길어지면 중간에 끊기지는 않을까, 누가 주소를 퍼뜨려 요청이 몰리면 요금은 얼마나 나올까, 새 버전을 올렸더니 어제까지 대화하던 캐릭터가 사라졌다면 어디를 봐야 할까. 이런 질문은 서비스가 사용자를 만나는 순간부터 매일 생깁니다.

일반 웹앱과 달리 AI 서비스는 답이 느리고, 요청마다 LLM 제공사(OpenAI, Google처럼 LLM API를 제공하는 회사)에 돈을 내며, 같은 요청에도 처리 시간이 들쭉날쭉합니다. 그래서 같은 Cloud Run 위에서도 요청 타임아웃, 인스턴스 수, 사용 한도를 AI 서비스에 맞게 따로 정해야 합니다.

📌 요약 — 작은 식당 비유

AI 서비스를 작은 식당이라고 생각해 보겠습니다. 요청 제한 시간은 손님을 기다리게 할 수 있는 시간입니다. 식당에서 주문한 음식이 너무 늦게 나오면 손님이 떠나듯, 제한 시간이 너무 짧으면 답변이 끝나기 전에 요청이 종료될 수 있습니다. 인스턴스 수는 동시에 일할 수 있는 직원 수입니다. 무작정 늘리면 서버 운영비와 AI API 비용이 커질 수 있습니다. 로그는 식당에서 일어난 일을 기록한 장부입니다. 어떤 요청이 들어왔는지, 오류가 났는지, 얼마나 걸렸는지 보면 원인을 찾는 데 도움이 됩니다.

로그식당에서 일어난 일의 장부요청·오류·처리 시간의 기록

주소를 단체 대화방에 올린 그날 밤

공개 AI 캐릭터 서비스에서 사용자가 "오늘 기분이 우울한데 위로해 줘."라고 보내면, 요청은 Cloud Run(요청 접수·서버 실행·처리 시간 관리)을 거쳐 LLM API(답변 생성·API 사용 비용 발생)를 부르고, 답변이 돌아오면 로그(성공 여부·처리 시간·오류 기록)가 남습니다. 이 흐름에서 세 가지 문제가 생길 수 있습니다.

2. 시작 상태 맞추기

오늘 실습은 N046의 결과 위에서 시작합니다. 먼저 현재 상태를 읽기만 하는 명령 세 개로 확인합니다. 아무것도 만들거나 바꾸지 않고, 시크릿 값은 출력하지 않습니다.

# 1. gcloud 계정, 프로젝트, 기본 리전

# 2. friend-agent 서비스와 서비스 URL
gcloud run services describe friend-agent --region us-central1 --format "value(status.url)"
# 3. 시크릿 llm-api-key 가 있는지 (값은 출력하지 않는다)
gcloud secrets describe llm-api-key --format "value(name)"
확인 대상식당 비유틀리면
프로젝트와 리전어느 식당의 어느 지점에서 일하는지엉뚱한 환경을 조회하거나 서비스를 못 찾는다

Secret Manager식당 직원만 아는 출입 비밀번호를 금고에 보관LLM API 키가 안전하게 보관돼 있는지

하나라도 없으면 템플릿 저장소의 "시작 상태 문서 A, B"(docs/start-states.md) 순서대로 준비합니다. Google Cloud 가입부터라면 30~50분이 걸립니다.

  1. Google Cloud 무료 체험 가입, 프로젝트 만들기, gcloud 설치와 gcloud init (문서 A)
  2. 기본 리전 us-central1 설정과 API 4개 사용 설정 (문서 A)
  3. 템플릿 저장소로 내 공개 저장소를 만들고 내려받기 (문서 A)
  4. 콘솔의 Secret Manager에서 시크릿 llm-api-key 만들기. 키 값은 콘솔에서 직접 넣는다 (문서 B)
  5. 기본 서비스 계정에 그 시크릿 읽기 권한을 주고, 시크릿을 참조해 friend-agent 배포 (문서 B)

"gcloud에 설정된 프로젝트와 리전, friend-agent 서비스의 서비스 URL, 시크릿 llm-api-key가 있는지 확인해 줘. 시크릿의 값은 읽거나 출력하지 마. 확인만 하고 아무것도 만들거나 바꾸지 마." 처럼 읽기 전용임을 못 박습니다.

3. 스트리밍과 요청 타임아웃

스트리밍은 피자를 한 조각씩 내놓는 것

식당에서 피자 한 판을 전부 만든 뒤 내놓을 수도 있고, 준비된 조각부터 내놓을 수도 있습니다. 스트리밍(streaming)은 두 번째 방식입니다. 답변을 생성하는 대로 조금씩 화면에 전달하므로 전체 시간이 같아도 사용자는 첫 글자를 일찍 봅니다.

그런데 에이전트 서비스는 답을 보낸 뒤에도 기억 정리를 같은 요청 안에서 마저 합니다. 요청 타임아웃이 짧으면 두 곳에서 끊길 수 있습니다.

그림 1 · 타임아웃 3초일 때의 요청 (원리 설명용 가상 시간표)
⚠️ 주의 — 틀린 결과가 정상처럼 보입니다

답을 보내는 중에 끊기면 "내일 서울은 맑다가"에서 멈춰 뒤의 비소식이 잘려 맑은 날로 읽힐 수 있습니다. 기억 정리 중에 끊기면 답은 끝까지 보이는데 방금 말한 일정은 저장되지 않을 수 있습니다. 요청 타임아웃을 짧게 잡았을 때의 더 큰 문제는, 이렇게 틀리거나 빠진 결과가 정상처럼 보인다는 것입니다. (위 시간 분배는 원리를 설명하기 위한 가상 예시이며 실제 측정값은 서비스마다 다릅니다.)

타임아웃을 3초로 줄여 관찰하고 300초로 복원

gcloud run services update friend-agent --region us-central1 --timeout 3
# 확인한 뒤 기본값으로 되돌린다
gcloud run services update friend-agent --region us-central1 --timeout 300

3초로 줄인 상태에서 몇 번 말을 걸면 답이 문장 중간에서 멈추거나 "응답이 끝까지 오지 않았어요" 안내가 붙습니다(스트림 종료 이벤트가 오지 않으면 클라이언트가 안내를 붙입니다). 화면 오른쪽 "이번 턴" 패널의 걸린 시간도 3초 근처에서 끊깁니다. 안 끊기면 처음에 읽은 요청 전체 시간보다 더 짧게 줄입니다.

값은 측정으로 정한다: P50과 P99

측정항목(Metrics) 탭의 요청 지연 시간(Request latencies) 그래프에서 백분위수를 읽습니다. 요청 100건을 처리 시간 순서로 줄 세웠다고 생각하면 쉽습니다.

지표뜻쓰임
P50요청의 약 절반이 이 값 이하의 시간에 끝남일반적인 응답 속도 파악
P95약 95%가 이 값 이하느린 요청까지 고려
P99약 99%가 이 값 이하매우 느린 요청의 영향 파악
  1. 콘솔 상단에서 프로젝트를 확인하고 검색창에 Cloud Run을 입력해 서비스 목록을 엽니다.
  2. friend-agent → 측정항목(Metrics) 탭.
  3. 기간을 1시간이나 6시간으로 줄여 방금 보낸 요청이 보이게 합니다.
  4. 요청 지연 시간 그래프에서 백분위수를 50번째, 99번째로 바꿔 값을 읽습니다(선 위에 마우스를 올리면 시각별 값).
  5. 두 값을 앞서 정한 요청 타임아웃과 비교합니다.
💡 팁 — P99는 최댓값이 아닙니다

P50만 보면 대부분 빨라 보여도 일부 요청이 매우 오래 걸리는 문제를 놓칩니다. 그래서 P50과 P99를 함께 봅니다. 다만 P99는 가장 느린 요청의 시간이 아니며, 실제 최댓값은 P99보다 클 수 있습니다. 측정된 요청이 적거나 최근 요청이 그래프에 덜 반영됐다면 신중히 해석합니다.

🧪 예제 — 타임아웃을 늘리면 AI가 빨라질까

아닙니다. Cloud Run의 요청 타임아웃과 LLM API의 처리 시간은 서로 다른 개념입니다. 요청 시간에는 답을 보내는 시간뿐 아니라 그 뒤의 기억 정리까지 들어가므로, 측정한 요청 전체 시간보다 넉넉하게 잡습니다. LLM 제공사 API가 느려지는 날에는 이 값이 몇 배로 늘 수도 있습니다. 기본값 300초가 모든 AI 서비스의 최적값이라는 뜻도 아닙니다. 답변 생성과 기억 저장을 분리하거나 작업 큐를 쓰는 것은 필수 실습이 아닌 향후 개선 방향입니다.

4. 인스턴스 수 제한과 사라지는 데이터

gcloud run services update friend-agent --region us-central1 --min-instances 0 --max-instances 2
설정뜻트레이드오프
최소 인스턴스(min)요청이 없어도 켜 두는 수. 0이면 요청이 없을 때 0개까지 줄어듦0: 유휴 비용 절감, 첫 요청이 늦을 수 있음 / 1: 시작 지연 감소, 유지 비용 발생
최대 인스턴스(max)요청이 몰려도 켜지는 수의 상한너무 낮으면 요청이 대기하거나 거절될 수 있음
콜드 스타트실행 환경을 새로 준비하느라 첫 응답이 늦어지는 현상직원이 모두 퇴근한 식당에 손님이 오면 직원을 다시 부르는 과정

설정한 뒤 10분쯤 서비스를 쓰지 않다가 다시 말을 걸어 보세요. 첫 답이 늦게 시작되는 것이 콜드 스타트이고, 측정항목 탭의 컨테이너 인스턴스 수(Container instance count) 그래프에서 0으로 내려갔다가 1로 올라오는 구간을 찾을 수 있습니다(기간 1시간. 선이 실행 중과 유휴로 나뉘면 둘을 합친 값이 인스턴스 수). 설정이 들어갔는지는 리비전 탭에서 맨 위 리비전을 눌러 오른쪽 패널에서 확인합니다.

⚠️ 주의 — 값이 반드시 0으로 보이진 않습니다

트래픽, 다른 설정, 관측 시점에 따라 인스턴스 수가 0으로 내려가는 모습이 안 나타날 수 있습니다. 콜드 스타트는 단순히 화면이 늦게 뜨는 현상이 아니라, 요청을 처리할 실행 환경이 준비되는 데 시간이 필요한 상황입니다.

왜 캐릭터와 대화가 사라졌을까

이번 강의에서 가장 중요한 부분입니다. 타임아웃과 인스턴스 수를 바꿀 때마다 새 리비전이 배포됐고, 배포 뒤 화면을 다시 열면 만들어 둔 캐릭터와 대화가 사라지고 캐릭터 만들기 화면이 다시 나왔을 것입니다.

그림 2 · 서버 메모리에 둔 데이터가 사라지는 과정

템플릿은 캐릭터·대화·기억을 인스턴스 메모리에 저장하기 때문입니다. 새 리비전은 새 인스턴스로 실행되고, 요청이 없어 인스턴스가 0개로 줄면 그 안의 메모리도 함께 지워집니다. 최대 인스턴스가 2라면 또 다른 문제가 생깁니다. 같은 사람의 요청이 서로 다른 인스턴스로 가면 한쪽에는 대화 기록이 있고 다른 쪽에는 없습니다.

📌 요약 — 인스턴스 수와 데이터 저장 위치는 별개

인스턴스를 1개만 써도 그 인스턴스가 교체되면 메모리 속 데이터가 사라질 수 있습니다. 반대로 인스턴스가 2개 이상이어도 외부 데이터베이스를 쓰면 여러 인스턴스가 같은 데이터를 조회·갱신할 수 있습니다. 컨테이너는 언제든 꺼지고 새로 켜질 수 있다는 전제로 쓰는 실행 단위이므로, 남겨야 하는 데이터는 컨테이너 밖의 데이터베이스에 둡니다.

수업용 서비스처럼 사용 빈도가 낮으면 최소 0으로 시작해 몇 초의 첫 응답 지연을 받아들이는 편이 합리적입니다. 고객이 언제든 접속하는 서비스라면 첫 응답 속도와 비용을 함께 비교합니다. 최소 1이라고 모든 지연이 사라지는 것은 아닙니다(외부 LLM API 응답 지연은 별도).

5. 최대 인스턴스로 막지 못하는 비용

"최대 인스턴스를 2로 막았으니 비용 걱정은 없다"는 흔한 오해입니다. 식당에 직원이 두 명 있다고 합시다. 최대 인스턴스 2개는 일할 수 있는 직원이 최대 두 명이라는 뜻이고, 동시성 80은 직원 한 명이 동시에 최대 80개의 주문을 처리할 수 있게 허용한다는 뜻입니다. LLM API 사용 한도는 식당이 쓸 수 있는 한 달 식재료 예산과 비슷합니다.

그림 3 · 동시 처리 상한은 총 호출량 상한이 아니다
요청 하나의 처리 시간이 8초라면(단순화한 계산)
160 x (3,600 ÷ 8) = 72,000   → 시간당 처리 가능한 요청

즉 최대 인스턴스가 2개여도 요청이 계속 들어오면 한 시간에 7만 건이 넘는 요청을 처리할 수 있는 규모가 됩니다. 학습서의 예시 원가로는 시간당 100달러를 넘습니다. 최대 인스턴스는 동시에 일하는 규모를 제한할 뿐, 시간이 지나며 누적되는 LLM API 호출 총량은 제한하지 않습니다. 총액을 막는 것은 LLM 제공사 쪽 월 사용 한도입니다. 한도에 닿으면 제공사가 호출을 거부해 서비스는 답을 못 하지만 비용은 정한 금액을 넘지 않습니다.

LLM 제공사 월 사용 한도한 달 LLM API 비용 총액Cloud Run 쪽 요금

⚠️ 주의 — 예산 알림은 비용 상한이 아닙니다

예산의 50%에서 알림을 받게 할 수 있지만, 알림은 메일을 보낼 뿐 서비스 사용을 자동으로 멈추지 않습니다. 또 모든 제공사가 같은 방식으로 한도를 강제하지는 않으니 제공사 계정과 요금제에서 확인해야 합니다. 이 과정에서 쓰는 키가 회사가 나눠 준 키라면 한도·알림은 회사 계정에 걸려 있어 수강생 화면에서는 보거나 바꿀 수 없고, 한도에 닿으면 같은 키를 쓰는 다른 수강생의 서비스도 함께 멈춥니다. 내 키로 운영할 때는 제공사 대시보드의 결제·사용량 메뉴에서 월 한도를 작게 걸고 한도 절반쯤에서 알림이 오게 하는 것이 배포 전 첫 작업이며, 결제 정보가 있는 화면이므로 명령이나 에이전트가 아니라 직접 설정합니다.

요청 100건당 비용 읽기

Cloud Run은 요청을 처리하는 동안의 CPU·메모리와 요청 수로 요금을 받고, LLM 제공사는 주고받은 토큰 수로 요금을 받습니다. 에이전트 서비스는 LLM API의 답을 기다리는 동안에도 요청이 열려 있어서 LLM이 느릴수록 Cloud Run 요금도 늘고, 메시지 하나에 LLM API를 세 번(도구 선택 → 답변 생성 → 대화 기억 정리) 호출합니다.

  1. friend-agent 측정항목 탭을 엽니다.
  2. 실습한 시간대로 기간을 설정합니다.
  3. 요청 수와 요청 지연 시간 그래프를 봅니다.
  4. 요청 지연 시간 P50을 읽습니다.
  5. 비용 계산 화면에 처리 시간과 LLM 제공사의 실제 토큰 단가를 넣습니다(토큰 수는 세 번의 호출을 합친 값).
  6. 요청 100건당 비용을 계산합니다.

학습서 예시 값으로는 요청 100건당 Cloud Run 비용이 2센트 정도이고 LLM API 호출 비용은 그보다 열 배 넘게 큽니다. Cloud Run 무료 사용량만으로 한 달 2만 건 넘게 처리할 수 있어, 수업 정도의 사용량이라면 실제로 돈이 나가는 곳은 LLM 제공사입니다. 다만 이는 예시 조건의 값이며 실제 비용은 모델·토큰 수·응답 길이·처리 시간·요금 정책에 따라 달라지고, 무료 사용량이 있어도 모든 사용량이 항상 무료는 아닙니다.

BYOK: 사용자가 자기 키를 넣는 구조

지금은 운영자의 키 하나로 모든 사용자의 요청을 처리합니다. 사용자가 늘면 LLM 비용도 운영자가 모두 내고, 한도에 닿으면 모든 사용자가 함께 멈춥니다. 그래서 사용자가 화면에서 자기 LLM API 키를 넣고 서비스가 그 키로 호출하는 구조를 BYOK(Bring Your Own Key)라 부릅니다. 비용은 사용자 계정으로 나가고 한도도 사용자가 정하지만, 남의 키를 받아 다루게 됩니다.

구조키가 있는 곳맞는 서비스대가
브라우저에 두고 요청마다 보내기사용자 브라우저. 서버는 처리하는 동안만 메모리에서 쓰고 저장하지 않음사용자가 화면을 열어 둔 동안에만 LLM API를 부르는 서비스기기를 바꾸면 다시 넣어야 하고, 사용자가 없을 때 서버가 먼저 LLM을 부를 수 없음
서버에 암호화해 저장하기서버 데이터베이스. 암호화 키는 Secret Manager화면을 닫은 동안에도 서버가 LLM을 불러야 하는 서비스로그인·암호화·키 삭제 기능이 필요하고, DB와 암호화 키가 함께 새면 사용자 키도 드러남

이 에이전트 서비스는 부탁받은 약속을 저장했다가 먼저 말을 거는 기능이 있어서, 화면을 닫은 동안에도 알림을 보내려면 두 번째 구조가 필요합니다. 화면을 열었을 때만 대화한다면 첫 번째 구조로 충분하고 훨씬 쉽습니다. 운영자 키가 완전히 사라지는 것도 아닙니다. 처음 써 보는 사용자에게 몇 번은 운영자 키로 답해 주거나 서비스가 스스로 하는 일에는 운영자 키를 계속 쓰며, 그 한도는 운영자가 관리합니다.

⚠️ 주의 — 키 보안 공통 원칙

① 요청 로그·오류 메시지·"이번 턴" 패널에 키가 들어가지 않게 합니다. ② 넣은 뒤에는 키 전체를 다시 보여 주지 않고 끝 네 자리 정도만 보여 줍니다. ③ 키가 틀렸거나 사용자 한도에 닿아 제공사가 거부하면 이유를 알기 쉽게 안내하되, 운영자 키로 몰래 대신 부르지 않습니다. ④ 키 지우기 버튼을 둡니다. 서버에 저장한다면 암호화·접근 권한·삭제 정책도 함께 설계합니다. sessionStorage에 둔다고 완전히 안전한 것은 아니므로 입력값 검증, XSS 방어, HTTPS, 민감한 로그 차단이 필요합니다. 코딩 에이전트에게 "사용자가 키를 넣게 해 줘"라고만 하면 키를 DB에 그대로 저장하거나 요청 로그에 남기는 코드가 나올 수 있으니, 키를 어디에 두고 어디에 남기지 않을지 먼저 정하고 요청합니다.

6. 로그의 세 종류와 근거로 진단하기

"AI가 느려요. 고쳐 주세요."만으로는 에이전트가 짐작으로 고치기 시작해 멀쩡한 곳을 바꾸기도 합니다. 좋은 요청은 이렇습니다. "오늘 오후 2시부터 2시 10분 사이에 friend-agent 서비스에서 응답 시간이 5초를 넘은 요청이 있습니다. 해당 시간대의 요청 로그와 관련 컨테이너 로그를 확인하고, 원인으로 판단한 근거를 먼저 보여 주세요. 아직 코드는 수정하지 마세요."

📌 요약 — 병원 응급실 비유

AI 서비스를 병원 응급실이라고 생각하면 세 로그의 차이가 쉽습니다. 요청 로그는 접수 기록(환자가 언제 왔고 얼마나 기다렸고 어떤 결과를 받았는지), 컨테이너 로그는 의료진의 진료 기록(어떤 처치를 했고 무엇이 잘못됐는지), 시스템 로그는 병원 시설 관리 기록(전원이 꺼졌는지, 장비가 작동하지 않았는지)입니다. 환자가 오래 기다렸다는 사실만으로는 원인을 알 수 없고, 세 기록을 함께 봐야 원인을 찾습니다. 학교 사고에 비유하면 학생 이야기뿐 아니라 출석 기록, CCTV, 교사의 관찰 기록을 함께 보는 것과 같습니다.

로그 탐색기 쿼리

로그 탐색기(https://console.cloud.google.com/logs/query?project=<프로젝트 ID>)의 입력 칸에 조건을 한 줄에 하나씩 적으면 줄 사이는 모두 AND로 묶입니다. 먼저 내 서비스로 범위를 좁힌 뒤 조건을 더합니다. :는 "이 말이 들어 있다", =는 "정확히 같다"입니다.

찾는 것쿼리

오류 이상만severity>=ERROR
서버 오류 응답httpRequest.status>=500

# 최근 로그 20줄을 콘솔과 비슷한 형식으로
gcloud run services logs read friend-agent --region us-central1 --limit 20
# 조건을 걸어 읽기: 지난 1시간 동안 friend-agent 의 오류 이상
gcloud logging read 'resource.type="cloud_run_revision" AND resource.labels.service_name="friend-agent" AND severity>=ERROR' --freshness 1h --limit 20

연습으로 세 가지 줄을 찾아봅니다. ① 서비스 URL 뒤에 /nope을 붙여 열고 httpRequest.status=404로 찾기. ② httpRequest.latency>"3s"로 느린 요청을 찾아 3절에서 측정한 시간과 비교하기. ③ 타임아웃 3초 때 보낸 요청은 504 같은 오류 상태 코드로 남으므로 httpRequest.status>=500으로 찾아 상태 코드와 걸린 시간 읽기. httpRequest 아래에 status: 404와 지연 시간(latency)이 보이면 쿼리가 제대로 걸린 것입니다.

에이전트에게 근거를 건네는 법

건넬 것은 네 가지입니다. 무엇을 했고 무엇이 보였는지(증상), 언제였는지(시간 범위), 어느 서비스와 리비전인지, 내가 이미 찾은 로그 줄이 무엇인지. 로그 줄을 붙여 넣기 전에는 API 키·토큰·사용자 이름이나 연락처가 없는지 봅니다. 로그 읽기 명령은 아무것도 바꾸지 않아 승인해도 되지만, 범위가 넓으면 엉뚱한 결론을 내므로 시간 범위와 서비스를 꼭 넣습니다. 에이전트가 근거로 든 로그 줄은 로그 탐색기에서 같은 시각·메시지로 다시 찾아 확인하고, 다르거나 못 찾으면 그 줄을 어디서 읽었는지 다시 묻습니다.

⚠️ 주의 — 콜드 스타트를 단정하지 마세요

첫 응답만 유독 늦었다고 콜드 스타트로 단정하면 안 됩니다. 요청 로그의 지연 시간, 컨테이너 인스턴스 수와 시작 관련 시스템 로그, LLM API 응답 시간, 앱 내부 처리 시간을 함께 봅니다.

7. 서로 써 보기와 추가 과제

옆 사람과 서비스 URL을 바꿔 들어가 봅니다. 상대 서비스에서 캐릭터를 만들고 몇 마디 나눈 뒤 내 서비스의 로그 탭을 엽니다. 내가 보내지 않은 요청이 찍혀 있고 측정항목의 요청 수도 늘어 있습니다.

📌 요약 — 주소는 식당 주소, 키는 내 결제 수단

서비스 URL은 식당 주소입니다. 주소를 알면 누구나 방문하고, 다른 사람이 주문해도 식재료 비용은 식당 주인이 부담할 수 있습니다. 서비스 URL을 공개했다고 해서 다른 사람의 사용 비용을 그 사람이 내주는 것이 아닙니다. 그래서 공개 서비스는 누가 얼마나 쓸 수 있는지, 비용이 어디까지 발생할 수 있는지를 함께 관리해야 합니다. 5절에서 건 인스턴스 수와 회사 계정의 사용 한도가 지켜 주는 것이 바로 이 상황입니다.

  1. Logs 탭을 엽니다.
  2. 검색 칸에 /api/chat을 입력합니다.
  3. 옆 사람이 들어온 시각 근처의 POST /api/chat 줄에서 지연 시간을 읽습니다.
  4. Metrics 탭의 요청 수(Request count) 그래프에서 같은 시각의 증가를 확인합니다.

써 본 뒤에는 상대에게 첫 답이 늦었는지, 답이 끊긴 적은 없는지 한 줄씩 알려 줍니다. 들은 내용은 내 로그에서 확인합니다. 늦었다는 시각의 요청 로그 지연 시간을 읽으면 콜드 스타트였는지 LLM API 응답이 늦었는지 가늠할 수 있습니다. 서비스는 대화를 인스턴스 메모리에 저장하므로 상대가 만든 캐릭터와 내 캐릭터가 같은 사용자 칸에 섞일 수 있는데, 이는 로그인이 없는 지금 구조의 한계입니다. 여러 사람이 쓰는 서비스라면 사용자를 구분해 데이터베이스에 저장해야 합니다.

최대 인스턴스와 동시성을 건물에 비유하면

최대 인스턴스는 건물의 최대 개수, 동시성은 건물 하나가 동시에 처리하는 요청 수입니다. 동시성 80에 최대 3이면 설정상 240개 동시 요청에 해당하지만 실제 처리량과 지연은 앱 구조, CPU 사용량, 외부 API 응답 시간, 플랫폼 동작에 따라 달라집니다.

설정예상 동작주의
동시성 80, 최대 3인스턴스 하나가 여러 요청 처리, 인스턴스는 적게 늘어남하나에 몰려 지연될 수 있음
동시성 1, 최대 20요청 하나당 인스턴스 하나 수준, 많이 늘어남인스턴스 수가 늘어 비용이 커질 수 있음
동시성 1, 최대 3인스턴스 수를 낮게 제한요청이 몰리면 대기하거나 일부 거절될 수 있음
💡 팁 — 직접 측정해서 판단

동시성을 낮추면 반드시 빨라지는 것도, 높이면 반드시 비용이 줄어드는 것도 아닙니다.

추가 과제 4종

과제난이도내용
1. 문구를 바꿔 다시 배포하고 롤백하기기본오늘 한 배포와 트래픽 전환을 혼자 다시 해 본다
2. 부하 테스트로 동시성과 최대 인스턴스 확인중간동시 요청 50개를 보내 설정마다 인스턴스 수와 응답을 비교
3. 내가 만든 앱을 Cloud Run에 올리기중간다른 앱을 배포하고, 실패하면 로그로 원인 찾기
4. BYOK 구조로 바꾸기도전사용자가 자기 LLM API 키를 넣어 쓰게 만들기

과제 1은 화면 문구나 기본 캐릭터를 바꿔 소스 배포하고, 이전 리비전으로 롤백했다가 최신으로 돌아오는 것입니다. update-traffic은 코드를 다시 빌드하는 명령이 아니라 사용자 요청을 보낼 리비전을 조정하는 명령입니다. 확인할 것은 새 리비전이 정상 생성됐는지, 트래픽이 의도한 리비전으로 100% 가는지, 요청 로그에 어느 리비전이 기록되는지입니다. 운영에서는 이전 리비전이 남아 있다는 사실만으로 롤백이 안전하다고 볼 수 없고, 정상 상태인지와 DB·설정 변경이 호환되는지도 확인해야 합니다.

과제 2는 에이전트 서비스 자체에 부하를 주면 요청마다 LLM이 호출돼 회사 키의 비용과 요청 한도를 써 버리므로, LLM을 부르지 않는 테스트용 서비스 load-test를 따로 만들어 합니다. 템플릿의 hello/ 앱에 2초 기다렸다 응답하는 /slow를 추가해 LLM 응답을 기다리는 에이전트와 비슷한 상황을 만듭니다(곧바로 끝나는 주소로 하면 인스턴스 하나가 다 처리해 늘어나는 모습을 볼 수 없습니다). 스크립트와 실행 순서는 부록 A에 있습니다.

과제 3은 이전에 만든 FastAPI·Streamlit 앱을 소스 배포하는 것입니다. 배포 전에 시작 명령이 PORT 환경변수를 쓰는지, 시크릿이 코드에 들어 있지 않은지, 필요한 라이브러리가 requirements.txt에 다 있는지 먼저 확인합니다. 실패하면 6절처럼 타임라인을 만들고 근거 로그 줄을 붙여 원인을 묻습니다.

과제 4는 첫 번째 BYOK 구조(브라우저 sessionStorage에 두고 요청마다 X-User-LLM-Key 헤더로 전달)로 바꾸는 것입니다. 키가 지나가는 곳을 하나씩 따라가 저장소나 로그에 쓰는 코드가 있으면 승인 전에 빼 달라고 하고, 배포 후에는 로그 탭 검색 칸에 내 키의 앞부분을 넣어 아무 줄도 나오지 않는지 확인한 뒤 검색 칸을 비웁니다. 키를 지웠을 때 운영자 키로 조용히 전환하면 사용자의 의도와 비용 부담이 헷갈리므로, 키가 없으면 명확히 안내합니다.

8. 오늘 배운 것: 걱정을 설정으로 나누기

1절에서 적은 걱정을 "오늘 건 설정이 막아 주는 것"과 "아직 막지 못하는 것"으로 나눠 봅니다.

걱정되는 문제도움이 되는 설정아직 막지 못하는 것
① 다른 사람이 많이 써서 비용이 폭증최대 인스턴스로 Cloud Run 규모 제한, LLM 제공사 사용 한도로 API 사용 제한최대 인스턴스만으로 LLM 비용은 못 막음. 요청별 호출 수·토큰 관리, 인증·사용자별 이용 제한은 따로 설계
② 요청이 몰리거나 늦어져 서비스가 느림타임아웃·최대 인스턴스·동시성으로 처리 방식과 확장 조절, 로그·측정항목으로 지연과 오류 확인타임아웃이 느린 요청을 빠르게 하진 않음. 최대 인스턴스를 제한하면 요청이 대기하거나 거절될 수 있음. 부하 테스트와 성능 개선 필요
③ 대화가 사라지거나 다른 사용자와 섞임로그로 오류와 리비전 변경 시점, 인스턴스 교체·배포 여부를 추적로그는 데이터를 복구하거나 사용자별로 분리해 주지 않음. 대화 기록을 DB에 저장하고 로그인·사용자 식별·접근 권한 구현 필요
📌 요약 — 세 단 정리

시간과 개수: 요청은 답을 보낸 뒤 기억 정리까지 같은 요청 안에서 끝나므로 요청 타임아웃은 측정한 요청 전체 시간보다 넉넉하게 잡습니다. 최대 인스턴스는 한 번에 처리하는 양만 막고, 최소 0은 요금 대신 콜드 스타트를 받아들이는 선택입니다. 데이터와 비용: 인스턴스 안의 대화는 배포나 교체 때 사라지고, 비용의 대부분은 Cloud Run이 아니라 LLM API 호출에서 나오며 총액은 제공사 한도가 막습니다. 예산 알림은 알려 주기만 합니다. 로그 읽기: 세 로그를 심각도·상태 코드·지연 시간·리비전으로 거르고 시간순으로 모으면 일을 재구성할 수 있습니다. 터미널 메시지는 결과이고 원인은 앞선 컨테이너 로그에 있습니다.

9. 핵심 한 문장 요약

📌 요약

AI 서비스를 안전하게 운영하려면 비용·성능·데이터 문제를 구분하고, 각 문제를 막아 주는 설정과 별도로 구현해야 할 기능을 정확히 알아야 합니다. 설정 하나가 모든 문제를 해결해 주지는 않습니다.

  1. 요청 타임아웃은 답변 시간이 아니라 후속 작업까지 포함한 실제 처리 시간을 측정해 느린 요청까지 고려해 정합니다.
  2. 최대 인스턴스는 처리 규모를 제한할 뿐 LLM 비용 총액을 막지 못합니다. 총액은 제공사 한도, 예산 알림은 알림일 뿐입니다.
  3. 인스턴스 수와 데이터 저장 위치는 별개입니다. 남겨야 하는 데이터는 외부 DB에 둡니다.
  4. 사용자 키(BYOK)는 로그·화면·오류 메시지 어디에도 남기지 않습니다.
  5. 로그 3종을 구분해 읽고, 에이전트에는 증상·시간 범위·서비스와 리비전·찾은 로그 줄을 근거로 건네고 "아직 고치지 마"를 함께 요청합니다.

A-2. 부하 테스트 (과제 2)

먼저 hello/main.py에 2초 기다렸다 응답하는 /slow를 추가하고(async 함수와 asyncio.sleep), hello/ 폴더를 load-test 서비스로 us-central1에 최대 인스턴스 3으로 배포합니다. 서비스 URL 끝에 /slow를 붙여 열면 2초쯤 뒤 {"status":"ok"}가 보여야 합니다. 아래 load_test.py는 표준 라이브러리만 씁니다(원본 PDF에서 추출 중 들여쓰기가 소실되어 문법에 맞게 복원한 것이니, 원본과 한 번 대조하세요).

"""서비스 URL에 동시 요청을 보내고 응답 코드와 응답 시간을 요약한다.
사용법: python load_test.py <서비스 URL>/slow 50
"""
import sys
import time
import urllib.error
import urllib.request
from concurrent.futures import ThreadPoolExecutor

url = sys.argv[1]
total = int(sys.argv[2]) if len(sys.argv) > 2 else 50

def send(_):
    start = time.time()
    try:
        with urllib.request.urlopen(url, timeout=120) as response:
            code = str(response.status)
    except urllib.error.HTTPError as error:
        code = str(error.code)
    except Exception:
        code = "연결 실패"
    return code, time.time() - start

with ThreadPoolExecutor(max_workers=total) as pool:
    results = list(pool.map(send, range(total)))

counts = {}
for code, _ in results:
    counts[code] = counts.get(code, 0) + 1
times = sorted(seconds for _, seconds in results)
print(f"보낸 요청: {total}개")
print("응답 코드별 개수:", counts)
print(f"응답 시간: p50 {times[len(times)//2]:.1f}초, p95 {times[int(len(times)*0.95)-1]:.1f}초, 최대 {times[-1]:.1f}초")
# 설정 A. 동시성 80(기본값), 최대 인스턴스 3
gcloud run services update load-test --region us-central1 --concurrency 80 --max-instances 3
python load_test.py <서비스 URL>/slow 50        # macOS에서 python 이 없으면 python3
# 설정 B. 동시성 1, 최대 인스턴스 20
gcloud run services update load-test --region us-central1 --concurrency 1 --max-instances 20
python load_test.py <서비스 URL>/slow 50
# 설정 C. 동시성 1, 최대 인스턴스 3
gcloud run services update load-test --region us-central1 --concurrency 1 --max-instances 3
python load_test.py <서비스 URL>/slow 50
# 끝나면 테스트용 서비스를 지운다
gcloud run services delete load-test --region us-central1
설정200 개수200이 아닌 응답p50최대최대 인스턴스 수(그래프)

문제 6. (주관식) 일부러 실패시킨 배포에서 터미널 메시지만 보고 원인을 짐작했다면 어떤 오해를 할 수 있었을지, 실제 원인은 어느 로그 줄에서 확인됐는지 설명해 보세요.

모범답안: 터미널의 마지막 메시지는 배포가 실패했다는 결과만 알려 주므로 배포 명령이나 Cloud Run 플랫폼에 문제가 있다고 오해할 수 있습니다. 실제 원인은 앱이 시작되는 과정의 설정 오류로, LLM_PROVIDER에 지원하지 않는 unknown 값이 설정된 것입니다. 컨테이너 로그의 ERROR 메시지에서 확인하고, 그 로그의 시각과 리비전을 시스템 로그·리비전 상태와 비교해 실패 과정이 일치하는지 검증합니다. 터미널 메시지는 결과를, 컨테이너 로그는 직접 원인을, 시스템 로그는 플랫폼에서 나타난 결과를 보여 줍니다. 정확한 메시지와 시각은 직접 확인한 로그를 기준으로 씁니다.
