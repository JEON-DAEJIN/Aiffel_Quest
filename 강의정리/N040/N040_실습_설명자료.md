## 1. 이 수업(N040)의 취지 — 왜 "영화추천"에 지도가 필요한가

N040은 이름은 "영화추천 에이전트"지만, 실제로는 **GraphRAG**(지식 그래프 기반 검색·답변)를 스키마 설계→추출→정규화→검증→에이전트 조립→평가까지 손으로 완주하는 실습입니다. 기존의 벡터 검색(RAG) 방식은 "봉준호 영화에 나온 배우가 출연한 다른 영화는?"처럼 여러 단계를 거쳐야 답이 나오는 질문(멀티홉)과, 특정 출발점이 없는 "전역 질문"에 약하다는 걸 먼저 숫자로 보여준 뒤, 그 벽을 넘기 위해 그래프를 만듭니다.

기존 방식과의 차이는 이렇게 비유합니다: "기존 RAG — 영화관 직원에게 질문합니다... 하지만 사람→영화→영화라는 관계를 직접 연결해서 찾아야 합니다. GraphRAG — 영화관에 미리 이런 지도를 만들어 놓습니다."

<a id="2"></a>
## 2. 실습이 알아보고자 한 것

이 실습이 가장 강조하는 결론은 이것입니다:

> "GraphRAG의 어려움은 그래프를 만드는 데 있지 않고, **만들어진 그래프를 믿을 수 있게 만드는 데** 있다."

즉 "그래프를 만들 수 있는가"보다 "그 그래프가 정말 맞는가, 이상한 연결(가짜 다리)이 섞이지는 않았는가"를 검증하는 게 진짜 어려운 부분이라는 걸 실제로 확인하는 실습입니다.

<a id="3"></a>
## 3. 실습에서 실제로 있었던 일

1. **기존 방식이 오히려 더 잘 맞은 경우도 있었다**: 최종 점수는 기본 검색(BM25 키워드 검색) 0.49 vs GraphRAG 0.42로, 그래프 방식이 오히려 낮게 나왔습니다(강의 원문 예시는 반대로 그래프 쪽이 훨씬 높았습니다 — 즉 결과는 만든 그래프의 품질에 따라 완전히 달라질 수 있습니다). 특히 단순한 질문에서는 키워드 검색 0.97 vs GraphRAG 0.67로 차이가 컸습니다.
2. **관계를 엉뚱한 자리에 채운 사건**: "기생충 배급사는?"이라는 질문에서 GraphRAG가 0점을 받았습니다. 원인을 열어보니, "칸 국제 영화제"가 "배급사"라는 관계 칸에 잘못 들어가 있었습니다 — AI가 정보 자체는 정확히 읽었지만, 엉뚱한 관계 칸에 채워 넣은 것입니다.
3. **안전장치가 오히려 유명한 정보를 밀어낸 사건**: 관계 하나당 최대 8개까지만 담고 "연결이 적은 것부터 담는다"는 규칙을 같이 썼더니, 송강호가 출연한 19개 작품 중 정작 유명한 '살인의 추억'·'괴물'이 밀려나고 덜 알려진 작품만 추천되는 부작용이 생겼습니다. 게다가 "배"라는 한 글자짜리 유령 노드가 "배우"라는 단어에 걸려 탐색의 출발점으로 잘못 잡히는 일도 있었습니다.

> 📌 **참고**: 같은 방식을 K-pop 도메인(N041 프로젝트)에 적용했을 때는 정반대로, GraphRAG가 12문항 전부(100%) 정답을 맞히고 기본 검색은 33%에 그쳤습니다. 즉 방식 자체의 우열이 아니라, **도메인과 스키마 설계·버그 수정 여부에 따라 결과가 크게 갈린다**는 걸 두 실습을 비교하면 알 수 있습니다.

<a id="4"></a>
## 4. 앞으로 내 프로젝트에 어떻게 적용하면 되는가

### 누구나 알아야 할 원칙

- **새 방식(그래프)이 옛 방식(키워드 검색)을 항상 이긴다고 가정하지 마세요.** 먼저 옛 방식의 점수를 재둬야("벽"을 세워야) 새 방식이 정말 나은지 판단할 수 있습니다.
- **코드가 에러 없이 돌아가는 것과 결과가 옳은 것은 다른 문제입니다.** AI가 자동으로 만든 데이터(그래프·관계)는 사람이 직접 몇 개를 열어봐야 숨은 오류(엉뚱한 칸에 채워짐, 유령 데이터)를 찾을 수 있습니다.
- **안전장치 하나가 다른 부작용을 낳을 수 있습니다.** "너무 흔한 정보는 거른다"는 규칙이 오히려 유명하고 진짜 중요한 정보까지 밀어낼 수 있으니, 규칙끼리 어떻게 상호작용하는지도 확인해야 합니다.

### 개발자용 체크리스트 (코드를 직접 짤 때만 해당)

- 관계 추출 결과를 표본으로 몇 건 직접 열어 "관계가 맞는 칸에 채워졌는지" 확인한다.
- 노드 병합 시 "이름+타입" 복합키를 쓴다 — 이름만 같으면 다른 개체가 합쳐질 수 있다.
- 탐색 예산·정렬 규칙을 걸 때는 시작 개체(질문의 주인공)에는 예외를 두는 걸 검토한다.

<a id="5"></a>
## 5. 동료에게 어떻게 설명하면 되는가

**한 줄 엘리베이터 피치**:
> "AI에게 영화 자료를 지도처럼 만들게 한 뒤, 실제로 그 지도를 믿을 수 있는지 직접 파봤어요 — 결론은, 지도를 만드는 것보다 지도가 맞는지 검증하는 일이 훨씬 어렵다는 거였습니다."

**좀 더 풀어서 설명할 때 순서**:
1. "일반 검색은 여러 단계를 거쳐야 나오는 질문에 약해서, 아예 미리 관계 지도를 만들어두는 방식을 써봤어요." (문제의식)
2. "그런데 이 지도, AI가 자동으로 만들다 보니 관계를 엉뚱한 칸에 채우는 실수가 실제로 있었어요." (경험담 1)
3. "이상한 정보를 거르려고 규칙을 넣었더니, 오히려 유명하고 진짜 중요한 정보까지 밀려나는 부작용도 생겼고요." (경험담 2)
4. "그래서 배운 게, 새 방식이 항상 좋다고 가정하지 말고 옛날 방식 점수부터 재두고 비교해야 한다는 거예요." (핵심 원칙)

## 6. 용어 사전

| 용어 | 쉬운 설명 |
|---|---|
| GraphRAG | 지식 그래프(지도)를 미리 만들어두고 그 위에서 답을 찾는 검색·답변 방식 |
| 지식 그래프 | 정보를 점과 선으로 미리 연결해둔 지도 |
| 삼중항 (Triple) | "누가-무엇을-했다" 형태로 저장하는 관계 한 조각 |
| 멀티홉 | 여러 관계를 연속으로 따라가야 답이 나오는 질문 |
| 가짜 다리 | 너무 흔한 단어·분류가 상관없는 것끼리 잘못 이어버리는 문제 |
| 허브 노드 | 연결이 지나치게 많은 노드(예: "미국", "드라마" 같은 흔한 개념) |
