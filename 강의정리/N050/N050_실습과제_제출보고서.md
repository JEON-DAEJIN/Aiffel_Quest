## 2. staging에서 OCR 켜고 실패 재현 (단계 3)

무엇을 했나: staging에만 `OCR_ENABLED=true`를 추가하고 같은 사진을 보냈다(11:34~11:35). production은 건드리지 않았다.

무엇이 보였나: 서비스 루트와 `/version`은 정상인데 사진 요청은 **HTTP 500**이었다. API 응답은 `{"detail":"사진에서 글자를 읽는 프로그램이 서버에 없습니다."}`였고, 화면에는 "사진에서 글자를 읽지 못했어요: …"로 보였을 것이다(화면 캡처는 없음).

원인을 어디서 찾았나: Cloud Run 로그. 11:35:05에 리비전 `friend-agent-staging-00006-dst`가 `tesseract 프로그램을 찾을 수 없습니다.`라는 ERROR와 `POST /api/ocr` 500을 남겼다. 서비스는 정상 시작했고 사진 요청이 들어온 순간 프로그램을 부르다 실패한 것이라, 배포는 성공이고 대화 기능은 정상이었다.

처리: Dockerfile로 해결했다(5~6절).

## 4. Dockerfile 쓰고 로컬에서 빌드 (단계 5)

- 템플릿 Dockerfile·`.dockerignore`를 복사해 5기준(베이스 고정 · tesseract와 kor 설치 · `.env` 제외 · `${PORT:-8080}` · `USER appuser`)을 검토했고 모두 통과했다
- 첫 빌드 이미지는 **460MB**였고, 컨테이너에서 같은 사진이 **200 · 153글자 · `e61b2db05f`**로 읽혔다. 이미지 안에는 `.env`·`tests`·`docs`가 없고 `whoami`는 `appuser`였다
- 막힌 일: 이미지 안 `/app/app/__pycache__`에 **.pyc 17개**(내 PC의 `.venv`가 만든 cpython-314)가 들어 있었다. 템플릿 `.dockerignore`의 두 줄이 맨 위 폴더에만 적용돼서였다. 하위 폴더까지 적용되는 패턴(앞에 별표 두 개와 슬래시를 붙이는 방식, 모양은 부록 코드 블록 참조)으로 고쳐 재빌드하자 `__pycache__`와 `.pyc`가 0개가 됐고, 크기는 460MB 그대로였다
- 교재와 달라진 것: 교재는 `__pycache__`가 "보이면" 고치라 했는데 실제로 나왔다. 교재의 레이어·이미지 크기와 이번 실측도 달랐다(교재 400MB대, 이번 460MB. 수치는 부록)

## 7. 과제 1·2 — 컨테이너 들여다보기, 같은 Dockerfile 두 번 빌드

- 과제 1: 실행 중인 컨테이너를 `docker exec`로 열어 보니 `appuser`, `/app`, `.env`·`tests`·`docs` 없음이었다. 대화 두 턴 뒤 메시지 **4개**였는데 컨테이너를 지우고 같은 이미지(ID 불변)로 다시 띄우자 **0개**가 됐다. Git Bash `curl -d`의 한글 JSON은 HTTP 400이 나서 파이썬 UTF-8 전송으로 확인했다. 교재와 다르게 브라우저 대신 **API로 확인**했다(화면 캡처 없음)
- 과제 2: `--no-cache`로 두 번 빌드하자 `pip freeze` 30줄과 deb 159개는 **같고 이미지 ID는 달랐다**(`8d665740853b…` / `3a23685075fb…`). 교안은 "몇 분씩"이라 했으나 이 PC에서는 30초대였다. 레이어 10개 중 베이스 4개와 `COPY . .`는 같고 apt · WORKDIR · requirements 복사 · pip · useradd 5개는 달랐다(레이어와 Dockerfile 줄의 대응은 추정, 원인 파일은 확인하지 않음). 며칠 간격의 빌드는 재현하지 않았다

## 8. 과제 3(도전) — PDF 공지문 읽기

poppler로 PDF를 읽는 기능을 붙였는데, Dockerfile에 poppler 줄이 없던 로컬 컨테이너에서만 PDF가 500("PDF를 읽는 프로그램이 서버에 없습니다.")이었다. 원인은 컨테이너 로그의 `poppler 프로그램을 찾을 수 없습니다`와 `pdftoppm` 부재였고, apt 줄에 `poppler-utils`를 더해 해결했다(이미지 473MB). 줄이 필요한 이유는 한 문장이다. "PDF를 이미지로 바꾸는 `pdftoppm`이 운영체제 프로그램이라 `pip`로는 설치되지 않기 때문이다." 이번에는 staging에 가기 전에 **로컬 컨테이너에서 잡았다**. 테스트는 기존 12 + 새 3 = 15 passed였고, PR #22(staging, Cloud Build `aa4d5d58`)와 PR #23(production, Cloud Build `057dbfd2`, 내가 직접 승인) 뒤 같은 입력이 네 곳에서 같은 결과였다. staging·production 빌드도 패키지는 같고 이미지 ID는 달랐다.

| 입력 | 네 곳(로컬 · 로컬 컨테이너 · staging · production) 공통 결과 |
| --- | --- |
| 사진(PNG) | 200, 153글자, e61b2db05f |
| PDF 1쪽 | 200, 153글자, e61b2db05f |
| PDF 4쪽(앞 3쪽만) | 200, 461글자, 4ba6dbbc32 |
| 깨진 PDF | 500 PDF 파일을 읽을 수 없습니다 |

한계: 새 테스트 3개는 변환 함수를 가짜로 바꾸므로 poppler가 서버에 있는지는 검증하지 못한다. 확인은 컨테이너와 staging의 몫이었다.

## 10. 풀지 못한 것 · 교재와 달라진 것

- staging 서비스·수업 키 처리는 이번에 다루지 않았다(수업 키를 staging·production이 공유, 한도 분리 못 함)
- 이미지 태그·digest 관리, 검증한 이미지를 그대로 승격하는 흐름, 이미지 저장 공간 관리는 교안이 "다음 실습"으로 남긴 숙제라 하지 않았다
- 며칠 간격 빌드의 패키지 버전 변화와 `--clear-base-image` 누락 오류는 재현하지 않았다
- 과제 1의 브라우저 대화는 API로 대체했고, QR·HEIC·ffmpeg는 구현하지 않았다

그 밖의 항목과 교재와 달라진 12가지는 부록 6절·8절에 있다.

## 11. 정리

- 문제를 **코드 · 환경 · 배포 문제**로 가른다. CI 통과와 배포 성공은 "실행 환경이 맞다"는 증거가 아니다
- 새 기능을 붙일 때는 "파이썬 라이브러리 말고 **운영체제에 설치할 프로그램**이 있는가"를 먼저 묻는다(이번 tesseract와 poppler)
- Dockerfile은 5기준으로 점검하고 이미지 안을 열어 실제 내용(`.env` · `tests` · `docs` · `__pycache__`)을 확인한다
- 컨테이너는 실행할 때마다 이미지에서 새로 시작하고 컨테이너 메모리의 대화는 함께 사라진다
- **같은 Dockerfile이라고 같은 이미지는 아니다.** 패키지 목록이 같아도 이미지 ID는 달랐다
- 같은 입력을 여러 환경에 보내 결과(글자 수 · 해시)를 비교하면 "같은 환경"을 숫자로 말할 수 있다
- 다음: 이미지 태그·digest 관리, 한 번 만든 이미지를 그대로 승격하는 흐름, 저장 공간 관리

**Q. 로컬에서 되던 사진 읽기가 왜 staging에서만 500이었나?**

- 코드는 같았지만 staging 서버의 실행 환경에 tesseract가 없었고, 사진 요청이 들어온 순간에 실패해서 배포 성공·대화 정상으로 보였다. 원인은 Cloud Run 로그의 ERROR 한 줄에서 찾았다

**Q. 컨테이너를 지우고 다시 띄우면 대화가 왜 사라지나?**

- 대화는 컨테이너 메모리에 있고 컨테이너는 실행할 때마다 이미지에서 새로 시작한다. 이미지 ID는 그대로이고 메시지만 4개에서 0개가 됐다

**Q. 같은 Dockerfile로 staging과 production을 따로 빌드하면 같은 이미지인가?**

- 패키지 버전은 같았지만 이미지 ID는 달랐다(Cloud Build 두 빌드는 빌드마다 붙는 LABEL의 build_id가 달랐다. 로컬 `--no-cache` 두 빌드에서 어느 레이어 내용이 달랐는지는 원인 파일까지 확인하지 못했다). 같다고 말하려면 이미지를 한 번만 만들어 두 환경에 보내야 하는데 이번에는 하지 않았다

**Q. PDF 읽기에 `pip` 패키지(`pdf2image`)를 넣었는데 왜 Dockerfile 줄이 또 필요했나?**

- `pdf2image`는 파이썬 라이브러리이고, PDF를 이미지로 바꾸는 `pdftoppm`은 운영체제 프로그램이라 `pip`로 설치되지 않는다
