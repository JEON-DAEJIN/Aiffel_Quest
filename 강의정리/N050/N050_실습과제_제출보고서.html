[제출 보고서] N050 「Dockerfile로 실행환경 정하기」 실습 과제 수행 결과

수신: N050 강의 강사님 · 발신: 수강생 전대진(DJ)

실습일: 2026-10-26

과제 대상: N049에서 CI·staging·승인을 붙인 AI 친구 에이전트 서비스(friend-agent)에 "사진·PDF 속 글자를 읽어 입력창에 넣어 주는 기능(OCR)"을 켜고, 로컬에서는 되던 기능이 staging에서 실패하는 것을 재현한 뒤 Dockerfile로 서버의 실행 환경을 직접 정해 고치는 실습. 이어서 컨테이너 들여다보기(과제 1), 같은 Dockerfile 두 번 빌드(과제 2), PDF 읽기 추가(과제 3, 도전)까지 수행했다

평가 방법: 13번 "평가 체크리스트"를 보고 항목별로 점수와 한 줄 의견을 남겨 주세요.

📌 요약 — 이 문서는 노션 「강의정리 양식」 구조(한눈에 → 절별 기록 → 사고 표 → 정리 → 궁금했던 것)로 쓴 한눈에 읽는 보고서이다. 명령·로그·수치를 있는 그대로 남긴 상세 기록은 같은 폴더의 부록 N050_실습과제_제출보고서_부록_상세기록에 있다. 서비스 주소·프로젝트 번호·계정 정보는 싣지 않았다(요청마다 수업 키로 비용이 나가는 공개 서비스라서). 시각은 한국 시간(KST)이다.

코드가 같아도 서버의 실행 환경(운영체제 프로그램)이 없으면 기능이 안 된다. 그래서 pip가 아니라 운영체제에 설치할 프로그램을 Dockerfile에 적어 서버의 실행 환경을 직접 정하고, 같은 입력을 여러 곳에 보내 결과가 같은지로 확인했다.

  • 저장소: friend-agent (N049에서 이어 사용, 공개 상태)
  • 오늘 연 PR 4개(#20~#23), 모두 머지
  • Cloud Build 4번(615ce1d8 · 4718e203 · aa4d5d58 · 057dbfd2) 모두 SUCCESS, 로그에 buildpacks 언급 0줄
  • 배포 워크플로: staging 2번 · production 2번(둘 다 내가 직접 승인) · 손으로 친 환경변수 추가 2번(staging 리비전 00006, production 리비전 00019)
  • 실패가 드러난 것 2건: staging의 사진 읽기 500(일부러 재현, tesseract 없음), 로컬 컨테이너의 PDF 읽기 500(poppler 줄이 없던 상태에서 처음 드러남). 둘 다 Dockerfile의 설치 줄로 해결
  • 같은 사진 schedule.png → 로컬·로컬 컨테이너·staging·production 네 곳 모두 200 · 153글자 · 결과 해시 e61b2db05f

1. 시작 상태와 로컬 OCR (단계 1~2)

  • 읽기만 한 시작 점검에서 서비스 둘과 저장소 변수 4개, 워크플로 3개가 정상이었고 두 서비스 모두 OCR_ENABLED가 없었다. 내 PC의 tesseract는 영어(eng)·osd만 있고 한국어(kor)가 없었으며 Docker는 없었다
  • 한국어 데이터 kor.traineddata를 받아(11:28) 내가 관리자 PowerShell로 복사하고 Path를 등록한 뒤, 가짜 LLM으로 서버를 띄워 schedule.png를 보내자 200 · 153글자 · e61b2db05f. 이 값이 이후 모든 비교의 기준이다
  • 교재와 다르게 한 것: 저장소 변수가 교재는 5개(BUILD_SA 포함)인데 이 템플릿은 4개(N049에서 확인). kor를 설치해 "로컬이 한국어까지 되는 정상 환경"에서 시작. .env는 접근 규칙에 막혀 환경변수로 직접 넘겼다

2. staging에서 OCR 켜고 실패 재현 (단계 3)

무엇을 했나: staging에만 OCR_ENABLED=true를 추가하고 같은 사진을 보냈다(11:34~11:35). production은 건드리지 않았다.

무엇이 보였나: 서비스 루트와 /version은 정상인데 사진 요청은 HTTP 500이었다. API 응답은 {"detail":"사진에서 글자를 읽는 프로그램이 서버에 없습니다."}였고, 화면에는 "사진에서 글자를 읽지 못했어요: …"로 보였을 것이다(화면 캡처는 없음).

원인을 어디서 찾았나: Cloud Run 로그. 11:35:05에 리비전 friend-agent-staging-00006-dst가 tesseract 프로그램을 찾을 수 없습니다.라는 ERROR와 POST /api/ocr 500을 남겼다. 서비스는 정상 시작했고 사진 요청이 들어온 순간 프로그램을 부르다 실패한 것이라, 배포는 성공이고 대화 기능은 정상이었다.

처리: Dockerfile로 해결했다(5~6절).

3. 이미지·컨테이너 실험 (단계 4, 교안 3장)

  • 공식 이미지 python:3.13-slim-bookworm에는 tesseract가 없다. 컨테이너 note-a에 적은 /tmp/note.txt는 같은 이미지의 새 컨테이너에서 없었다
  • 포트 9000·9001은 둘 다 200이었고, 이미 쓰는 9000에 다른 컨테이너를 띄우면 port is already allocated(의도한 실패)가 났다. 컨테이너 4개는 지우고 이미지는 남겼다
  • 교재와 다르게 한 것: 포트 확인을 브라우저 대신 curl로 했다

4. Dockerfile 쓰고 로컬에서 빌드 (단계 5)

  • 템플릿 Dockerfile·.dockerignore를 복사해 5기준(베이스 고정 · tesseract와 kor 설치 · .env 제외 · ${PORT:-8080} · USER appuser)을 검토했고 모두 통과했다
  • 첫 빌드 이미지는 460MB였고, 컨테이너에서 같은 사진이 200 · 153글자 · e61b2db05f로 읽혔다. 이미지 안에는 .env·tests·docs가 없고 whoami는 appuser였다
  • 막힌 일: 이미지 안 /app/app/__pycache__에 .pyc 17개(내 PC의 .venv가 만든 cpython-314)가 들어 있었다. 템플릿 .dockerignore의 두 줄이 맨 위 폴더에만 적용돼서였다. 하위 폴더까지 적용되는 패턴(앞에 별표 두 개와 슬래시를 붙이는 방식, 모양은 부록 코드 블록 참조)으로 고쳐 재빌드하자 __pycache__와 .pyc가 0개가 됐고, 크기는 460MB 그대로였다
  • 교재와 달라진 것: 교재는 __pycache__가 "보이면" 고치라 했는데 실제로 나왔다. 교재의 레이어·이미지 크기와 이번 실측도 달랐다(교재 400MB대, 이번 460MB. 수치는 부록)

5. PR #20 — Dockerfile을 staging에 (단계 6)

  • deploy.yml에 --clear-base-image 한 단어만 추가했고(diff +1/−1) 커밋은 3파일(Dockerfile, .dockerignore, deploy.yml)이다. PR #20은 CI 통과 후 내가 머지를 승인해 c92135c가 됐다
  • Cloud Build 615ce1d8이 12:12~12:14에 SUCCESS(약 1분 14초). 로그에 Dockerfile 업로드와 apt-get install … tesseract-ocr tesseract-ocr-kor 단계가 있고 buildpacks 언급은 0줄이다
  • staging 새 리비전 friend-agent-staging-00007-94j에서 같은 사진이 200, 로그에 ERROR가 없었다. OCR_ENABLED=true는 배포 후에도 유지됐다. 화면에서는 📷 버튼으로 사진을 고르면 입력창에 일정 세 줄이 들어갔다(내가 직접 사진을 골라 캡처)
  • 교재와 다르게 한 것: --clear-base-image를 교재 안내대로 처음부터 추가해서 이 옵션이 없을 때의 Missing required argument 오류는 직접 본 적이 없다

6. production 배포 (단계 7)

  • staging→main PR #21(머지 23b49b1)의 배포가 승인 대기에서 멈췄고 내가 직접 승인했다(캡처 10b). 머지(12:40)부터 빌드 시작(13:45)까지 대기가 약 1시간이었고 이유는 기록이 없다. Cloud Build 4718e203이 SUCCESS했고 production 리비전 friend-agent-00018-klq가 100%가 됐다

7. 과제 1·2 — 컨테이너 들여다보기, 같은 Dockerfile 두 번 빌드

  • 과제 1: 실행 중인 컨테이너를 docker exec로 열어 보니 appuser, /app, .env·tests·docs 없음이었다. 대화 두 턴 뒤 메시지 4개였는데 컨테이너를 지우고 같은 이미지(ID 불변)로 다시 띄우자 0개가 됐다. Git Bash curl -d의 한글 JSON은 HTTP 400이 나서 파이썬 UTF-8 전송으로 확인했다. 교재와 다르게 브라우저 대신 API로 확인했다(화면 캡처 없음)
  • 과제 2: --no-cache로 두 번 빌드하자 pip freeze 30줄과 deb 159개는 같고 이미지 ID는 달랐다(8d665740853b… / 3a23685075fb…). 교안은 "몇 분씩"이라 했으나 이 PC에서는 30초대였다. 레이어 10개 중 베이스 4개와 COPY . .는 같고 apt · WORKDIR · requirements 복사 · pip · useradd 5개는 달랐다(레이어와 Dockerfile 줄의 대응은 추정, 원인 파일은 확인하지 않음). 며칠 간격의 빌드는 재현하지 않았다

8. 과제 3(도전) — PDF 공지문 읽기

poppler로 PDF를 읽는 기능을 붙였는데, Dockerfile에 poppler 줄이 없던 로컬 컨테이너에서만 PDF가 500("PDF를 읽는 프로그램이 서버에 없습니다.")이었다. 원인은 컨테이너 로그의 poppler 프로그램을 찾을 수 없습니다와 pdftoppm 부재였고, apt 줄에 poppler-utils를 더해 해결했다(이미지 473MB). 줄이 필요한 이유는 한 문장이다. "PDF를 이미지로 바꾸는 pdftoppm이 운영체제 프로그램이라 pip로는 설치되지 않기 때문이다." 이번에는 staging에 가기 전에 로컬 컨테이너에서 잡았다. 테스트는 기존 12 + 새 3 = 15 passed였고, PR #22(staging, Cloud Build aa4d5d58)와 PR #23(production, Cloud Build 057dbfd2, 내가 직접 승인) 뒤 같은 입력이 네 곳에서 같은 결과였다. staging·production 빌드도 패키지는 같고 이미지 ID는 달랐다.

10. 풀지 못한 것 · 교재와 달라진 것

  • staging 서비스·수업 키 처리는 이번에 다루지 않았다(수업 키를 staging·production이 공유, 한도 분리 못 함)
  • 이미지 태그·digest 관리, 검증한 이미지를 그대로 승격하는 흐름, 이미지 저장 공간 관리는 교안이 "다음 실습"으로 남긴 숙제라 하지 않았다
  • 며칠 간격 빌드의 패키지 버전 변화와 --clear-base-image 누락 오류는 재현하지 않았다
  • 과제 1의 브라우저 대화는 API로 대체했고, QR·HEIC·ffmpeg는 구현하지 않았다

그 밖의 항목과 교재와 달라진 12가지는 부록 6절·8절에 있다.

11. 정리

  • 문제를 코드 · 환경 · 배포 문제로 가른다. CI 통과와 배포 성공은 "실행 환경이 맞다"는 증거가 아니다
  • 새 기능을 붙일 때는 "파이썬 라이브러리 말고 운영체제에 설치할 프로그램이 있는가"를 먼저 묻는다(이번 tesseract와 poppler)
  • Dockerfile은 5기준으로 점검하고 이미지 안을 열어 실제 내용(.env · tests · docs · __pycache__)을 확인한다
  • 컨테이너는 실행할 때마다 이미지에서 새로 시작하고 컨테이너 메모리의 대화는 함께 사라진다
  • 같은 Dockerfile이라고 같은 이미지는 아니다. 패키지 목록이 같아도 이미지 ID는 달랐다
  • 같은 입력을 여러 환경에 보내 결과(글자 수 · 해시)를 비교하면 "같은 환경"을 숫자로 말할 수 있다
  • 다음: 이미지 태그·digest 관리, 한 번 만든 이미지를 그대로 승격하는 흐름, 저장 공간 관리

12. 궁금했던 것

아래 질문은 이번 실습의 사고 표에서 뽑은 것이다.

Q. 로컬에서 되던 사진 읽기가 왜 staging에서만 500이었나?

  • 코드는 같았지만 staging 서버의 실행 환경에 tesseract가 없었고, 사진 요청이 들어온 순간에 실패해서 배포 성공·대화 정상으로 보였다. 원인은 Cloud Run 로그의 ERROR 한 줄에서 찾았다

Q. 컨테이너를 지우고 다시 띄우면 대화가 왜 사라지나?

  • 대화는 컨테이너 메모리에 있고 컨테이너는 실행할 때마다 이미지에서 새로 시작한다. 이미지 ID는 그대로이고 메시지만 4개에서 0개가 됐다

Q. 같은 Dockerfile로 staging과 production을 따로 빌드하면 같은 이미지인가?

  • 패키지 버전은 같았지만 이미지 ID는 달랐다(Cloud Build 두 빌드는 빌드마다 붙는 LABEL의 build_id가 달랐다. 로컬 --no-cache 두 빌드에서 어느 레이어 내용이 달랐는지는 원인 파일까지 확인하지 못했다). 같다고 말하려면 이미지를 한 번만 만들어 두 환경에 보내야 하는데 이번에는 하지 않았다

Q. PDF 읽기에 pip 패키지(pdf2image)를 넣었는데 왜 Dockerfile 줄이 또 필요했나?

  • pdf2image는 파이썬 라이브러리이고, PDF를 이미지로 바꾸는 pdftoppm은 운영체제 프로그램이라 pip로 설치되지 않는다
