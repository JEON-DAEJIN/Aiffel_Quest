핵심 한 문장 요약

📌 요약 — 코드가 한 글자도 다르지 않은데 "내 컴퓨터에서는 되고 서버에서는 안 되는" 이유는 코드가 아니라 실행 환경이 달랐기 때문이다 — 그래서 베이스 이미지·시스템 패키지·시크릿 제외·포트·실행 사용자를 Dockerfile 한 파일에 적어 저장소에 넣고, 로컬 컨테이너에서 검증한 뒤 기존 자동 배포(staging → production)에 그대로 태운다.

이번 강의는 N049에서 만든 품질 게이트(CI·staging·브랜치 보호·배포 승인)가 붙은 AI 친구 에이전트 서비스(friend-agent, 줄여서 에이전트 서비스)에 새 기능 하나를 붙이면서 시작한다. 동아리 공지나 수업 일정표 사진을 보내면 글자를 읽어 입력창에 넣어 주고, 거기 적힌 일정을 약속으로 저장하게 하는 기능(OCR)이다. 이 기능의 코드는 이미 PR로 들어와 CI를 통과했고 staging과 production에 자동 배포돼 있다. 그런데 staging에서 켜 보면 사진을 읽지 못한다. 이 한 장면에서 출발해, 원인을 로그로 찾고, 이미지와 컨테이너를 구분하고, Dockerfile을 쓰고 검토하고, 로컬에서 빌드해 실행하고, 자동 배포에 올려 빌드 기록으로 확인한 뒤, 마지막에 "아직 남은 숙제"까지 짚는다.

코드는 한 글자도 다르지 않다. 기능의 기본값이 꺼짐이라 아직 아무도 쓰지 못했을 뿐, 배포는 이미 끝나 있었다. 이 네 가지 사실(로컬 성공 · 배포 성공 · 대화 기능 정상 · staging OCR만 실패)을 연결해 원인을 찾아가는 것이 이번 강의의 뼈대다.

🧪 예제 — [해설서 비유] 식당에서 요리한다고 생각해 보자. 내 컴퓨터는 요리사와 조리 도구, 재료가 모두 준비된 주방이다. 서버는 똑같은 요리사가 있지만 필요한 조리 도구 하나가 없는 주방이다. 코드는 요리사가 따라 하는 레시피다. 레시피가 똑같아도 도구가 없으면 요리를 완성할 수 없다.

buildpacks와 Dockerfile — 자동으로 준비해 주는 서비스 vs 상세 작업 지시서

지금까지의 배포 방식(소스 배포)에서는 코드를 올리면 Cloud Run이 buildpacks(소스 코드를 보고 이미지를 자동으로 만드는 도구)로 실행 환경을 알아서 꾸려 이미지를 만들어 준다. buildpacks는 Python 버전과 라이브러리처럼 코드에 적혀 있는 것은 잘 챙긴다. 하지만 운영체제에 따로 설치해야 하는 시스템 패키지(apt 패키지처럼 운영체제에 설치하는 프로그램)는 코드만 보고 알 수 없다.

💡 팁 — [보충 비유] 프랜차이즈 본사가 새 점포를 열 때 "주방 설비 목록 + 표준 조리 순서"를 문서로 내려보내면 어느 지점에서든 같은 맛이 나온다. 점주가 알아서 준비하게 두면 지점마다 빠지는 설비가 생긴다. Dockerfile은 이 설비 목록·표준서에 해당한다.

오늘의 학습 목표 다섯 가지

  1. 로컬 환경에서는 되는데 서버에서는 안 되는 상황에서 로그로 원인을 찾고, buildpacks가 만든 이미지에 무엇이 들어 있고 무엇이 빠지는지 설명한다.
  2. 이미지와 컨테이너의 차이를 설명하고, Docker Desktop 화면에서 둘을 구분한다.
  3. Dockerfile을 한 줄씩 읽고 베이스 이미지(Dockerfile이 출발점으로 삼는 이미지), 설치할 시스템 패키지, 시크릿 제외, 포트, 실행 사용자를 기준으로 검토한다.
  4. 로컬에서 이미지를 빌드해 컨테이너로 실행하고, API 키를 이미지에 넣지 않고 실행할 때 건네는 이유를 설명한다.
  5. Dockerfile이 있는 저장소를 환경별 자동 배포로 staging과 production에 올리고, 빌드 기록에서 Dockerfile이 쓰였는지 확인한다.

2-2. OCR이 무엇이고 왜 시스템 패키지가 필요한가

사진 속 글자를 읽는 기능을 OCR(광학 문자 인식, 이미지 속 글자를 텍스트로 바꾸는 기술)이라고 한다. 이 기능의 코드는 템플릿 저장소 app/ocr.py에 이미 들어 있고, 환경변수 OCR_ENABLED로 켜고 끈다. 기본값은 꺼짐이라 켜기 전에는 화면에 사진 버튼(📷)이 보이지 않는다.

사진을 받으면 pytesseract라는 Python 라이브러리로 글자를 읽는데, 이 라이브러리는 직접 글자를 읽지 않고 운영체제에 설치된 tesseract라는 프로그램을 불러 쓰는 래퍼(wrapper) 라이브러리다.

🧪 예제 — [해설서 비유] pytesseract는 "통역을 요청하는 사람"이고 tesseract는 "실제로 글자를 읽는 도구"다. 통역을 부탁하는 사람만 있고 통역사가 없으면 번역이 안 된다.

그래서 OCR이 돌려면 세 가지가 모두 필요하다.

필요한 것설치 방법역할
① pytesseractrequirements.txt → piptesseract를 부르는 Python 라이브러리
② tesseract 프로그램운영체제 시스템 패키지(apt, brew 등)실제로 글자를 읽는 프로그램
③ kor 언어 데이터시스템 패키지(tesseract-ocr-kor 등)한국어를 읽기 위한 글자 데이터

requirements.txt로 라이브러리를 설치하는 것만으로는 부족하다. ②와 ③을 운영체제에 따로 설치해야 하고, 이렇게 Python 라이브러리 밖에 있는 프로그램이나 파일을 해설서는 시스템 의존성이라고 부른다.

2-3. 로컬 환경에 tesseract 설치하고 OCR 켜기

먼저 내 컴퓨터에 tesseract를 설치한다.

  • macOS: Homebrew로 프로그램과 언어 데이터를 함께 설치한다(brew install tesseract tesseract-lang). 설치 후 tesseract --list-langs에 kor가 있어야 한국어를 읽는다.
  • Windows: tesseract 공식 안내가 권하는 UB Mannheim 설치 파일(tesseract-ocr-w64-setup-…exe)을 받아 실행한다. 설치 중 Choose Components 화면에서 Additional language data(download)를 펼쳐 Korean에 체크하고, 설치 폴더는 기본값(C:\Program Files\Tesseract-OCR)으로 둔다. 설치가 끝나면 "시스템 환경 변수 편집"에서 사용자 변수 Path에 그 폴더를 추가한 뒤, 열려 있던 터미널과 VS Code를 모두 닫았다가 다시 연다. 새 터미널에서 tesseract --version과 tesseract --list-langs(kor 확인)로 점검한다.

⚠️ 주의 — 코딩 에이전트가 sudo로 root 권한(운영체제 전체를 바꿀 수 있는 최고 권한)을 요구하는 명령을 제안하면, 무엇을 바꾸는지 다시 묻고 판단한다. Homebrew 설치에는 보통 필요하지 않다. 언어 목록에 kor가 없으면 기능은 동작하지만 영어로만 읽고, 서비스 로그에 한국어 데이터가 없다는 경고가 남는다.

이제 .env에 OCR_ENABLED=true 한 줄을 넣고 서비스를 로컬에서 실행한다(부록 A-3). 입력창 왼쪽에 사진 버튼(📷)이 생기면 템플릿의 data/samples/schedule.png(산책 동아리 10월 일정 세 줄이 적힌 사진)를 고른다. 잠시 뒤 입력창에 "사진에서 읽은 글이야"로 시작하는 문장과 일정 세 줄이 들어온다. 읽은 글자가 틀렸으면 입력창에서 고친 뒤 보내고, 보내면 에이전트 서비스가 일정 가운데 하나를 약속으로 저장하며 오른쪽 "이번 턴" 패널에 약속 저장 도구가 선택된 것이 보인다.

2-4. staging에서 같은 기능 켜기 — `--update-env-vars`

이제 staging에서도 기능을 켠다. 코드는 이미 배포돼 있으므로 staging 서비스의 환경변수만 하나 추가하면 된다. 환경변수를 바꾸면 새 리비전이 만들어지고, 자동 배포 워크플로는 기존 환경변수를 지우지 않고 합치는 방식으로 배포하므로 이후 배포에서도 이 값이 유지된다. production은 아직 건드리지 않는다.

실행하기 전에 서비스 이름이 friend-agent-staging인지, 옵션이 기존 값을 지우는 --set-env-vars가 아니라 추가하는 --update-env-vars인지 확인한다.

옵션동작
--update-env-vars지정한 환경변수를 추가하거나 해당 값만 갱신

⚠️ 주의 — 해설서가 짚은 구분: OCR 기능을 켜는 것과 OCR이 실제로 작동하도록 실행 환경을 갖추는 것은 서로 다른 작업이다. 이번 단계에서는 앞의 것만 했다.

배포가 끝나면 staging 주소를 열어 같은 사진을 보낸다. 이번에는 "사진에서 글자를 읽지 못했어요: 사진에서 글자를 읽는 프로그램이 서버에 없습니다."라는 안내가 뜬다.

2-5. 로그에서 원인 찾기

화면의 안내는 결과만 말해 준다. 화면만 보고 원인을 단정하지 않고, Cloud Run 로그에서 같은 시각에 남은 오류 줄을 찾는다.

  1. Cloud Run에서 friend-agent-staging 서비스를 열고 로그(Logs) 탭으로 간다.
  2. 심각도를 오류(Error)로 거르고, 사진을 보낸 시각 근처의 줄을 연다.
  3. 같은 시각에 POST /api/ocr 요청이 상태 코드 500으로 남았는지도 확인한다.

2-7. 왜 CI 테스트는 이 문제를 못 잡았을까

CI가 통과했다는 것은 테스트에서 확인한 조건이 충족됐다는 뜻이지 모든 운영 환경이 완벽하다는 뜻이 아니다. 이번 사례에는 두 가지 이유가 있다.

  1. 템플릿의 OCR 테스트는 기능이 꺼져 있을 때 요청을 거절하는지만 확인한다. 실제로 사진을 읽는 데 필요한 시스템 프로그램까지는 검증하지 않는다.
  2. 테스트가 도는 GitHub 러너와 staging 이미지는 서로 다른 실행 환경이다. 러너에서 통과했다고 staging 이미지에 tesseract가 있다는 뜻이 되지 않는다.

이 문제를 풀려면 실행 환경을 만드는 방법 자체를 적어 저장소에 넣어야 하고, 그 파일이 Dockerfile이다.

객관식 퀴즈 — staging에서 OCR이 실패했는데 배포는 성공했고 다른 대화 기능도 정상이었습니다. 이유로 가장 알맞은 것은?

① Cloud Run이 tesseract 없이도 시작할 수 있도록 오류를 숨겨 주기 때문이다 ② 앱은 시작할 때 tesseract를 확인하지 않고, 사진 요청이 들어와 프로그램을 부를 때에야 없다는 것을 알게 되기 때문이다 ③ staging에서는 OCR_ENABLED가 꺼져 있어서 기능이 실행되지 않았기 때문이다 ④ buildpacks가 tesseract를 설치했지만 한국어 데이터만 빠졌기 때문이다

정답: ② ①은 Cloud Run이 오류를 숨긴 것이 아니라 요청 처리 중 오류가 난 것이다. ③은 staging에서 OCR_ENABLED=true로 켰기 때문에 OCR 요청이 실행됐다. ④는 한국어 데이터만 빠진 것이 아니라 tesseract 프로그램 자체를 찾지 못한 것이다.

3. 이미지와 컨테이너의 차이

Dockerfile을 쓰기 전에 Docker가 다루는 두 가지를 구분해 둔다.

  • 이미지(image): 운영체제 기본 파일, 프로그램, 라이브러리, 코드, 시작 명령까지 실행에 필요한 것을 모두 묶어 둔 파일. 한 번 만들면 내용이 바뀌지 않는다.
  • 컨테이너(container): 그 이미지를 실행한 것. 같은 이미지로 컨테이너를 여러 개 띄울 수 있고, 컨테이너마다 자기 메모리와 파일 변경을 따로 가진다.

🧪 예제 — [해설서 비유] 이미지는 붕어빵 틀과 재료를 갖춘 준비물, 컨테이너는 그 준비물로 실제로 만들어 낸 붕어빵이다. 붕어빵 하나를 먹어 치워도 틀과 재료(이미지)는 그대로 남아 있고, 같은 준비물로 붕어빵을 몇 개든 만들 수 있다. Dockerfile은 이 준비물을 만드는 방법을 적은 문서다. 컨테이너 안에서 파일을 바꿔도 원본 이미지는 자동으로 바뀌지 않는다.

이 구조로 N048·N049에서 겪은 현상이 설명된다. 에이전트 서비스는 대화 기록을 컨테이너의 메모리에 둔다. 새 리비전을 배포하면 새 컨테이너가 실행되고, 새 컨테이너는 이전 컨테이너의 메모리를 자동으로 이어받지 않는다. 그래서 새 리비전을 배포할 때마다 대화 기록이 사라졌다. 서비스가 재시작되거나 인스턴스가 교체돼도 유지돼야 하는 데이터는 Supabase 같은 외부 데이터베이스(영속 저장소)에 보관해야 한다.

이미지 안에 키 같은 시크릿을 넣지 않는 이유도 여기서 나온다. 이미지는 저장소에 올라가 여러 곳에서 내려받아 실행되는 파일이므로, 안에 든 값은 이미지를 받은 누구나 꺼내 볼 수 있다.

3-2. Docker Desktop 준비

이 장부터는 로컬 환경에서 Docker를 쓴다. Docker Desktop은 macOS와 Windows에서 컨테이너를 실행할 수 있게 해 주는 프로그램으로, 컨테이너가 쓰는 리눅스 환경을 컴퓨터 안에 띄우고 docker 명령과 이미지·컨테이너를 보는 화면을 함께 제공한다. 이미 설치돼 있다면 Docker Desktop을 켜고 docker --version과 docker info만 실행한다. 둘 다 오류 없이 결과가 나오면 준비 완료다. docker info가 데몬(daemon, 실제로 이미지를 만들고 컨테이너를 실행하는 프로그램)에 연결할 수 없다는 오류를 내면 Docker Desktop이 꺼져 있는 것이니 켠 뒤 다시 실행한다.

없을 때 설치하는 순서(원문):

  1. Docker Desktop 내려받기 페이지에서 내 운영체제에 맞는 설치 파일을 받는다. macOS는 Apple Silicon(M 시리즈)과 Intel 칩 가운데 내 컴퓨터에 맞는 것을 고른다(Apple 메뉴 > 이 Mac에 관하여).
  2. macOS는 Docker.dmg를 열어 Docker 아이콘을 응용 프로그램 폴더로 끌어넣고 실행한다. Windows는 설치 파일을 실행하며 설정 화면에서 WSL 2(Windows 안에서 리눅스를 실행하는 기능)를 사용하는 옵션을 켠 채 설치한다. 설치 중 함께 켜지거나 재시작을 요구할 수 있다.
  3. 처음 실행하면 이용 약관에 동의하고 Docker Hub 계정으로 로그인한다. 계정이 없으면 무료로 만든다. 강의실처럼 여러 사람이 같은 인터넷 주소를 쓰면 로그인하지 않은 이미지 내려받기가 횟수 제한에 금방 걸리기 때문이다.
  4. 화면 아래쪽에 엔진이 실행 중(Engine running)이라고 나오면 새 터미널에서 확인 명령을 실행한다.

⚠️ 주의 — 설치 중 막히는 곳은 운영체제마다 다르다. macOS는 칩에 맞지 않는 설치 파일을 받으면 실행되지 않고, Windows는 WSL 2가 켜지지 않았거나 BIOS에서 가상화 기능이 꺼져 있으면 엔진이 시작되지 않는다. 회사 컴퓨터에 설치한다면 Docker Desktop은 직원 250명 이상이거나 매출이 일정 규모를 넘는 회사에서 쓸 때 유료 구독이 필요하다. 개인 컴퓨터와 교육 목적으로는 무료다.

3-3. 공식 Python 이미지 실행해 보기 — 여기에도 tesseract는 없다

Docker가 공식으로 배포하는 Python 이미지(python:3.13-slim-bookworm, 이후 Dockerfile의 베이스 이미지로 쓸 것과 같다)를 내려받아 컨테이너로 실행한다(부록 A-5). 첫 줄은 Python 3.13 버전을 출력하고, 둘째 줄은 "tesseract 없음"을 출력한다. --rm은 실행이 끝나면 컨테이너를 자동으로 지우라는 옵션이고 이미지는 남아 다음 실행에서 재사용된다.

공식 Python 이미지에도 tesseract는 없다. Python이 설치된 이미지라고 해서 OCR에 필요한 모든 외부 프로그램까지 들어 있는 것은 아니므로, 이 이미지 위에 설치하는 줄을 Dockerfile에 넣어야 한다.

3-4. 컨테이너끼리 나누지 않는 것

컨테이너 하나 안에 파일을 만들고, 같은 이미지로 새 컨테이너를 띄워 그 파일이 보이는지 확인한다(부록 A-6). 첫 컨테이너(note-a)는 --rm 없이 실행해 끝난 뒤에도 남겨 둔다.

실행 단계결과
첫 컨테이너 note-a 안에서 /tmp/note.txt에 "메모"를 쓰고 읽기메모
같은 이미지로 새 컨테이너에서 같은 파일 읽기파일 없음
docker rm note-anote-a 컨테이너가 삭제됨

두 컨테이너는 같은 이미지에서 시작했지만 한쪽에서 생긴 파일을 다른 쪽이 보지 못한다. docker rm note-a 전에 Docker Desktop을 열어 보면 이미지(Images) 화면에는 python:3.13-slim-bookworm이 한 줄, 컨테이너(Containers) 화면에는 실행이 끝난 note-a가 보인다(--rm으로 실행한 컨테이너는 이미 지워져 목록에 없다). docker rm note-a는 컨테이너를 지우는 명령이지 이미지를 지우는 명령이 아니므로, 지우기 전에 대상이 컨테이너 note-a인지 확인한다.

💡 팁 — 해설서의 단서: 이 실험은 컨테이너 내부의 임시 파일을 쓴 경우다. 볼륨이나 외부 저장소를 연결하면 여러 컨테이너가 같은 데이터를 공유하도록 구성할 수 있다.

객관식 퀴즈 — 같은 이미지로 컨테이너 두 개를 실행했고 첫 컨테이너 안에서 /tmp/note.txt를 만들었습니다. 둘째 컨테이너에서 읽으면?

① 같은 이미지에서 시작했으므로 파일이 보인다 ② 파일이 보이지 않는다. 파일은 첫 컨테이너 안에서만 생긴 변경이고 이미지는 바뀌지 않았다 ③ 첫 컨테이너가 실행 중일 때만 보인다 ④ 첫 컨테이너를 지우면 그때부터 보인다

정답: ② 파일은 첫 컨테이너의 파일 변경 사항이며 원본 이미지나 둘째 컨테이너에 자동으로 반영되지 않는다.

3-5. 포트로 컨테이너에 요청 보내기

지금까지 실행한 컨테이너는 명령 하나를 실행하고 바로 끝났다. 에이전트 서비스처럼 웹 서버를 담은 컨테이너는 켜진 채로 요청을 기다리는데, 바깥에서 요청을 보내려면 포트를 알아야 한다. 포트(port)는 한 컴퓨터에서 여러 프로그램이 네트워크를 함께 쓸 때 들어온 연결을 어느 프로그램에 줄지 정하는 번호다. 주소 localhost가 어느 컴퓨터인지를 가리킨다면 :9000 같은 포트는 그 컴퓨터의 어느 프로그램인지를 가리키고, 한 포트에서는 한 프로그램만 기다릴 수 있다.

컨테이너는 파일뿐 아니라 네트워크도 따로 가진다. 컨테이너 안의 프로그램이 8000번에서 기다려도 내 컴퓨터의 8000번과는 이어져 있지 않다. 둘을 잇는 것이 docker run의 -p 9000:8000이다.

표기의미
-p 9000:8000의 앞 숫자 9000내 컴퓨터의 포트
-p 9000:8000의 뒤 숫자 8000컨테이너 안의 포트
동작내 컴퓨터의 9000번으로 들어온 요청을 Docker가 컨테이너의 8000번으로 넘기고, 응답을 받아 그대로 돌려줌

공식 Python 이미지에 들어 있는 간단한 웹 서버(python -m http.server 8000)로 같은 이미지에서 컨테이너를 두 개 띄워 확인한다(부록 A-7). 결과는 다음과 같다.

확인결과
브라우저로 http://localhost:9000, http://localhost:9001둘 다 컨테이너 안 폴더의 파일 목록이 보임
브라우저로 http://localhost:8000열리지 않음 — 컨테이너 안 8000번은 내 컴퓨터 8000번과 이어져 있지 않음
docker ps같은 이미지로 띄운 컨테이너 두 줄, 포트 칸에 9000->8000, 9001->8000
세 번째 컨테이너를 -p 9000:8000으로 띄우기port is already allocated 오류 — 내 컴퓨터 9000번에서는 이미 web-a로 가는 연결이 기다리고 있음

컨테이너마다 네트워크가 따로라서 컨테이너 안의 포트는 모두 같은 번호를 써도 부딪히지 않는다. 그래서 안쪽 포트는 이미지가 한 번 정해 두고, 여러 개를 띄울 때는 바깥 포트만 바꾼다. 정리 명령 docker rm -f web-a web-b web-c는 해당 이름의 컨테이너를 강제로 종료하고 삭제하므로, 실행 전에 실습용 컨테이너 이름인지 확인한다.

3-6. Cloud Run과 PORT 환경변수

Cloud Run은 이 연결을 대신 해 준다. 요청을 보낼 컨테이너 안의 포트를 PORT 환경변수(기본값 8080)로 알려 준다. 그래서 에이전트 서비스는 포트 번호를 코드에 박아 두지 않고 PORT 환경변수를 읽어 그 번호에서 기다리게 만든다(4장 체크리스트에서 이 점을 확인한다). 예를 들어 docker run -p 9000:8080 friend-agent:local로 띄웠다면 접속 주소는 http://localhost:9000이다. 앞의 9000은 내 컴퓨터 포트, 뒤의 8080은 컨테이너 내부 포트이기 때문이다.

객관식 퀴즈 — docker run -p 9000:8080 friend-agent:local 로 띄웠습니다. 브라우저에서 서비스를 열려면?

① http://localhost:8080 ② http://localhost:9000 ③ 두 주소 모두 열린다 ④ 컨테이너 안에서만 열 수 있다

정답: ② 앞의 9000은 내 컴퓨터의 포트, 뒤의 8080은 컨테이너 내부 포트다. 내 컴퓨터의 8080은 이어져 있지 않다.

3-7. 이 장이 AI 서비스 운영에서 주는 세 가지 원칙 (해설서)

  1. 실행 환경의 재현성: 같은 이미지를 사용해 일관된 실행 환경을 구성할 수 있다.
  2. 데이터의 지속성: 컨테이너의 메모리나 임시 파일에만 데이터를 보관하면 재시작이나 교체 시 사라질 수 있다.
  3. 서비스 접근성: 포트 연결을 이해해야 로컬에서 컨테이너 안의 웹 서비스에 접속할 수 있다.

📌 요약 — Docker 이미지는 실행 환경을 담은 패키지이고 컨테이너는 그 패키지를 실행한 독립적인 인스턴스다. 둘의 차이를 이해해야 데이터·네트워크·배포를 올바르게 관리할 수 있다.

4. Dockerfile에 적을 것

2장에서 서버에 빠져 있던 것은 tesseract와 한국어 데이터였고, 3장에서 공식 Python 이미지에도 tesseract가 없다는 것을 확인했다. Dockerfile에는 이 둘을 포함해 실행 환경을 처음부터 끝까지 적는다. 어떤 베이스 이미지에서 출발할지, 어떤 시스템 패키지와 라이브러리를 설치할지, 코드를 어디에 둘지, 누구의 권한으로 어떤 명령으로 실행할지다.

🧪 예제 — [해설서 비유] 새 식당을 여러 곳에 열어도 같은 음식을 만들 수 있도록 조리법과 준비물 목록을 적어 놓는 것과 같다. 어떤 Python 환경에서 시작할 것인가, 어떤 프로그램과 라이브러리를 설치할 것인가, 소스 코드를 어디에 둘 것인가, 어떤 사용자 권한으로 실행할 것인가, 컨테이너가 시작되면 어떤 명령을 실행할 것인가를 적는다.

Dockerfile은 코딩 에이전트에게 쓰게 하거나 템플릿의 예시 파일(starter/Dockerfile, starter/dockerignore)을 복사해 쓴다. 에이전트에게 맡길 때도 무엇을 넣어야 하는지는 요청문에 직접 적는다. 에이전트는 요청받은 대로 파일을 쓸 뿐, Python 버전을 고정할지, root 사용자로 실행할지 같은 판단을 대신 정해 주지 않는다.

4-1. 한 줄씩 읽기

아래는 템플릿 예시에서 설명 주석을 뺀 Dockerfile이다. 에이전트가 쓴 파일과 줄 순서나 표현이 조금 달라도 괜찮고, 표의 각 줄이 하는 일이 들어 있는지를 본다.

FROM python:3.13-slim-bookworm
RUN apt-get update \
    && apt-get install -y --no-install-recommends tesseract-ocr tesseract-ocr-kor \
    && rm -rf /var/lib/apt/lists/*
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
RUN useradd --create-home appuser
USER appuser
CMD ["sh", "-c", "uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8080}"]
줄하는 일
FROM python:3.13-slim-bookworm공식 Python 3.13 이미지(Debian bookworm 기반의 작은 버전)에서 시작. python:3.13은 버전, slim은 비교적 작은 이미지, bookworm은 Debian 운영체제 기반
RUN apt-get ... tesseract-ocr tesseract-ocr-kor시스템 패키지 tesseract와 한국어 데이터 설치(apt-get update는 설치 가능한 패키지 목록 갱신). 마지막에 내려받은 패키지 목록(rm -rf /var/lib/apt/lists/*)을 지워 이미지 크기를 줄임. 이 줄이 2장 OCR 오류를 푸는 핵심
WORKDIR /app이후 명령을 실행하고 파일을 둘 폴더. 파일 복사·명령 실행의 기준이 됨
COPY requirements.txt . 과 RUN pip install라이브러리 목록만 먼저 복사해 설치
COPY . .나머지 코드 복사. .dockerignore에 적힌 파일은 빠짐
RUN useradd 과 USER appusernon-root 사용자(root 권한이 없는 일반 사용자) appuser를 만들고 그 사용자로 실행
CMD [...]컨테이너가 시작할 때 실행할 명령. --host 0.0.0.0은 컨테이너 바깥에서 들어오는 요청을 받도록 바인딩, ${PORT:-8080}은 PORT 값이 있으면 그 값, 없으면 8080

⚠️ 주의 — pytesseract와 tesseract-ocr는 서로 다른 역할이다. 전자는 Python 라이브러리(requirements.txt), 후자는 운영체제 수준에서 설치하는 실제 OCR 프로그램(apt-get)이다. Dockerfile에 둘 다 있어야 한다.

root로 앱을 실행하면 보안 문제가 생겼을 때 공격자가 할 수 있는 일이 더 많아진다. 일반 사용자로 실행하면 이 위험을 줄이는 데 도움이 된다. python:latest 대신 구체적인 버전을 쓰면 빌드 시점에 따라 Python 버전이 달라질 위험을 줄일 수 있다.

4-2. 레이어와 레이어 캐시

이미지는 Dockerfile의 줄을 따라 쌓이는데, 줄 하나가 만든 파일 변경을 묶은 단위를 레이어(layer)라고 한다. 원문의 그림은 레이어마다 크기를 이렇게 보여 준다(2026년 10월 로컬 빌드 기준).

Dockerfile 줄의미레이어 크기
FROM python:3.13-slim-bookworm베이스 이미지약 225MB
RUN apt-get install … tesseract-ocr tesseract-ocr-kor시스템 패키지약 95MB
COPY requirements.txt . + RUN pip install -r requirements.txt라이브러리약 89MB
COPY . .에이전트 서비스 코드약 0.2MB
RUN useradd … / USER appusernon-root 사용자거의 0
CMD … --port ${PORT:-8080}시작 명령0
레이어 1 베이스 이미지
Python 3.13 + Debian
→
레이어 2 시스템 패키지
tesseract + kor
→

자주 바뀜

빌드할 때 Docker는 위에서부터 내려오며 내용이 바뀌지 않은 줄은 이전 빌드에서 만든 레이어를 다시 쓰고, 처음 바뀐 줄부터 아래를 새로 만든다. 이렇게 이전 레이어를 다시 쓰는 것이 레이어 캐시다. 시간이 오래 걸리는 시스템 패키지와 라이브러리 설치를 위에 두고, 자주 바뀌는 코드 복사를 아래에 둔 이유다. requirements.txt만 먼저 복사한 것도 같은 이유로, 코드 전체를 먼저 복사했다면 코드 한 줄만 고쳐도 라이브러리 설치를 매번 다시 했을 것이다. 이미지 크기는 베이스 이미지와 tesseract, 라이브러리가 대부분을 차지하고 코드는 1MB도 되지 않는다. 해설서의 단서: 이 레이어 그림은 개념도이며 실제 레이어 경계는 Docker 명령과 빌드 방식에 따라 달라질 수 있다.

4-3. `.dockerignore` — 무엇을 이미지에 넣지 않을까

COPY . .은 폴더 전체를 이미지에 넣으므로, 빼야 할 파일을 .dockerignore에 적는다. 원문과 해설서가 언급하는 항목은 이렇다.

항목이유
.envAPI 키 등 민감한 환경변수가 들어 있을 수 있음
.venv로컬 가상환경 파일은 이미지에 불필요
.gitGit 이력과 내부 저장소 정보가 이미지에 들어가는 것을 막음
tests, docs실행에 필요 없는 테스트 파일·문서
__pycache__, *.pyc파이썬 캐시

⚠️ 주의 — .dockerignore는 민감한 파일이 이미지에 들어가는 위험을 줄이는 장치이지 시크릿 관리 자체를 대신하지 않는다.

4-4. 체크리스트로 검토하기 — 다섯 가지

에이전트가 쓴 파일이든 복사한 파일이든 아래 표의 다섯 가지를 확인한다. 한 줄이라도 걸리면 그 부분만 고쳐 달라고 다시 요청한다.

확인할 것올바른 기준고치지 않으면(이유)
베이스 이미지와 Python 버전이 고정돼 있는가python:3.13-slim-bookworm처럼 구체적으로(python:latest가 아님)빌드할 때마다 다른 버전이 들어와 결과가 달라질 수 있음
tesseract와 한국어 데이터를 설치하는 줄이 있는가tesseract-ocr, tesseract-ocr-kor 설치2장에서 서버에 없던 것 — OCR 실패
.dockerignore에 .env가 들어 있는가.env 포함빠지면 COPY . .이 API 키가 든 파일을 이미지에 넣음
실행 명령이 PORT 환경변수를 쓰는가${PORT:-8080}Cloud Run은 정해 준 포트로 요청을 보내므로 다른 포트를 리슨(listen, 포트를 열고 요청을 기다림)하면 시작에 실패함
non-root 사용자로 실행하는가USER appuser 등앱에 문제가 생겨도 컨테이너 안에서 할 수 있는 일을 줄임

Procfile과 .python-version은 buildpacks가 시작 명령과 Python 버전을 정할 때 쓰던 파일이다. 저장소에 Dockerfile이 생기면 배포할 때 Dockerfile로 빌드하므로 시작 명령은 CMD 줄이, Python 버전은 FROM 줄이 정한다. 두 파일은 지우지 않아도 되지만 Dockerfile과 값이 다르면 헷갈리니 같은 버전인지 한 번 확인한다.

4-5. 주관식 퀴즈와 해설서 모범 답안

문제: 에이전트가 쓴 Dockerfile이 FROM python:latest로 시작하고, 마지막 줄이 CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]이며, USER 줄이 없다. 체크리스트로 검토한 결과를 적고, 각각 고치지 않으면 어떤 일이 생길지 설명하라.

문제고치지 않으면고치는 방법
FROM python:latest빌드 시점에 따라 서로 다른 Python 환경이 쓰여 결과가 달라질 수 있음(재현성)FROM python:3.13-slim-bookworm처럼 버전 고정
고정된 8000번 포트의 CMDCloud Run이 전달하는 PORT를 쓰지 않아 서버가 기대하는 포트와 앱이 기다리는 포트가 달라질 수 있음(배포 호환성)${PORT:-8080} 사용
USER 줄 없음별도 사용자 지정이 없으면 root 권한으로 실행될 수 있음(보안)appuser 같은 일반 사용자를 만들고 USER appuser

결론: 베이스 이미지 버전 고정, PORT 환경변수 사용, non-root 실행은 각각 재현성·배포 호환성·보안 측면에서 중요하다.

💡 팁 — 해설서의 마지막 단서: 코딩 에이전트에게 Dockerfile 작성을 맡길 수는 있지만, 어떤 Python 버전을 고정할지, 어떤 권한으로 실행할지, 어떤 파일을 제외할지에 대한 판단은 여전히 사람의 몫이다.

5. 이미지 빌드와 실행

서버에 올리기 전에 로컬 환경에서 Dockerfile로 이미지를 만들고 컨테이너로 실행해 본다. 이번에는 로컬에 설치한 tesseract가 아니라 이미지 안에 설치된 tesseract가 사진을 읽는다. 첫 빌드는 베이스 이미지와 시스템 패키지를 내려받느라 몇 분 걸린다.

⚠️ 주의 — --env-file은 값을 감싼 따옴표를 지우지 않으므로 .env 값은 따옴표 없이 적어야 한다. 또한 이미지에서 키를 빼도 실행 중인 컨테이너의 환경이나 로그 등에 키가 노출될 가능성까지 없어지지는 않는다. 운영 서버에서는 Secret Manager 같은 비밀정보 관리 수단을 쓰는 것이 좋다.

5-5. 왜 로컬에서 만든 이미지를 서버에 올리지 않을까

서버에서 쓸 이미지는 배포 과정에서 같은 Dockerfile로 다시 만든다. 이유는 두 가지다.

  • CPU 아키텍처 차이: 로컬과 서버의 CPU 아키텍처(amd64, arm64처럼 CPU가 실행할 수 있는 명령 형식)가 다를 수 있다.
  • 재현성과 추적 가능성: 로컬에서 만든 이미지는 누가 언제 어떤 코드로 만들었는지 기록이 남지 않는다. 서버 배포 과정에서 코드·설정·빌드 과정을 관리하면 어떤 버전이 배포됐는지 확인하기 쉽다.

확인이 끝나면 컨테이너를 실행한 터미널에서 Ctrl+C로 멈춘다. --rm으로 실행했으므로 컨테이너도 함께 지워지지만 이미지까지 자동으로 삭제되지는 않는다.

📌 요약 — Dockerfile은 설계도, 이미지는 실행 패키지, 컨테이너는 실제 실행 환경이다. 이미지에 tesseract와 한국어 데이터를 넣으면 내 컴퓨터의 설치 상태에 대한 의존을 줄일 수 있다. 단 로컬 이미지가 실행된다고 운영 서버에서도 반드시 성공하는 것은 아니므로 서버 환경과 배포 과정을 따로 검증해야 한다.

6. Dockerfile을 기존 자동 배포로 올리기

시작 상태의 deploy.yml은 저장소 코드를 그대로 올리는 소스 배포를 쓴다. Cloud Run의 소스 배포는 올라온 코드에 Dockerfile이 있으면 buildpacks 대신 그 Dockerfile로 이미지를 만든다. 그래서 새로운 배포 시스템을 만들 필요가 없고, Dockerfile과 .dockerignore를 커밋해 CI를 거쳐 staging 브랜치로 PR을 보내면 된다.

방식흐름
기존소스 코드 → buildpacks → 이미지 → Cloud Run (Google이 실행 환경을 자동 구성)
변경소스 코드 + Dockerfile → Dockerfile 기반 빌드 → 이미지 → Cloud Run (우리가 정의한 Python·시스템 패키지·라이브러리로 이미지 생성)

🧪 예제 — [해설서 비유] 기존 방식은 식당에 필요한 재료를 이야기하면 주방에서 알아서 준비해 주는 방식이고, 변경 방식은 재료 목록과 조리법을 직접 작성해 전달하는 방식이다. 자동 배포 시스템을 새로 만드는 것이 아니라 기존 파이프라인의 빌드 방식을 바꾸는 것이다.

6-1. 한 군데만 고친다 — `--clear-base-image`

buildpacks로 배포한 서비스에는 Google이 관리하는 베이스 이미지를 자동으로 최신 보안 패치로 바꿔 주는 자동 베이스 이미지 업데이트가 켜져 있다. 이 기능은 Dockerfile로 만든 이미지에는 쓸 수 없어서, 그대로 배포하면 Missing required argument [--clear-base-image] 오류로 멈춘다. 이제 베이스 이미지는 Dockerfile의 FROM 줄이 정하므로, .github/workflows/deploy.yml의 flags: 줄 끝에 --clear-base-image를 붙여 이 기능을 끈다.

⚠️ 주의 — 기존 flags: 줄의 다른 옵션은 그대로 두고 끝에 --clear-base-image 하나만 추가한다. 그 대신 베이스 이미지의 보안 패치는 FROM 줄을 바꾸고 다시 빌드할 때 들어온다. 해설서의 표현으로, Dockerfile을 도입하면 실행 환경을 더 명확하게 통제할 수 있지만 보안 패치 관리 책임도 커진다.

6-2. 올라가는 파일은 세 번 확인한다

단계파일하는 일
① Git 커밋커밋 대상 목록커밋에 .env가 들어가지 않았는지
② 소스 업로드.gcloudignore소스 배포가 코드를 올릴 때 적힌 파일을 뺌
③ 이미지 빌드.dockerignore빌드할 때 COPY . .이 적힌 파일을 다시 뺌

.gcloudignore와 .dockerignore 모두 .env를 빼고 있는지 커밋 전에 확인한다. 해설서의 단서: .dockerignore가 있다고 해서 Git 커밋에서 자동으로 제외되는 것은 아니다. 세 가지는 서로 다른 확인 사항이다.

6-3. staging으로 PR 보내기

수정 대상은 세 파일뿐이다.

파일변경 목적
Dockerfile실행 환경과 필요한 시스템 패키지 정의
.dockerignore이미지에 포함하지 않을 파일 지정
.github/workflows/deploy.yml기존 배포 설정에 --clear-base-image 추가

작업 브랜치(add-dockerfile)를 만들어 세 파일만 커밋하고 staging 브랜치로 PR을 만든다(명령은 부록 A-13). 실행 전에 커밋 대상이 세 파일뿐인지, deploy.yml에서 바뀐 것이 flags: 줄 끝의 한 단어뿐인지, 강제 푸시 같은 옵션이 없는지 본다. 실무에서는 git status와 git diff --cached로 변경 파일과 내용을 확인하는 습관이 중요하다. PR 화면에서 상태 체크(status check, CI 결과)가 통과한 것을 확인하고 머지하면 staging 배포 워크플로가 실행된다. 에이전트에게 맡길 때의 조건은 다음과 같이 명시한다.

  • 지정된 세 파일만 수정·커밋한다.
  • .env가 커밋 대상에 없는지 확인한다.
  • deploy.yml에서는 flags: 줄 끝에 옵션 하나만 추가한다.
  • 강제 푸시 등 위험한 명령을 쓰지 않는다.
  • PR의 CI가 통과했는지 확인하고 결과를 보고한다(머지는 사람이 확인한 뒤에).

6-4. 빌드 기록에서 Dockerfile이 쓰였는지 확인하기

배포 워크플로가 끝나도 GitHub Actions 결과만 보고 끝내지 않는다. Dockerfile을 커밋했더라도 실제 빌드에 쓰이지 않았다면 원하는 실행 환경이 만들어지지 않는다. 빌드 로그는 배포 성공 여부를 넘어 의도한 방식으로 이미지가 만들어졌는지 보여 주는 증거다.

  1. GitHub 저장소의 Actions 탭에서 방금 실행된 배포가 성공했는지 본다.
  2. Google Cloud 콘솔의 Cloud Build > 기록(History)에서 가장 최근 빌드를 연다.
  3. 빌드 로그에서 FROM python:3.13-slim-bookworm과 tesseract-ocr를 설치하는 단계를 찾는다.
  4. Cloud Run > friend-agent-staging > 리비전 탭에서 새 리비전이 트래픽 100%를 받는지 본다.

staging 주소에서 같은 사진을 보내면 이번에는 일정 세 줄이 입력창에 들어온다. OCR_ENABLED=true는 2장에서 staging 서비스에 넣어 두었고 배포할 때 지워지지 않았기 때문이다. 로그 탭에도 tesseract 오류 대신 OCR에 성공했다는 정보 줄이 남는다. 확인할 사항은 일정 세 줄이 들어오는가, 로그에 성공 기록이 남는가, 예전 "tesseract 프로그램을 찾을 수 없습니다" 오류가 사라졌는가, 새 리비전이 정상 처리하는가다. 해설서의 단서: OCR이 성공했다고 모든 기능과 보안 설정이 검증된 것은 아니며 다른 기능은 별도로 테스트해야 한다.

6-5. production 배포

staging에서 확인했으면 production에 올린다. staging에서 main으로 PR을 보내 CI를 통과시키고, 머지한 뒤 배포 승인 화면에서 승인한다. production 서비스에는 아직 OCR_ENABLED가 없으므로 배포가 끝난 뒤 환경변수를 추가한다(--update-env-vars OCR_ENABLED=true, 부록 A-14). 실행 전에 서비스 이름(friend-agent)과 리전을 확인하고 기존 환경변수에 영향이 없는지 점검한다. production 변경은 사용자의 승인과 배포 정책에 따라 진행하는 것이 안전하다.

production 주소에서도 같은 사진을 보내 확인한다. 로컬 컨테이너, staging, production에서 같은 사진이 같은 결과로 읽히면 실행 환경이 이미지 하나로 고정됐다는 뜻이다.

💡 팁 — [보충 비유] 신제품을 시제품으로 검수(staging)하고 통과했는데, 납품(production)할 때 공장에서 같은 설계도로 다시 양산하는 것과 같다. 설계도(Dockerfile)는 같아도 그사이 원자재(패키지) 로트가 바뀌었다면, 검수한 제품과 납품한 제품이 같다고 말할 수 없다. 검수한 바로 그 제품을 납품하려면 "한 번 만든 것을 두 곳에 보낸다"는 구조가 필요하다.

객관식 퀴즈 — Dockerfile을 커밋했는데 staging 빌드 로그에 tesseract 설치 단계가 보이지 않고 OCR도 여전히 실패합니다. 가장 먼저 확인할 곳은?

① OpenAI 대시보드의 사용 한도 ② Dockerfile이 저장소 루트에 Dockerfile이라는 이름으로 있는지, 그리고 .gcloudignore가 Dockerfile을 빼고 있지 않은지 ③ Cloud Run의 최대 인스턴스 수 ④ staging 서비스의 요청 타임아웃

정답: ② Dockerfile이 저장소 루트에 없거나 이름이 다르면 소스 배포가 기대한 Dockerfile을 찾지 못할 수 있고, .gcloudignore가 Dockerfile을 제외하면 Google Cloud에 소스가 올라갈 때 그 파일이 전달되지 않을 수 있다. 빌드 로그에 설치 단계가 없다면 먼저 Dockerfile이 빌드 단계에 실제로 전달됐는지부터 의심하는 것이 합리적이다. 나머지는 이 현상의 첫 원인이 아니다.

7. 과제 구성

오늘 만든 이미지로 이미지와 컨테이너가 어떻게 움직이는지 직접 확인하고, 오늘 겪은 문제를 새 기능에 스스로 적용해 본다. 수업 시간에는 기본 과제를 하고 나머지는 골라서 한다. 해설서의 핵심 질문 세 가지는 이것이다.

  1. 컨테이너를 삭제하고 다시 실행하면 이전 대화와 기억은 어떻게 될까?
  2. 같은 Dockerfile로 이미지를 두 번 만들면 완전히 같은 이미지가 나올까?
  3. OCR처럼 운영체제에 별도 프로그램이 필요한 기능을 새로 만들 때 어떤 순서로 개발하고 배포해야 할까?
과제단계하는 일확인하는 것
1. 실행 중인 컨테이너 들여다보기기본컨테이너 안에 들어가 보고, 컨테이너를 지웠다 다시 띄워 대화가 남는지 본다컨테이너는 실행할 때마다 이미지에서 새로 시작한다
2. 같은 Dockerfile로 두 번 빌드하기중간캐시 없이 이미지를 두 번 만들어 이미지 ID와 설치된 패키지를 비교한다Dockerfile이 같아도 따로 빌드한 이미지는 서로 다른 이미지다
3. 시스템 프로그램이 필요한 기능 하나 더 붙이기도전원하는 기능을 정해 필요한 시스템 프로그램을 Dockerfile에 직접 넣는다오늘 배운 순서를 처음 보는 기능에 스스로 적용할 수 있다

7-1. 과제 1 — 실행 중인 컨테이너 들여다보기

5장에서 띄운 컨테이너를 이번에는 이름을 붙여 뒤에서(-d) 실행하고, 실행 중인 컨테이너 안에서 docker exec로 명령을 실행해 본다.

명령확인하는 것
docker exec friend-agent-test whoami현재 실행 사용자
docker exec friend-agent-test pwd현재 작업 폴더
docker exec friend-agent-test ls현재 폴더의 파일 목록

docker exec는 이미 실행 중인 컨테이너 안에서 추가 명령을 실행하는 기능이라, 컨테이너를 새로 만들지 않고도 내부 환경을 점검할 수 있다. 브라우저로 http://localhost:8080을 열어 캐릭터와 한두 마디 나눈 뒤 컨테이너를 지우고 같은 이미지로 다시 띄운다. 다시 띄운 컨테이너의 화면에는 방금 나눈 대화가 없다. 지금 에이전트 서비스는 대화와 기억을 컨테이너 안의 메모리에 두고, 컨테이너는 실행할 때마다 이미지에서 새로 시작하기 때문이다. Cloud Run에서 새 리비전을 배포할 때마다 대화가 사라지는 것도 같은 이유다.

구분설명
이미지프로그램과 실행 환경을 담은 패키지
컨테이너 메모리실행 중에 만들어진 임시 상태
영속 저장소컨테이너가 종료돼도 데이터를 보존하는 데이터베이스·파일 저장소

📌 요약 — 컨테이너는 실행 환경을 분리하지만 데이터의 영속성을 자동으로 보장하지 않는다. 사용자의 글과 인터뷰 기록을 보존해야 하는 서비스(예: MSM)는 Supabase 같은 외부 데이터베이스에 저장하고, 새 컨테이너가 시작될 때 필요한 정보를 다시 읽도록 설계해야 한다.

7-2. 과제 2 — 같은 Dockerfile로 두 번 빌드하기

Dockerfile 하나로 이미지를 만들면 언제 어디서 만들어도 같은 이미지가 나올까? 캐시를 쓰지 않고(--no-cache) 같은 Dockerfile로 이미지를 두 번 만든 뒤 두 이미지의 ID와 이미지 안에 설치된 Python 패키지 목록(pip freeze)을 비교한다. 이미지 ID는 이미지 내용으로 계산한 값이라 내용이 조금이라도 다르면 달라진다.

비교 결과의미
이미지 ID가 다름동일한 이미지가 아님(이번 실험의 결과)
이미지 ID 다름 + pip freeze 같음Python 패키지는 같지만 이미지의 다른 내용은 다를 수 있음
pip freeze까지 다름Python 의존성 구성에도 차이가 있음

몇 분 사이에 만들었다면 패키지 목록은 같게 나올 가능성이 높지만, 빌드 중에 만들어지는 파일과 시각이 달라 이미지 내용 전체는 같지 않다. 며칠 간격을 두고 빌드하면 그사이 새로 나온 패키지 버전이 들어가 목록까지 달라질 수 있다. 그래서 staging과 production에 같은 Dockerfile로 따로 빌드해 배포하면 두 환경은 같은 Dockerfile로 만든 서로 다른 이미지를 실행하게 된다. 확인한 이미지를 그대로 내보내는 방법은 다음 실습에서 다룬다.

⚠️ 주의 — 비교 명령의 diff <(...) 형식은 macOS·Linux의 Bash 계열 터미널에서 쓸 수 있다. Windows의 일반 PowerShell에서는 그대로 작동하지 않을 수 있으므로 Git Bash 같은 Bash 환경을 쓰는 것이 편하다. --no-cache도 모든 외부 입력을 고정하지는 않아서, 빌드 중 최신 패키지를 내려받으면 시점에 따라 결과가 달라질 수 있다. 실험이 끝나면 docker rmi friend-agent:try-a friend-agent:try-b로 실습용 이미지를 지운다.

운영 서비스에서는 단순히 Dockerfile만 공유하는 것보다 ① 베이스 이미지와 의존성 버전 고정 ② 빌드 결과 기록과 이미지 다이제스트 관리 ③ staging에서 검증한 이미지를 production으로 그대로 승격하는 방법을 고려할 수 있다(해설서).

7-3. 과제 3 — 시스템 프로그램이 필요한 기능 하나 더 붙이기

OCR은 Python 라이브러리만으로는 동작하지 않고 운영체제에 tesseract 프로그램이 필요했다. 이렇게 시스템 프로그램이 필요한 기능을 하나 골라 에이전트 서비스에 직접 붙여 본다. 무엇을 만들지는 자유이며, 원문의 예시는 다음과 같다(실제로 필요한 시스템 패키지는 선택한 라이브러리와 구현 방법에 따라 달라질 수 있다).

만들 기능검토할 도구
PDF 공지문에서 글자 읽기poppler
아이폰 사진 형식(HEIC) 받기libheif
음성 메모를 글로 옮기기 전 소리 파일 변환ffmpeg
사진 속 QR 코드 읽기zbar

오늘 OCR에서 한 그대로 밟는 순서는 이렇다.

  1. 어떤 기능을 어느 화면에 붙일지, 그 기능에 필요한 시스템 프로그램이 무엇인지 정한다. 모르겠으면 코딩 에이전트에게 "이 기능에 Python 라이브러리 말고 운영체제에 따로 설치해야 하는 프로그램이 있는지" 묻는다.
  2. 로컬에 그 프로그램을 설치하고, 코딩 에이전트에게 기능을 만들게 해 로컬 환경에서 동작을 확인한다.
  3. Dockerfile에 무엇을 더해야 할지 스스로 정하고 고친다. 4장의 체크리스트로 다시 검토한다.
  4. 로컬 컨테이너에서 같은 입력으로 같은 결과가 나오는지 확인한다.
  5. staging으로 PR을 올려 머지하고, staging 주소에서도 같은 결과가 나오는지 확인한다.

다 했는지 확인하는 방법: 같은 입력이 로컬 환경, 로컬 컨테이너, staging 세 곳에서 같은 결과를 내고, Dockerfile에서 바뀐 줄이 왜 필요한지 한 문장으로 설명할 수 있다. 가장 중요한 것은 기능이 작동하는지 확인하는 데 그치지 않고 Dockerfile에 추가한 각 줄이 왜 필요한지 설명하는 것이다.

8. 오늘 배운 것 (회고)

8-1. 네 가지 요약

주제핵심
실행 환경의 차이같은 코드가 로컬에서는 되고 staging에서는 안 된 이유는 코드가 아니라 실행 환경. 로컬에 직접 설치한 tesseract는 저장소에 기록되지 않았고, 코드만 보고 이미지를 만드는 buildpacks는 그 프로그램을 알 수 없었음. 원인은 화면 안내가 아니라 로그의 오류 줄에서 찾음
이미지와 컨테이너이미지는 실행에 필요한 것을 묶은 바뀌지 않는 파일, 컨테이너는 그 이미지를 실행한 것. 한 컨테이너에서 만든 파일을 다른 컨테이너가 보지 못함. Cloud Run의 리비전·인스턴스도 같은 구조로 설명됨
Dockerfile 검토베이스 이미지 고정, 필요한 시스템 패키지 설치, .dockerignore의 .env, PORT 환경변수, non-root 사용자의 다섯 기준으로 파일을 읽음. 로컬에서 이미지 안의 파일 목록과 실행 사용자로 기준을 확인. 키는 이미지에 넣지 않고 실행할 때 건넴
배포 흐름은 거의 그대로워크플로에는 자동 베이스 이미지 업데이트를 끄는 옵션 하나만 더하고 Dockerfile을 커밋했는데, 소스 배포가 Dockerfile을 찾아 그 파일로 빌드함. 빌드 기록에서 FROM 줄과 tesseract 설치 단계를 찾아 확인

8-2. 회고 질문과 해설서 모범 답안

회고 질문: 1장에서 로컬 환경과 서버 사이에 무엇이 다를 수 있을지 적었다. 그 답을 다시 읽고 오늘 실제로 달랐던 것과 비교해 보라. 그리고 이제 Dockerfile이 생긴 저장소에서 같은 종류의 문제가 다시 생긴다면 어디부터 확인할지 적어 보라.

모범 답안(해설서)의 요지는 이렇다. 로컬에서는 직접 설치한 tesseract와 한국어 언어 데이터가 있어서 OCR이 작동했지만 staging에서는 실행 환경에 해당 프로그램이 없어 실패했다. 코드만으로 이미지를 만드는 buildpacks가 로컬에 설치된 시스템 프로그램까지 자동으로 포함하지 못한 것이 원인이었다. 같은 문제가 다시 생기면 확인 순서는 이렇다.

  1. staging 로그에서 오류 메시지를 확인한다.
  2. Dockerfile에 필요한 시스템 프로그램과 언어 데이터가 설치돼 있는지 살핀다.
  3. Dockerfile을 사용해 빌드했는지, 빌드 기록에 해당 설치 단계가 있는지 확인한다.
  4. 로컬 컨테이너에서 재현한 뒤 staging에서도 같은 입력으로 테스트한다.

8-3. 아직 남은 숙제 세 가지 — 다음 강의로 이어지는 것

이제 에이전트 서비스의 실행 환경은 Dockerfile 한 파일에 적혀 있고, 로컬 컨테이너와 staging과 production에서 같은 사진을 같은 결과로 읽는다. 그래도 남은 것이 있다.

숙제문제앞으로의 방향
① 이미지 추적서버용 이미지는 배포할 때마다 Cloud Build가 새로 만들고 이름이 자동으로 붙어, 지금 production에서 도는 이미지가 어느 커밋으로 만든 것인지 이름만 보고는 알기 어렵다태그와 digest 관리
② 이미지 일관성staging에서 확인한 이미지와 production에 올라간 이미지는 같은 Dockerfile로 따로 만든 별개의 이미지다. 확인한 것과 나간 것이 같다고 말하려면 이미지를 한 번만 만들어 두 환경에 보내야 한다검증한 이미지를 그대로 승격하는 빌드·배포 흐름
③ 저장 공간이미지 크기가 400MB대여서 배포할 때마다 쌓이는 저장 공간을 아직 관리하지 않았다불필요한 이미지·레이어 정리

특히 해설서는 이미지 크기를 줄이는 것만큼 중요한 것이 검증한 결과물을 그대로 운영 환경에 배포하는 것이며, 크기 최적화와 배포 추적은 별개의 과제로 나누어 접근하라고 권한다.

용어뜻
태그(tag)friend-agent:v1.0처럼 사람이 알아보기 쉬운 이름. 같은 태그가 나중에 다른 이미지로 바뀔 수 있음
digest이미지 내용을 식별하는 고유한 해시값. digest를 기준으로 하면 특정 이미지 내용을 더 정확히 지정할 수 있음

Dockerfile은 베이스 이미지·시스템 패키지·라이브러리·코드·실행 사용자·시작 명령을 한 파일에 적고, 키는 이미지에 넣지 않고 실행할 때 건네며, 기존 자동 배포는 --clear-base-image 한 단어만 더해 그대로 쓴다. 남은 것은 "확인한 이미지"와 "나간 이미지"를 같게 만드는 일이다.

Q1. staging에서 OCR이 실패했는데 배포는 성공했고 다른 대화 기능도 정상이었던 이유로 가장 알맞은 것은?

① Cloud Run이 오류를 숨겨 주기 때문이다 ② 앱은 시작할 때 tesseract를 확인하지 않고, 사진 요청이 들어와 프로그램을 부를 때에야 없다는 것을 알게 되기 때문이다 ③ staging에서는 OCR_ENABLED가 꺼져 있었기 때문이다 ④ buildpacks가 tesseract를 설치했지만 한국어 데이터만 빠졌기 때문이다

정답: ② 서비스는 정상적으로 시작하고, 실제 OCR 요청이 들어온 순간에야 프로그램을 부르다 실패한다. 그래서 배포는 성공이고 다른 기능은 그대로 쓸 수 있다.

Q2. CI 테스트가 통과했는데도 staging에서 OCR이 실패한 이유로 알맞은 두 가지는?

(주관식) 모범 답안: ① 템플릿의 OCR 테스트는 기능이 꺼져 있을 때 요청을 거절하는지만 확인하고, 실제 사진을 읽는 데 필요한 시스템 프로그램까지는 검증하지 않는다. ② 테스트가 도는 GitHub 러너와 staging 이미지는 서로 다른 실행 환경이라, 러너에서 통과했다고 staging 이미지에 tesseract가 있다는 뜻이 아니다.

Q3. 같은 이미지로 컨테이너 두 개를 실행하고 첫 컨테이너에서 /tmp/note.txt를 만들었다면 둘째 컨테이너에서는?

① 파일이 보인다 ② 파일이 보이지 않는다 ③ 첫 컨테이너가 실행 중일 때만 보인다 ④ 첫 컨테이너를 지우면 보인다

정답: ② 파일은 첫 컨테이너 안에서만 생긴 변경이고 이미지는 바뀌지 않았다.

Q4. docker run -p 9000:8080 friend-agent:local 로 띄웠다면 브라우저로 열 주소는?

① http://localhost:8080 ② http://localhost:9000 ③ 둘 다 ④ 컨테이너 안에서만

정답: ② 앞 숫자(9000)는 내 컴퓨터 포트, 뒤 숫자(8080)는 컨테이너 안의 포트다.

Q5. Dockerfile에서 requirements.txt를 코드(COPY . .)보다 먼저 복사해 라이브러리를 설치하는 이유는?

(주관식) 모범 답안: 레이어 캐시 때문이다. Docker는 내용이 바뀌지 않은 줄의 이전 레이어를 다시 쓰고 처음 바뀐 줄부터 아래를 새로 만든다. 시간이 오래 걸리는 시스템 패키지·라이브러리 설치를 위에 두고 자주 바뀌는 코드 복사를 아래에 두면, 코드만 고쳤을 때 라이브러리 설치를 다시 하지 않아도 된다. 코드 전체를 먼저 복사하면 코드 한 줄만 고쳐도 설치가 매번 다시 실행된다.

Q6. 에이전트가 쓴 Dockerfile이 FROM python:latest로 시작하고 --port 8000 고정 CMD에 USER 줄이 없습니다. 각각 고치지 않으면?

(주관식) 모범 답안: python:latest는 빌드 시점에 따라 다른 Python이 들어와 결과가 달라질 수 있어 python:3.13-slim-bookworm처럼 고정한다(재현성). 고정 8000번 포트는 Cloud Run이 PORT로 알려 주는 포트와 달라 시작에 실패할 수 있어 ${PORT:-8080}을 쓴다(배포 호환성). USER 줄이 없으면 root로 실행될 수 있어 appuser를 만들고 USER appuser로 실행한다(보안).

Q7. API 키를 --env-file .env 로 건네는 방식이 Dockerfile의 COPY .env . 보다 나은 이유는?

① 두 방식은 같다 ② 이미지에 넣는 편이 안전하다 ③ 실행할 때 건네면 키가 이미지 파일에 남지 않아 이미지가 저장소에 올라가거나 다른 사람에게 전달돼도 키가 따라가지 않는다 ④ Secret Manager가 필요 없어진다

정답: ③ ②는 이미지가 바뀌지 않는다는 사실이 이미지 안의 비밀을 안전하게 만들어 주지 않고, ④는 --env-file이 비밀정보 관리 시스템을 대체하지 않는다.

Q8. 이미지 안 ls -a /app 결과에 .env가 보입니다. 어떻게 해야 하나요?

(주관식) 모범 답안: 그 이미지를 다른 곳에 올리지 말고 지운다. .dockerignore에 .env를 넣어 고친 뒤 다시 빌드한다. 실제 키가 이미지에 들어갔다면 키 교체도 검토한다.

Q9. 배포가 Missing required argument [--clear-base-image]로 멈췄습니다. 원인과 해결은?

(주관식) 모범 답안: buildpacks로 배포한 서비스에 켜져 있던 자동 베이스 이미지 업데이트는 Dockerfile로 만든 이미지에는 쓸 수 없다. deploy.yml의 flags: 줄 끝에 --clear-base-image 하나만 붙여 끈다. 대신 베이스 이미지 보안 패치는 FROM 줄을 바꾸고 다시 빌드할 때 들어온다.

Q10. Dockerfile을 커밋했는데 staging 빌드 로그에 tesseract 설치 단계가 없고 OCR도 계속 실패합니다. 가장 먼저 확인할 곳은?

① OpenAI 대시보드의 사용 한도 ② Dockerfile이 저장소 루트에 Dockerfile이라는 이름으로 있는지, .gcloudignore가 Dockerfile을 빼고 있지 않은지 ③ Cloud Run 최대 인스턴스 수 ④ staging 서비스의 요청 타임아웃

정답: ② Dockerfile이 빌드 단계에 실제로 전달됐는지부터 확인하는 것이 합리적이다.

Q11. staging과 production에서 같은 Dockerfile로 빌드했는데도 두 이미지가 같다고 말할 수 없는 이유는?

(주관식) 모범 답안: staging·main 브랜치에 머지할 때마다 Cloud Build가 Dockerfile로 이미지를 각각 새로 만들기 때문이다. apt-get install·pip install이 그사이 새로 나온 패키지 버전을 받으면 이미지 내용이 달라질 수 있다. 확인한 이미지를 그대로 내보내려면 이미지를 한 번만 만들어 두 환경에 보내야 한다.

Q12. 컨테이너를 지우고 같은 이미지로 다시 띄웠더니 대화가 사라졌습니다. 서비스를 어떻게 설계해야 하나요?

(주관식) 모범 답안: 대화·기억이 컨테이너 메모리에만 있어서 새 컨테이너가 이전 메모리를 이어받지 못한 것이다. 계속 보존해야 하는 데이터는 Supabase 같은 외부 데이터베이스(영속 저장소)에 저장하고, 새 컨테이너가 시작될 때 필요한 정보를 다시 읽도록 설계한다.

(주관식) 모범 답안(작성 방법 예시): 선택한 기능 — 음성 메모 변환, 필요한 시스템 프로그램 — FFmpeg, 추가한 줄 — apt-get install -y --no-install-recommends ffmpeg, 추가한 이유 — Python 코드가 FFmpeg 실행 프로그램을 호출하므로 컨테이너 안에도 설치돼야 함, 줄이 없을 때 — 로컬에 FFmpeg가 있으면 로컬에서는 되지만 이미지 안에는 없어 로컬 컨테이너에서 처음 실패. 실제 과제에서는 직접 고른 기능과 검증 결과를 적는다.

📌 요약 — 이번 강의의 핵심: ① 코드가 같아도 실행 환경이 다르면 실패하고, 원인은 화면이 아니라 로그에서 찾는다 ② 이미지는 바뀌지 않는 실행 패키지, 컨테이너는 그 이미지를 실행한 것이며 컨테이너 메모리는 영속 저장소가 아니다 ③ Dockerfile에는 베이스 이미지·시스템 패키지·.env 제외·PORT·non-root를 적고, 키는 이미지에 넣지 않고 실행할 때 건넨다 ④ 기존 자동 배포는 --clear-base-image 한 단어만 더해 Dockerfile 빌드로 바뀌고, 빌드 기록으로 확인한다 ⑤ 남은 숙제는 이미지 추적(태그·digest)·staging과 production의 동일 이미지·저장 공간 관리다.
