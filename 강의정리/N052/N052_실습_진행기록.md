- reload는 Nginx를 재시작하지 않는데도 요청 실패 0건이었다 — 이전 작업 프로세스가 하던 요청을 끝내는 동안 새 작업 프로세스가 새 설정으로 받는다(교안 3-8).

- 순서를 지켰다: 수정 → 검사 → reload. 이전 서버(blue)는 끄지 않고 남겨 두었기 때문에 롤백이 1초 만에 가능했다.

## 4. 5장 실험 ② 가중치 3 대 1 (09:18)

**왜**: 서버 목록에 `weight=3`을 주면 요청이 3 대 1로 나뉘는지 본다. 이것이 카나리 배포(새 버전에 일부 요청만 보내기)의 원리다.

**한 일**: `default.conf`를 편집기로 교안 그대로 바꿨다(`server blue:8080 weight=3;` + `server green:8080;`, `zone` 유지). `nginx -t` → `nginx -s reload` → `watch_requests.py … --seconds 30` (원본: `실습로그/04_실험2_가중치.log`).

**결과 (요약 원문)**: 전체 요청 **147건, 실패 0건**, 30초 / blue 110건(**75%**) / green 37건(**25%**).
- 110 : 37 = 2.97 : 1로 3 대 1에 가깝다. 교안이 말한 "약 75%와 25%" 그대로다.
- 로그의 응답 리비전이 바뀐 시각을 보면 `green(09:18:56.285) → blue(56.492) → green(57.104) → blue(57.314) → green(57.929)`처럼 **green은 약 0.6~0.8초(요청 4개)마다 한 번**, 그 사이 blue가 세 번 응답한다 — "요청 4개마다 3개가 blue로" 간다는 Nginx의 순서 세기가 그대로 보인다.
- `zone active_app 64k;` 줄이 있어서 작업 프로세스들이 순서를 함께 센다(교안 3-6). 이번 환경에서는 zone이 있는 상태로만 실험해서, zone을 뺀 경우의 어긋남은 확인하지 않았다.

**알게 된 것**: 비율이 정확히 3 대 1이 아니라 2.97 대 1인 이유는 측정 시작·끝이 순서 중간에 걸리기 때문이다(교안). 이 숫자를 90 대 10, 99 대 1로 바꾸면 카나리 배포가 된다.

**읽는 법**
- 실패 간격 2.83초는 "green 차례 요청 1개가 스크립트의 2초 제한에 걸려 실패(2초) + 그 사이 blue 차례 요청 3개(각 약 0.2초) + 간격" 한 바퀴의 길이와 맞는다. 즉 **4번에 한 번(green 차례)** 요청이 멈춘 채 기다리다 실패로 센 것이고, 나머지 blue 요청은 정상이었다(로그는 응답 리비전이 바뀔 때만 찍으므로 blue 성공은 안 보인다).
- **교안과 다른 점**: 교안은 "Nginx는 연결 대기 시간(`proxy_connect_timeout`, 기본 60초)이 지나야 실패로 보고 다른 서버로 넘긴다"고 설명한다. 이번 환경에서는 실패 구간이 **60초가 아니라 약 38초**(09:19:32 → 09:20:10)였고, Nginx 로그의 원인은 타임아웃이 아니라 `113: Host is unreachable`(연결 시도가 운영체제 수준에서 도달 불가로 실패)이었다. 멈춘 컨테이너의 주소로 가는 연결이 Docker 네트워크에서 응답을 못 받다가 커널이 도달 불가로 판정한 것으로 **추정**한다(확인한 것은 로그의 오류 문구와 시각까지). 그래서 "60초를 다 기다린다"는 숫자는 재현되지 않았지만, **"알아채는 비용을 사용자 요청이 낸다"는 교안의 핵심은 그대로 재현**됐다: 실패 13건 = 알아채는 데 쓰인 요청들.
- 에러 로그의 `upstream server temporarily disabled`는 교안 3-3의 `max_fails=1, fail_timeout=10s`(기본값) 동작이다 — 한 번 실패하자 green을 잠시 뺐고, 그 뒤 요청은 blue만 받았다(실패가 더 이어지지 않음).
- 이 비교는 **실행 환경(Docker Desktop·Windows 11)에 따라 달라질 수 있다**. 같은 실험을 macOS에서 한 교안 설명과 숫자가 다른 것은 오류가 아니라 환경 차이일 수 있다.

**알게 된 것**: 사용자 눈으로 본 것은 "일부 요청이 멈췄다가 실패, 곧 정상"이었다. 서버 하나가 멈춘 것을 로드밸런서가 알아채기까지 걸린 시간만큼(여기서는 약 38초) 4번에 한 번씩 사용자가 기다렸다. 실패 수를 줄이려면 연결 대기 시간을 줄이는 것(다음 실험) 또는 능동 헬스체크가 필요하다.

## 6. 5장 실험 ③-b 연결 대기 시간을 1초로 줄이고 같은 실험 (09:21~09:23)

**왜**: 실패하기까지 기다리는 시간이 사용자 실패 수를 좌우하는지 확인한다. 같은 실험을 `proxy_connect_timeout 1s;` 한 줄만 더한 설정으로 반복했다.

**한 일** (원본: `실습로그/06_*.log`)
1. 09:21:07 `docker start green` (멈춘 서버 다시 켬)
2. 편집기로 `default.conf`의 `location /` 안에 `proxy_connect_timeout 1s;` 추가 → `nginx -t` ✅ → `nginx -s reload` (green을 다시 켰으니 **reload로 이름을 다시 찾게** — 교안 5-4)
3. 스크립트 60초 시작 → 09:21:33 `docker stop green` (09:21:37에 끝남)

**결과 (요약 원문)**: 전체 요청 **272건, 실패 0건**, 60초 / blue 257건(94%) / green 15건(6%).

**Nginx 에러 로그** (`06_실험3_1초_nginx_에러로그.log`)
- 09:21:38 (stop 끝난 지 1초 뒤): `upstream timed out (110: Operation timed out) while connecting to upstream` + `upstream server temporarily disabled`
- 이어서 **00:21:50 → 00:22:02 → 00:22:14 (UTC)**, 약 12초마다 같은 두 줄이 반복됨 — Nginx가 `fail_timeout`(기본 10초)이 지나면 실제 요청 하나를 다시 green에 보내 보고, 1초 만에 실패하면 다시 뺀다.

**지연 측정** (`06_실험3_1초_지연측정.log`): green이 멈춘 채 30초 동안 0.2초 간격으로 요청(52건). 0.5초를 넘은 요청은 **2건**, 둘 다 **약 1.0초(1.006초·1.015초)에 상태 코드 200**이었고 시각은 09:22:49·09:23:04로 약 15초 간격이다. 나머지 50건은 정상(0.5초 이하).

### ③-a와 ③-b 비교

| 항목 | ③-a 기본값 | ③-b 1초 |
|---|---|---|
| 요청 수 (60초) | 159 | 272 |
| **실패 수** | **13건** | **0건** |
| 서버 하나가 멈춘 것을 Nginx가 알아챈 시점 | 멈춘 뒤 약 38초(`113 Host is unreachable`) | 멈춘 뒤 1초(`110 Operation timed out`, 설정한 1초) |
| 사용자가 겪은 것 | 4번에 한 번(green 차례) 멈췄다가 2초 제한에서 실패 | green 차례 요청이 약 1초 늦게 200 |
| green을 뺀 뒤 | 더 이상 실패 없음 | 12~15초마다 요청 하나가 1초씩 더 기다림(다시 시험해 봄) |

**읽는 법**
- 교안의 핵심 3가지가 모두 재현됐다. ① 대기 시간을 줄이면 **실패가 사라진다**(13 → 0) ② 대신 green 차례 요청은 **1초 늦게** 응답한다 ③ green을 뺀 뒤에도 `fail_timeout` 간격으로 한 요청이 1초를 더 기다린다 — "고장을 알아채는 비용을 사용자 요청이 낸다"(수동 헬스체크).
- 실패가 0건이 된 이유는 Nginx가 1초 안에 실패로 보고 **같은 요청을 blue로 다시 보냈고**, 스크립트의 2초 안에 blue 응답이 돌아왔기 때문이다.
- **주의**: 대기 시간을 너무 짧게 잡으면 잠깐 바빠서 늦게 연결된 정상 서버까지 실패로 볼 수 있다(교안). 이번에는 그런 오판을 시험하지는 않았다. 또 `proxy_connect_timeout`은 연결 시도에만 적용되는 제한이라 연결 뒤 응답이 늦는 경우는 따로 읽기 타임아웃을 봐야 한다.
- ③-a에서 60초가 아닌 38초가 나온 것(환경 차이 추정)과 달리, ③-b는 **설정한 1초가 그대로 동작**했다.

## 8. 6장 준비 — 사용자가 직접 해야 하는 단계에서 멈춤 (09:27)

**왜 멈추나**: 6장은 Supabase 계정 가입·프로젝트 생성·키 확인이 필요하다. 계정 생성, 키·비밀번호 입력은 에이전트가 대신하지 않고 **사용자가 직접** 해야 하는 단계다(교안도 "키 값은 채팅이나 명령, 코드에 붙여 넣지 않는다"). 그래서 이 지점에서 5장까지의 기록을 정리하고 사용자 단계 안내를 준비했다.

**사용자 단계 (템플릿 `docs/supabase.md` 1절 그대로)**
1. Supabase 대시보드에서 프로젝트 생성 — 이름은 `friend-agent-staging`처럼 시험용임을 알 수 있게, 리전은 us-central1과 가까운 미국 리전(예: East US (Ohio)), DB 비밀번호는 Supabase가 만들어 주는 값을 비밀번호 관리 도구에 저장
2. SQL Editor에 `supabase/migrations/0001_init.sql` 내용을 붙여 넣고 실행(캐릭터·대화·요약·기억·약속 테이블, 전부 RLS 켬)
3. `Authentication > Sign In / Providers` → `Allow anonymous sign-ins` 켜기
4. `Authentication > Rate Limits`에서 익명 로그인 한도 확인(기본 IP당 시간당 30건)
5. `Project Settings > API Keys`에서 URL·publishable key·secret key 확인 → **편집기로 저장소 루트 `.env`에 직접 입력**(`STORAGE=supabase`, `AUTH=supabase`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_SECRET_KEY`)

**이 세션이 지키는 규칙**: `.env` 파일의 내용을 읽거나 출력하지 않는다. 이 세션에서 `.env`의 줄 이름만 확인하려던 명령도 허용되지 않아 실행하지 않았고, 변수 이름은 `.env.example`로 확인했다(`LLM_PROVIDER · LLM_API_KEY · LLM_MODEL · ENV · STORAGE · AUTH · SUPABASE_URL · SUPABASE_PUBLISHABLE_KEY · SUPABASE_SECRET_KEY · GOOGLE_LOGIN`). 값이 맞게 들어갔는지는 컨테이너 시작 로그의 `"storage": "supabase"`, `"auth": "supabase"`로만 확인한다.

**사용자 단계가 끝나면 이어서 할 일(6-4~6-6)**: `docker rm -f blue green` → `--env-file .env`로 같은 이름 재기동(`-e`로 LLM_PROVIDER=fake·K_REVISION·BANNER 유지, `-p` 없음) → `nginx -s reload` → blue 로그 처음 5줄 확인 → 브라우저에서 게스트 로그인·약속 만들기 → Supabase Table Editor `messages`·`reminders` 행 확인 → green 전환·blue 재시작·다른 브라우저(시크릿 창)에서도 이어지는지 확인 → 정리(`docker rm -f blue green bg-nginx`, `docker network rm bg-lab`).

## 10. 6장 Supabase 2단계 — 테이블 만들기 (사용자 직접 진행, 09:42)

**결과 ✅**: 배너 **BLUE**, 대화창에 인사 → "내일 아침 8시에 물 마시라고 알려 줘" → "약속을 저장했습니다: 10월 29일(목) 08:00에 '물 마시기'." 3개가 **그대로**, 왼쪽 아래 "게스트로 사용 중"도 그대로다. 새로고침을 해도 인사 메시지가 또 생기지 않았다(인사는 대화가 비어 있을 때 처음 한 번만 만든다).

| 5장 ④ 마지막 장면 | 6장 ②-b |
|---|---|
| `docker restart blue` + reload 뒤 대화·약속 **0/0** (완전히 사라짐) | 같은 조작 뒤 대화 3개·약속 **그대로** |

**6-5의 ①~②를 한 줄로**: 대화의 유일한 사본이 서버 메모리에 있을 때는 **전환·롤백·재시작** 어느 쪽이든 사용자 입장의 "무중단"이 깨졌고, 사본을 컨테이너 밖 데이터베이스로 옮기자 같은 조작에서 모두 이어졌다.

## 19. 6-5 ③ 시크릿 창 — 다른 게스트에게는 앞의 대화가 보이지 않는다 (사용자 직접 확인, 14:33)

> 캡처에는 프로젝트 주소·`user_id`가 보였으나 기록에는 적지 않는다. 사용자를 구분하려고 첫 번째 게스트를 "게스트 A", 시크릿 창의 게스트를 "게스트 B"라고 부른다.

**한 일**: 사용자가 Chrome **시크릿 모드** 창에서 `http://localhost:8080`을 열었다(blue 활성). 이어서 왼쪽 메뉴의 `대화`를 보고, 대화창에 **"내 약속 뭐 있어?"**를 보낸 뒤 Supabase `Table Editor`의 `messages`를 새로고침했다.

**결과 ✅ (캡처 3장)**
1. **시크릿 창의 대화 화면은 비어 있다.** 배너 BLUE, 왼쪽 아래 "게스트로 사용 중", 캐릭터 카드는 기본값(하루 · 20대 · 대학원생 · 친구). 게스트 A의 대화 3개는 **보이지 않는다**.
2. "내 약속 뭐 있어?"에 대한 답이 **"(가짜 응답) 저장된 약속이 없습니다."**다. 오른쪽 개발용 패널에서 도구는 `약속 보기 · list_reminders`(확신도 75%, 기준 60%, 키워드 규칙), 도구 결과는 "저장된 약속이 없습니다.", 기억 메모 없음, 대화 요약 없음, "최근 대화 1개 메시지를 함께 넣었습니다". 게스트 A의 약속("물 마시기")은 **게스트 B에게 나오지 않았다**.
3. Supabase `messages` 테이블에 행이 **6개**가 되었다. 1~3번 행은 게스트 A의 것(그대로), **4~6번 행은 다른 `user_id`**(앞 8자리가 게스트 A와 다름): 인사(`greeting`, 05:31:26 UTC) → user "내 약속 뭐 있어?"(05:31:38) → assistant "저장된 약속이 없습니다."(`list_reminders`, 05:31:38). 즉 **두 게스트의 대화가 한 테이블에 서로 다른 사용자 ID로 나뉘어 저장**됐다. (`reminders`는 이번에 캡처하지 않았다 — 게스트 B는 약속을 만들지 않았으므로 1행 그대로일 것으로 예상, 확인은 못 함)

**교안의 설명과 대조**: "다른 브라우저에서 앞의 대화가 보이지 않은 것은 브라우저마다 다른 게스트 사용자로 로그인하고, 서버가 모든 조회에 그 사용자의 ID 조건을 붙이기 때문이다" → 시크릿 창이 새 게스트가 되었고(행 4~6의 `user_id`가 다름), 서버가 그 사용자 ID로만 조회해 앞의 대화·약속이 안 보였다. 교안 6-5 확인 5단계가 모두 확인됐다.

**새로 관찰한 것 (추정, 직접 확인하지 않음)**: 오른쪽 "걸린 시간" 패널이 도구 선택·첫 글자·답 전체 모두 **3.0초**였다. 페이크 LLM은 외부 AI를 부르지 않는데도 3초가 걸린 것이다. 5장에서 메모리 모드로 요청했을 때는 지연을 재지 않았으나 응답이 즉시 왔다. 이번 3초는 **저장소가 한국 PC가 아닌 미국 동부(Ohio)의 데이터베이스**라 요청 하나에 데이터베이스를 여러 번 왕복하는 시간이 들어간 것으로 **추정**한다. "데이터를 밖으로 옮기면 지연이 늘 수 있고 리전 선택이 중요하다"는 점은 교안이 리전을 신경 쓰라는 이유와 이어진다(확인하려면 같은 요청을 서울 리전에서 재 봐야 함).

**알게 된 것**: 사용자 분리의 증거는 "앞의 대화가 안 보인다"(화면)와 "테이블에 다른 `user_id`로 쌓인다"(데이터) 두 가지를 함께 봐야 단단하다. 게스트는 그 브라우저의 로그인 정보로 정해지므로 같은 사람이 브라우저를 바꾸면 다른 게스트가 된다(화면의 "이 브라우저에만 저장됩니다" 안내).

## 20. 6-7 정리 — 컨테이너와 네트워크 지우기 (14:33)

**지우기 전 확인**: `docker ps -a`에 `green`·`blue`·`bg-nginx` 세 개, 네트워크 목록에 `bg-lab` — 이름이 실습에서 만든 것과 일치했다. (비밀·주소 흔적 검사: 실습로그·진행기록에서 키 값·프로젝트 주소·사용자 ID 원문은 **0건**, `sb_…`·`.supabase.co`는 형식 설명 문장 안에만 있음.)

**한 일**: `docker rm -f blue green bg-nginx` → `docker network rm bg-lab`. 컨테이너를 지우면 환경변수로 들어 있던 Supabase 값도 함께 사라진다.

**남긴 것**: Supabase 프로젝트와 `.env`, `friend-agent:local`·`nginx:1.27-alpine` 이미지, 설정 폴더 `%USERPROFILE%\bluegreen-lab`(처음 상태로 되돌려 둔 `default.conf`). `.env`의 `STORAGE`·`AUTH`는 `supabase` 그대로라 이후 로컬에서 에이전트를 띄우면 같은 시험용 데이터베이스를 쓴다. 메모리 저장으로 돌아가려면 두 줄을 `memory`·`none`으로 되돌린다(교안).
