[제출 보고서] N052 「로드밸런서로 무중단 배포 구성하기」 실습 과제 수행 결과

수신: N052 강의 강사님 · 발신: 수강생 전대진(DJ)

실습일: 2026-10-28

과제 대상: AI 친구 에이전트 서비스(friend-agent)의 이미지를 내 컴퓨터의 Docker에서 두 벌(blue·green)로 띄우고, 그 앞에 Nginx 로드밸런서를 세워 ① 설정 한 줄로 전환·롤백 ② 가중치 3 대 1 ③ 서버 하나가 멈췄을 때(기본값과 연결 대기 1초) ④ 전환하면 사라지는 대화를 측정하는 실습. 이어서 대화를 컨테이너 밖 Supabase 데이터베이스로 옮겨 전환·재시작 뒤에도 대화가 이어지는지, 브라우저가 다르면 다른 사용자가 되는지 확인했다.

평가 방법: 12번 "평가 체크리스트"를 보고 항목별로 점수와 한 줄 의견을 남겨 주세요.

요약 — 이 문서는 N051 보고서와 같은 구조(한눈에 → 절별 기록 → 사고 표 → 정리 → 궁금했던 것)로 쓴 한눈에 읽는 보고서이다. 근거는 같은 폴더의 N052_실습_진행기록.md와 실습로그\ 원본 로그(번호 01~14 묶음, 파일 24개)뿐이며, 로그에 없는 것은 "확인하지 못했다"고 적었다. 누가 했는지를 절마다 구분한다. Docker·Nginx 명령과 요청 측정은 AI 코딩 도우미(Claude)가 실행했고, Supabase 대시보드 작업·.env 편집·브라우저 확인은 사용자(DJ)가 직접 했다. 저장소가 공개이므로 Supabase 프로젝트 주소·ID, 키 값, 사용자 ID, DB 비밀번호, GitHub 계정·저장소 주소는 싣지 않았다. 시각은 한국 시각(KST)이며, Nginx 에러 로그와 Supabase 테이블의 시각(created_at·due_at)은 UTC로 찍혀 있어 그대로 UTC라고 표시했다.

측정 결과: 전체 요청 341건, 실패 0건, 70초 / blue 274건(80%) / green 67건(20%). green이 응답한 구간은 09:16:57~09:17:11, 약 14초이고 0.2초 간격이므로 약 70건인데 실제 green은 67건이다. 80%·20%는 "green이 응답한 시간이 70초 중 20%"라서 나온 숫자이지 분배 규칙(가중치)이 아니다.

  • 브라우저 화면도 전환 중에는 맨 위 배너가 GREEN으로 바뀌었다(증거화면/02_전환후_GREEN배너.jpg).
  • 교안 예시(1013건, blue 68%·green 32%, 215초)와 비율이 다른 것은 전환 시각을 내가 정했기 때문이다. 실패 0건은 같다.
  • 도구: Windows에는 sed가 없어 교안은 편집기로 고치라고 한다. 이번에는 강의노트 부록 A-6에 [보충]·미실행으로 적었던 PowerShell 방식 (Get-Content …) -replace "server blue:8080;","server green:8080;" | Set-Content … -Encoding ascii를 실제로 썼다. 전환·롤백 두 번 모두 의도한 한 줄만 바뀌고 Nginx가 문제없이 읽었다. 이 명령은 동작한다.
  • reload는 Nginx를 재시작하지 않는데도 실패 0건이었다. 순서(수정 → 검사 → reload)를 지켰고 blue는 끄지 않고 남겨 두어 롤백이 1초 만에 가능했다. 실패 0건은 이 70초 구간의 결과일 뿐이다.

  • 결과: 전체 요청 147건, 실패 0건, 30초 / blue 110건(75%) / green 37건(25%). 110 : 37 = 2.97 : 1로 교안이 말한 "약 75%와 25%"와 같다.
  • 응답 리비전이 바뀐 시각 green(09:18:56.285) → blue(56.492) → green(57.104) → blue(57.314) → green(57.929)에서 green은 약 0.6~0.8초(요청 4개)마다 한 번, 그 사이 blue가 세 번 응답한다. "요청 4개마다 3개가 blue로" 가는 순서 세기가 그대로 보인다.
  • zone active_app 64k;가 있는 상태로만 실험했다. zone을 뺀 경우의 어긋남은 확인하지 못했다.

5. 실험 ③ green을 멈췄을 때 — 기본값과 연결 대기 1초 (교안 5-4, 09:19~09:23) — 실행: Claude

무료 Nginx에는 능동 헬스체크가 없다. 서버 하나가 갑자기 멈추면 사용자 요청이 어떻게 되는지, 3 대 1 설정 그대로 스크립트를 60초 돌리고 시작 약 10초 뒤 docker stop green을 실행해 보았다.

결과: 전체 요청 159건, 실패 13건, 60초 / blue 130건(82%) / green 16건(10%) / 실패 시각 처음 09:19:32.482, 마지막 09:20:06.439.

  • 실패 간격 2.83초는 "green 차례 요청 1개가 2초 제한에 걸려 실패 + 그 사이 blue 차례 3개" 한 바퀴와 맞는다. 4번에 한 번(green 차례) 요청이 실패한 것으로 읽힌다(로그는 응답 리비전이 바뀔 때만 찍히므로 blue 성공은 로그에 보이지 않는다).
  • 에러 로그의 upstream server temporarily disabled는 교안 3-3의 max_fails=1, fail_timeout=10s(기본값) 동작이다. green을 잠시 빼서 실패가 더 이어지지 않았다.
  • 교안과 다른 점: 교안은 연결 대기 시간(proxy_connect_timeout, 기본 60초)이 지나야 실패로 본다고 설명한다. 이번 환경에서는 실패 구간이 60초가 아니라 약 38초(09:19:32 → 09:20:10)였고, 로그의 원인도 타임아웃이 아니라 113: Host is unreachable이었다. 멈춘 컨테이너 주소로 가는 연결이 Docker 네트워크에서 응답을 못 받다가 커널이 도달 불가로 판정한 것으로 추정한다. 확인한 것은 오류 문구와 시각까지다. 실행 환경(Docker Desktop·Windows 11) 차이일 수 있다.
  • 그래도 교안의 핵심인 "알아채는 비용을 사용자 요청이 낸다"는 재현됐다. 실패 13건이 알아채는 데 쓰인 요청들이다.

5-2. ③-b 연결 대기 1초 (원본 실습로그/06_*.log)

  1. 09:21:07 docker start green
  2. Claude가 편집기 도구로 location / 안에 proxy_connect_timeout 1s; 한 줄 추가 → nginx -t 통과 → nginx -s reload(green을 다시 켰으니 reload로 이름을 다시 찾게 함, 교안 5-4)
  3. 스크립트 60초 시작, 09:21:33 docker stop green(09:21:37에 끝남)

11. 궁금했던 것

아래는 실습 중 사용자(DJ)가 실제로 한 질문이다.

Q1. "Supabase 진행과정을 상세하게 알려줘"

  • 사용자 몫(7-1의 5단계: 프로젝트 → SQL → 익명 로그인 → 한도 확인 → .env 입력) 뒤에 Claude가 컨테이너를 --env-file .env로 다시 띄우고 시작 로그의 storage·auth를 확인한다. 이어 게스트 로그인·약속 만들기 → Table Editor 확인 → green 전환·blue 재시작·시크릿 창 확인 → 정리 순서다. 실제 진행은 7절에 시각순으로 적었다.

Q2. "Supabase로 내가 어떤 일을 하면 되는지 상세하게 알려줘"

  • 사용자가 직접 할 일은 7-1의 5단계다(프로젝트 생성, SQL 실행, 익명 로그인 켜기, 한도 확인, 키 값을 편집기로 .env에 입력). 계정·키·비밀번호를 다루는 일은 에이전트가 대신하지 않고, 키 값은 채팅·명령·문서에 붙여 넣지 않는다. Claude는 .env를 읽지 않고 컨테이너 재기동·Nginx reload·시작 로그 확인만 한다. .env에서 기존 STORAGE·AUTH 줄은 새로 넣는 것이 아니라 값을 바꾸는 일이라는 점을 이번에 겪었다(8절 4번).

Q3. "Table Editor를 확인할 수 있는 URL을 알려줘"

  • 주소 자체는 이 보고서에 적지 않는다(프로젝트 주소가 들어 있고 저장소가 공개). Supabase 대시보드에 로그인해 해당 프로젝트(friend-agent-staging)를 선택한 뒤 Table Editor로 들어가 schema public에서 messages·reminders 테이블을 연다.
