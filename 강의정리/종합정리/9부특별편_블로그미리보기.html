AI 서비스를 세상에 내놓으며 깨진 9가지 착각 — 50대 기획자의 아이펠 배포·운영 특별편

‘배포 성공’, ‘상태 코드 200’, ‘CI 통과’가 떠도 사용자는 실패를 겪을 수 있다. AI 친구 서비스 하나를 열하루 동안 설계부터 무중단 배포까지 키우며 확인한 아홉 번의 착각.

$ deploy ✓ 배포 성공 (37초)$ watch ✗ 요청 295건 중 54건 실패 · 503 · 약 21초

터미널에는 배포 성공이라고 떴습니다. 같은 시각, 옆 창의 측정 스크립트는 실패 54건을 세고 있었습니다.

2026년 10월 29일, 아이펠 N053 실습 중에 본 장면입니다. 준비가 30초쯤 늦는 버전을 기본 설정으로 배포했더니 배포 명령은 깔끔하게 성공으로 끝났는데, 그 사이 약 21초 동안 사용자 요청 295건 중 54건이 503 오류를 받았습니다. 제가 화면만 봤다면 “잘 끝났다”고 보고했을 겁니다.

28년을 신규사업 기획과 경영으로 살면서 “보고서상 완료”와 “현장에서 실제로 된 것”이 다르다는 말은 수없이 했습니다. 그런데 이번 열하루 동안, 그 말을 아홉 번 다른 모양으로 다시 배웠습니다.

이 글은 아이펠 9부 「서비스화·배포·운영」(N045~N053) 아홉 강의를 마치고 쓰는 특별편입니다. 개발을 모르는 분도 읽을 수 있게, 각 착각을 “내가 믿은 것 → 실제로 본 숫자 → 남은 교훈” 순서로 적었습니다.

먼저, 무엇을 했나

열하루(10월 19일~29일) 동안 AI 친구 에이전트 서비스 하나(friend-agent, 대화하고 약속을 기억해 주는 챗봇)를 붙잡고, 매일 한 단계씩 키웠습니다. 아홉 강의는 네 구간으로 묶입니다. 세상에 내보내고, 배포를 자동화해 거르고, 확인한 것과 같은 것을 보내고, 바꾸는 동안 끊기지 않게 하는 순서입니다.

10-19 N045 코드 없이 서비스 설계하기 (PRD·아키텍처)

10-28 N052 로드밸런서로 끊김 없이 바꾸는 원리 익히기
10-29 N053 Cloud Run에서 무중단 배포하기

그리고 열하루 내내, 같은 일이 반복됐습니다. “성공했다”는 표시가 뜬 바로 그 순간에, 사용자 쪽에서는 무언가 실패하고 있었습니다.

착각 1. “이 서비스는 작가를 위한 것이다” — N045

믿은 것. 제가 구상하던 ASP(AI Story Partner)는 웹소설 작가가 쓰는 도구라고 생각했습니다. 스토리위즈 대표 시절 “이거 뜨겠습니까?”라는 질문에 근거를 대지 못했던 경험에서 나온 아이디어였으니까요.

실제로 본 것. N045는 PRD(기획서)를 쓰기 전에 사용 맥락 분석부터 하라고 순서를 정해 줍니다. 그 순서대로 PD 인터뷰 4문항과 자료 조사 2건을 해 보니, 이 서비스를 가장 먼저 쓸 사람은 작가가 아니라 PD였습니다.

교훈. 기획서부터 썼다면 처음부터 다시 만들 뻔했습니다. 순서를 지키는 것 자체가 리스크 관리입니다.

→ 그날의 기록: 순서를 지키지 않았다면 처음부터 다시 만들 뻔한 하루

착각 2. “오류 메시지가 원인을 알려 준다” — N046

믿은 것. 배포가 실패하면 화면에 뜬 메시지를 보고 고치면 된다고 생각했습니다.

실제로 본 것. 일부러 API 키 없이 배포해 보니, 터미널은 “포트를 열지 못했다”고 했습니다. 그 말만 믿었다면 엉뚱하게 포트 설정을 뒤졌을 겁니다. 컨테이너 로그를 열어 보니 진짜 원인은 한 줄, LLM_API_KEY 누락이었습니다. 그날 일지에 저는 이렇게 적었습니다. “단순 연결 불가가 아니라 키가 없음이었는데, 로그를 찾지 않았더라면 모를 뻔한 이야기.”

교훈. 터미널 메시지는 결과이고, 원인은 로그에 있습니다. 키는 코드가 아니라 Secret Manager(비밀 금고)에 두고 이름으로만 연결합니다.

→ 그날의 기록: 로그를 찾지 않았다면 키가 없다는 것을 몰랐을 하루

착각 3. “200이면 정상이고, 서버를 늘리면 버틴다” — N047

믿은 것. HTTP 상태 코드 200(성공)이면 사용자는 제대로 답을 받은 것이고, 최대 서버 수를 늘리면 사람이 몰려도 버틴다고 생각했습니다.

실제로 본 것. 두 가지 모두 깨졌습니다.

  • 평소 4.1초 걸리는 요청에 타임아웃을 3초로 걸자, AI 친구의 답이 문장 중간에서 잘렸습니다. 그런데 상태 코드는 200이었습니다.
  • 부하 테스트에서 서버 한 대가 요청을 하나씩만 받게 해 두고, 최대 서버 수를 3대로 둔 설정과 20대로 둔 설정을 비교했습니다. 결과는 똑같이 50건 중 15건만 성공했습니다. 로그에는 no available instance가 지연 0초로 찍혔습니다. 서버 수 상한이 아니라 서버를 새로 띄우는 속도가 먼저 막힌 것이었습니다. 교안에 없던, 직접 재서 알게 된 사실입니다.

교훈. 상태 코드만 보는 모니터링은 품질 문제를 못 잡습니다. 그리고 “최대 서버 수”는 처리 능력의 보증도, 비용의 상한도 아닙니다.

→ 그날의 기록: 최대 인스턴스를 늘려도 달라지지 않았던 이유

착각 4. “자동 배포가 성공했으면 문제없다” — N048

믿은 것. 사람이 손으로 하던 배포를 GitHub Actions에 맡기고, 배포가 초록불로 끝나면 안심해도 된다고 생각했습니다.

실제로 본 것. 일부러 사고 두 건을 머지해 봤습니다.

사고 자동 배포 결과 사용자에게 일어난 일
환경변수 이름 오타 실패 아무 일도 없음 — 이전 버전이 계속 응답
시간대 처리 오류 성공 “내일 아침 8시” 약속이 오후 5시(17:00)로 저장

배포가 실패한 사고는 오히려 안전했고, 배포가 성공한 사고가 사용자에게 피해를 줬습니다.

교훈. 자동 배포는 서비스가 “켜지는지”만 확인합니다. 제대로 “동작하는지”는 확인하지 않습니다.

→ 그날의 기록: 권한을 줬는데도 거절당한 이유

착각 5. “테스트가 빨간불이면 알아서 막아 준다” — N049

믿은 것. 자동 테스트(CI)를 붙이면 실패한 변경은 들어오지 못한다고 생각했습니다.

실제로 본 것. 어제의 시간대 버그는 서버와 같은 조건(TZ=UTC)으로 테스트를 돌리자 17:00 실패로 정확히 잡혔습니다. 그런데 테스트가 빨간불인 변경도 그대로 머지가 됐습니다(UNSTABLE). 머지를 실제로 막은 것은 테스트가 아니라 브랜치 보호 규칙이었습니다(BLOCKED). 또 하나, 보내기 버튼을 숨긴 변경은 모든 자동 검사를 통과했고, 시험 서버(staging)를 직접 열어 본 사람만 발견했습니다.

교훈. CI는 알려 줄 뿐 막지는 못합니다. 막는 것은 규칙이고, 화면과 말투는 여전히 사람이 봐야 합니다.

→ 그날의 기록: CI는 알려 줄 뿐 막지 못한다는 것을 배운 하루

착각 6. “내 컴퓨터에서 되면 서버에서도 된다” — N050

믿은 것. 사진 속 글자를 읽는 기능(OCR)이 제 PC에서 잘 돌았으니, 서버에서도 될 거라 생각했습니다.

실제로 본 것. staging에 올리자 사진 요청이 500 오류. 로그에는 tesseract 프로그램을 찾을 수 없습니다. 코드는 같았지만 서버에 그 프로그램이 깔려 있지 않았던 겁니다. Dockerfile에 “이 프로그램을 설치하라”는 줄을 적자, 같은 사진이 내 PC·내 PC의 컨테이너·staging·production 네 곳 모두에서 200, 153글자, 똑같은 결과를 냈습니다. 다음에 PDF 읽기를 붙일 때는 서버에 올리기 전, 내 PC의 컨테이너에서 같은 문제를 먼저 잡았습니다.

교훈. 코드만이 아니라 실행 환경도 코드로 적어 둬야 같은 결과를 약속할 수 있습니다.

→ 그날의 기록: 내 컴퓨터와 같은 환경이 서버에서는 보장되지 않는다는 것을 배운 하루

착각 7. “같은 코드로 만들면 같은 것이다” — N051

믿은 것. staging과 production이 같은 코드에서 각각 빌드되니, 둘은 같은 것이라고 생각했습니다.

실제로 본 것. 전날(N050) 같은 Dockerfile로 두 번 빌드했을 때, 설치된 패키지는 같은데 이미지 ID가 달랐습니다. staging에서 확인한 것과 production에 나간 것이 엄밀히는 다른 물건이었던 셈입니다. 그래서 이미지를 한 번만 만들고, staging에서 확인한 그 이미지의 지문(다이제스트)을 그대로 production으로 옮기게 바꿨습니다. 두 환경 모두 sha256:d339e5d333ec…로 일치했고, 덤으로 production 배포 시간이 1분 26초에서 46초로 줄었습니다.

교훈. “확인한 것을 배포했다”고 말하려면, 다시 만들지 말고 옮겨야 합니다.

→ 그날의 기록: 한 번 만든 이미지를 그대로 옮겨야 같은 이미지라고 말할 수 있다는 것을 배운 하루

착각 8. “요청이 하나도 안 끊겼으면 무중단이다” — N052

믿은 것. 서버 두 벌(blue·green)을 띄우고 로드밸런서로 갈아 끼우면서 실패한 요청이 0건이면 “무중단 배포 성공”이라고 생각했습니다.

실제로 본 것. 전환·롤백하는 70초 동안 요청 341건, 실패 0건. 완벽해 보였습니다. 그런데 green으로 전환하고 대화창을 열자 대화가 0개였습니다. 대화가 각 서버의 메모리에만 있었기 때문입니다. 대화를 서버 밖 데이터베이스(Supabase)로 옮기자, 같은 전환과 재시작 뒤에도 대화 3개가 그대로 남았습니다.

교훈. 요청이 안 끊겨도 사용자가 하던 일은 끊길 수 있습니다. 전환 성공은 곧 무중단이 아닙니다.

→ 그날의 기록: 전환에 성공해도 무중단이 아닐 수 있다는 것을 배운 하루

착각 9. “배포가 성공했으면 사용자도 괜찮다” — N053

믿은 것. 이 글 첫 장면의 그 믿음입니다.

실제로 본 것. Cloud Run은 기본적으로 “포트가 열렸는지”만 보고 새 버전이 준비됐다고 판단합니다. 그래서 앱이 아직 준비 중인데도 트래픽이 넘어가 503이 54건 났습니다. 준비 확인 경로를 /health로 바꾸자 같은 조건에서 0건. 대신 배포 시간은 27초에서 약 84초로 늘었습니다. 사용자가 오류를 보는 것보다 배포가 1분 늦는 편이 낫다고 판단했습니다.

마지막으로 이 절차를 자동화했습니다. 새 버전을 트래픽 0%로 먼저 올리고 → 전용 주소로 점검(스모크 테스트)하고 → 통과해야 사용자에게 전환합니다. 일부러 망가진 버전을 머지해 보니, 자동 테스트는 통과했지만 스모크 테스트가 전환을 막았고, 그 사이 사용자 요청 735건은 하나도 실패하지 않았습니다.

교훈. 배포 성공은 “사용자가 오류를 보지 않았다”는 증거가 아닙니다. 그리고 하나 더, 버튼 하나로 되돌리는 롤백조차 직후 몇 초 동안 4건이 실패했습니다. 롤백은 배포보다 약했습니다.

→ 그날의 기록: 배포가 성공해도 받을 준비가 된 것은 아니라는 것을 배운 하루

왼쪽 열은 모두 시스템이 스스로 내리는 판정이고, 오른쪽 열은 모두 사용자가 겪는 일입니다. 9부 아홉 강의는 결국 이 두 열 사이의 간격을 하나씩 재고, 장치를 하나씩 끼워 넣어 좁히는 과정이었습니다.

열하루 뒤, 내 손에 남은 배포 라인

처음엔 터미널에 명령 한 줄을 쳐서 배포했습니다. 열하루 뒤에는 이런 라인이 됐습니다.

경영 언어로 바꾸면 이것은 신규 매장 오픈 매뉴얼과 닮았습니다.

  • 간판 불이 켜진 것(배포 성공)과 손님이 불편 없이 주문하고 나간 것(사용자 경험)은 다릅니다.
  • 본점에서 검수한 레시피는 지점에서 새로 만들지 말고 그대로 보내야 합니다(이미지 승격).
  • 교대할 때 인수인계 노트가 없으면 앞 근무자가 받은 주문이 사라집니다(메모리에만 있던 대화).
  • 가오픈(0% 배포)과 철수 기준(롤백)은 오픈 전에 정해 둡니다.

내 AI 서비스를 내놓기 전에 던질 9가지 질문

이번 열하루를 질문 아홉 개로 압축했습니다. 개발자가 아니어도, AI로 무언가를 만들어 남에게 보여 줄 계획이라면 한 번쯤 써먹을 수 있을 겁니다.

  1. 이 서비스를 가장 먼저 쓸 사람은 정말 내가 생각한 그 사람인가? 한 명이라도 직접 물어봤나? (N045)
  2. 오류가 나면 원인을 어디서 볼 것인가? 화면 메시지 말고 로그를 볼 줄 아는가? (N046)
  3. “성공” 응답 안의 내용은 멀쩡한가? 답이 잘려도 200일 수 있다. (N047)
  4. 배포가 성공한 뒤, 실제로 한 번 써 봤는가? 자동 배포는 켜지는지만 본다. (N048)
  5. 실패한 테스트가 머지를 정말 막는가? 아니면 알려 주기만 하는가? (N049)
  6. 서버에 필요한 프로그램이 내 PC에만 있는 건 아닌가? (N050)
  7. 확인한 것과 내보낸 것이 같은 물건인가? (N051)
  8. 버전을 바꿔도 사용자가 하던 일(대화·장바구니·작성 중인 글)이 남는가? (N052)
  9. 망가진 버전이 나가려 할 때, 사용자에게 닿기 전에 멈추는 장치가 있는가? 되돌리는 데 몇 초 걸리는가? (N053)

아직 못 한 것

솔직하게 남겨 둡니다.

  • 배포 알림(성공·실패·롤백을 메신저로 받기)은 N047부터 계속 다음으로 미뤄졌고, N053에서 선택 과제로 나왔지만 이번에도 하지 못했습니다.
  • 오류율을 보고 새 버전 비율을 자동으로 올리거나 되돌리는 카나리 자동 승격, 데이터베이스 구조가 바뀌는 배포는 아직 이론으로만 압니다.
  • 롤백 직후 4건이 실패한 원인은 서버가 식어 있었던 것(콜드 스타트)으로 추정만 할 뿐 확인하지 못했습니다.
  • 이 라인을 제 서비스(My-Story-Maker 등)에 옮기는 일이 다음 숙제입니다.

용어 정리

용어 쉬운 설명
배포 내 컴퓨터의 코드를 서버에 올려 다른 사람이 쓸 수 있게 하는 일
Cloud Run 구글 클라우드의 서버 대여 서비스. 요청이 오면 서버를 띄우고, 없으면 줄인다
리비전 배포할 때마다 생기는 서비스의 한 벌. 이전 리비전으로 트래픽을 돌리면 롤백
상태 코드 서버가 요청에 붙이는 결과 번호. 200은 성공, 500·503은 서버 쪽 실패
콜드 스타트 한동안 쉬던 서비스에 첫 요청이 오면 서버를 새로 띄우느라 느려지는 현상
CI 코드가 바뀔 때마다 자동으로 테스트를 돌리는 장치
브랜치 보호 테스트를 통과해야만 코드를 합칠(머지) 수 있게 막는 규칙
staging 사용자에게 내보내기 전에 먼저 써 보는 시험 서버
Dockerfile 서버에 깔아야 할 프로그램과 실행 방법을 적은 설계도. 이걸로 만든 결과물이 이미지

스모크 테스트 새 버전을 사용자에게 보내기 전에 핵심 기능만 빠르게 점검하는 시험

맺으며

53개 강의를 지나오며 저는 AI를 쓰는 사람에서, AI를 아는 사람, AI에게 일을 설계해 맡기는 사람을 거쳐, 이번 9부에서 그 일을 서비스로 운영하는 사람의 문턱에 섰습니다.

돌아보면 9부가 가르친 기술은 매번 달랐지만 질문은 하나였습니다. “시스템이 성공이라고 말할 때, 사용자는 정말 괜찮은가?” 그리고 그 질문에 답하는 방법도 하나였습니다. 화면을 믿지 말고 사용자 쪽에서 숫자를 재는 것. 503 54건, 잘린 답, 17시로 저장된 8시 약속, 사라진 대화. 모두 화면이 아니라 측정이 보여 준 것들입니다.

28년 동안 “현장에 가 봐라”는 말을 귀에 못이 박히도록 듣고, 또 했습니다. 클라우드에도 현장이 있었습니다. 로그와 측정 스크립트가 그곳이었습니다.
