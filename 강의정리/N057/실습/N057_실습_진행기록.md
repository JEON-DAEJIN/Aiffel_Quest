## 0. 시작 질문 (학습서 1장, 사용자가 직접 씀)

> Q. 웹으로 잘 돌아가는 서비스를 휴대폰 앱으로 만든다고 할 때, 무엇이 새로 필요하고 무엇은 그대로 쓸 수 있을 것 같은지 적어 보세요. 화면, 서버, 데이터베이스, 로그인, 배포로 나눠 생각해 보면 됩니다. (/300)

**사용자의 답(원문 그대로, 2026-11-05)**:

> 화면은 PC가 아니라 스마트폰에 보기 좋은 것으로 최적화할 필요가 있고, 아무래도 앱으로 배포되는 만큼 중요한 정보는 서버나 데이터베이스에 보관해야 하는 것으로 알고 있다.

**교안과 대어 본 것(9장 회고에서 다시 꺼낼 메모)**:

| 답에 있는 것 | 교안의 어느 장과 이어지나 |
|---|---|
| 화면은 스마트폰에 맞게 새로 | 6장 — 앱은 화면만 가진다(React Native 화면), 8장 화면 고치기 |
| 중요한 정보는 서버·DB에 | 6-6 — `EXPO_PUBLIC_` 값은 앱 파일에 들어가 공개되므로 비밀값은 백엔드에만. 2-7 — 대화 기록은 백엔드, 로그인 토큰만 폰 |

아직 답에 없는 것(오늘 채울 것): **서버·DB·로그인은 그대로 쓸 수 있는가**(6장 — 백엔드 API를 하나도 바꾸지 않음), **로그인**이 기기마다 따로 생긴다는 점(7장 — 다른 게스트), **배포**가 웹과 다르다는 점(2장 — 앱 파일·스토어·옛 버전이 남음, 하위 호환성).

```text
PATH="C:\Program Files\Tesseract-OCR;$PATH"  OCR_ENABLED=true
.venv\Scripts\python -m uvicorn app.main:app --host 0.0.0.0 --port 8080
```

## 4. 백엔드 주소 넣고 내 폰에서 띄우기 (학습서 7장, 2026-11-05)

**백엔드 로그(폰 = 같은 와이파이의 다른 기기)** — 교안 6장 시퀀스와 같은 순서:

### 4-1. 결과 해석: 같은 백엔드, 다른 게스트 (교안 7-4, 2026-11-05)

**예상**: 같은 백엔드를 노트북 브라우저(`http://localhost:8080`)로 열면, 앱의 대화가 보이거나(같은 사람) 캐릭터 만들기 화면이 나온다(새 게스트).

**실제(사용자 화면)**: **둘 다 아니었다** — 예전(N052~N056) 실습 때의 화면이 떴다. 🐻 "하루", 크레딧 30, 예전 날씨 대화. 이 브라우저는 그때 받은 게스트 토큰을 브라우저 저장소에 간직하고 있어, 같은 주소를 열자 **예전 게스트로 다시 로그인**했다. 폰에서 오늘 만든 캐릭터는 이름은 같은 "하루"지만 🐶 강아지였다(사용자).

## 5. 저장하면 바로 바뀌는 것 (학습서 8-1, 2026-11-05)

**① 문구 바꾸기** — 교안의 "첫 메시지를 보내 보세요."(`index.tsx` 100행)는 `messages.length === 0`일 때만 보인다. 이미 대화가 있어 바꿔도 화면 변화가 없으므로, 지금 보이는 입력창 안내 문구(113행 `placeholder="메시지 보내기"`)로 바꿨다. 새 문구는 사용자가 정했다: "오늘 같은 날 커피는 어떤 걸로 마실까?"

- 저장 뒤 사용자가 계속 지켜봤는데 **폰에 변화가 없었다.** 확인 순서: 파일 저장됨(113행) → Metro `/status` = `packager-status:running` → 사용자 터미널에 `Android Bundled 76ms … (1 module)` → 개발자 메뉴 **Reload** 뒤 `Android Bundled 103ms … (1 module)`, 그제야 폰에 새 문구가 떴다.

**② 일부러 괄호 지우기** — 66행 `setMessages((prev) => […]);`의 `)`를 지우고 저장했다(Reload 없이 지켜봄).

- 사용자 터미널: `ERROR SyntaxError: …\src\app\index.tsx: Unexpected token, expected "," (66:104)`와 코드 발췌(`^`가 지운 자리), 그 아래 Babel 내부 경로 수십 줄(같은 덩어리 2회).
- 폰: **`TransformError: SyntaxError`가 저절로 떴다**(사용자). → 파일 감지·자동 반영(Fast Refresh) 모두 살아 있음. ①에서 자동 반영이 안 된 것은 그때만의 일시적 연결 문제로 정리(원인은 확인 못 함).
- 괄호를 되돌려 저장했다(`])`).

교안과 다른 점: 교안은 "몇 초 안에 폰 화면이 바뀐다"고 했지만, 첫 번째 변경은 Reload해야 바뀌었다. 두 번째(오류)부터는 자동으로 반영됐다.

## 7. 사진 OCR 시험 — 사진첩 경로 결과 (2026-11-05)

- 사진첩에서 고른 사진: **손글씨** 메모. 실제 내용은 "11월7일 오전 10시30분 미용실예약".
- 백엔드 기록: `POST /api/ocr 200`, `lang: kor+eng`, `chars: 22` — 요청·응답은 정상.
- 입력창에 들어온 글(앞 안내 문장 뒤):
  ```
  11 1%
  OK 1 0A! 204
  AOA
  ```
- 판단: 코드 오류가 아니라 **엔진·사진 조건의 한계**. tesseract는 인쇄체용이라 한글 손글씨를 거의 읽지 못한다(교안 8-10).

- 엔진을 바꾸는 일(예: 손글씨에 강한 OCR)은 백엔드 몫이라 앱을 다시 빌드할 필요는 없다(교안 8-11).
- 그 뒤 Expo Go에서 하루친구를 다시 열자 **원만 계속 돌고 열리지 않음** → 7-1에서 다룸.

### 7-1. 카메라 경로 — 고친 뒤 성공 (2026-11-05)

- 원이 계속 돌던 문제: 노트북 쪽은 정상(Metro `running`, 안드로이드 묶음 약 6MB 정상 생성, 폰 요청이 백엔드에 0건).
  → 폰이 묶음을 받아 오는 연결 구간 문제로 판단, 폰에서 다시 열어 해결.
- 카메라 시험: **인쇄물**을 찍음 → 사용자 확인 **"정확히 읽었어"**. 백엔드에 `POST /api/ocr 200`이 기록됨(카메라 경로로는 처음 도착).
- 카메라 경로가 막혔던 원인과 해결(앞의 세 번 시도 포함):
  1. `fetch` + `{uri,name,type}` → "Unsupported FormDataPart implementation" (SDK 58은 `expo/fetch`가 전역 fetch)
  2. expo-file-system `File` → "FileSystemFile.bytes … missing 'READ' permission" (Expo Go 안에서 JS 파일 읽기 막힘)
  3. `XMLHttpRequest` → 사진첩은 성공, 카메라만 "네트워크 오류". 백엔드엔 요청이 오지 않음
  4. **찍은 사진 주소를 화면 이동 주소(params)에 싣지 않고 앱 안의 작은 보관함(`src/lib/photoHandoff.ts`)으로 넘김 → 성공**
- 교훈: 같은 업로드 함수가 사진첩에선 되고 카메라에선 안 될 때, 함수가 아니라 **두 경로의 차이(사진 주소를 넘기는 방법)**를 의심한다.
  오류 문구 "백엔드 주소·와이파이 확인"은 이번 경우엔 틀린 힌트였다(요청이 폰 밖으로 나가기도 전에 실패).
- 손글씨(7절)와 인쇄물(7-1)의 차이 = 엔진의 한계는 **사진 종류**에 따라 갈린다는 실제 비교.

### 7-2. 앱이 멈춘 것처럼 보인 진짜 원인 — 노트북 와이파이가 바뀜 (2026-11-05)

- 증상: 보내기 뒤 앱이 멈춤 → 다시 열자 `fetch failed: java.net.ConnectException: Failed to connect to /<노트북 주소>:8080`.
- 확인: 백엔드에 `/api/chat` 요청 0건. 노트북이 다른 와이파이로 자동 전환돼 주소가 바뀌어 있었다(앱의 `.env` 주소는 옛 주소 그대로).
  앞(7-1)의 "원만 계속 도는" 증상도 같은 원인이었을 가능성이 크다.
- 해결: 폰·노트북을 **같은 와이파이(<원래 와이파이>)**로 다시 연결 → 노트북 주소가 원래대로 돌아와 8080·8081 모두 응답.
- 교훈: 노트북 백엔드 + 같은 와이파이 방식은 **노트북 주소가 바뀌면 앱이 길을 잃는다**. 클라우드 배포(고정 주소)가 필요한 이유 하나를 몸으로 확인.

3. **같은 기능이 한 경로만 실패하면 두 경로의 차이를 본다** — 사진첩은 되고 카메라만 안 될 때 원인은 업로드 함수가 아니라 사진을 넘기는 방법이었다(7-1).

### 11-6. 가장 오래 막힌 곳 (사용자가 직접 씀, 원문 그대로)

> 카메라 열기를 통해 손글씨를 인식하는 것이 가장 힘들었어.
> 인쇄된 다른 글씨는 잘 읽히는데 손글씨와 화면 모니터를 찍은 것은 잘 구분하지 못했어. 그래도 클로드와 대화를 통해 하나하나 변수를 바꿔가면 고쳐가는 과정이 재미있었어. 결과가 잘 나와 다행이야.

- 기록과 대조: 손글씨 시험은 사진첩에서 고른 사진이었다(7절). 카메라 경로는 업로드가 세 번 막힌 뒤 고쳐졌고(7-1), 화면 사진은 깨지고 캡처는 정확했다(7-3).
