핵심 한 문장 요약

📌 요약 — 웹으로 잘 돌아가는 AI 친구 서비스를 폰 앱으로 가져갈 때 새로 만드는 것은 화면(사용자 접점)뿐이고 백엔드·데이터베이스·AI는 그대로 쓴다. ① 웹은 열 때마다 서버에서 화면 코드를 받지만 앱은 설치해 둔 파일을 실행하므로 옛 버전 앱이 사용자 폰에 남고, 그래서 백엔드 응답 모양을 함부로 바꾸지 않는다(하위 호환성). ② PWA·웹 래핑·네이티브·React Native+Expo 가운데, Windows 노트북 + 코딩 에이전트 + 이미 있는 백엔드라는 조건에서는 내 컴퓨터에 Node.js만 두고 컴파일을 클라우드(EAS)에 맡기는 Expo가 iOS까지 다룰 수 있는 방법이다. ③ 개발할 때는 네이티브 부분이 미리 컴파일된 Expo Go가 노트북의 번들을 받아 실행하므로 저장하면 폰 화면이 몇 초 안에 바뀌고, Expo Go에 없는 네이티브 기능만 개발용 빌드가 필요하며, 프로젝트와 Expo Go의 SDK 버전(58)이 같아야 열린다. ④ 앱은 백엔드 주소 하나로 시작해 설정을 받고 익명 로그인 토큰을 붙여 같은 API를 부르며 답을 스트리밍으로 받고, 비밀값은 앱에 넣지 않는다. ⑤ 화면을 고칠 때는 그 정보가 어디서 오는지 먼저 확인한 뒤 에이전트에게 맡기고, 카메라로 찍은 일정표는 백엔드 OCR이 읽되 보내기 전에 사람이 확인하게 한다.

🧪 예제 — 한 줄 예: 종이에 "11월 20일 오후 3시 치과"라고 크게 적고 앱의 📷 버튼으로 찍으면, 앱은 사진을 받아 권한을 묻고 백엔드 /api/ocr에 보내는 일까지만 한다. 글자를 읽는 일(OCR)과 약속을 만드는 일은 백엔드가 하고, 읽은 글은 바로 보내지 않고 입력창에 넣어 사람이 "2시"를 "3시"로 고친 뒤 보낸다. 그래서 나중에 OCR 엔진을 더 좋은 것으로 바꿔도 앱은 다시 빌드할 필요가 없고, 카메라 화면의 안내 문구를 바꿀 때만 앱을 고친다.

한눈에

  • 무엇을 하나 — N046~N056에서 키운 AI 친구 에이전트 서비스(friend-agent)는 지금 웹 주소로만 쓸 수 있다. 오늘은 같은 백엔드를 그대로 쓰는 휴대폰 앱(friend-agent-mobile)을 Windows 노트북과 코딩 에이전트로 만들어 내 폰에서 띄운다.
  • 어떻게 배우나 — 휴대폰으로 가져가는 네 가지 방법을 비교해 Expo를 고르고, 템플릿 저장소로 앱을 만들어 폰의 Expo Go로 QR 코드를 찍어 실행한 뒤, 답 아래 기억·약속 메모를 붙이고, 카메라로 찍은 일정표를 읽어 약속으로 만드는 기능까지 더한다.
  • 순서 — 웹과 앱의 차이 → 네 가지 방법과 선택 기준 → Expo의 구조 → 시작 상태 맞추기 → 템플릿 구조와 데이터 흐름 → 내 폰에서 띄우기 → 화면 고치기와 사진 기능 → 정리.
  • 오늘의 교훈 — 좋은 모바일 앱은 모든 기능을 앱 안에 만드는 것이 아니라, 앱과 백엔드가 각자 잘하는 일을 나누도록 설계하는 것이다. 코딩 에이전트가 코드를 써도 무엇을 어디에 만들지 정하는 것은 사람이다.

⚠️ 주의 — 오늘의 범위: 앱 파일을 빌드해 다른 사람 폰에 설치하고 스토어 출시를 준비하는 일은 다음 단계다(학습서 p1, "오늘은 빌드를 하지 않으므로" p15). 해설서 Ch02의 개발 전략에 "Android와 iOS 앱을 각각 빌드하고 배포합니다"가 들어 있지만, 그것은 전체 여정을 말한 것이고 오늘 실습은 Expo Go로 내 폰에서 띄우는 데까지다.

1. 잘 돌아가는 웹 서비스를 왜 폰 앱으로 가져가나? (원문 Ch01)

1-1. 오늘의 상황

학습서 도입은 이렇게 시작한다.

지금 AI 친구 에이전트 서비스는 웹 주소로만 쓸 수 있습니다. 친구처럼 매일 말을 거는 서비스라면 사용자는 브라우저를 열고 주소를 찾기보다 폰 홈 화면의 앱 아이콘을 누르고 싶어 합니다. 그런데 앱을 만들려면 Swift와 Kotlin을 따로 배우고, Android Studio와 Xcode를 설치하고, iOS 앱은 Mac에서만 빌드할 수 있다고 알려져 있습니다. Windows 노트북으로, 코딩 에이전트와 함께, 지금 있는 백엔드를 그대로 쓰는 앱을 만들 수는 없을까요. (학습서 p1)

해설서는 이것을 출입구가 다르다고 말한다 — 같은 AI 친구와 대화하더라도 웹에서는 크롬 브라우저로, 앱에서는 스마트폰에 설치된 AI 친구 아이콘을 눌러 들어온다. 두 출입구는 같은 백엔드와 데이터베이스를 쓸 수 있다.

웹 서비스:  브라우저 → 웹 주소 → 서버
모바일 앱:  앱 아이콘 → 앱 실행 → 서버
공통점:     두 방식 모두 같은 백엔드와 데이터베이스를 사용할 수 있다

1-2. AI 개발자가 모바일을 알아야 하는 세 가지 이유 (해설서)

  1. 서비스 접근성 — 매일 쓰는 서비스는 브라우저 주소보다 홈 화면 아이콘이 가깝다.
  2. 스마트폰의 하드웨어 활용 — 카메라·사진첩·알림 같은 기능을 AI와 연결할 수 있다.
  3. 기존 시스템의 재사용 — 백엔드를 다시 만들지 않으므로 개발 비용과 운영 복잡성이 줄어든다.

해설서의 한 줄: 모바일은 웹사이트를 작은 화면으로 옮기는 것이 아니라 AI 서비스가 사용자의 일상 속으로 들어가는 접점이다.

  3. Expo가 개발, 빌드, 배포를 어떻게 나눠 처리하는지 설명하고, Expo Go와 개발용 빌드의 차이와 한계를 말할 수 있다.

  5. 템플릿으로 만든 앱을 내 폰의 Expo Go로 실행하고, 연결이 안 될 때 원인을 찾아 해결할 수 있다.

2. 웹과 앱은 무엇이 다르고, 왜 iOS는 Mac이 필요한가? (원문 Ch02)

2-1. 웹은 매번 받아서 실행하고, 앱은 설치해 둔 파일을 실행한다

지금까지 만든 에이전트 서비스는 웹 서비스입니다. 사용자가 브라우저에 주소를 넣으면 브라우저가 서버에서 화면 코드(HTML, JavaScript)를 받아 그 자리에서 실행하고, 탭을 닫으면 그 코드는 사라집니다. 다음에 주소를 열면 서버에서 다시 받으므로, 서버에 새 버전을 배포하면 모든 사용자가 곧바로 새 화면을 봅니다. (학습서 p2)

앱은 폰에 설치해 두고 실행하는 프로그램이다. 앱 파일 안에는 화면 코드, 아이콘과 이미지, 앱 이름과 권한 같은 설정이 함께 들어 있고, 사용자는 스토어에서 이 파일을 한 번 내려받아 설치한다. 그래서 화면을 고치면 앱 파일을 새로 만들어 스토어에 올리고 사용자가 업데이트해야 바뀌며, 업데이트하지 않은 사용자의 폰에는 옛 버전이 계속 남는다.

그림 2. 웹과 앱이 화면 코드를 얻는 길. 화면 코드가 오는 길은 다르지만, 대화·기억·크레딧 같은 데이터는 둘 다 같은 백엔드 API에서 받는다.

읽는 법: 위 두 줄은 "화면 코드가 어디서 오는가"만 다르고, 아래 칸(백엔드)은 같다. 그래서 웹에서 앱으로 바꿔도 대화·기억·크레딧은 백엔드가 그대로 돌려주지만, 옛 버전 화면이 폰에 남는 문제가 새로 생긴다.

해설서의 비유: 웹은 인터넷 서점에 매번 접속해 책을 가져오는 방식, 앱은 책을 한 번 사서 내 책장에 보관하고 읽는 방식이다.

2-2. 왜 백엔드 응답 모양을 함부로 바꾸면 안 되나? (하위 호환성)

웹은 화면과 서버를 함께 배포하면 끝나지만, 앱을 내놓은 뒤에는 옛 버전 화면이 새 백엔드를 부르는 상황이 생깁니다. 그래서 앱이 쓰는 백엔드 API의 응답 모양은 옛 앱이 읽지 못하게 함부로 바꾸지 않습니다. (학습서 p3)

이것을 하위 호환성(Backward Compatibility)이라고 한다 — 새로운 시스템을 만들더라도 이전 버전의 사용자들이 계속 이용할 수 있도록 배려하는 것.

💡 팁 — [보충 비유] 경영 언어로는 이미 나간 계약서 양식과 같다. 거래처(옛 앱)가 옛 양식으로 주문서를 보내오는 한, 본사(백엔드)는 새 양식을 만들더라도 옛 양식을 계속 받아 줘야 한다. 필드 이름을 바꾸고 싶으면 옛 이름을 한동안 같이 보내 주고, 옛 앱이 충분히 사라진 뒤에 뺀다.

2-3. 운영체제와 플랫폼은 무엇인가?

2-5. 빌드는 무엇이고, 무엇을 바꾸면 다시 해야 하나?

빌드는 소스 코드와 설정을 받아 폰이 설치할 수 있는 앱 파일로 바꾸는 과정이다. 해설서: 요리 레시피를 실제 음식으로 완성하는 과정.

그림 3. 빌드 순서(학습서 p5 그림을 다시 그림). 3번은 JavaScript를 묶고, 4번은 네이티브 부분을 기계어로 바꾸고, 5번은 누가 만들었는지 표시한다.

읽는 법: 3번까지는 어느 컴퓨터에서나 할 수 있지만, 4번 컴파일과 5번 서명은 플랫폼 회사가 내놓은 도구로만 할 수 있다. 오른쪽 끝의 앱 파일이 사용자 수만큼의 폰에 설치되므로 한 번 내보낸 앱 파일은 되돌릴 수 없다.

그림의 3번 번들(bundle)은 내 JavaScript 코드를 실행에 필요한 파일 하나로 묶은 것이고, 4번 컴파일(compile)은 네이티브 부분의 코드를 기계가 실행하는 형태로 바꾸는 일입니다. 5번 서명은 개발자의 키로 누가 만든 파일인지 표시하는 일이라, 폰과 스토어는 서명을 보고 파일이 중간에 바뀌지 않았는지, 같은 개발자가 낸 새 버전인지 확인합니다. (학습서 p5)

3. 휴대폰으로 가져가는 방법은 몇 가지이고, 무엇을 고르나? (원문 Ch03)

3-1. 네 가지 방법은 각각 무엇인가?

PWA(Progressive Web App)는 웹 페이지에 설정 파일과 서비스 워커를 더해, 브라우저에서 "홈 화면에 추가"로 앱처럼 설치하게 하는 방식입니다. 따로 빌드하지 않으므로 가장 가볍지만, 스토어에 올라가지 않고 알림 같은 기기 기능은 브라우저가 허용하는 만큼만 씁니다. 웹 래핑(Capacitor 등)은 웹 페이지를 앱 껍데기에 넣어 스토어용 앱 파일로 만드는 방식입니다. 화면은 여전히 웹이고, 앱 파일을 만들려면 내 컴퓨터에 Android Studio와 Xcode가 있어야 합니다. (학습서 p7)

네이티브는 iOS는 Swift, Android는 Kotlin으로 각각 만들거나, Flutter처럼 한 코드로 두 플랫폼의 네이티브 앱을 만드는 방식입니다. 폰의 모든 기능을 쓸 수 있지만, 빌드 도구를 내 컴퓨터에 설치해야 하고 iOS 앱은 Mac에서만 빌드할 수 있습니다. React Native는 JavaScript로 코드를 쓰면 폰의 네이티브 화면 요소로 그려 주는 프레임워크이고, Expo는 React Native 앱을 만들고 빌드하고 배포하는 과정을 묶어 주는 도구 모음입니다. Expo는 앱 파일을 클라우드에서 빌드하므로, 내 컴퓨터에는 Node.js만 있으면 되고 Windows에서도 iOS 앱 파일을 만들 수 있습니다. (학습서 p7)

3-4. 이 과정은 왜 Expo인가?

이 과정의 조건은 세 가지입니다. 수강생 노트북은 대부분 Windows이고, 코딩 에이전트와 함께 만들며, 백엔드는 이미 있어서 앱은 화면만 새로 만들면 됩니다. 이 조건에서 iOS까지 다룰 수 있으면서 내 컴퓨터에 설치할 것이 가장 적은 방법이 Expo라서, 오늘은 Expo로 진행합니다. 다만 Expo도 앱 파일은 결국 컴파일해야 하므로, 그 일을 클라우드 서비스(EAS)에 맡긴다는 점과 무료 플랜의 빌드 횟수 제한은 감수합니다. (학습서 p8)

해설서는 두 가지를 덧붙인다.

  • "다른 방법들이 잘못된 것은 아닙니다." 단순히 웹사이트를 폰에서 편하게 쓰는 것이 목적이면 PWA가 더 경제적일 수 있고, 카메라·사진첩·AI 대화·향후 알림까지 쓰려는 서비스라면 Expo가 더 적합하다.
  • "모든 서비스를 처음부터 모바일 앱으로 만들 필요는 없습니다." 초기에는 PWA나 웹으로 시장 반응을 확인하고, 사용자가 스마트폰 기능을 적극적으로 쓰기 시작할 때 Expo 앱으로 넓히는 전략도 좋다.

⚠️ 주의 — React Native와 Expo가 모든 네이티브 기능을 자동으로 해결하는 것은 아니다. 추가 네이티브 모듈이나 설정이 필요할 수 있고, EAS 클라우드 빌드는 무료 플랜에서도 제한이 있다(해설서 p19). 무료 플랜의 정확한 횟수는 원문에 없으니 Expo 요금 안내에서 확인한다.

💡 팁 — [보충 비유] 경영 언어로는 사업 확장 단계별 채널 전략이다. PWA는 기존 매장에 "모바일 주문" 링크를 붙인 테스트 마케팅, Expo는 직영 앱을 내는 본격 진출, 네이티브는 플랫폼별 전담 조직을 따로 꾸리는 대규모 투자다. 시장 검증 전에는 작은 투자부터 하라는 해설서의 조언과 같은 이야기다.

🧪 예제 — [이해 점검, 학습서 p8] PWA와 웹 래핑은 둘 다 화면을 웹으로 그린다. 두 방법의 차이로 맞는 것은? → 웹 래핑은 스토어에 올릴 앱 파일을 만들기 때문에 내 컴퓨터에 Android Studio와 Xcode가 필요하다. (부록 G 문제 2)

▶ 한 줄 요약: 네 방법은 화면을 무엇으로 그리고 앱 파일을 어디서 만드느냐가 다르며, Windows + 코딩 에이전트 + 백엔드 있음이라는 조건에서 iOS까지 가장 가볍게 다루는 방법이 Expo다(대가: 클라우드 빌드 의존과 무료 횟수 제한).

4. Expo는 무엇을 대신해 주고, 무엇을 대가로 받나? (원문 Ch04)

4-1. Expo는 무엇인가?

Expo는 React Native로 Android와 iOS 앱을 만들 때 필요한 개발 도구, 기기 기능 라이브러리, 클라우드 서비스를 한데 묶은 오픈 소스 프레임워크입니다. React Native는 JavaScript 코드로 네이티브 화면을 그리는 일까지만 맡기 때문에, React Native만으로 앱을 만들면 화면 이동, 카메라 같은 기기 기능, 네이티브 프로젝트 설정, 빌드와 서명에 쓸 도구를 하나씩 골라 직접 맞춰야 합니다. Expo는 이 도구들을 서로 버전이 맞는 한 묶음으로 제공합니다. React Native 공식 문서도 새 앱은 Expo 같은 프레임워크로 시작하기를 권합니다(2026년 11월 기준). (학습서 p9)

해설서: React Native는 자동차의 엔진과 차체를 만드는 기술이고, Expo는 자동차를 만들 때 필요한 공구, 설계도, 조립 시설, 시험 주행장을 한곳에 제공하는 종합 자동차 제작 시스템이다.

CNG(Continuous Native Generation) — 네이티브 폴더를 사람이 관리하지 않고, app.json을 읽어 그때그때 만들어 내는 방식이다. 폴더를 만드는 명령은 npx expo prebuild이고, 두 폴더는 언제든 다시 만들 수 있으므로 보통 저장소에 올리지 않고 직접 고치지도 않는다. 해설서의 비유: 일반 방식은 집을 지을 때마다 벽돌과 배관을 직접 설계하고 관리하고, Expo 방식은 설계도에 필요한 내용을 적으면 건축 시스템이 벽과 배관을 만들어 준다.

💡 팁 — 학습서가 CNG의 장점으로 든 한 줄이 코딩 에이전트 시대에 특히 중요하다: "코딩 에이전트가 고칠 곳이 app.json 한 파일로 모이므로, 승인할 때 무엇이 바뀌는지 읽기도 쉬워집니다." 에이전트가 권한을 바꾸자고 하면 diff에서 app.json 한 곳만 보면 된다.

4-4. Expo를 쓰는 대가는 무엇인가?

이 편의에는 조건이 붙습니다. Expo Go에 들어 있지 않은 네이티브 기능을 쓰려면 개발용 빌드를 따로 만들어야 하고, 클라우드 빌드는 무료 플랜에서 한 달에 쓸 수 있는 횟수가 정해져 있습니다. 빌드 환경과 서명 키를 Expo라는 회사의 서비스에 맡긴다는 점도 고려해야 합니다. Expo Update로 스토어 심사 없이 바꿀 수 있는 것은 JavaScript 코드와 이미지 같은 네이티브가 아닌 부분뿐이라서, 네이티브 라이브러리를 더하거나 app.json의 권한을 바꾸면 앱 파일을 다시 빌드해 스토어에 올려야 합니다. (학습서 p10)

4-5. 컴파일이 필요한 부분은 어떻게 피하나? — Expo Go와 EAS Build

Expo는 컴파일이 필요한 부분을 두 가지 방법으로 피합니다. 개발할 때는 Expo Go를 씁니다. Expo Go는 자주 쓰는 네이티브 부분을 미리 컴파일해 둔 앱이라서, 내 노트북의 개발 서버(npx expo start)가 만든 번들을 와이파이로 받아 바로 실행합니다. 코드를 고치고 저장하면 폰 화면이 몇 초 안에 바뀝니다. 다른 사람에게 줄 앱 파일을 만들 때는 EAS Build를 씁니다. 프로젝트를 Expo의 클라우드로 올리면, Android SDK가 깔린 서버와 Xcode가 깔린 Mac 서버가 컴파일하고 서명해 설치 링크를 돌려줍니다. 그래서 내 컴퓨터에는 Node.js만 있으면 됩니다. (학습서 p10)

4-6. Expo Go로는 어디까지 되고, 언제 개발용 빌드가 필요한가?

4-7. SDK 버전은 왜 맞춰야 하나?

Expo는 1년에 몇 번 새 SDK를 내고, 그때마다 바뀌는 API가 있습니다. 프로젝트가 쓰는 SDK 버전은 package.json의 expo 버전으로 정해지고, 폰의 Expo Go가 그 SDK를 지원해야 앱이 열립니다. 스토어의 Expo Go는 보통 최신 SDK 하나만 지원하므로, 프로젝트와 Expo Go의 SDK 버전이 같아야 실행됩니다. 오늘 실습할 내용은 SDK 58에 맞춰 준비했고, 2026년 10월 기준으로 Play 스토어와 App Store의 Expo Go 모두 SDK 58을 지원합니다. (학습서 p12)

새 SDK가 나오면 스토어의 Expo Go가 먼저 새 버전으로 올라가서 이전 SDK 프로젝트가 열리지 않을 수 있고, 반대로 App Store는 Apple 심사 때문에 Expo Go가 늦게 올라오거나 한동안 멈춰 있던 적도 있다. 그래서 실행 전에 Expo Go 설정 화면의 SDK 버전이 프로젝트와 같은지 먼저 본다. 해설서는 맞아야 할 것을 네 가지로 적는다 — 프로젝트의 Expo SDK 버전, React Native 버전, Expo SDK 라이브러리 버전, 폰에 설치된 Expo Go의 지원 버전. 비유: 같은 규격의 자동차 부품을 써야 조립이 된다.

6. 앱과 백엔드는 어떻게 이어져 있나? (원문 Ch06)

6-1. 앱은 화면만 가진다

앱은 화면만 가지고, 데이터와 판단은 모두 백엔드에 있습니다. 웹 화면이 하던 일을 폰 화면이 대신 하는 것이라, 백엔드 API는 하나도 바꾸지 않았습니다. (학습서 p15)

해설서의 식당 비유: 웹 화면은 식당의 기존 주문 단말기, 모바일 앱은 새로 만든 스마트폰 주문 앱, 백엔드는 식당 주방, 데이터베이스는 주문 내역과 고객 정보를 보관하는 장부다. 주문 단말기가 바뀌어도 주방의 조리 방식과 고객 정보 관리 시스템은 그대로 쓸 수 있다.

6-2. 템플릿의 파일은 각각 무엇을 하나?

파일하는 일
src/app/_layout.tsx앱 전체 틀. 로그인 상태를 모든 화면에 나눠 주고 화면을 쌓아 보여 줌
src/app/index.tsx대화 화면. 캐릭터가 없으면 캐릭터 화면으로 보냄
src/app/character.tsx캐릭터 화면
src/lib/api.ts백엔드 주소, API 호출, 답 스트리밍 읽기
src/lib/session.tsx, src/lib/supabase.ts앱이 켜질 때 설정 읽기와 익명 로그인
src/components/여러 화면이 같이 쓰는 버튼, 불러오는 중과 오류 화면

(학습서 p16) 해설서는 폴더를 매장에 빗댄다 — app은 매장과 각 공간, lib은 매장 운영 시스템, components는 공통 집기와 도구.

src/app/은 Expo Router의 규칙을 따른다 — 이 폴더의 파일 하나가 화면 하나이고, 파일 이름이 화면 주소가 된다. 예를 들어 src/app/memories.tsx를 만들면 /memories 화면이 생긴다.

6-3. 왜 화면 파일에서 fetch를 직접 부르지 않나?

화면 파일에서는 fetch를 직접 부르지 않고 src/lib/api.ts를 거치게 했다. 백엔드 주소와 로그인 토큰을 붙이는 일을 한곳에 모으기 위해서다. 해설서: 모든 화면에서 백엔드 주소를 직접 입력하고 토큰을 붙인다면 주소가 바뀌거나 인증 방식이 바뀔 때 여러 파일을 고쳐야 하지만, api.ts 한곳에서 관리하면 그곳만 고치면 된다. 이런 구조를 관심사의 분리(Separation of Concerns)라고 한다 — 화면을 만드는 역할과 데이터를 가져오는 역할을 나누는 것.

화면 A ─┐
화면 B ─┼─→ api.ts (백엔드 주소 + 로그인 토큰 + API 요청 관리) ─→ 기존 백엔드 API
화면 C ─┘

6-4. 앱이 켜질 때부터 답을 받을 때까지 무엇이 오가나?

학습서 p17의 시퀀스 다이어그램은 PDF에 그림으로만 들어 있어, 그림을 보고 다시 그렸다. 세로 점선이 각 참여자의 시간 축이고, 실선 화살표가 요청, 점선 화살표가 응답이다.

그림 5. 앱이 켜질 때부터 답을 받을 때까지(학습서 p17 시퀀스를 단계로 펼침). 앱에 넣는 설정은 백엔드 주소 하나이고, 나머지는 백엔드에서 받아 오며, 모든 요청에 로그인 토큰을 붙인다.

읽는 법: 맨 위 한 번(설정 받기)만 토큰 없이 부르고, 그 아래 모든 요청에는 Supabase에서 받은 토큰이 붙는다. 백엔드는 토큰을 직접 믿지 않고 Supabase에 "이 토큰이 누구냐"고 물어 user_id를 얻은 뒤 그 사용자의 데이터만 돌려준다. 맨 아래 답은 한 번에 오지 않고 한 줄에 이벤트 하나씩 흘러오며, 앱은 받는 대로 글자를 이어 붙인다.

앱에 넣는 설정은 백엔드 주소(EXPO_PUBLIC_API_URL) 하나뿐입니다. 앱은 먼저 /api/config에서 Supabase 주소와 publishable key, 캐릭터 화면에 쓸 선택지를 받아 옵니다. 백엔드가 Supabase 로그인을 쓰면 앱은 익명 로그인으로 게스트 사용자를 만들고, 받은 토큰을 기기에 저장해 앱을 껐다 켜도 같은 게스트로 이어지게 합니다. 그 뒤 모든 요청에 이 토큰을 붙이고, 백엔드는 토큰이 누구인지 Supabase에 확인해 그 사용자의 데이터만 돌려줍니다. 웹 화면도 똑같이 동작하므로, 같은 사람이 웹과 앱을 쓰면 브라우저와 폰에서 각각 다른 게스트가 됩니다. (학습서 p16~17)

해설서는 토큰을 일종의 신분증이라고 부른다 — 백엔드는 이 신분증을 Supabase에 확인하고 해당 사용자의 데이터만 준다. 그리고 "익명 로그인을 사용하는 동안에는 웹과 앱의 사용자 데이터가 자동으로 하나로 합쳐지지 않습니다."

6-5. 답은 왜 조금씩 흘러오고, 앱은 어떻게 읽나? (스트리밍)

/api/chat의 답은 한 번에 오지 않고 한 줄에 이벤트 하나(JSON)씩 흘러온다. 해설서: 스트리밍은 수도꼭지에서 물이 조금씩 흘러나오는 것과 비슷하다 — 물을 다 모아 놓았다가 한꺼번에 붓는 것이 아니라 생성되는 대로 전달한다.

이벤트의미앱에서 하는 일
delta답변 글자 조각화면에 답변을 이어 붙임
reminder도구가 약속을 만들었을 때의 정보약속 정보 처리
memory기억 정리 결과사용자 기억 정보 처리
done답변 완료스트리밍 종료 처리

(학습서 p17, 해설서 p47) React Native의 기본 fetch는 이렇게 조금씩 오는 응답을 읽지 못해서, 템플릿은 Expo의 expo/fetch로 응답을 줄 단위로 읽어 글자를 이어 붙인다. 해설서: "AI 서비스에서는 답변의 정확성만큼 사용자에게 답변을 전달하는 속도와 경험도 중요하기 때문입니다."

6-6. 앱에 넣으면 안 되는 값은 무엇인가?

EXPO_PUBLIC_으로 시작하는 환경변수는 빌드할 때 앱 파일 안에 그대로 들어갑니다. 앱 파일은 누구나 내려받아 열어 볼 수 있으므로, 이 값은 공개되는 값이라고 생각해야 합니다. 백엔드 주소와 Supabase publishable key는 원래 공개되어도 되는 값이라 괜찮지만, Supabase secret key나 LLM API 키를 앱에 넣으면 앱을 받은 누구나 그 키로 모든 사용자의 데이터를 읽거나 내 비용으로 LLM을 부를 수 있습니다. 비밀값은 지금처럼 백엔드에만 두고, 앱은 백엔드를 거쳐서만 씁니다. (학습서 p18)

어디에무엇을예
모바일 앱 (공개 가능)공개되어도 되는 값백엔드 주소, Supabase publishable key
백엔드 (비밀정보 보관)비밀값LLM API 키, Supabase secret key, DB 비밀번호

앱은 백엔드 API를 통해서만 기능을 쓰고, 백엔드가 비밀정보로 외부 서비스를 호출한다(해설서 p49).

⚠️ 주의 — 해설서의 덧붙임 두 가지. ① "단, 공개 키를 사용하더라도 실제 데이터 접근 권한은 인증과 데이터베이스 보안 정책으로 보호해야 합니다." — publishable key가 공개돼도 괜찮은 것은 Supabase의 행 단위 보안(RLS)과 로그인 토큰이 있기 때문이다. ② 이 원칙은 모바일 앱뿐 아니라 웹 서비스, AI 에이전트, SaaS 모두 같다. N056에서 결제 시크릿 키를 서버에만 둔 것과 같은 이야기다.

🧪 예제 — [이해 점검, 학습서 p18] 앱의 .env에 EXPO_PUBLIC_으로 시작하는 이름으로 넣어도 되는 값은? ① Supabase secret key ② LLM API 키 ③ 백엔드 주소 ④ 데이터베이스 비밀번호 → ③ (부록 G 문제 4)

해설서는 이 장 끝에 기획자가 던질 세 질문을 남긴다 — 사용자가 직접 보고 조작하는 기능은 어디에서 구현할 것인가? 데이터와 AI 판단은 어디에서 처리할 것인가? 보안이 필요한 정보는 어디에 보관할 것인가?

▶ 한 줄 요약: 앱은 백엔드 주소 하나로 시작해 설정을 받고, 익명 로그인 토큰(신분증)을 모든 요청에 붙이며, 답은 expo/fetch로 한 줄씩 받아 이어 붙이고, 비밀값은 앱이 아니라 백엔드에만 둔다.

7. 내 폰에서 어떻게 띄우고, 안 되면 어디부터 보나? (원문 Ch07)

7-1. 백엔드 주소를 넣는다

저장소 루트의 .env.example을 .env로 복사하고, EXPO_PUBLIC_API_URL에 백엔드 주소를 넣는다. 주소 끝에는 /를 붙이지 않는다. 넣기 전에 브라우저로 <백엔드 주소>/health를 열어 {"status":"ok"}가 나오는지 먼저 본다 — 여기서 안 열리면 앱에서도 열리지 않는다. .env는 .gitignore에 들어 있어 커밋되지 않는다(학습서 p18). 명령은 부록 A-4.

해설서의 원칙: "앱에서 문제가 발생했을 때 앱부터 의심하지 말고 백엔드가 정상적으로 작동하는지 먼저 확인하는 것입니다."

7-2. 개발 서버를 켜고 QR 코드를 찍는다

npx expo start를 실행하면 개발 서버가 켜지고 터미널에 QR 코드가 나온다. Android 폰에서 Expo Go를 열고 Scan QR code로 이 코드를 찍으면, Expo Go가 노트북에서 번들을 받아 앱을 실행한다. 노트북과 폰은 같은 와이파이에 있어야 한다. Windows에서 처음 실행하면 Node.js의 네트워크 접근을 허용할지 묻는 방화벽 창이 뜨는데, 개인 네트워크를 허용해야 폰이 노트북에 붙는다(학습서 p19).

명령언제
npx expo start기본 개발 서버 실행
npx expo start --tunnel같은 와이파이로 연결되지 않을 때(강의실 와이파이, 방화벽)
npx expo start --clear.env를 바꿨는데 반영되지 않을 때(캐시 지우고 다시 시작)

💡 팁 — iPhone은 Expo Go 안에 QR 스캔 버튼이 따로 없을 수 있다 — [보충] iPhone은 기본 카메라 앱으로 QR 코드를 비추면 Expo Go로 열기 안내가 뜬다. 학습서·해설서는 Android 절차만 자세히 적었다.

7-3. 내 폰에서 무엇을 확인하나? (4가지)

  1. Expo Go로 QR 코드를 찍으면 진행 막대가 차오르며 번들을 받은 뒤 앱이 열린다.
  2. 처음 열면 캐릭터 화면이 나온다. 이름과 모습, 말투를 고르고 "저장하고 대화하기"를 누른다.
  3. 대화 화면 위에 아바타와 이름이 보이는지, 메시지를 보내 답이 글자 단위로 이어 나오는지 본다.
  4. Expo Go를 완전히 닫았다가 다시 열어 같은 대화가 이어지는지 본다.

(학습서 p19) 학습서 p20의 캡처에는 Android 폰의 Expo Go에서 "하루" 캐릭터가 날씨·공휴일 질문에 답하고 "내일 아침 8시에 물 마시게 알려줘"에 약속을 잡아 주는 대화 화면이 보인다. 해설서: "이 네 가지가 모두 정상적으로 작동한다면 앱과 백엔드의 기본 연결이 성공한 것입니다."

7-4. 결과 해석 — 같은 백엔드, 다른 게스트

앱에서 저장한 캐릭터와 대화는 백엔드에 저장된다. 백엔드가 Supabase를 쓴다면 Table Editor의 messages 테이블에 방금 보낸 메시지가 쌓인 것을 볼 수 있다. 앱을 닫았다 열어도 대화가 이어지는 것은 앱이 익명 로그인 토큰을 기기에 저장해 두었다가 같은 게스트로 다시 로그인하기 때문이다.

그런데 같은 백엔드를 브라우저로 열면 앱에서 나눈 대화가 보이지 않습니다. 브라우저와 폰은 로그인 정보를 따로 저장하므로 각각 다른 게스트 사용자로 로그인하고, 백엔드는 모든 조회에 그 사용자의 ID 조건을 붙이기 때문입니다. 같은 사람이 웹과 앱에서 같은 대화를 보려면 구글 로그인처럼 기기와 상관없이 같은 사용자로 알아보는 방법이 필요합니다. (학습서 p21)

 스마트폰 앱 ── 게스트 A ──┐                       ┌─ 게스트 A의 캐릭터·대화
                         ├─→ 같은 백엔드 ─→ Supabase ┤
 노트북 웹   ── 게스트 B ──┘  (user_id로 나눠 조회)    └─ 게스트 B의 캐릭터·대화
 → 같은 사람이어도 서로의 대화가 안 보인다. 구글 로그인이면 둘 다 같은 user_id가 된다.

해설서가 제안하는 확인 세 가지: 앱에서 보낸 메시지가 messages 테이블에 있는가? 그 메시지의 사용자 ID가 앱의 익명 사용자 ID와 같은가? 브라우저는 다른 사용자 ID로 조회하고 있는가? 그리고 결론: "이번 강의의 익명 로그인은 초기 테스트에는 적합하지만, 실제 서비스 출시 단계에서는 계정 통합과 사용자 데이터 이전까지 설계해야 합니다."

💡 팁 — 첫 메시지의 답이 유독 늦다면 쉬고 있던 백엔드 인스턴스가 켜지는 콜드 스타트 때문이고, 두 번째 메시지부터는 빨라진다(학습서 p21). Cloud Run 같은 서버리스 환경은 요청이 없으면 인스턴스를 줄이거나 끈다. 해설서 비유: 영업시간 전에 닫아 둔 식당에 첫 손님이 왔을 때 주방을 준비하는 시간.

⚠️ 주의 — --tunnel로 붙였다면 요청이 외부 서버를 한 번 더 거쳐서 느리고, 터널 주소는 인터넷에 공개된다. 같은 와이파이로 연결되면 기본 방식으로 돌아가는 편이 좋다(학습서 p21).

8-2. 바꿀 화면의 구조를 먼저 정한다 — 데이터는 어디서 오나?

웹 화면은 답 아래에 "기억했어요", "약속 알림" 같은 작은 메모를 보여 주는데, 앱은 답 글자만 보여 준다. 코딩 에이전트는 시키는 대로 코드를 쓰지만 어떤 데이터를 어디에 보여 줄지는 대신 정해 주지 않으므로 구조를 먼저 정한다(학습서 p22).

(학습서 p23) A는 모두 하고, B와 C는 사진 기능까지 마친 뒤 시간이 되면 한다. 세 가지 모두 백엔드는 바꾸지 않는다 — 필요한 데이터를 백엔드가 이미 보내고 있는지 먼저 확인한 것이 표의 두 번째 열이다. "앱에 필요한 데이터를 백엔드가 주지 않는다면, 앱에서 우회하지 말고 백엔드에 무엇이 필요한지부터 정합니다."

해설서는 이 표를 기획자가 에이전트에게 맡기기 전에 할 네 가지 결정으로 바꿔 말한다 — ① 어떤 정보를 보여 줄 것인가? ② 그 정보는 백엔드의 어디에서 가져올 것인가? ③ 어느 파일을 고쳐야 하는가? ④ 화면에는 어떤 모양으로 보여 줄 것인가? 예: 앱에 사용자의 생일을 보여 주고 싶은데 백엔드가 생일을 보내 주지 않는다면, 앱 코드만 계속 고쳐도 생일 정보를 만들어 낼 수는 없다.

💡 팁 — [보충 비유] 경영 언어로는 보고서 양식을 바꾸기 전에 데이터 출처부터 확인하는 일이다. 사장님이 "매출 보고서에 지역별 수치도 넣어 줘"라고 할 때 ERP에 지역 필드가 없으면 보고서 담당자가 아무리 양식을 고쳐도 숫자는 나오지 않는다. 그때는 양식이 아니라 ERP(백엔드)에 필드를 추가해 달라고 요청해야 한다.

🧪 예제 — [요청] "대화 중에 나에 대한 걸 기억하거나 약속을 저장했을 때, 답 말풍선 아래에 회색 작은 글씨로 무엇을 기억했는지 같이 보여 주는 기능 만들어 줘." (학습서 p23)

학습서의 힌트: 백엔드 app/agent.py의 run_turn이 어떤 순서로 이벤트를 보내는지 먼저 읽는다. memory 이벤트는 답 글자(delta)가 다 온 뒤에 오므로, 메모를 붙일 말풍선은 "지금 받고 있는 마지막 답"이다. 지금 대화 화면에 delta를 마지막 말풍선에 이어 붙이는 함수가 있으니, 메시지 타입에 메모 목록을 하나 더하는 구조를 생각한다.

확인 세 가지(학습서 p23):

  1. "나 고양이 두 마리 키워"처럼 나에 대한 사실을 보낸다. 답 아래에 기억 메모(🧠 기억했어요: 고양이 두 마리를 키움)가 붙는지 본다.
  2. "내일 아침 8시에 물 마시라고 알려 줘"를 보낸다. 답 아래에 약속 메모(⏰ 내일 오전 8시 물 마시기)가 붙는지 본다.
  3. 앱을 닫았다 다시 열면 지난 대화에는 메모가 없다. 메모는 그 턴의 스트리밍 이벤트로만 오기 때문이다.

8-4. 결과 해석 — 데이터가 어디서 오는지 알고 고친 화면

기억 메모는 나에 대한 사실을 말했을 때만 붙고, 인사나 질문에는 붙지 않습니다. 백엔드가 매 턴 기억을 정리하지만, 새로 기억할 것이 없으면 added 목록이 비어 있기 때문입니다. 지난 대화를 다시 불러왔을 때 메모가 없는 것도 같은 이유입니다. 메모는 저장된 메시지가 아니라 그 턴에 흘러온 이벤트라서, 지난 대화에도 보이게 하려면 백엔드가 메시지와 함께 메모를 저장하고 돌려줘야 합니다. 이렇게 화면에 보이는 정보마다 어디서 오는지를 알고 있으면, 무엇을 앱에서 고치고 무엇을 백엔드에 요청할지 나눌 수 있습니다. (학습서 p24)

🧪 예제 — [이해 점검, 학습서 p24] A를 구현한 뒤 앱을 닫았다 열었더니 지난 대화의 기억 메모가 모두 사라졌다. 이유는? → 메모는 그 턴의 /api/chat 스트리밍 이벤트로만 오고, /api/messages가 돌려주는 지난 대화에는 들어 있지 않다. (부록 G 문제 6)

8-5. 사진으로 약속 만들기 — 백엔드에 이미 무엇이 있나?

웹 화면에는 📷 버튼이 있어서 일정표나 안내문 사진을 올리면 백엔드가 사진 속 글자를 읽고 그 글로 약속을 만들게 할 수 있다. 사진 속 글자를 읽어 텍스트로 바꾸는 기술을 OCR(optical character recognition)이라고 한다(해설서: 사람이 직접 타이핑하지 않아도 컴퓨터가 대신 읽어 주는 기술). 휴대폰에서는 종이 일정표를 그 자리에서 찍는 일이 훨씬 자연스러워서 앱으로 만든 이유가 가장 잘 드러나는 기능이다. 백엔드는 이미 있으므로 이번에도 앱 화면만 만든다.

백엔드에 이미 있는 것내용
POST /api/ocr사진 파일을 multipart 폼의 photo 필드로 받아 글자를 읽고 {"text": "읽은 글"}을 돌려줌. 로그인 토큰 필요
/api/config의 ocr_enabled백엔드에서 OCR이 켜져 있는지(OCR_ENABLED=true). 꺼져 있으면 /api/ocr은 404
웹 화면의 처리읽은 글 앞에 "사진에서 읽은 글이야. 여기 있는 일정 중에 알려 줘야 할 게 있으면 약속으로 저장해 줘."를 붙여 입력창에 넣고, 사용자가 확인한 뒤 보냄

(학습서 p25) 먼저 브라우저로 내 백엔드의 /api/config를 열어 ocr_enabled가 true인지 본다. false라면 OCR 프로그램(tesseract)이 들어간 이미지로 배포했는지와 OCR_ENABLED 환경변수를 확인하고, 바로 고칠 수 없으면 강사의 시연용 주소로 진행한다. 해설서: "백엔드 기능이 꺼져 있다면 앱 화면만 수정해서는 해결할 수 없습니다."

8-8. 왜 읽은 글을 바로 보내지 않나? (HITL)

읽은 글을 바로 보내지 않는 데는 이유가 있습니다. OCR은 손글씨, 기울어진 사진, 흐린 글자를 잘못 읽기 쉽고, 잘못 읽은 날짜로 약속이 저장되면 사용자는 틀린 시각에 알림을 받습니다. 사람이 한 번 확인하는 단계를 두면 이런 오류를 보내기 전에 고칠 수 있습니다. (학습서 p26)

해설서는 이것을 HITL(Human-in-the-Loop), 즉 사람이 중간에 확인하는 구조라고 부른다 — AI가 초안을 만들고 사람이 검토한 다음 최종 실행한다. OCR이 잘못 읽기 쉬운 경우: 손글씨가 흘려 쓰인 경우, 사진이 기울어진 경우, 조명이 어두운 경우, 글자가 작거나 흐릿한 경우. [보충] 앞선 실습에서 에이전트의 위험한 행동 앞에 사람의 승인을 둔 것과 같은 원리다.

9. 오늘 새로 만든 것과 그대로 쓴 것은 무엇인가? (원문 Ch09)

9-1. 오늘 배운 것 다섯 묶음

  • 모바일 선택지 — PWA, 웹 래핑, 네이티브, React Native와 Expo는 화면을 그리는 방식과 앱 파일을 만드는 곳이 다르다. Windows 노트북이 많고 백엔드가 이미 있는 조건에서는, 내 컴퓨터에 Node.js만 두고 빌드를 클라우드에 맡기는 Expo가 iOS까지 다룰 수 있는 방법이었다.
  • Expo의 구조 — 내 코드는 JavaScript 번들로, 네이티브 부분은 Expo Go에 미리 컴파일되어 있고, 최종 앱 파일은 EAS가 클라우드에서 만든다. Expo Go에 없는 네이티브 기능은 개발용 빌드가 필요하고, 프로젝트와 Expo Go의 SDK 버전이 같아야 앱이 열린다.
  • 앱과 백엔드 — 앱은 백엔드 주소 하나로 시작해 설정을 받고, 익명 로그인 토큰을 붙여 같은 API를 부르고, 답을 스트리밍으로 받는다. 비밀값은 앱에 넣지 않고 백엔드에만 둔다.
  • 구조를 정하고 고치기 — 화면에 보일 정보가 어디서 오는지 먼저 확인하고, 바꿀 파일과 모양을 정한 뒤 코딩 에이전트에게 맡겼다. 저장하면 폰 화면이 바로 바뀌고, 오류가 나면 빨간 화면의 문구로 원인을 찾았다.
  • 기기 기능 붙이기 — 사진첩과 앱 안 카메라 화면으로 받은 사진을 백엔드 OCR로 읽어 약속을 만들었다. 앱은 사진을 받고 권한을 묻고 보내는 일까지만 하고, 글자를 읽고 약속을 만드는 일은 백엔드에 두었으며, 잘못 읽은 글은 보내기 전에 사람이 고치게 했다.

(학습서 p29)

그림 7. 오늘 만든 것의 전체 구조. 새로 만든 것은 왼쪽 두 칸(폰 화면과 기기 기능)뿐이고, 오른쪽 세 칸은 그대로 썼다.

읽는 법: 선 하나(앱 → 백엔드 API)가 두 세계를 잇는다. 왼쪽을 아무리 새로 만들어도 오른쪽은 한 줄도 바뀌지 않았고, 그래서 오른쪽을 고칠 때(OCR 엔진, 프롬프트)는 앱을 다시 빌드할 필요가 없다.

import { fetch } from "expo/fetch";          // 기본 fetch 는 조금씩 오는 응답을 못 읽음

const res = await fetch(`${API_URL}/api/chat`, {
  method: "POST",
  headers: { Authorization: `Bearer ${token}`, "Content-Type": "application/json" },
  body: JSON.stringify({ message }),
});
// 응답을 줄 단위로 읽는다: 한 줄 = 이벤트 하나(JSON)
for await (const line of readLines(res.body)) {
  const ev = JSON.parse(line);
  if (ev.type === "delta")    appendToLastBubble(ev.text);       // 글자 이어 붙이기
  if (ev.type === "memory")   addNoteToLastBubble("🧠", ev.added);  // A에서 새로 붙임
  if (ev.type === "reminder") addNoteToLastBubble("⏰", ev.summary);
  if (ev.type === "done")     finish();
}

문제 11. [추가] (주관식) OCR이 읽은 글을 바로 보내지 않고 입력창에 넣어 사람이 확인하게 한 이유는? 이 구조를 무엇이라 부르나?

모범 답안: OCR은 손글씨, 기울어진 사진, 어두운 조명, 작거나 흐린 글자를 잘못 읽기 쉽고, 잘못 읽은 날짜로 약속이 저장되면 사용자는 틀린 시각에 알림을 받는다. 사람이 한 번 확인하는 단계를 두면 보내기 전에 고칠 수 있다. AI가 초안을 만들고 사람이 검토한 뒤 실행하는 이 구조를 HITL(Human-in-the-Loop)이라고 한다(학습서 p26, 해설서 p67).

문제 12. [추가] (객관식) 사진을 /api/ocr에 보냈더니 400 오류와 함께 "사진이 없다"는 응답이 왔습니다. 가장 먼저 확인할 것은?

① 백엔드에서 OCR이 꺼졌는지 ② 로그인 토큰이 붙었는지 ③ 공통 헤더의 JSON용 Content-Type이 OCR 요청에도 붙어, multipart 폼의 경계 문자열이 만들어지지 않았는지 ④ 사진이 흐린지

정답: ③ OCR이 꺼졌으면 404(①), 토큰이 없으면 401(②), 흐린 사진은 오류 없이 엉뚱한 글이 온다(④). multipart 폼은 경계 문자열이 들어간 Content-Type을 요청이 직접 만들어야 하므로, 손으로 지정하면 백엔드가 photo 필드를 찾지 못한다(학습서 p28).

문제 13. [추가] (객관식) 스토어의 Expo Go를 업데이트했더니 어제까지 열리던 프로젝트가 "버전이 맞지 않는다"며 열리지 않습니다. 이유로 가장 알맞은 것은?

정답: ② 스토어의 Expo Go는 보통 최신 SDK 하나만 지원하므로, 프로젝트(package.json의 expo 버전)와 Expo Go의 SDK가 같아야 열린다(학습서 p12). 실행 전에 Expo Go 설정 화면의 SDK 버전을 먼저 본다.
