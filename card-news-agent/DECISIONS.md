# DECISIONS — 결정과 이유

이 문서는 "무엇을 선택했는가"가 아니라 "왜 그렇게 정했는가"를 남긴다. 코드만 보면 사라지는 맥락이다.

## Project 1 (강의 그대로 따라 하기 — ai_news 토픽)

| 결정 | 선택 | 이유 |
|---|---|---|
| 실행 엔진 | Claude Agent SDK (CLI/OpenCode 아님) | 이 환경 자체가 Claude Code라 별도 인증 없이 바로 쓸 수 있고, `query()`를 코드에서 직접 호출해 세션·구조화 출력을 다루기가 CLI 파싱보다 명확함 |
| 백엔드 | Python + FastAPI, `uv`로 의존성 관리 | 강의 참고 구현이 Python+`uv` 조합이라 그대로 따름. FastAPI는 async 백그라운드 작업(BackgroundTasks)이 상태 머신 폴링 구조에 자연스럽게 맞음 |
| 저장소 | SQLite(WAL 모드) | 1인 사용 로컬 앱에 별도 DB 서버가 필요 없음. WAL 모드는 폴링(읽기)과 백그라운드 작업(쓰기)이 동시에 일어나도 막히지 않게 함 |
| 상태 표현 | `status`(running/waiting_for_user/completed/failed) × `stage`(세부 단계) 2축 | 강의 4챕터의 "waiting_for_user는 정상 상태" 원칙을 코드 수준 값으로 그대로 옮김. 두 축으로 나눈 이유는 "지금 멈춰있나 진행중인가"(status)와 "어느 단계인가"(stage)를 UI가 각각 다르게 써야 하기 때문 |
| 이미지 생성 | OpenAI `gpt-image-1` (Antigravity 아님) | Antigravity가 이 컴퓨터에 설치돼 있지 않음. 강의는 두 도구를 실행 엔진과 별개로 취급하므로 대체가 원칙에 어긋나지 않음 |
| 이미지 규격 | 1024×1536 생성 → 1080×1350 크롭 | gpt-image-1이 1080×1350을 직접 지원하지 않음(1024×1024/1536×1024/1024×1536/auto만 가능). 세로형 카드뉴스에 가장 가까운 프리셋을 고르고 Pillow로 후처리 |
| 텍스트 합성 | AI가 이미지에 글자를 넣지 않고, Pillow로 별도 레이어 합성 | 강의의 "텍스트 분리 편집" 원칙. AI 이미지 생성은 글자를 정확히 못 그리는 경우가 많아 분리가 품질·재수정 양쪽에 유리 |
| 재시도 정책 | JSON 파싱 실패만 1회 재시도, 예산초과/타임아웃은 재시도 안 함 | 실제로 `max_budget_usd=0.5`가 부족해 실패했을 때 무작정 재시도하면 예산만 두 배로 태우고 다시 실패하는 것을 확인함(아래 "실패와 개선" 참고) |

## Project 2 (나만의 확장 — 원고 → 카드뉴스)

| 결정 | 선택 | 이유 |
|---|---|---|
| 확장 대상 | "회의록 정리"·"복습문제 생성"이 아니라 "완성된 칼럼/에세이 → 인스타 카드뉴스" | 실제로 반복해서 겪는 불편이 이것이었음: 프로젝트 VOICE(Making_Contents)의 기획서에 이미 "M7 채널 파생(카드 8장)"이 있었고, 브런치 연재는 발행할 때마다 홍보용 카드가 필요했음. 가상의 예제보다 진짜 쓸 산출물을 고름 |
| "후보"의 재정의 | 뉴스 후보 → 원고를 8장으로 나누는 분할안 2~3개 | 카드뉴스 PRD의 "조사→후보비교→선택" 골격은 그대로 두고, "무엇을 후보로 볼 것인가"만 토픽마다 다르게 해석. 이러면 엔진 코드를 안 건드리고도 완전히 다른 입력 형태(원고 1편)를 수용할 수 있음 |
| "검증"의 재정의 | 웹 사실 확인 → 원문 대조 자가 검증 | source_text 토픽은 외부 사실이 아니라 "카드 문구가 원문에 있는 내용인가"만 확인하면 됨. confirmed_facts/unconfirmed_claims 스키마는 그대로 재사용하되 의미만 바꿈 |
| 확장 메커니즘 | `engine.py` 무수정, `TopicConfig`에 `tools`/`input_mode`/`cta_card` 3개 필드만 추가 | "엔진은 토픽이 선언한 값을 그대로 쓸 뿐" 원칙을 지키기 위해. 토픽별 `if topic_id == "..."` 분기를 넣기 시작하면 새 토픽을 추가할 때마다 엔진이 커지고, 결국 아무도 안전하게 못 건드리는 코드가 됨 |
| CTA(URL 안내) 카드 | AI가 아니라 로컬에서 QR+URL을 합성 | 이미지 생성 없이 텍스트+QR만 필요한 카드에 OpenAI를 호출하는 건 낭비. `qrcode` 라이브러리로 로컬 처리하면 비용 0원이고 실제로 파일 용량도 다른 카드의 1/30 수준(~67KB vs ~2MB) |
| QR+텍스트 동시 표시 | QR코드만이 아니라 URL 텍스트도 같이 표시 | 인스타그램은 게시물 이미지 안의 링크가 클릭되지 않음. QR을 못 찍는 상황(스캔 앱 없음 등)에도 URL을 손으로 입력할 수 있게 이중 안전장치를 둠(사용자 요청 사항) |
| 실전 테스트 재료 | 가상 예제가 아니라 실제로 발행된 원고 2편 | VOICE 칼럼("벌레 먹은 멜론을 도시락에 담다")과 실제 브런치 발행 글(`brunch.co.kr/@storywiz/3`, "개취를 버리는 일")을 그대로 입력해 완주. 가짜 데이터로 통과시키면 실제 사용 시 나올 문제를 못 미리 봄 |

## 공통 원칙

| 결정 | 선택 | 이유 |
|---|---|---|
| 검증 방식 | 매 단계 실제 API를 호출해 실행 결과로 확인, 코드 리뷰만으로 끝내지 않음 | "그럴듯해 보인다"와 "실제로 된다"는 다르다는 게 이번 프로젝트에서 두 번 실제로 확인됨(예산 버그, 상표 로고 버그 — 둘 다 코드만 봐서는 안 보이고 실행해야 보였음) |
| 서버 재시작 절차 | `pkill`이 아니라 `netstat`으로 실제 PID를 찾아 `taskkill`로 종료 | 이 Windows/uv 환경에서 `pkill -f`가 프로세스를 못 죽이고도 성공한 것처럼 보이는 경우를 반복적으로 겪음. 재시작 후에는 `/topics` 응답 내용으로 새 코드가 실제 로드됐는지까지 확인함 |
